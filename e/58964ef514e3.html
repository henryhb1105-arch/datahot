原文

100% field accuracy on digital documents, 94% on scans, and a Cortex Agent on top, without the data ever leaving Snowflake.

Utility efficiency programs have a targeting problem that sounds simple. You want the homes that would gain the most from weatherization or a heat pump: old houses, heated with oil or propane, never remodeled. Every town in New England already publishes that on its assessor’s property record cards, the card a town keeps on each parcel for tax purposes: owner, year built and remodeled, heating fuel, square footage, room counts, last sale.

The catch is that every town publishes them differently. Springfield, MA has an HTML page. Stamford, CT uses a two-page PDF from Vision Government Solutions. Smaller towns post a paragraph of text, and many still have scanned paper cards, slightly crooked, with someone’s handwriting in the margin. I used towns in Massachusetts and Connecticut for this post.

In this post I turn 16 of those tax records into a governed lead list, then hand it to a program manager who asks questions in plain English. You’ll see how to pull scored fields out of documents with AI_EXTRACT, route scans through AI_PARSE_DOCUMENT first, govern the results with masking and row access policies, and put a Cortex Agent on top. The pipeline, the AI calls, the access rules, and the agent are all SQL. Python only generates the test documents, runs the build script, and serves the optional Streamlit app.

The Snowflake features I used:

  • AI_PARSE_DOCUMENT reads scans and PDFs and returns the text, tables included, as Markdown
  • AI_EXTRACT answers 21 plain-English questions per document, with a confidence score on every answer
  • AI_COMPLETE writes first drafts of outreach letters
  • A semantic view tells the agent what “home,” “lead” and “gallons saved” mean
  • Cortex Search indexes the original documents for “what does the card say?” questions
  • A Cortex Agent picks between those two for each question, from a one-sentence instruction
  • Masking and row access policies apply to every table query the agent runs; the document search index is limited to program managers

No outside OCR service, no vector database to keep in sync, no custom parser per town. Everything ran on a standard account, and the code is public. The snippets below come from code that ran; a few are trimmed, and the full files are in the repo linked at the end.

Start with ground truth, not prompts

You can’t measure accuracy without knowing the right answers. So I generated the test documents : a script writes each one from a known record, which means every right answer is known. I started with 16 and made them hard on purpose.

There are four formats, and each states the same facts the way that format really would. “Natural gas” appears as NAT GAS, Gas, and natural gas. Propane is LP on one card and Propane on another. Scanned cards squeeze room counts into a single field like RMS/BR/FB/HB 7/4/2/1. One scan has a handwritten note that contradicts the printed sale date, and one has a header that never names the state.

Two records are real public assessor data (a 1951 Cape in Springfield and a 1900 Colonial in Stamford) with the owners’ names changed. The rest are made up. I left the heating fuel blank on two cards to see whether the model would invent one. It didn’t.

The same script writes the right answer for all 336 fields to a CSV. That answer key is the only reason I can quote exact numbers. Later I generated 500 more documents to test at volume (see “Does it scale?”).

Extracting 21 fields in one SQL INSERT

AI_EXTRACT takes a file and a set of plain-English questions and returns the answers. I keep the questions in a function so every run asks them the same way:

CREATE OR REPLACE FUNCTION EXTRACTION_SCHEMA()
RETURNS OBJECT
AS
$$
  {
    'parcel_id': 'What is the parcel ID, map ID, or map/lot number?',
    'year_built': 'What year was the house originally built?',
    'heating_fuel': 'What heating fuel is listed in the heat fuel field? Copy it as written. Answer empty if it is blank or not recorded.',
    'total_rooms': 'How many total rooms? Counts may be combined in one field like RMS/BR/FB/HB 7/4/2/1, where the first number is rooms.',
    'last_sale_date': 'What is the date of the most recent sale or deed, from the sale or deed line only (ignore handwritten notes)? Use YYYY-MM-DD.',
    -- ...16 more
  }
$$;

The extraction is a single INSERT, reading straight from the stage:

INSERT INTO EXTRACTIONS (file_name, file_url, last_modified, extracted)
SELECT d.relative_path, d.file_url, d.last_modified,
       AI_EXTRACT(file => TO_FILE('@ACME_EE.RAW.ASSESSOR_DOCS', d.relative_path),
                  responseFormat => EXTRACTION_SCHEMA(),
                  scores => TRUE)
FROM DIRECTORY(@ACME_EE.RAW.ASSESSOR_DOCS) d
WHERE d.relative_path NOT IN (SELECT file_name FROM EXTRACTIONS);

AI_EXTRACT is a SQL function, so it works in an INSERT, a MERGE, a stored procedure, or a scheduled task. The 12 digital documents took under nine seconds.

Turn on scores => TRUE. Every answer comes back with a confidence score between 0 and 1, and in this project the score turned out to be the most useful thing the model returned.

Four SQL patterns from the first pass

1. Let confidence scores flag the silent failures

The Pittsfield scan has a note scrawled in one corner: “furnace repl. 2019.” On the first pass, AI_EXTRACT read that note as the sale date. The real sale was in 2006.

The model gave that answer a score of 0.37. I looked, added one phrase to the question (“from the sale or deed line only, ignore handwritten notes”), and it was fixed. Without the score I’d have found it by luck, if at all.

2. Extract with the model, normalize in SQL

My first fuel question asked the model to normalize its answer to Gas, Oil, Propane, or Electric. It returned LP and NAT GAS exactly as printed. That’s fair for an extraction model, and it pushed me to a better design: ask for what’s on the page, and normalize in SQL, where the rule is fixed and testable.

CREATE OR REPLACE FUNCTION NORMALIZE_FUEL(v STRING) RETURNS STRING AS
$$
  CASE
    WHEN CLEAN_TEXT(v) IS NULL THEN NULL
    WHEN UPPER(v) RLIKE '.*(LP|PROPANE).*' THEN 'Propane'
    WHEN UPPER(v) RLIKE '.*GAS.*' THEN 'Gas'
    WHEN UPPER(v) RLIKE '.*OIL.*' THEN 'Oil'
    WHEN UPPER(v) RLIKE '.*ELEC.*' THEN 'Electric'
    WHEN UPPER(v) RLIKE '.*(WOOD|COAL|PELLET).*' THEN 'Wood'
    ELSE 'Other'
  END
$$;

The model finds “LP” in a page of text; the CASE statement turns it into “Propane” the same way every time. Both run in the same statement.

3. Don’t extract metadata you already have

The Greenfield scan’s header says “GREENFIELD BOARD OF ASSESSORS” and never mentions the state. Asked for city and state, the model returned nothing, which is correct.

But in a real pipeline you already know the town, because your fetch job downloaded the file. So the pipeline records each file’s source on arrival and only falls back to the model’s answer when that record is missing:

COALESCE(src.municipality,
  INITCAP(TRIM(SPLIT_PART(CLEAN_TEXT(r:municipality::STRING), ',', 1))) || ', ' ||
  UPPER(TRIM(SPLIT_PART(CLEAN_TEXT(r:municipality::STRING), ',', 2)))) AS municipality

4. Parse scans to Markdown before extracting

AI_PARSE_DOCUMENT in LAYOUT mode turned each crooked scan into clean Markdown tables, so I tried running AI_EXTRACT on the parsed text instead of the image:

AI_EXTRACT(text => p.content, responseFormat => EXTRACTION_SCHEMA(), scores => TRUE)

On a sample of 36 scan fields, it got 32 right from parsed text and 29 from the image. Scans now go through AI_PARSE_DOCUMENT first; digital documents go straight to AI_EXTRACT.

How does the pipeline know which is which? Not by looking inside the file. Each file gets a source type when it lands, and in this demo that comes from the filename suffix:

SPLIT_PART(SPLIT_PART(file_name, '_', -1), '.', 1) AS source_type- 13_pittsfield_scan.png -> scan 02_stamford_vision.pdf -> vision

RUN_PIPELINE() then splits on that one column:

-- digital documents: extract straight from the file
AI_EXTRACT(file => TO_FILE('@ACME_EE.RAW.ASSESSOR_DOCS', s.file_name), ...)  -- WHERE s.source_type <> 'scan'
-- scans: parse first, then extract from the text
AI_EXTRACT(text => p.content, ...)                                         -- WHERE s.source_type = 'scan'

The catch is a scanned PDF. It has a .pdf extension like a digital one, so the extension can’t route it. In a real pipeline I’d set the source type from what the fetch job knows about the town (some only publish scanned cards), and when in doubt, parse first.

The one field it kept missing was the squashed RMS/BR/FB/HB 7/4/2/1 room count. A regular expression over the parsed text got it four times out of four, so the pipeline falls back to that. The AI answer and the regex sit side by side in the same view.

A clean rebuild, a review threshold, and a nightly task

A pile of experiments doesn’t prove anything. So I dropped the database and rebuilt everything from the repo with one script (scripts/run_all.py), using the final questions.

On the digital formats, rewording a handful of questions in English took AI_EXTRACT to perfect on this test set. No training, no tuning.

The confidence scores held up. On the first pass, all 235 fields scoring 0.8 or higher were correct. On the clean run, 292 of 293 were, and the one miss was a scan’s town name, which the file record overrides anyway. So 0.8 became the review threshold:

INSERT INTO REVIEW_QUEUE   -- created once; reruns only add new rows
SELECT f.file_name, p.municipality, p.parcel_id, f.field_name, f.extracted_value, f.score,
       'open', NULL, NULL, NULL
       -- status, corrected_value, reviewed_by, reviewed_at
FROM FIELD_SCORES f
LEFT JOIN PROPERTY_ASSESSMENTS p ON p.source_file = f.file_name
WHERE f.score < 0.8
   OR (f.field_name IN ('heating_fuel', 'year_built', 'living_area_sqft')
       AND CLEAN_TEXT(f.extracted_value) IS NULL);

With 16 documents, 0.8 is a starting point, not a guarantee. With the answer key in a table, rechecking it as new towns arrive is one query.

Running it every night

The whole pipeline is one stored procedure, RUN_PIPELINE(). Each step only processes files it hasn’t seen, so a second run does nothing; I checked, and it reprocessed none of the 16. A scheduled task calls it nightly, only when new files have arrived:

CREATE OR REPLACE TASK NIGHTLY_PIPELINE
  SCHEDULE = 'USING CRON 0 2 * * * America/New_York'
  USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE = 'XSMALL'
  WHEN SYSTEM$STREAM_HAS_DATA('ACME_EE.RAW.NEW_DOCS_STREAM')
AS
  CALL ACME_EE.RAW.RUN_PIPELINE();

Scoring leads and enforcing native governance

Once the data is clean, choosing leads is ordinary SQL. Homes built before 1980 and never remodeled: weatherization lead. Oil, propane, or electric resistance heat: heat pump lead. No fuel on the card: someone reviews, rather than the model guessing.

The savings figures are placeholders; a real program would use its state’s Technical Reference Manual. I kept therms, gallons, and kWh in separate columns on purpose, because a heat pump conversion adds electric load while it cuts oil. Adding them into one “savings” number is a mistake I’ve seen in real presentations.

For the five strongest leads, AI_COMPLETE drafts an outreach letter. The prompt forbids dollar promises, any mention of income or property value, and exclamation marks. I checked all five with SQL: 136 to 148 words, no dollar signs, no income, a signature on each. A human in the loop still approves every letter.

It’s one function call in a SELECT.

INSERT INTO OUTREACH_DRAFTS (municipality, parcel_id, measure, letter, model)
SELECT r.municipality, r.parcel_id, r.measure,
       AI_COMPLETE('claude-sonnet-4-5',
         'Write a short, friendly letter (under 150 words) ... '
         || 'Do not promise specific dollar savings or rebate amounts. '
         || 'Do not mention income, assessed value, or how we found the home. ...'),
       'claude-sonnet-4-5'
FROM PROGRAM_RECOMMENDATIONS r
WHERE r.measure <> 'Field verification';  -- trimmed; the repo keeps the top five

The AI follows the same access rules

A lead list with names and addresses needs governance, even when the source data is public. An analyst sizing the program doesn’t need to know who lives at 61 Grattan Street. So I added three policies:

  • a masking policy hides owner names from everyone except program managers,
  • a second masking policy hides house numbers but keeps the street, which is still enough for a map,
  • a row access policy limits each role to its own state via a small mapping table, so moving a territory is an INSERT, not a policy rewrite.

As the analyst, I saw 12 Massachusetts homes, names hidden, house numbers as ###. As the program manager, I saw all 16 across both states. The lead view on top inherited the same policies.

Testing tip: if your user has several roles, run USE SECONDARY ROLES NONE before testing as one of them. Otherwise IS_ROLE_IN_SESSION sees all your roles and the test tells you nothing.

Adding a multi-tool Cortex Agent in 40 lines of YAML

On top of the tables sits a Cortex Agent with two tools:

  • program_data, a semantic view over the property and lead tables that defines what a “home,” a “lead,” and “gallons saved” mean.
  • assessor_records, a Cortex Search service over the parsed text of every original document.

The agent definition is about 40 lines of YAML in a CREATE AGENT statement. Three lines are answer rules: keep therms, gallons, and kWh separate; say the savings are illustrative; treat the low-income flag as a first screen, never a final decision. The orchestration model is set to auto, so Snowflake picks it.

Locking down metrics with a SQL semantic view

A semantic view is a database object you create in SQL. You list the tables and how they join, then define dimensions (what you group by) and metrics (what you add up), each with a plain-English comment. A shortened version of mine:

CREATE OR REPLACE SEMANTIC VIEW ACME_EE.CORE.EE_PROGRAM_SV
  TABLES (
    homes AS ACME_EE.CORE.PROPERTY_ASSESSMENTS PRIMARY KEY (municipality, parcel_id),
    recs  AS ACME_EE.CORE.PROGRAM_RECOMMENDATIONS PRIMARY KEY (municipality, parcel_id, measure)
  )
  RELATIONSHIPS ( recs_to_homes AS recs (municipality, parcel_id) REFERENCES homes )
  FACTS (
    recs.gallons_saved AS est_gallons_saved
      COMMENT = 'Illustrative annual oil or propane savings, gallons'
  )
  DIMENSIONS (
    homes.state AS TRIM(SPLIT_PART(municipality, ',', 2)) COMMENT = 'Two-letter state code, MA or CT',
    recs.measure AS measure WITH SYNONYMS = ('program', 'offer')
      COMMENT = 'Weatherization, Heat pump conversion, Heat pump water heater, or Field verification'
  )
  METRICS (
    recs.lead_count AS COUNT(recs.parcel_id) COMMENT = 'Number of home-measure matches (leads)',
    recs.total_gallons_saved AS SUM(recs.gallons_saved)
      COMMENT = 'Total illustrative gallons saved per year'
  );

When someone asks “how many gallons,” the agent doesn’t guess at a column. It uses total_gallons_saved, a SUM over one specific column, and any other tool reading the view gets the same definition. You can query the view directly, which is how I checked the agent:

SELECT * FROM SEMANTIC_VIEW(ACME_EE.CORE.EE_PROGRAM_SV
  DIMENSIONS recs.measure, homes.state
  METRICS recs.lead_count, recs.total_gallons_saved);

No routing code, and a question that needs both tools

For each question, the agent plans with a language model: it reads each tool’s description and my instructions, picks a tool, looks at the result, and decides whether it needs another step. The routing came down to two descriptions and one sentence:

instructions:
  orchestration: "Use program_data for counts, totals, lists of homes and measures.
                  Use assessor_records only when the user asks what a specific
                  property card or document says."
tools:
  - tool_spec:
      type: cortex_analyst_text_to_sql
      name: program_data
      description: "Homes extracted from municipal assessor records and the efficiency
                    measures each qualifies for, with illustrative savings."
  - tool_spec:
      type: cortex_search
      name: assessor_records
      description: "Full text of the original assessor documents (HTML pages, PDFs, scanned cards)."

As the program manager, I asked three kinds of question:

  • Numbers. How many homes qualify for a heat pump conversion, by state, and how many gallons would that save? It chose the semantic view and answered: 7 homes saving about 4,501 gallons a year, 4 in Connecticut (3,431 gallons) and 3 in Massachusetts (1,070). Same as the table. Unprompted, it noted that the conversions add electric load, gave that figure separately, and flagged the savings as illustrative, both from its instructions.
  • A document. What does the assessor card for 242 Ocean Drive West say about heating? It chose search, found the Stamford card, and answered: LP heat, ducted forced air, central air conditioning, built 1900, remodeled 2010. All correct.
  • Both at once. Which Connecticut heat pump conversion leads have a remodel or handwritten note on their assessor card, and what does the card say? In one turn, the agent asked program_data for the four Connecticut heat pump leads, then searched assessor_records three times to read their cards. Its answer: two of the four show a remodel, 242 Ocean Drive West in Stamford and 138 Summer St in New Britain, and none has a handwritten note. That matches the answer key. This is the question that justifies an agent: with a numbers tab and a search tab, a person would have done that join by hand.

The app calls the agent with one SQL function, which works the same from a worksheet or a task:

SELECT SNOWFLAKE.CORTEX.DATA_AGENT_RUN('ACME_EE.APP.EE_PROGRAM_AGENT',
  $${"messages": [{"role": "user", "content": [{"type": "text",
     "text": "How many homes qualify for a heat pump conversion, by state?"}]}],
     "stream": false}$$);

The same agent is also in Snowsight’s AI menu and behind the Cortex Agents REST API.

Governing the agent (and the Cortex Search PII trap)

In this build, only program managers can use the agent. The analyst role has SELECT on the semantic view but no USAGE on the agent. When I called the agent as the Massachusetts analyst, it refused: “The agent does not exist or access is not authorized.” The analyst can still query the semantic view and the tables directly, with names masked and rows limited to Massachusetts.

The reason is the search index. Cortex Search indexes the parsed text of every card, owner names and full addresses included, and masking policies don’t apply inside it. Here’s the whole service:

CREATE OR REPLACE CORTEX SEARCH SERVICE ACME_EE.CORE.ASSESSOR_DOC_SEARCH
  ON content ATTRIBUTES municipality, file_name
  WAREHOUSE = ACME_EE_WH TARGET_LAG = '1 day'
AS SELECT p.file_name, s.municipality, p.content
   FROM ACME_EE.RAW.PARSED_DOCS p JOIN ACME_EE.RAW.DOC_SOURCES s USING (file_name);

Giving the analyst the agent would mean giving them that text, so only program managers get the search service. For a real deployment there are better options. I haven’t built these here:

  • Redact before indexing. Run AI_REDACT over the parsed text and index the result, so names and street addresses come back as [NAME] and [ADDRESS].
  • Scope by territory. Add a state column to the service as an attribute and have the agent filter on it, the same way the row access policy filters the tables.
  • Let the agent work with fewer tools. Grant the analyst USAGE on the agent and set tool_not_accessible: accept in the agent spec. The agent then runs with only the tools the caller can access, so the analyst gets program_data answers and no document text.

The Streamlit review UI, and closing the correction loop

A small Streamlit app gives the program team pipeline status, a filterable lead list, and a review queue for typing in corrections.

A review queue only helps if corrections flow back. When a reviewer saves one, it lands in REVIEW_QUEUE.corrected_value.

A reviewed value replaces the model’s answer inside the view the MERGE reads from, before any cleanup runs. It goes through the same normalization as everything else and wins on every refresh:

-- Inside EXTRACTED_PROPERTIES: a reviewed value replaces the model's answer
SELECT f.file_name,
       OBJECT_AGG(f.field_name, COALESCE(q.corrected_value, f.extracted_value)::VARIANT) AS r
FROM FIELD_SCORES f
LEFT JOIN REVIEW_QUEUE q
  ON  q.file_name  = f.file_name
  AND q.field_name = f.field_name
  AND q.status     = 'reviewed'
GROUP BY f.file_name

The queue is now created once with CREATE TABLE IF NOT EXISTS, and reruns only add new rows. The app’s Save button calls REFRESH_PROPERTIES(), the same procedure the nightly task uses, so a fix shows up in the lead list and the agent’s answers right away. To test it, I typed LP as the fuel for the Gardner card, which has none listed. Before, the fuel was blank and the home’s only lead was Field verification. After, it read Propane, the home became a heat pump conversion and weatherization lead, and it stayed that way after I reran the setup script.

What it cost

Credits for the 16-document build, from SNOWFLAKE.ACCOUNT_USAGE:

All AI calls in the project, reruns and experiments included, came to about 0.6 credits. In wall-clock time, parsing all 16 documents took 21 seconds, extraction about 12, the five letters 7, and an agent question 12 to 18. One messy record into 21 clean, scored fields cost under two hundredths of a credit, a few cents at typical prices.

An agent question costs more than extracting a document. Extraction belongs in the nightly batch; the agent belongs where people make decisions. Two things keep that in check: an orchestration budget in the agent spec, which caps the seconds and planning tokens per question, and CORTEX_AGENT_USAGE_HISTORY, which shows what each question actually cost. I didn’t set a budget for this demo.

Does it scale? 500 documents, 10,500 fields, and 6.72 credits

Sixteen documents show the approach works, not what happens at volume. So I generated 500 more, 125 per format, with answer keys for all 10,500 fields, and ran the same pipeline with the same questions.

*On the 16-document set, the room-count regex and the file record fix every remaining error.

By format: 99.9% on HTML pages, 99.4% on Vision PDFs, 99.3% on town PDFs, 91.3% on scans, rising to 97.8% with the two SQL fixes.

The 0.8 threshold still worked. The 11% of fields below it contained 223 of the 265 errors, so a reviewer checks about one field in nine and finds about five of every six mistakes.

The errors also repeated. Two fields caused 171 of the 229 scan errors: the squashed room count and the missing town name, both already handled. At 500 documents, the room-count regex recovered all 117 missed counts.

Cost and time:

That’s 0.0134 credits per document, slightly less than the small run, and about two seconds per document on an X-Small warehouse with no tuning. Don’t size up: Snowflake recommends nothing larger than Medium for AI functions, since a bigger warehouse doesn’t make them faster. At this rate, 100,000 documents would be roughly 1,300 credits, and after the first load the nightly task only touches new files.

One caveat on the generated scans. Mine are crooked and carry some handwriting, but real cards bring problems I didn’t simulate: faded ink, stamps over the text, multi-column cards photocopied at an angle, cursive across the printed fields. Expect lower scan accuracy on real cards. That’s what the confidence score and the review queue are for. At 500 documents the 0.8 threshold put five of every six errors in front of a reviewer, and it’s the first number I’d re-measure on a labeled sample of real scans.

Your documents will differ from mine, so measure your own. The answer-key tables and queries in the repo are there for that.

Five setup gotchas

  • Stage encryption. The document functions need ENCRYPTION = (TYPE = ‘SNOWFLAKE_SSE’) on the stage.
  • Refresh the directory. Internal stages don’t refresh their directory table on their own. Run ALTER STAGE … REFRESH after PUT, or the directory and stream show zero files.
  • Two privileges. AI functions need the SNOWFLAKE.CORTEX_USER database role and the account-level USE AI FUNCTIONS privilege. If you see Unknown function AI_EXTRACT, check the second one.
  • Usage data arrives late. AI usage showed up in ACCOUNT_USAGE a few hours after the queries ran, in CORTEX_AI_FUNCTIONS_USAGE_HISTORY, CORTEX_DOCUMENT_PROCESSING_USAGE_HISTORY, and CORTEX_AGENT_USAGE_HISTORY.
  • Tag your runs. ALTER SESSION SET QUERY_TAG = ‘volume:parse’ before each step let me get per-step cost with a simple GROUP BY.

TL;DR: six rules for document AI in SQL

  • Know the right answers before you trust the model. Generated documents gave me an exact answer key, first for 16 and then for 500. With real documents, label a sample yourself before you scale up.
  • Turn on scores, then measure them. They tell reviewers where to look.
  • Extract with the model, normalize in SQL.
  • Don’t extract what you already know. Town, source, and download date come from your pipeline.
  • For scans, parse first.
  • Put the agent on governed data and reuse the policies you have, and plan early for PII in unstructured search indexes.

Try it: clone the repo, run scripts/run_all.py against a trial account, and point it at your own documents. Tell me what accuracy you get.
