译文

AI 逐段翻译

Moonfrog Labs使用 Amazon Redshift 分析移动游戏遥测数据。每次会话、购买和玩家流失都会生成事件，产品和分析团队利用这些事件了解游戏表现。更快的加载和查询有助于这些团队使用更新鲜的数据开展工作。

Moonfrog 运行一个生产分析集群，其中约有 148 TB 的 Amazon Redshift Managed Storage (RMS)，以及约 4,000 个仓库表。它还会查询约 1,000 个 外部数据湖表。该仓库支持遥测数据摄取、收入报告、营销归因，以及面向产品、数据科学、分析和支持团队的自助式仪表板。

在本文中，我们展示 Moonfrog 如何将其生产分析仓库从 Amazon Redshift RA3 迁移到 RG 实例，并使用 弹性调整大小。我们说明团队如何为不断增长的分析需求和更频繁的加载选择容量、验证仓库和数据湖访问，以及评估迁移后的性能和成本。

挑战

Moonfrog 的 RA3 集群运行可靠，没有稳定性问题。其制约因素是随着分析需求增长而出现的计算余量不足。迁移前摄取量保持稳定。增长来自分析查询和数据湖扫描。团队已计划从五个 RA3 节点扩展到六到七个节点，并希望获得容量来更频繁地加载仓库数据。

五节点 ra3.4xlarge 集群的平均 CPU 利用率约为 54%。在大约 98% 的小时内，CPU 峰值达到或超过 90%。其他指标显示需求在增加：

  • 从 1 月到 7 月，每天的 SELECT 查询增加了 31%。
  • 最高优先级查询的平均工作负载管理 (WLM) 队列等待时间从 5 月的 505 毫秒上升到 7 月的 940.7 毫秒。
  • 并发扩展使用量在同一时期几乎翻倍，从每天 4,453 秒增加到 8,516 秒。

RA3 上的 COPY 操作平均耗时 16.8 秒。该时长限制了统计管线可以加载的频率。团队评估了 RG，将其作为支持不断增长的分析需求并使更频繁的加载变得可行的一种方式。

Moonfrog 还查询了 Amazon Simple Storage Service (Amazon S3) 中约 1,000 个外部表。通过 Redshift Spectrum 扫描的数据增加了 33%，从 3 月的 84.9 TB 增加到 6 月的 112.5 TB。单独的 Spectrum 扫描费用增加了扩展 RA3 计算的成本。

Moonfrog 使用 WLM 查询监控规则来阻止超过 1 TB 的扫描。这些规则在 RA3 配置下控制了扫描支出。

ra3.4xlarge 的一年期无预付 预留节点承诺于 2026 年 7 月到期。续订让 Moonfrog 有机会重新评估其计算承诺，并确定切换到 RG 是否能为其不断增长的工作负载需求提供额外余量。

解决方案概述

Amazon Redshift RG 实例使用 AWS Graviton 处理器和集成的数据湖查询引擎。AWS 发布的基准测试显示，仓库工作负载最高快 2.2 倍，Apache Iceberg 工作负载最高快 2.4 倍，且每 vCPU 价格比 RA3 低 30%。这些基准测试与 Moonfrog 的生产结果无关。RG 在集群节点上运行 Apache Iceberg 和 Apache Parquet 扫描，取消了这些扫描单独按 TB 计费的 Spectrum 费用。弹性调整大小支持更改节点系列和容量，无需客户管理的导出和重新加载。

Moonfrog 在切换时保留了其摄取和分析架构。没有添加或移除任何服务，应用程序继续使用同一个仓库。

下图说明了该架构。

图 1：摄取管线将列式文件写入 Amazon S3。COPY 加载仓库表，RG 上的集成数据湖引擎就地查询外部表。对话式分析是对额外余量的计划用途

该架构使用以下 AWS 服务：

  • Amazon Redshift提供分析仓库和集成数据湖引擎。
  • Amazon S3存储事件文件、加载暂存数据和外部数据湖表。
  • AWS Glue Data Catalog存储外部架构和表的元数据。
  • Amazon Elastic Compute Cloud (Amazon EC2)运行摄取管线。
  • Amazon CloudWatch和 AWS Cost Explorer提供性能和账单计量。

实施步骤

Moonfrog 建立了基线，使用弹性调整大小更改节点系列，并验证了仓库和数据湖访问。随后在评估早期结果后选择最终配置。

步骤 1：建立基线

变更之前，团队捕获了 Amazon CloudWatch 的指标，包括 CPU 利用率、按优先级划分的 WLM 队列等待时间、按类型划分的查询时长以及每天的查询数。COPY 加载和 SELECT 查询分别进行了测量。账单记录提供了预留计算、Spectrum 扫描和并发扩展成本，因此比较涵盖了此次迁移影响的每一条账单项目。

AWS 在 AWS RA3 到 RG 最佳实践博客中提供了迁移规划和工作负载验证指导。

步骤 2：验证目标配置并使用弹性调整大小

AWS 建议在生产迁移之前，在非生产环境中使用代表性工作负载测试目标 RG 配置。该测试旨在衡量收益、发现问题，并在生产迁移前验证目标规模。

7 月 26 日，Moonfrog 使用 弹性调整大小 从五个 ra3.4xlarge 节点迁移到八个 rg.4xlarge 节点，临时提供额外容量以降低迁移风险。它没有导出或重新加载 148 TB 的仓库。架构、ETL 作业、应用程序 SQL、驱动程序、连接字符串和 BI 工具继续正常工作。

Amazon CloudWatch 记录了一个五分钟区间，期间集群报告为不健康。数据库连接随后立即恢复。此采样区间描述了观察到的影响。它并不确立确切的五分钟停机时长。

AWS 指导将弹性调整描述为一种短时操作，通常大约10到15分钟。在从RA3到RG的节点类型变更后，数据水合会将频繁访问的数据从托管存储引入新节点的本地缓存。在解读早期性能测量结果时，应考虑这种缓存预热。

步骤3：验证仓库和数据湖访问

Moonfrog验证了调整大小后仓库加载和外部查询仍在继续。外部模式和表仍在使用，AWS Glue Data Catalog为其提供元数据。

Moonfrog确认，在随后的账单记录中，其RG查询已不再产生按TB计的S3扫描费用。这些查询使用了预置集群容量，而该容量仍会计费。

步骤4：审查工作负载管理规则

Moonfrog的Auto WLM配置包含分别面向管理员、分析师、ETL、加载和可视化的独立队列，以及短查询加速。这些队列在迁移后得以保留。团队审查了查询监控规则，因为数据湖扫描现在会消耗RG集群容量。

该审查考虑了数据湖扫描与仓库工作负载共享计算资源的情况。此前用于控制扫描支出的规则仍可保护这些共享资源。

结果和主要收益

以下四张CloudWatch图表覆盖2026年5月1日至10月25日。每张图都标出了7月26日的调整大小，并对7月26日至8月3日期间进行阴影标注，该期间集群从八个RG节点依次缩减到七个，再到六个。查询时长和WLM等待图表显示七天滚动平均值。查询计数包括COPY、SELECT、INSERT、实用程序及其他操作。

阶段1：在切换后评估RG

首次评估聚焦于工作负载连续性和查询运行时间。仓库加载和数据湖查询继续进行，应用程序使用相同的模式、SQL、驱动程序和连接字符串。初始RG配置上的查询在预期运行时间内完成。Moonfrog随后分阶段减少节点数，以评估每次缩减是否影响查询运行时间。

COPY时长最清晰的对比是7月27日至31日，当时加载量保持不变。平均时长从RA3上的16.8秒降至RG上的3.6秒，缩短了约79%。该窗口落在7月26日至8月3日的规模优化期间，此时最终六节点配置尚未确立。

选择六个节点

Moonfrog在八天内将集群从八个RG节点缩减到七个，然后再到六个。团队相对其五节点RA3基线保留了一个额外节点，以支持不断增长的分析需求和更频繁的加载。它此前已计划将RA3扩展到六或七个节点。

从五个RA3节点迁移到六个RG节点使节点数增加了20%。已发布的节点规格显示每个ra3.4xlarge有12个vCPU，每个rg.4xlarge有16个vCPU，因此预置vCPU从60个增至96个，即增加60%。这些结果反映了节点系列和容量的双重变化。

阶段2：在工作负载增长时保持性能

在验证六节点配置上的可用余量后，Moonfrog于8月24日提高了加载频率。集群现在每天执行超过70,000次COPY操作，约为RA3基线的4.3倍。这些加载使用更小、更频繁的批次，因此后续COPY时长也反映了加载模式的变化。图2显示了早期时长改善以及工作负载变化后的后续性能。

8月下旬，在8月24日提高加载频率之后，Moonfrog为六节点RG配置购买了一年期的无预付预留。该购买是在其使用生产流量评估RG并为预期工作负载增长承诺容量之后进行的。

图2：平均COPY和SELECT时长。早期COPY对比使用未变的加载量。后续平均值也反映了8月24日之后更小的批次

每日查询更多，且计算余量充足

所有类型的每日查询从RA3上约49,122次增至8月的83,603次、9月的125,350次，以及10月1日至25日的125,374次。从9月起，这一数字超过RA3基线的2.5倍。COPY占该增长的大部分，因此总查询增长应与图3中的查询组合一并解读。

图3：按类型划分的每日成功查询。COPY频率在8月24日增加，此时迁移和规模优化期已结束

并发扩展保持启用，以配合六个预留节点吸收峰值突发。尽管总查询量增长，8月、9月和10月的平均每日使用量仍比RA3基线低14–29%。随着需求上升，使用量从9月到10月有所增加。

尽管查询计数更高，平均CPU利用率从RA3上约54%降至9月起的35–39%。图4将每日平均CPU与典型峰值区分开来，典型峰值定义为每小时最大CPU读数的每日平均值。

需求增长时的队列等待

队列等待在迁移后下降，并随着10月流量增加而从8月低点上升。在10月1日至25日期间，最高优先级等待平均为561毫秒，而7月RA3基线为940.7毫秒；高优先级等待平均为193毫秒，而基线为294毫秒。普通优先级等待约为11毫秒，高于7月基线约3.6毫秒。图5为每个优先级使用单独的纵轴刻度。

图 5：按优先级划分的 WLM 队列等待时间的七天滚动平均值。虚线标记 7 月 RA3 基线。每个面板有各自的刻度。

集成数据湖查询和计费

外部数据湖查询在迁移后继续进行。Moonfrog 确认，从 7 月 27 日到所报告的月份，单独的 Spectrum 扫描费用始终恰好为 0 美元：

  • Amazon Redshift 系统视图显示外部查询仍在继续。最近的一个三天样本记录了约 200,000 次针对 Amazon S3 的外部查询，包括 Parquet 扫描。外部模式和表仍在使用中。
  • 计费记录显示没有单独的按 TB 扫描费用。外部扫描使用预置的 RG 容量，该容量仍需计费。Amazon S3 存储和其他费用不在本次比较范围内。

每次查询成本

Moonfrog 为增长选择了额外容量，预留计算、Spectrum 扫描和并发扩展的月度支出合计增长约 4–6%。按一致的 30 天基准计算，9 月每 1,000 次总查询的成本下降约 59%，10 月下降约 58%。8 月至 10 月，每 1,000 次 SELECT 查询的成本下降 38–50%。

团队计划如何使用这些余量

更大的配置为测试更多分析用例创造了空间。此前的测量显示，短查询的平均持续时间从约 2.8 秒降至 1.8 秒。该观察结果适用于所测量的短查询工作负载，并不构成对每个分析问题的响应时间保证。

Moonfrog 计划使用大语言模型（LLM）代理评估对话式分析。此类代理可能执行多次查询来回答一个问题，因此查询延迟只是端到端响应时间的一部分。额外的计算余量让团队有空间在现有分析之外测试这些工作负载。

经验教训

  • 利用预留节点续约的机会，审视容量和架构，以满足您不断增长的工作负载需求。Moonfrog 在做出另一个一年承诺之前评估了 RG。
  • 根据预期的工作负载增长确定集群规模，并对照已配置的容量评估结果。Moonfrog 增加了第六个节点以留出余量。要结合查询组合来解读总查询数，因为更小、更频繁的 COPY 批次会增加操作数量。
  • 将并发扩展纳入容量规划。在此部署中，它继续与预留节点一起吸收峰值突发，因此在评估仓库吞吐量时应考虑其贡献。
  • 将即时迁移结果与后续工作负载变化区分开来。数据量不变的 COPY 对比反映了切换后的头几天。后续结果包括加载频率变化和需求上升。请单独测量仪表板延迟和查询放弃率，以量化对用户的影响。

后续步骤

Moonfrog 已经提高了仓库加载频率。团队计划测量仪表板加载时间和查询放弃率，以评估更高的新鲜度和更短的查询持续时间如何影响产品和分析团队的体验。

Moonfrog 正在考虑为目前以 Parquet 文件形式存储的数据湖表采用 Apache Iceberg。该表格式将增加模式演变和时间旅行等能力。团队将结合性能和运营要求评估这些变更。

团队还计划评估更广泛的自然语言访问。治理必须定义哪些团队可以访问每张表，以及探索性查询如何共享集群资源。端到端代理响应时间需要单独测量。

结论

Moonfrog 使用弹性调整大小将其 148 TB 的生产 Amazon Redshift 仓库从五个 RA3 节点迁移到 RG，然后在经过八天的测量进行合理调整后确定为六个节点。RA3 一直运行可靠。此次变更满足了不断增长的分析需求以及更频繁的仓库加载需求。在切换后数据量不变的情况下，COPY 持续时间立即从 16.8 秒降至 3.6 秒。

借助六个 RG 节点，Moonfrog 从 9 月起每日处理超过 125,000 次各类查询，是 RA3 基线的 2.5 倍以上。平均 CPU 利用率为 35–39%。更频繁的 COPY 批次促成了查询组合的变化。外部查询继续进行，没有单独的 Spectrum 扫描费用，并发扩展在预留节点之外提供了突发容量。

要评估 RG 是否适合您的仓库，请查看 Amazon Redshift 定价、弹性调整大小文档以及 RA3 到 RG 迁移最佳实践。先建立基线，并在非生产环境中测试具有代表性的工作负载。验证仓库和数据湖访问，然后在承诺预留容量之前比较总支出和单位工作成本。
