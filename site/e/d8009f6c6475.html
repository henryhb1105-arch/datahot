欢迎来到 What's New in ClickStack 的六月至七月版。我们将两个版本合并进一次更新，因此要介绍的内容比平时稍多。过去两个月的大部分工作集中在追踪（traces）上，并且直接来自用户反馈。瀑布视图现在为每个服务使用单独的颜色。一个新的缩略图（minimap）让你在检查其中一部分时，仍能保持整个追踪的形状可见。OpenTelemetry span 链接出现在 span 详情面板中，让你可以轻松地在追踪之间移动。对于指标，我们增加了对指数直方图的分位数支持，引入了更精简的默认 schema，并支持连接外部 Prometheus 兼容端点。这使 ClickStack 超越了单一来源的可观测性体验，并为评估 TimeSeries Engine 和迁移现有 Prometheus 工作负载带来了新的可能性，我们将在下面探讨。

仪表盘过滤器现在可以互相缩小范围，类似于分面搜索。事件模式（Event patterns）现在可以用作仪表盘磁贴类型，信息亭模式（kiosk mode）可以将仪表盘锁定为只读视图，用于墙面展示。我们还更改了过滤器值的获取方式。自动补全和过滤器下拉框现在在可用时使用 ClickHouse 文本索引，而不是扫描源表。

追踪瀑布视图改进

追踪视图是 ClickStack 用户花费时间最多的地方，从 Jaeger 迁移过来的团队往往会仔细审视这一工作流。我们在 6 月和 7 月对此进行了大量投入，重新设计了视图并支持了 span 链接。

### 重新设计的追踪瀑布视图

上个月，我们将 span 详情移入一个拆分窗格，这样在检查 span 时瀑布视图仍然可见。这个月，我们专注于瀑布视图本身。每个服务现在都有一个稳定的颜色，显示在操作和服务标签旁边的垂直条中。此前，颜色显示为 span 栏内文本后面的填充背景。绿色仍保留用于关联的日志行，红色用于错误 span，因此两者都不会被误认为服务颜色。span 持续时间现在以弱化文本显示在栏外。悬停时，span 主体会显示在光标一侧空间更大的位置。我们还修复了非常短的 span 在缩放时的行为。此前，其最小宽度被定义为瀑布区面积的一个百分比，而该百分比会随缩放而增加。这可能导致非常短的 span 看起来与持续数秒的 span 一样宽。

固定最小宽度与折叠控件

最小宽度现在是一个固定的像素宽度，使跨度在所有缩放级别下都保持比例，同时确保亚像素跨度仍然可以点击。深层追踪的导航也变得更简单了。展开和折叠控件现在可以作用于单个层级或整个追踪，并且仅在存在可折叠节点时出现。

长追踪的迷你地图

尽管追踪视图的上述改进有助于导航大型追踪，但大型追踪仍然不一定能完整显示在一屏内。当放大到某个区域后，仍可能难以判断该区域在整个追踪中的位置。此前若要返回完整视图，需要滚动缩小或完全重置。为了解决这个问题，现在瀑布图上方有一个迷你地图。它以时间轴的形式显示完整的追踪范围，每个跨度对应一条条带。一个带边框的矩形标记当前视口，同时一个变暗的遮罩将其与追踪的其余部分区分开。您可以在地图上刷动以缩放，拖动视口以平移，或拖动任一边缘以调整大小。

追踪查看器中的 Span 链接

Span 链接是 OpenTelemetry 用来将某个跨度连接到不同追踪中的另一个跨度的方式。它覆盖了以下场景：生产者将工作交给消费者、批处理作业引用其源记录、或者重试的请求启动新追踪。这些跨度虽然不共享追踪 ID，但存在因果关系。ClickStack 一直将 Span 链接摄取到标准的 Links 列中，但并没有显示出来。因此，在扇出（fan-out）和批处理工作流中，相关跨度会表现为孤立节点，与导致它们的工作没有可见的连接。现在，当所选跨度包含链接时，跨度详情面板会包含一个 Span Links 区域。每个链接显示为一行紧凑的记录，追踪状态和链接属性以标签（chips）形式展示。悬停时可看到完整的追踪和跨度 ID。点击 Open trace 操作会在原位跳转到关联的追踪。

连接外部 Prometheus 数据存储

上个月，我们发布了基于 ClickHouse TimeSeries Engine 的实验性 PromQL 支持。它允许使用许多工程师已经熟悉的语言来查询存储在 ClickHouse 中的 Prometheus 风格指标。然而，许多团队已经在运行 Prometheus 或与 Prometheus 兼容的系统。现在，您可以通过 ClickStack UI 将其中一个系统配置为指标源。PromQL 查询会被代理到配置的端点，并且同一个图表编辑器也可以与任一后端配合使用。因此，现有 Prometheus 指标可以与日志和追踪一起绘制图表，而无需先迁移底层数据。这使 ClickStack 超越了单一来源的可观测性体验。随着我们对原生指标支持的成熟，团队可以使用现有的 Prometheus 部署来评估 ClickStack，并跨系统迁移仪表板，而无需立即进行完整迁移。它还支持混合方法。团队可以将高基数工作负载从 Prometheus 迁移到 ClickHouse TimeSeries Engine，逐步迁移，继续使用现有仪表板，并比较两个系统之间的结果。这样可以更容易地验证两个后端在完成迁移前是否产生等效结果。全面迁移并非每个人的目标。

对现有 Prometheus 兼容部署感到满意的团队，可以保留该部署，并使用 ClickStack 将这些指标与日志和 Trace 关联起来。

更快的筛选值与自动补全

自动补全和筛选器下拉框需要回答一个代价高昂的问题：这一列包含哪些值？在数据量很大的源上，扫描表会让原本即时的下拉框变成漫长的等待。ClickStack 使用元数据物化视图来降低这一成本已有一段时间，但选择查询对象的逻辑已经演变成多条重叠路径。我们重构了决定过滤器生成策略的逻辑，使其按成本从低到高依次尝试每个可用选项。首选是 ClickHouse 文本索引，通过 mergeTreeTextIndex() 表函数读取。它列出索引中已存储的术语，无需读取底层数据部分。它适用于 map 上的文本索引，也适用于 TraceId 等原生列。当没有合适的文本索引时，路由器回退到元数据汇总物化视图。只有当两个选项都不可用时，才直接查询源表。自动补全现在使用同一路径，让建议和筛选值共享同一实现。mergeTreeTextIndex() 路径需要 ClickHouse 26.3 或更高版本。对更早版本，路由器会跳过该路径并使用元数据汇总，因此筛选功能在两种情况下都能工作。

级联仪表盘筛选器

过去几个月，仪表盘筛选能力有了显著改进：先是能够限制筛选器中显示的值，随后在 5 月支持了源作用域筛选器。然而，此前每个下拉框仍然会列出其列中的每个值，而不考虑已经应用的筛选器。在 Kubernetes 仪表盘上，选择一个集群后，命名空间下拉框仍满是来自其他集群的命名空间，其中大部分会返回空结果。仪表盘筛选栏和 Kubernetes 视图现在包含一个“Link filters”开关。启用后，每个下拉框只提供与当前选择同时出现的值。例如，选择集群后，命名空间列表会缩小到该集群中存在的命名空间。Kubernetes 筛选栏上的自由文本搜索也会促成同样的缩小。

由于查询成本，链接默认关闭。缩小后的值取决于当前选择，不能来自普通下拉框使用的廉价逐键汇总。随着源的增长，这些查询会变得昂贵得多。为了限制这种成本，缩小后的值只在下拉框打开时才获取。这为仪表盘可触发的额外查询数量设置了一个上限。

连续窗口告警

一个嘈杂的评估窗口就足以让告警在凌晨三点呼叫某人，而问题其实是短暂的且已经过去。短暂的延迟尖峰、一批重试，或一次临时抬高错误率的部署，都可能越过阈值、触发告警，然后在任何人读完通知之前就已经恢复。告警现在支持在触发前，等待某个条件连续多个窗口都成立。如果一条告警要求连续三个一分钟窗口，那么只有当阈值被连续突破三次后，它才会发送通知。这可以在不提高阈值、不降低告警对持续问题的敏感性的情况下，滤除短暂尖峰。

PENDING 状态

当警报正在累积所需的时间窗口时，它会报告一个新的 PENDING 状态。这可以把可能即将触发的警报与当前没有活动条件的警报区分开来。numConsecutiveWindows 设置在警报编辑器和外部 API 中均可用，因此以代码方式管理的警报也可以使用该设置。

指数直方图指标

指数直方图是 OpenTelemetry 两种直方图类型中更为紧凑的一种。它不需要预先定义固定的桶边界，而是使用一个缩放因子和一个索引来表示每个桶。这样一来，单个指标就能以高分辨率覆盖很宽的值域，而埋点作者也无需事先预测有用的延迟边界可能落在哪里。对指数直方图的支持一直是我们在指标支持方面收到的最常见请求之一。

查询构建器现在支持对指数直方图指标进行分位数（quantile）和总和（sum）聚合。这些指标也会与其他指标类型一起出现在指标名称选择器中。

计算分位数比固定桶直方图更复杂。缩放因子可能因序列而异，也可能在同一序列的不同数据点之间变化。在进行任何聚合之前，ClickStack 会将计数归一化为当前存在的最小缩放因子。这会把较细的桶合并为较粗的桶，同时保持它们的偏移对齐。偏移也可能在不同数据点之间移动。为了将累计计数转换为增量计数，ClickStack 会在减去计数之前，将每个桶索引与同一序列中的前一个数据点对齐。对齐之后，再按每个时间桶内的序列对各桶计数求和。ClickStack 使用累计计数定位包含所请求分位数的桶，然后在该桶内使用对数线性插值估算分位数值。这与 Prometheus 的行为一致。

分类条形图

ClickStack 长期以来一直支持条形图，但只能作为时间序列使用，即沿着时间轴每个时间桶一个条。要回答“今天哪十个端点产生的错误最多？”这类问题，过去只能使用饼图，而要比较的值很多时，饼图会变得难以阅读。现在，分类条形图在图表资源管理器、仪表盘、MCP 服务器和外部仪表盘 API 中拥有了自己的显示类型。每个条代表一个分组，而不是一个时间桶，排名比较因此变得容易阅读得多。

新的条形图和现有饼图也支持时间序列图表中已有的系列数量限制。不过，分类图表的实现有所不同：该限制会变成查询中的 ORDER BY 和 LIMIT，而时间序列图表则需要 CTE 才能计算每个时间桶内的 Top 序列。排序方式也是可配置的。分类图表以前固定为按值降序排列，现在你可以提供任意 SQL 表达式作为排序依据，默认仍为值降序。

事件模式作为仪表盘图块

事件模式会将相似的消息归并为一小组具有代表性的模式。这通常是理解某个服务正在输出什么的最快方式。以前，事件模式仅限于搜索页面使用。你可以在调查过程中使用它们，但无法将结果保存到仪表盘上，与它帮助解释的图表放在一起。现在，事件模式已经可以作为仪表盘图块类型使用。

Tile 编辑器中的模式挖掘

Tile 编辑器有一个专门区域，用于指定要分析的列表达式（日志默认使用 Body，trace 数据源默认使用 SpanName），还可以提供可选过滤器，过滤器可使用 Lucene 或 SQL 编写——这对于将模式挖掘限制在数据子集内很有用。该功能覆盖 UI、MCP server 和外部 API，因此代理（agent）也可以使用 displayType: "event_patterns" 创建模式磁贴（pattern tile）。

只读 Kiosk 模式

很多团队会在办公室的屏幕上展示一个仪表盘。在此之前，这意味着要保留一个可编辑的仪表盘并保持打开状态，同时希望没有人拿着鼠标路过。创作界面也占用了本不该被交互的显示空间。现在仪表盘有了 kiosk 模式，可从溢出菜单（overflow menu）进入。该模式将界面缩减为仪表盘名称、实时只读指示器，以及磁贴本身。所有编辑控件都被禁用，自动刷新始终保持开启，包括 trace 磁贴和搜索磁贴的实时行为。

Kiosk 模式通过 URL 中的 kiosk=true 存储。壁挂显示屏可以直接打开该 URL，并在重启后回到 kiosk 模式，而无需任何人重新配置。

指标表默认 Schema 变更

这会改变 Collector 创建的默认 schema，因此仅适用于新建的指标表。现有部署会保留当前的排序键（sorting key），因为主键无法就地修改。如何迁移到新的主键，请参见我们现有的指南。

OpenTelemetry Collector 的 Datadog Receiver

ClickStack 发行的 OpenTelemetry Collector 现在包含一个可选的 Datadog receiver。现有的 Datadog Agent 可以直接向 ClickStack 发送追踪（traces）、指标（metrics）和日志（logs），无需立即更改任何埋点。设置 ENABLE_DATADOG_RECEIVER 后，OpAMP 控制器会将 contrib datadogreceiver（监听 0.0.0.0:8126）添加到 traces、metrics 和 logs 三条流水线中。启用 Collector 认证后，该 receiver 会对照团队 API 密钥校验 DD-API-KEY 请求头。

这大大降低了用现有工作负载评估 ClickStack 的门槛，也提供了一条渐进式迁移路径。团队可以立即开始向 ClickStack 发送数据，然后逐步将埋点迁移到 OpenTelemetry SDK 和 Collector，而不必一次性全部替换。并行运行两套系统是另一种选择。团队可以把日志或追踪迁到 ClickStack，同时把指标留在 Datadog，无需替换每个信号背后的埋点。这样，各个工作负载可以在运维或成本收益合适的时候单独迁移。我们在专门的一篇博客中详细介绍了这条迁移路径，包括 receiver 能转换和不能转换的内容。

MCP 服务器改进

自从在 Open House 上发布 ClickStack MCP 服务器以来，我们一直在扩展 agent 可以借它完成的工作。我们自己的评估框架显示，当 agent 获得可观测性原语时，其表现明显优于被要求用原始 SQL 重建调查工作流时的表现。本月有两项改进尤为突出。

### 指标作为一等数据源

MCP 服务器现在具备一整套发现和查询 OpenTelemetry 指标的工作流。两个新工具负责指标发现。clickstack_list_metrics 返回分页的指标名称目录，支持按指标类型（metric kind）、名称模式和时间窗口过滤。clickstack_describe_metric 返回所选指标的单位、描述、属性键和采样值。clickstack_describe_source 也具备指标感知能力：它会根据指标类型选择一个有代表性的表，并运行与其他数据源类型相同的列发现与值采样流程。clickstack_timeseries 和 clickstack_table 工具现在接受 metricType 和 metricName 参数，从而支持对指标进行查询。

### 数据源与 Webhook 管理

几位用户提出，希望让 agent 参与 ClickStack 的初始设置过程，而不只是等数据流入后再用 agent 做调查。此前，这隐含了一个前提：在 agent 介入之前，数据源和 webhook 已经配置完成。现在，MCP 服务器可以创建、更新和删除数据源与 webhook。agent 可以从初始化阶段开始，创建数据源，将采集器（shipper）指向 ClickStack，然后开始摄取数据。之后，它就可以基于同一份数据构建搜索、仪表盘和告警。支撑这一工作流的工具包括 clickstack_save_source、clickstack_delete_source、clickstack_save_webhook 和 clickstack_delete_webhook。
