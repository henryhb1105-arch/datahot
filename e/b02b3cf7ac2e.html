Amazon Redshift 解决 Iceberg 表并发写冲突

Amazon Redshift 现在可自动解决许多 Apache Iceberg 表的并发写入冲突，把此前会失败并要求重试的提交直接完成。文章解释 Iceberg 使用乐观并发控制（OCC）与快照隔离，写写冲突来自按表版本而非按行或分区检查。Redshift 会把检查从操作级逐步升级到分区级和文件级，以判断并发写入是否真正重叠，并说明由此带来的吞吐提升。该机制面向流式任务、调度管道和一次性转换同时写同一张表的场景。

为什么值得关注：对使用 Redshift/Iceberg 的数据平台团队，这是并发写入可靠性、吞吐与快照隔离语义的关键更新；理解冲突检测粒度有助于设计流批一体写入和重试策略。

AI 逐段翻译

在Amazon Redshift 中开始使用 Apache Iceberg 写入支持 – 第 1 部分中，你学习了如何创建 Apache Iceberg 表并使用INSERT向其中写入数据。在第 2 部分中，你使用DELETE、UPDATE和MERGE在行级别修改了数据。这两篇文章都假设你的写入独占该表。在生产环境中，这种情况很少见：流式作业、计划管道和一次性转换经常会同时写入同一张表。Amazon Redshift 现在可以自动解决其中许多并发写入，提交那些以前会失败并被迫重试的更改。在本文中，我们将解释为什么对 Iceberg 表的并发写入会发生冲突，Amazon Redshift 如何解决那些实际上并不重叠的冲突，引擎如何将其检查从操作升级到分区再升级到单个文件，以及它带来的吞吐量提升。

并发写入的挑战

Apache Iceberg 使用乐观并发控制（OCC）来在多个写入者同时提交时保持表的一致性。每个写入者基于表的当前版本准备其更改，并通过在目录中以原子方式推进表版本来提交，前提是没有其他写入者先推进了版本。如果在此期间有其他写入者提交，该条件就会失败，整个写入将被丢弃。这种严格性维护了快照隔离语义：如果后来的提交无论如何都被应用，它将在没有较早写入者更改的情况下替换表版本，从而静默丢失一个已提交的写入。

读取者不会遇到这个问题。Iceberg 扫描始终读取一个已提交的快照，因此读取永远不会因并发写入而失效。这使得写-写冲突成为引擎必须解决的唯一情况，而正确解决它们正是为表保持快照隔离语义的关键。

问题在于这种检查过于笼统。该条件是针对表版本进行评估的，而不是针对每个写入者所触及的行或分区。在这个粒度上，它的答案是正确的，因为版本确实发生了变化。然而，它并没有说明两次写入在底层数据上是否重叠。两个修改了完全独立分区的写入者，或者各自独立插入新数据的写入者，与两个重写了相同行的写入者发生冲突的程度完全相同。只要它们从查询开始到提交的时间窗口重叠，这种情况就会发生。

考虑一个零售分析平台，其中有一张customer_orders Iceberg 表。一个流式管道可能持续写入新订单，每分钟有数百次插入。一个夜间合规作业删除超过七年的记录，运行大约需要一个小时。这两次写入从不会触及相同的数据：流式写入只添加最近的订单，而合规作业只删除旧订单。在基本的乐观并发控制下，这无关紧要。如果在那一个小时内的任何时间点有一次流式插入提交，合规作业就会输掉竞争，它一个小时的工作将被丢弃，下一次尝试会重新扫描数 TB 的数据，结果只是再次进入同样的竞争。表版本冲突是真实存在的，尽管数据冲突并不存在。

避免这种情况的常见方法都是手动操作，而且每种都有代价。你可以将写入者串行化，使得一次只有一个提交，但这完全放弃了并发性。你可以将一张逻辑表拆分为多张物理表，这样就没有两个写入者会共享同一张表。这以清晰的数据模型和跨表查询的能力为代价，换取了并行写入的能力。或者你可以将每次写入都包装在应用端的重试循环中，并承担重新运行那些实际上从未冲突的语句的成本。在每种情况下，精力都花在了绕过提交协议上，而不是花在你的数据上。

Amazon Redshift 如何解决写入冲突

当一次提交输掉竞争时，Amazon Redshift 现在会在放弃之前提出一个更精确的问题：在它之前提交的那些写入者是否实际更改了它更改的相同分区、文件或行？当答案是否定的时，就没有理由丢弃这些工作。Amazon Redshift 不会中止，而是对更改进行变基（类似于git rebase），将已经准备好的写入重放到表的最新版本上，并提交该结果。两次写入都成功落地，无需重新扫描、无需重新执行，也无需在应用程序中设置重试循环。

在零售示例中，合规删除以前会在其执行窗口内有流式插入提交的那一刻失败。现在，Amazon Redshift 会检查这两次写入，发现插入只添加了数据文件，而删除只移除了其他文件，并确认它们从未触及相同的数据。由于这些更改可证明是独立的，Amazon Redshift 会将删除变基到更新后的表版本上并提交它。两次写入都成功，一个小时的工作得以保留，下游消费者也能看到这两项更改。

此行为对符合条件的写入是自动的，无需选择聚簇键、无需重新分区，也无需启用任何设置。当两次写入真正冲突时，行为与目前保持不变：冲突会暴露出来，后写入者会失败并且必须重试。

有两个原则指导着这种解决方式的工作机制。第一个原则是，冲突是一个粒度问题。一次失败的竞争并不自动意味着冲突。这是一个可以在不同分辨率下提出的问题。引擎可以询问是否有任何写入者删除了数据，还是它们只是添加了数据；如果数据被删除了，它是来自当前写入所触及的同一分区、同一文件，还是同一行。所检查的粒度越细，就越多的表面冲突会显现为可以安全共存的独立更改。但更细的检查成本也更高：推至极限，引擎可以逐行求两个变更集的交集，而这是昂贵的，而且通常是不必要的。因此，Amazon Redshift 会先评估成本最低的层级，只有在必须时才检查更细的层级。

第二条原则是正确性优先于并发性。冲突解决完全依据表元数据进行，绝不重新扫描数据或重新规划查询。当引擎无法证明两次写入相互独立时，它不会猜测。它会拒绝解决冲突，写入将重试，与当前行为完全一致。不必要的重试只耗费少量时间，而错误的解决则可能导致数据丢失，因此系统刻意偏向安全的结果。解决过程在快照隔离下运行，这与 Amazon Redshift 已用于 Iceberg 读取的模型相同。诸如 Apache Spark、Amazon EMR和 Amazon Athena 之类的引擎通过表的隔离级别属性来遵循它，因此跨引擎共享的表能保持一致的语义。对于写入隔离属性设置为 serializable 的表，Amazon Redshift 会保留更严格的契约，并暴露每一个冲突，而不是解决它。这就是 Iceberg 表属性 write.*.isolation-level。它与通过 ALTER DATABASE … ISOLATION LEVEL 设置的 Amazon Redshift 数据库隔离级别无关，后者管理 Amazon Redshift 事务，对 Iceberg 提交冲突解决没有影响。

在恰当的粒度上解决

当提交在竞争中失败时，引擎会按从最廉价到最精确的顺序逐级进行检查。每一级本身都是一次完整的解决，如果某项检查证明写入相互独立，则变基提交，不再运行更细粒度的检查。下图展示了这一逐级升级序列：先进行操作级检查，然后是分区级检查，最后是文件级检查。每一级要么证明写入相互独立，要么升级到下一级，真正的冲突只有在最后一级之后才会浮现。

图 1：冲突解决从操作级到分区级再到文件级检查的升级过程

第一项检查是按操作进行。只添加数据的写入，例如由流式作业落地新数据的 INSERT，不可能移除另一个写入者所依赖的任何内容，因此任何写入都可以针对它进行变基。这一条规则解决了至少有一次写入仅追加的所有组合。一次 DELETE、UPDATE 或 MERGE 提交都能在并发插入流下干净地完成，而一次 INSERT 提交可在任何其他并发更改（包括压缩）之上干净地完成。

接下来，当两次写入都移除了数据时，引擎会比较它们各自触及的分区。修改了不相交分区的写入，例如更新不同日期的批处理作业，或维护同一张表各自切片的按 Region 流水线，从构造上就是相互独立的，二者都能干净地提交。

最后，当两次写入触及同一分区时，引擎会比较各自更改的单个文件。删除同一日期分区中不同行的两个作业通常落在不同文件中，一旦如此，二者都能干净地提交。只有当两次写入修改了同一文件时，冲突才会浮现，语句才会重新运行。该协议还为更进一级保留了空间：区分单个文件内不同行的更改。

性能

为了衡量效果，我们让越来越多的并发写入者在固定时间窗口内向单张 Iceberg 表提交。我们将基本的乐观并发模式（失败的提交被中止并重新运行）与启用自动冲突解决模式进行了对比。每个写入者都发出相同的单语句 INSERT，因此各次运行之间唯一的变量是争用程度，而非工作负载。我们将并发写入者从 1 扩展到 16，并记录每种配置下有多少提交成功、有多少因冲突被拒绝。

设置：一张未分区的 Iceberg 表，注册在 US East（N. Virginia）AWS 区域（us-east-1）的 AWS Glue Data Catalog 中。每个写入者是一个独立会话，在 60 秒内循环发出自动提交的 INSERT 语句。我们报告每种配置下完成的提交数和因冲突被拒绝的尝试数。

第一张图展示了随着写入者增加，写入吞吐量相对于单写入者情况归一化后的变化，因此比较不依赖于实例类型或表大小。

图 2：随着并发写入者增加，启用和不启用自动冲突解决时的写入吞吐量

在基本乐观并发下，增加写入者会使向表写入变慢。在 16 个写入者时，吞吐量降至单写入者的 0.17 倍，因为几乎所有写入者的工作都被丢弃并重做，而不是提交。使用自动冲突解决时，相同工作负载可扩展到约 2 倍，且在任何测量配置下都没有提交被拒绝。在 16 个并发写入者时，同一窗口内完成的提交多出 12 倍。第二张图展示了原因。

图 3：随着并发写入者增加，启用和不启用自动冲突解决时的提交失败率

基线的失败率几乎恰好是 (N−1)/N，例如两个写入器时为 50%，四个写入器时为 75%，16 个写入器时为 94%。这说明了此前发生的表级检查：每轮提交只有一个写入器成功，其他所有进行中的写入器都被拒绝。额外的写入器几乎完全转化为重复工作，而不是进展。启用冲突解决后，同样的运行完全不会记录到任何冲突，因为此工作负载中的每次写入都是追加，而追加永远不会移除其他写入器所依赖的数据。

此基准测试有意隔离出最基本的追加场景：单个未分区表和仅插入的写入器，这正是持续摄取背后的模式。会移除数据的工作负载会触发前面描述的分区和文件检查，其结果取决于两次写入是否触及了同一分区和同一批文件。

集群范围结果

在冲突解决之前，并发写入冲突是 Amazon Redshift 中 Iceberg 写入失败的唯一最大原因，每周约占失败的 Iceberg 写入查询的五分之一。我们分阶段推出了此功能，首先是涵盖并发追加的操作级检查。当该阶段于 2026 年 9 月初达到全集群部署时，并发写入引发的冲突错误降至几乎为零，即便集群上的 Iceberg 写入量增加了一倍以上。下方显示的一个残余峰值来自某个发出并发 UPDATE 语句的工作负载，这一类冲突将在后续分区级和文件级检查随集群部署时得到解决。

观察冲突解决

每次 Iceberg 提交尝试都记录在 stl_iceberg_commit 系统表中，包括结果、尝试次数、写入在其上重定基线的并发操作，以及重定基线所花费的时间。要查看在示例表上冲突解决触发的频率：

SELECT outcome, count(*), avg(attempt_number)
FROM stl_iceberg_commit
WHERE trim(table_name) = 'customer_orders'
GROUP BY outcome;

结论

并发写入是生产数据湖的常态，在此之前，它们迫使你串行化写入器、围绕问题进行分区，或进行重试。借助自动冲突解决，Amazon Redshift 会提交实际上并不重叠的并发写入。这些包括各种写入与并发追加的任意组合，以及更改同一表的不同分区或不同文件的行级写入。要开始使用，请在 patch 203 或更高版本 上从多个作业写入你的 Iceberg 表。不冲突的提交会自行开始解决。要了解有关 Amazon Redshift 中 Iceberg 写入支持的更多信息，请参阅 第 1 部分 和 第 2 部分。
