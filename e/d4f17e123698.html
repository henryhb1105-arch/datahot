过去一年里，我们与数十支来自不同行业的团队合作，共同构建大语言模型（LLM）代理。一个一致的现象是：最成功的实现并没有使用复杂框架或专用库，而是用简单、可组合的模式构建。在本文中，我们分享与客户合作以及自行构建代理过程中学到的心得，并为开发者提供关于构建高效代理的实用建议。

什么是代理？

“代理”（Agent）可以有多种定义方式。一些客户将代理定义为完全自主的系统，能够在较长时间内独立运行，使用各种工具完成复杂任务。另一些人则用这个词来描述更具规定性的实现——这些实现遵循预定义的工作流。

在Anthropic，我们将所有这些变体统称为代理系统（agentic systems），但在工作流（workflows）与代理（agents）之间划出了一条重要的架构区分：

**工作流**（Workflows）是通过预定义代码路径编排LLM和工具的系统。

**代理**（Agents）则是由LLM动态引导自身流程和工具使用的系统，自主控制如何完成任务。

下面我们将详细探讨这两类代理系统。在附录1（“实践中的代理”）中，我们描述了客户从这类系统中获得特别价值的两个领域。

何时（以及何时不该）使用代理

在构建LLM应用时，我们建议尽可能寻找最简单的解决方案，只在必要时增加复杂度。这可能意味着根本不构建代理系统。代理系统通常以延迟和成本换取更好的任务性能，你应该判断这种权衡何时是合理的。

当确实需要更高复杂度时：对于定义明确的任务，工作流能提供可预测性和一致性；而当需要在大规模场景中灵活应变、由模型驱动决策时，代理是更优的选择。但对许多应用而言，通过检索和上下文示例来优化单次LLM调用通常已经足够。

何时以及如何使用框架

有许多框架能让代理系统更容易实现，包括：

**Claude Agent SDK**；**AWS的Strands Agents SDK**；**Rivet**——一个拖拽式GUI LLM工作流构建器；以及**Vellum**——另一个用于构建和测试复杂工作流的GUI工具。

这些框架通过简化调用LLM、定义和解析工具、串联调用等标准底层任务，让入门变得容易。然而，它们也常常引入额外的抽象层，可能掩盖底层的提示词和响应，使其更难调试。它们还可能诱使你在简单方案已足够时增加复杂度。

我们建议开发者从直接使用LLM API开始：许多模式只需几行代码即可实现。如果确实使用框架，请确保你理解底层代码——对内部实现的不正确假设是客户出错的常见来源。更多示例实现参见我们的cookbook。

构建块、工作流与智能体

在本节中，我们将探讨在生产环境中看到的智能体系统的常见模式。我们首先从基础构建块——增强型 LLM——开始，然后逐步增加复杂度，从简单的组合式工作流到自主智能体。

构建块：增强型 LLM

智能体系统的基本构建块，是经过检索、工具和记忆等增强能力加持的 LLM。我们当前的模型能够主动使用这些能力——生成自己的搜索查询、选择合适的工具，并决定要保留哪些信息。

我们建议重点关注实现的两个关键方面：一是针对你的特定用例调整这些能力，二是确保它们为 LLM 提供一个简单、文档完善的接口。虽然实现这些增强的方法有很多，一种方式是通过我们最近发布的 Model Context Protocol（MCP），它允许开发者通过一个简单的客户端实现，与不断增长的第三方工具生态系统集成。在本文其余部分，我们假设每次 LLM 调用都能访问这些增强能力。

工作流：提示词链

提示词链将任务分解为一系列步骤，其中每次 LLM 调用都会处理前一次调用的输出。你可以在任何中间步骤添加程序化检查（见下图中的“gate”），以确保流程仍处于正轨。

何时使用此工作流：这种工作流非常适合任务能够轻松、清晰地分解为固定子任务的情况。其主要目标是以延迟换取更高的准确性，方法是让每次 LLM 调用都变成一个更简单的任务。

提示词链有用的示例：

- 生成营销文案，然后将其翻译成另一种语言。

- 撰写文档大纲，检查大纲是否满足某些标准，然后基于大纲撰写文档。

工作流：路由

路由会对输入进行分类，并将其引导至专门的后续任务。这种工作流允许实现关注点分离，并构建更专门的提示词。没有这种工作流时，针对某一种输入进行优化可能会损害其他输入的性能。

何时使用此工作流：路由适合复杂任务，尤其是当存在更适合分别处理的不同类别，并且可以由 LLM 或更传统的分类模型/算法准确完成分类时。

路由有用的示例：

- 将不同类型的客户服务查询（一般问题、退款请求、技术支持）引导到不同的下游流程、提示词和工具中。

- 将简单/常见问题路由到更小、成本效益更高的模型（如 Claude Haiku 4.5），将困难/不常见问题路由到能力更强的模型（如 Claude Sonnet 4.5），以优化整体性能。

工作流：并行化

LLM 有时可以同时处理一项任务，并通过程序化方式聚合它们的输出。这种工作流称为并行化，有两种关键变体：

- 切分（Sectioning）：将任务分解为并行运行的独立子任务。

- 投票（Voting）：多次运行同一任务，以获得多样化的输出。

何时使用此工作流：当被拆分的子任务可以并行以提升速度时，或者当需要多种视角或多次尝试才能获得更高置信度的结果时，并行化非常有效。

代理

代理可以在检查点或遇到阻碍时暂停，等待人工反馈。任务通常在完成时终止，但引入停止条件（如最大迭代次数）也很常见，以便保持控制。代理能够处理复杂的任务，但其实现往往直截了当。它们通常就是在循环中基于环境反馈使用工具的LLM。因此，精心设计工具集及其文档至关重要。我们在附录2（"为你的工具进行提示工程"）中详细阐述了工具开发的最佳实践。

自主代理

**何时使用代理：** 代理可用于开放式问题——即难以或无法预测所需步骤数量、无法硬编码固定路径的场景。LLM可能会运行很多轮次，你必须对其决策能力有一定程度的信任。代理的自主性使其非常适合在可信环境中扩展任务。但自主性也意味着更高的成本和错误累积的潜在风险。我们建议在沙盒环境中进行广泛测试，并设置适当的防护措施。

组合与定制这些模式

这些构建模块并非规定性的。它们是开发者可以根据不同用例进行塑造和组合的常见模式。与任何LLM功能一样，成功的关键在于衡量性能并迭代实现。重申一遍：只有当复杂性能够显著改善结果时，才应考虑增加它。

总结

在LLM领域的成功不在于构建最复杂的系统，而在于为你的需求构建合适的系统。从简单提示开始，通过全面的评估进行优化，只有当更简单的解决方案不足时才添加多步代理系统。

在实现代理时，我们遵循三个核心原则：

- 保持代理设计的简洁性。

- 优先保证透明度，明确展示代理的规划步骤。

- 通过全面的工具文档和测试，精心设计代理-计算机接口（ACI）。

框架可以帮助你快速起步，但在进入生产环境时，不要犹豫减少抽象层，使用基础组件进行构建。遵循这些原则，你可以创建不仅强大，而且可靠、可维护、并赢得用户信任的代理。

### A. 客户支持

客户支持将熟悉的聊天机器人界面与通过工具集成增强的能力相结合。

工具定义与防错优化

良好的工具定义通常包含示例用法、边界情况、输入格式要求，以及与其他工具的清晰界限。你如何调整参数名称或描述，让事情更加一目了然？不妨把这看作是为团队中的初级开发者编写一份出色的文档字符串（docstring）。当你同时使用许多相似工具时，这一点尤其重要。

测试模型如何使用你的工具：在我们的工作台（workbench）中运行大量示例输入，观察模型会犯哪些错误，然后迭代改进。为你的工具做防错（poka-yoke）设计——修改参数，让错误更难发生。

在为 SWE-bench 构建代理时，我们实际上在优化工具上花费的时间比优化整体提示词还要多。例如，我们发现，当代理移出根目录后，模型在使用相对文件路径的工具时会出错。为解决这个问题，我们将工具改为始终要求绝对文件路径——结果模型完美无误地使用了这一方法。
