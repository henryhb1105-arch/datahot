译文

AI 逐段翻译

Amazon S3 Tables，这是 Amazon Simple Storage Service（Amazon S3）的一项功能，提供内置 Apache Iceberg 支持的云对象存储，并简化大规模表格数据的存储。将其与 dbt 和 AWS Glue 集成后，您可以借助现代湖仓的可靠性和性能运行基于 SQL 的数据转换，将软件工程最佳实践引入数据领域。

本文演示如何使用 Amazon S3 Tables 和 dbt-glue 适配器配置并实现 dbt 转换。从 1.12.4 版本开始，dbt-glue 适配器为 S3 Tables 增加了增量合并支持，本文中的模式基于此构建。我们将介绍 dbt-glue 适配器的具体配置要求，以及基于 S3 Tables 增量模型的实用实现模式：用于保持每条记录最新状态的合并策略，以及用于构建便于审计的变更历史的追加策略。

示例场景

在本次演练中，我们模拟一个跟踪客户档案及其订单的电商系统。我们首先针对初始数据集运行管道，然后模拟上游源数据的更新并再次运行，以演示增量更新。

我们的示例场景遵循一个全程使用 S3 Tables 的数据管道架构。原始电商数据（customers.csv 和 orders.csv）以逗号分隔值（CSV）格式写入常规 S3 存储桶。随后 dbt 通过两层 S3 Tables 对其进行转换。暂存层对每个数据源进行清洗和标准化，集市层生成可直接用于分析的维表和事实表。您可以从各种分析和商业智能（BI）工具中查询生成的集市数据，例如 Amazon Athena 和 Amazon Quick Sight。本文中，我们从 Athena 查询。

集市层并排演示了两种增量策略：fact_orders 模型使用 merge 来保持每个订单的最新状态，而 fact_order_history 使用 append 来累积完整的变更历史。

该数据管道流程如下图所示：

Source Data (Regular S3 - CSV)
    └─ customers.csv, orders.csv
    ↓
Staging Models (S3 Tables)
    ├─ stg_customers
    └─ stg_orders
    ↓
Mart Models (S3 Tables)
    ├─ dim_customers
    ├─ fact_orders                (incremental with merge --- latest state per order)
    └─ fact_order_history         (incremental with append --- change history)
    ↓
Consumption Layer (Athena, Quick Sight, BI tools)

下图展示了该管道背后的架构：dbt-glue 将每个模型作为 Spark SQL 语句提交到 AWS Glue 交互式会话，该会话读取原始 S3 存储桶，并将暂存表和集市表作为 S3 Tables 写入同一数据湖中。

图 1：基于 AWS Glue 的 Amazon S3 Tables 上 dbt 转换管道的架构

先决条件

开始之前，请确保您具备以下先决条件：

  • AWS 账户。
  • 一个 AWS Identity and Access Management（IAM）角色，供 dbt-glue 在运行 AWS Glue 交互式会话时担任，需具备 AWS Glue、AWS Glue Data Catalog、Amazon S3 和 Amazon S3 Tables 的权限。请参阅 为 AWS Glue 设置 IAM 权限。
  • dbt-glue 1.12.4 或更高版本（S3 Tables 增量模型所需）。
  • Python 3.10、3.11 或 3.12。请参阅 Python 兼容性矩阵，以查找各 dbt-core 版本支持的 Python 版本。
  • AWS Glue 6.0 或更高版本。
  • AWS Command Line Interface（AWS CLI）2.x 版本。
  • 将 Amazon S3 表存储桶与 AWS 分析服务集成。

创建 S3 Tables 命名空间和 AWS Glue 数据库

在本节中，您将设置 dbt-glue 所需的 AWS 基础设施：一个用于存放 dbt 模型的 S3 表存储桶和命名空间，以及一个用于源数据的 AWS Glue 数据库。

首先，设置环境变量。将 YOUR_ACCOUNT_ID、YOUR-REGULAR-BUCKET 和 YOUR_Glue_Role_ARN 替换为您的数据：

export DBT_GLUE_REGION="us-east-1"
export AWS_ACCOUNT_ID="<YOUR_ACCOUNT_ID>"
export S3_TABLES_BUCKET_NAME="dbt-glue-s3-tables-bucket"
export DBT_ROLE_ARN="<YOUR_Glue_Role_ARN>"
export DBT_S3_LOCATION="s3://<YOUR-REGULAR-BUCKET>/glue/data/"
export DBT_S3_TABLES_BUCKET="${AWS_ACCOUNT_ID}:s3tablescatalog/${S3_TABLES_BUCKET_NAME}"

其中 DBT_S3_TABLES_BUCKET 的格式为 AWS_ACCOUNT_ID:s3tablescatalog/BUCKET_NAME，而不是 Amazon Resource Name（ARN）。

其次，创建 S3 表存储桶和命名空间：

aws s3tables create-table-bucket \
  --region $DBT_GLUE_REGION \
  --name $S3_TABLES_BUCKET_NAME
aws s3tables create-namespace \
  --region $DBT_GLUE_REGION \
  --table-bucket-arn "arn:aws:s3tables:${DBT_GLUE_REGION}:${AWS_ACCOUNT_ID}:bucket/${S3_TABLES_BUCKET_NAME}" \
  --namespace dbt_glue_s3_tables
aws glue get-database \
  --region $DBT_GLUE_REGION \
  --catalog-id "$DBT_S3_TABLES_BUCKET" \
  --name dbt_glue_s3_tables
aws glue create-database \
  --region $DBT_GLUE_REGION \
  --database-input Name=raw_ecommerce,Description='Raw e-commerce data'

创建 dbt 模型

在本节中，您将构建完整的模型层：一个 sources.yml，用于注册原始 AWS Glue 表；两个暂存模型，用于清洗和准备客户与订单数据；以及三个数据集市模型，将这些暂存数据转换为一个维度表和两个事实表，其中一个使用增量合并，另一个使用增量追加。

首先，创建 sources.yml 定义您的原始数据表：

version: 2

sources:
  - name: raw_ecommerce
    description: "Raw e-commerce data in regular S3 buckets"
    schema: raw_ecommerce

    tables:
      - name: customers
        description: "Customer master data"
        columns:
          - name: customer_id
            tests:
              - unique
              - not_null
          - name: email
            tests:
              - unique
              - not_null

      - name: orders
        description: "Order transactions"
        columns:
          - name: order_id
            tests:
              - unique
              - not_null
          - name: customer_id
            tests:
              - not_null
              - relationships:
                  arguments:
                    to: source('raw_ecommerce', 'customers')
                    field: customer_id
          - name: updated_at
            tests:
              - not_null
-- Staging model as S3 Tables with incremental merge
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='customer_id',
    on_schema_change='sync_all_columns',
    file_format='s3tables'
) }}

SELECT
    customer_id,
    LOWER(TRIM(email)) AS email,
    first_name,
    last_name,
    CAST(registration_date AS DATE) AS registration_date,
    customer_segment
FROM spark_catalog.{{ source('raw_ecommerce', 'customers') }}
WHERE customer_id IS NOT NULL
-- Staging model as S3 Tables with incremental merge
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='order_id',
    on_schema_change='sync_all_columns',
    file_format='s3tables'
) }}

SELECT
    order_id,
    customer_id,
    CAST(order_date AS DATE) AS order_date,
    CASE
        WHEN LOWER(TRIM(order_status)) = 'completed'  THEN 'completed'
        WHEN LOWER(TRIM(order_status)) = 'shipped'    THEN 'shipped'
        WHEN LOWER(TRIM(order_status)) = 'processing' THEN 'processing'
        WHEN LOWER(TRIM(order_status)) = 'cancelled'  THEN 'cancelled'
        ELSE 'unknown'
    END AS status,
    CAST(order_amount AS DECIMAL(10,2)) AS total_amount,
    EXTRACT(YEAR  FROM CAST(order_date AS DATE)) AS order_year,
    EXTRACT(MONTH FROM CAST(order_date AS DATE)) AS order_month,
    CAST(updated_at AS TIMESTAMP) AS updated_at
FROM spark_catalog.{{ source('raw_ecommerce', 'orders') }}
WHERE order_id IS NOT NULL
-- Dimension table using S3 Tables
{{ config(
    materialized='table',
    file_format='s3tables',
    partition_by=['registration_year'],
    table_properties={
        'format': 'iceberg',
        'write.format.default': 'parquet'
    }
) }}

SELECT
    customer_id,
    email,
    first_name,
    last_name,
    registration_date,
    YEAR(registration_date) as registration_year,
    customer_segment,
    CASE
        WHEN customer_segment = 'Premium' THEN 1
        WHEN customer_segment = 'Regular' THEN 2
        ELSE 3
    END as segment_priority,
    CURRENT_TIMESTAMP() as dbt_updated_at
FROM {{ ref('stg_customers') }}
-- Fact table using S3 Tables with incremental merge
{{ config(
    materialized='incremental',
    file_format='s3tables',
    incremental_strategy='merge',
    unique_key='order_id',
    partition_by=['order_year', 'order_month'],
    table_properties={
        'format': 'iceberg',
        'write.format.default': 'parquet'
    }
) }}

SELECT
    o.order_id,
    o.customer_id,
    o.order_date,
    YEAR(o.order_date)  AS order_year,
    MONTH(o.order_date) AS order_month,
    o.status,
    o.total_amount,
    c.customer_segment,
    c.segment_priority,
    CURRENT_TIMESTAMP() AS dbt_updated_at
FROM {{ ref('stg_orders') }} o
LEFT JOIN {{ ref('dim_customers') }} c
  ON o.customer_id = c.customer_id
-- Fact table using S3 Tables with incremental append
{{ config(
    materialized='incremental',
    file_format='s3tables',
    incremental_strategy='append',
    partition_by=['event_year', 'event_month'],
    table_properties={
        'format': 'iceberg',
        'write.format.default': 'parquet'
    }
) }}

SELECT
    order_id,
    customer_id,
    status,
    order_date,
    total_amount,
    updated_at,
    CURRENT_TIMESTAMP() AS recorded_at,
    YEAR(updated_at)    AS event_year,
    MONTH(updated_at)   AS event_month
FROM {{ ref('stg_orders') }}

结论

在本文中，我们展示了如何使用 AWS Glue 6.0 在 Amazon S3 Tables 上构建端到端的 dbt 转换管道，并采用暂存层与集市层架构。该管道的核心是 S3 Tables 上的增量模型，它让我们能够使用 SQL 以增量方式转换和维护数据。我们演示了两种增量策略的协同工作：merge 策略用于在 fact_orders 中保留每个订单的最新状态，append 策略用于在 fact_order_history 中构建便于审计的变更历史。

dbt-glue 适配器对 S3 Tables 的支持目前处于实验阶段（截至 1.12.4 版本），并将在后续版本中持续演进。与任何实验性功能一样，我们建议您在使用前先在自己的环境中进行全面测试。

要了解更多信息，请参阅 Amazon S3 Tables 和 dbt-glue 适配器。
