AI 逐段翻译

本文与 Twilio 的 Sean McKibben 共同撰写。

本文介绍了 Twilio 的 Commerce Platform 团队如何通过从传统的 MySQL 系统迁移到 AWS 上的现代数据架构，对其计费管道进行现代化改造。新的计费平台构建于 Amazon Redshift Serverless 之上，并使用 Amazon Managed Streaming for Apache Kafka (Amazon MSK) 和 Zero-ETL 与 Amazon Aurora MySQL 的集成来实现流式摄取。

“我们借助 Amazon Redshift 完成的计费转型，使业务能够提供此前无法考虑的全新销售方式。它在实现这一点的同时，还将成本降低了 70% 并减少了运维开销，这让我们认识到该方案有多么强大。”

— Sean McKibben，Twilio 首席软件工程师

Twilio 是一个云通信平台，提供用于消息、语音、电子邮件和视频的 API。它服务于超过 40 万个活跃客户账户以及全球超过 1200 万名开发者，帮助他们为客户构建独特、个性化的体验。Twilio 的 Commerce Platform 业务部门负责购物、计量和评级领域，每月在 2 亿个价格点上处理数百亿次使用事件。该平台支持 Twilio 的 Opportunity-to-Revenue (OTR) 计划，这是一项全公司范围的计划，旨在实现从客户接入到开票的整个计费生命周期的现代化。

传统计费系统面临的挑战

Twilio 将其计费系统构建在 Amazon Aurora MySQL 上，该系统可靠地支撑着 70 个分区数据库实例，并将消息、语音、电子邮件和视频领域的数十亿个事件转换为发票。随着 Twilio 业务的增长和数据量的显著扩大，团队意识到有机会演进架构以满足新的需求。

以下是传统平台面临的主要挑战：

  • 处理速度变慢，积压有时需要数小时才能清除。
  • 运维脆弱，因为频繁出现 ETL 故障，导致工程师花在排查管道问题上的时间比交付新功能还多。
  • 基础设施成本较高，且与所交付的业务价值不成比例。它还缺乏灵活性，无法在没有人工干预的情况下顺利交付诸如对定价模型进行追溯性更改或复杂的组织生命周期等功能。

计费系统需要生成具有财务级一致性的发票行项目。不能出现重复收费或遗漏事件。现有系统无法在不重新架构的情况下支持新的定价模型，而且财务团队无法在不影响生产的情况下运行分析查询。

Twilio 需要一个分布式数据仓库架构，既能处理事务性计费完整性，又能提供分析灵活性。该架构必须在几分钟而非几小时内完成计费计算，并让财务和产品团队能够在不影响生产的情况下查询数据。

解决方案概述

Twilio 的 Commerce Platform 团队评估了多种方案，包括传统数据仓库、带查询引擎的数据湖，以及将运营系统与分析系统分离的拆分架构。传统数据仓库以牺牲实时数据一致性为代价来优化分析，而运营数据库处理事务性工作负载，但在大规模复杂分析查询方面表现不佳。

借助 Amazon Redshift，Twilio 弥合了这一差距，即使面对并发写入工作负载也能帮助查询返回一致的结果，同时仍保持较高的分析性能。促使 Twilio 采用 Amazon Redshift Serverless 的关键能力如下：

  • 无服务器运维 — Amazon Redshift Serverless 消除了预置、容量规划和故障转移管理。计算根据工作负载需求自动扩缩，无需人工干预即可优化成本。
  • 实时流式摄取 — 计费事件通过 Amazon MSK 持续流式传输。Amazon Redshift 流式摄取将近乎实时的事件数据直接交付到数据仓库，无需中间着陆区。
  • 事务完整性 — 使用 可串行化隔离与 Amazon Redshift 结合，帮助在并发工作负载下提供一致的查询结果，从而防止需要自定义核对逻辑的数据异常。
  • 物化视图 AUTO 刷新 — 物化视图（MV）通过 AUTO 刷新，按客户、产品和日期增量聚合计费事件，无需批处理即可向上下游工作组提供近乎实时的评级数据。
  • Zero-ETL 集成 — 启用Amazon Aurora 与 Amazon Redshift 的 zero-ETL 集成并开启历史模式后，可自动将完整的变更历史从 Amazon Aurora MySQL 数据库复制到 Amazon Redshift，无需自定义变更数据捕获 (CDC) 管道。
  • 分布式数据仓库 — 借助 Amazon Redshift 数据共享，多个工作组可跨工作负载安全地共享数据。这通过在独立的消费者工作组上运行分析查询而不会拖慢发票处理，实现了工作负载隔离，并提供按工作负载的成本可见性。
  • 与现有数据湖集成 — Amazon Redshift 卸载到 Amazon Simple Storage Service (Amazon S3)以及直接写入 Amazon S3 Iceberg 表并通过AWS Glue Data Catalog建立索引，消除了用于数据湖交付的 Spark ETL 作业，使更广泛的组织能够访问数据。
  • 使用 dbt 进行转换编排 — dbt（数据构建工具）用于编排 Amazon Redshift MV 刷新和存储过程执行，管理覆盖超过 2 亿个价格点的依赖关系图，并具备自动生成的文档和完整的计算血缘。Amazon Redshift 与 dbt Core 的完全 SQL 兼容性使他们能够将计量、评级和记账逻辑定义为可复现的 SQL 有向无环图 (DAG)。

该架构的关键实施步骤如下：

1. 摄取层

Twilio 的计费事件来自消息、语音、电子邮件和视频领域的产品团队。来自这些源系统的数据通过以下摄取管道摄取到计费系统中：

流式摄取

每个产品都会向其 Amazon MSK Serverless 集群内的 Amazon MSK 主题发出用量事件。来自这些主题的计费事件通过流式摄取流入 Amazon Redshift。Amazon Redshift 物化视图的 AUTO 刷新选项可在事件到达时提供实时聚合，按客户、产品和日期进行增量聚合，从而每天处理数十亿个事件。

可序列化事务隔离与物化视图中的去重逻辑相结合，使每个事件都恰好被计数一次。

Zero-ETL 集成

Twilio 的产品目录和定价配置数据分布在多个 Amazon Aurora MySQL 集群中。此旧系统包含客户账户数据、定价配置和历史计费记录，新引擎必须能够访问这些数据以进行对账。旧系统在处理时使用当时现行的配置为所有内容定价，这对于前瞻性计费效果很好。然而，团队需要灵活性，以便为更正、促销调整和合同变更而对历史用量重新定价。

使用带历史模式的 Zero-ETL 将 Amazon Aurora 数据库与 Amazon Redshift 集成，每次价格更新和配置变更都会被自动捕获并带有时间戳。因此，团队可以重建启用历史模式后任意时间点的任何账单。他们还可以使用本应适用的确切配置对历史用量重新定价，或者模拟不同场景下发票会是什么样子。

此外，Zero-ETL 通过 CDC 将数据从旧版 MySQL 计费分片复制到 Amazon Redshift Serverless，从而消除了自定义提取管道。这实现了：

  1. 新引擎与旧系统之间的用量和定价比较，这是 萨班斯-奥克斯利（SOX）合规 所要求的。
  2. 并行运行期间的计费准确性验证。
  3. 跨所有分片的统一查询层，无需管理分片感知查询。

用于从 Amazon S3 加载的 COPY 命令

最终确定的发票数据从发票平台 Zuora 导出，以 Apache Parquet 格式写入 Amazon S3，提供已完成的发票行项目、客户费用和计费摘要，这些内容需要可供客户自助服务和控制台体验使用。Amazon S3 中的此发票数据使用 从 Amazon S3 上的 Parquet 执行 COPY 加载到 Amazon Redshift 表中。

2. 转换层

计费转换逻辑运行在开源 dbt Core 上，由 SQL DAG 定义以下转换管道：

计量

计量使用事务标识符对原始计费事件进行去重，然后按客户、产品和时间段聚合事件。它还处理迟到事件和事件更正等边缘情况。dbt Core 编排摄取，而自动维护的增量刷新物化视图聚合计费事件。

定价

定价将定价规则应用于计量聚合结果。它管理超过 2 亿个价格点，涵盖多层级数量折扣、按特定顺序叠加的促销折扣、多产品捆绑以及拆分税款。每条定价规则都是一个离散的 SQL 模型，dbt 编排它们之间的依赖图。

记账

dbt Core 编排 SQL 转换 DAG，生成格式化为发票平台发票行项目的定价聚合产物。Bookkeeper 系统还会从定价系统的数据共享创建只读 Iceberg 表，用于数据湖交付。dbt 通过 Amazon S3 以 Parquet 格式清理和转换从发票平台返回的发票数据，然后将其写入 Amazon DynamoDB，用于客户控制台体验。

3. 存储层

计费引擎使用多个具有 AI 驱动扩缩容的 Amazon Redshift Serverless 工作组，基准主要为 128 个 Redshift 处理单元（RPU），重负载时最多可达 1,024 个。Amazon Redshift 数据共享无需 ETL 或数据副本即可在工作组之间分发定价数据，并实时提供给所有使用方。

作为计费管道的一部分，三个 Amazon Redshift Serverless 工作组服务于不同的工作负载：

计量工作组

该 Amazon Redshift Serverless 工作组托管自动刷新的物化视图，用于对计费事件去重和聚合，并存储超过 5000 亿个事件供即时查询。它将精选的财务数据集直接以 Iceberg 表形式写入 Amazon S3，并通过 AWS Glue Data Catalog 建立索引。

定价工作组

该 Amazon Redshift Serverless 工作组处理来自聚合 Zero-ETL 源的定价配置信息。然后它将定价应用于用量聚合结果，以创建定价用量的中央记录系统。这些核心数据集随后与 Bookkeeper 共享，用于特定用例的交付。

Bookkeeper 工作组（发票生成）

用于发票生成的 Amazon Redshift Serverless 工作组通过数据共享从定价工作组接收定价数据。此工作组的数据共享还用于为 Customer Usage API 工作组提供数据。它还存储格式化为发票平台发票行项目的定价聚合产物。它处理发票平台返回到 Amazon S3 的数据，并写入 Amazon DynamoDB 以支持客户控制台体验。

此外，以下 Amazon Redshift Serverless 工作组通过其公共 API 为 Twilio 的最终客户提供服务：

Customer Usage API 工作组

这个专用的 Amazon Redshift Serverless 工作组通过存储过程从源系统接收评级用量数据和产品目录配置，并通过来自记账员工作组的数据共享接收计量聚合数据。它为面向客户的用量 API 提供近实时的计费查询，同时不影响计费管道的计算资源。

4. 消费层

处理后的计费数据服务于五个下游消费者：

  1. 开票平台 — Bookkeeper 工作组将定价后的聚合数据作为发票行项目交付，用于客户计费。
  2. Twilio 公共 API — Customer Usage API 工作组为客户的近实时计费查询提供支持，其后端由来自 Metering 工作组的实时数据共享提供支撑。
  3. One Admin — 内部计费运营仪表板直接由 Amazon Redshift 提供，响应时间为亚分钟级。
  4. One Console — 客户自助服务体验（例如余额查询、CSV 发票下载等）由 Amazon DynamoDB 提供。Bookkeeper 工作组将开票平台返回的最终发票数据加载到 DynamoDB，以便为最终用户提供低延迟的 API 服务。
  5. 产品团队 — Amazon Athena 通过 AWS Glue Data Catalog 查询 Iceberg 表上的精选财务数据集，在不直接访问 Amazon Redshift 的情况下，为更广泛的组织提供访问权限。

成果

Twilio 现代化后的计费引擎将基础设施成本降低了 70%，同时将计费重新计算速度提升了 12 倍，并且每月处理数十亿个事件。Twilio 于 2026 年中期在生产环境中上线了新的计费系统，通过 Zuora 为真实客户发票提供评级用量。这个基于 Amazon Redshift Serverless 实现现代化的新引擎在各个方面都带来了可衡量的改进，包括：

  1. 基础设施成本降低 70% — 计费系统的持续成本下降了 70%，同时系统扩展至可存储近两万亿个事件，而这是传统架构所无法容纳的。
  2. 计费重新计算速度提升 12 倍 — 整月重新计算从超过 6 小时降至 30 分钟，同时还支持了此前不切实际的追溯定价变更和场景建模。
  3. 处理时间减少超过 80% — 整个管道实现了 80-85% 的运营效率提升，团队也满足了业务服务水平协议（SLA）。
  4. 亚分钟级财务报告 — 财务仪表板从每日批量刷新转变为亚分钟级响应时间，为计费数据提供了近实时可见性。
  5. 完整的定价灵活性 — 评级引擎现在管理 Twilio 包含 2 亿个价格点的完整目录（此前仅支持受限子集），且没有重复扣费或遗漏事件。
  6. 更精简的运营 — 此前需要庞大运营团队管理的工作，现在由一个小团队即可完成。

最重要的是，工程师们从四处救火处理管道故障转向构建新的产品能力，这是由无服务器架构的可靠性和简洁性所驱动的文化转变。

结论

在本博文中，我们展示了 Twilio 如何通过采用 Amazon Redshift Serverless 作为大规模金融级实时计费系统的基础，对其传统计费系统进行现代化改造。

现代化架构由使用 Amazon MSK 的流式摄取以及来自 Amazon Aurora MySQL 的 Amazon Redshift Zero-ETL 驱动。借助 直接写入 Amazon S3 Iceberg 表（通过 AWS Glue Data Catalog 编目）以及 dbt 驱动的转换，Twilio 构建了一个可随业务扩展的计费引擎。新解决方案帮助工程团队将重点放在计费产品创新而非基础设施运维上。要了解更多关于 Amazon Redshift 如何帮助 Twilio 重新设计其计费引擎的信息，请观看他们在 AWS re:Invent 2025 上的演讲，他们在那里与 Amazon Redshift 和 Amazon Athena 服务团队共同做了分享。

要了解更多用于在 AWS 上构建现代数据解决方案的 AWS 服务，请参阅 AWS 公开文档，并通过 AWS 大数据博客 保持关注。
