Epic Games如何调优OpenSearch支撑Fortnite分析

Epic Games与AWS合作，对其Amazon OpenSearch Service集群进行优化，用于Fortnite游戏遥测数据的存储与分析。团队通过调整实例规格、重新平衡分片、优化索引映射以及升级引擎和Graviton版本，在降低运营成本的同时显著提升了查询延迟和吞吐量。该实践支撑了数十亿级遥测事件的处理，帮助Epic识别玩法趋势并辅助实时运营决策。
推荐理由聚焦游戏数据分析场景下的OpenSearch调优实践，涉及大规模遥测处理、查询性能与成本优化，对数据平台从业者有直接参考价值。

自 2017 年 Fortnite 上线以来，Epic Games 已覆盖全球数亿玩家。Fortnite 运行在 Amazon Web Services（AWS）上，并利用 Amazon OpenSearch Service 等服务支撑部分内部分析工作，在大规模场景下辅助决策。Amazon OpenSearch Service 在理解游戏生态系统方面发挥了重要作用。

OpenSearch Service 支撑两类用例：搜索工作负载与分析工作负载。Epic Games 的一个团队有一个用例，需要存储并分析滑动窗口内的游戏事件数据。这涉及支持复杂查询和多层聚合，并将分析结果馈入其他内部系统，从而帮助驱动不断演进的玩家体验。在 Fortnite 这样拥有庞大玩家基础的游戏规模下，这些查询需要处理海量的传入数据。

这些洞察有助于识别新兴的游戏玩法趋势，理解玩家如何与新内容互动，并揭示更多关于 Fortnite 生态系统的信息。它们为实时运营决策提供依据，并基于社区整体聚合行为，向玩家呈现相关内容。

随着 Epic Games 的基础设施处理数十亿级别的遥测事件，该团队发现了优化其 OpenSearch Service 集群以提升性能和成本效率的机会。本文介绍了 Epic Games 如何与 AWS 合作，对其 OpenSearch Service 部署进行改造，在显著改善查询延迟和资源利用率的同时降低了运营成本。

挑战

Epic Games 运行着一个 OpenSearch Service 域，需要处理持续的高容量写入，以及 CPU 密集型的批量聚合作业。理想情况下，这些聚合作业应该更频繁地运行，以保持分析结果的新鲜度。更短的作业间隔意味着更新的数据，从而能更快地识别游戏玩法趋势、检测异常，并为实时运营决策提供信息。但现有的配置无法在不将域扩展到超出工作负载合理需求的情况下支持这一点，否则会推高成本。

Epic Games 与 AWS 合作，确定了可以改进的方面，重点关注硬件利用率、分片策略、索引映射和查询行为等领域。

观测结果

该集群运行在 r7g 内存优化型数据节点上，每个节点拥有 48 个 vCPU 和 384 GiB 内存。在每台节点的可用内存中，只有一小部分（32 GiB）分配给了 Java 虚拟机（JVM）堆，该值设置为压缩普通对象指针（compressed oops）所支持的最大推荐值。其余内存（堆外内存）用于文件系统缓存和操作系统。各数据节点的系统内存并未得到充分利用（图 1）。

该集群的数据节点分布在多个可用区（Availability Zones）。每个索引使用固定数量的主分片并配置副本，分片达到一定大小后执行滚动（rollover）。乍看之下，该配置似乎相当均衡：分片副本分布在各个可用区，每个节点持有可控份额的数据。

然而，主分片数量低于数据节点总数。这意味着，针对最新数据的搜索——这是最常见的访问模式——只会在一部分可用节点上执行。结果，部分节点持续出现 CPU 热点，而其余节点处于低利用率状态（图 5）。

建议与实施

基于上述观察，AWS 与 Epic Games 合作实施了一系列针对性优化，涵盖硬件选型、分片策略、索引映射和查询行为。以下各节详细说明每项建议及其落地方式。

合理调整集群规格

由于聚合查询天然属于 CPU 密集型，且集群的 JVM 内存压力远在可接受范围内，AWS 建议从内存优化型 r7g 实例迁移至计算优化型 c7g 实例。c7g 系列提供更高的 vCPU 与内存配比，更适合处理能力而非内存容量构成瓶颈的工作负载。

所提议的架构要求使用比现有 r7g 数量更多的 c7g 节点。这一迁移使集群总 CPU 容量提升约 33%，同时内存仅为原来的三分之二。净效果是成本显著降低约 10%——通过让实例配置与实际工作负载特性对齐，以更低成本获得更强的处理能力（表 1）。

表 1：实例迁移对比，r7g 与 c7g

| 项目 | r7g（迁移前） | c7g（迁移后） | 净影响 |

|------|--------------|--------------|--------|

| 实例家族 | 内存优化 | 计算优化 | CPU 与内存配比更适合聚合工作负载 |

| 每节点 vCPU | 相同 | 相同 | 每节点 CPU 相同；节点更多 = 总 CPU 更高 |

| 每节点内存 | 更高 | 更低 | 减少未使用的内存；JVM 堆保持不变 |

| 总 CPU | 基线 | 总 vCPU 增加 33% | 在更多节点上分布更均匀 |

| 成本 | 基线 | 降低约 10% | 每美元获得更高性能 |

分片策略

为配合新的集群规格，Epic Games 团队更改了分片策略，使主分片数量与数据节点数量保持一致，并配置 1 个副本。这样可将写入密集负载和批量聚合搜索查询负载均匀分布到所有可用数据节点上。

分片优化

团队采用 ISM（索引状态管理）策略，通过滚动（rollover）机制管理分片大小，利用 `min_primary_shard_size` 将分片大小控制在建议范围内。这使分片数量保持有界且可预测，并提供了一条清晰的扩展模式：先调整节点数量，再相应更新 ISM 策略。实施后，节点级 CPU 利用率呈现出更加均匀的分布（图 6）。

图 6：分片优化后的节点级 CPU 利用率

如图 6 所示，域内所有节点的 CPU 利用率水平相近，证实数据和流量在集群中分布良好，不存在节点热点。

映射优化

索引映射中许多字段同时启用了 text 和 keyword 字段类型，尽管访问模式显示这些字段仅用于聚合、排序或过滤场景，从未用于全文匹配查询。移除冗余的 text 字段类型降低了存储开销，并通过消除索引时不必要的分析（analysis）提升了查询性能。

对于高基数字符串字段，murmur3 字段类型为基数聚合提供了一种“计算一次并存储”的优化：murmur3 不是在查询时对 keyword 值进行哈希，而是在索引时计算一次哈希并将其存储为数值型 doc_value，从而让聚合跳过查询时昂贵的字符串哈希步骤（基数估算本身仍在查询时计算）。以下示例说明了映射变更：

索引优化

还应用了额外的索引级优化来提升查询性能并减少开销。索引排序被配置为默认使用主日期字段，通过将物理数据布局与最常见的查询顺序对齐，改善了基于时间的访问模式的性能。ISM 策略被更新为在滚动后将索引强制合并（force merge）为 1 个段，减少了只读索引上的段开销。最后，调整了刷新间隔（refresh interval），以在索引吞吐量与搜索新鲜度之间取得平衡。

从 OpenSearch Service 2.17 升级到 3.1

该域从 OpenSearch Service 2.17 升级到 3.1，降低了错误计数并提升了 Amazon OpenSearch Ingestion 管道层面的吞吐量。性能提升显著：仅升级后，sum 聚合的 p99 延迟就下降了 40%–50%，大型 96 小时基数聚合的 p95 下降了超过 40%。所有查询类型的总体查询性能均有所提升，线程池压力显著降低，429 错误大幅减少（图 7）。

图 7：OpenSearch Service 3.1 升级前后的查询性能

从 Graviton 3 升级到 Graviton 4

实例类型从 c7g（Graviton 3）升级到 c8g（Graviton 4）。

性能提升立竿见影：所有查询的 p99 从 380 ms 降至 250 ms；所有查询的 p95 从 245 ms 降至 230 ms；所有查询的 p90 从 225 ms 降至 200 ms；所有查询的 p50 从 100 ms 降至 70 ms。日期窗口基数查询的 p99 从 220 ms 减半至 98 ms，基于 sum 的聚合也获得了类似的提升。整体吞吐量提升了 16%。

分层缓存（Tiered caching）

升级到 OpenSearch Service 3.1 后，团队启用了分层缓存。分层缓存用基于磁盘的层级扩展了默认的堆内请求缓存。当条目从堆内缓存中逐出时，它们会溢出到节点本地 SSD 上更大的磁盘缓存中，而不是被丢弃。这使集群能够在不增加 JVM 堆使用量的情况下，为更大量的查询保留缓存结果。

Epic Games 工作负载中的批量聚合任务会在重叠的时间窗口上重复发出查询。仅靠堆内缓存太小，无法在连续的任务运行之间保留结果，因此昂贵的聚合每次都要重新计算。启用磁盘层级后，较长时间窗口聚合（例如 96 小时基数查询）的结果可以在两次运行之间保留。这使得一些较大的聚合查询（尤其是那些跨越较长时间窗口的查询）获得了更一致、更快速的结果。

结论

通过对 OpenSearch Service 部署进行优化，Epic Games 的一个团队将 p99 查询延迟从 380 ms 降至 250 ms，吞吐量提升了 16%，成本降低了 10%。这些收益来自使实例类型、分片策略、映射和引擎版本与实际工作负载需求保持一致。
