dbt State如何削减仓库计算成本并加速每次运行

DataHot 主播约 1 分钟精华朗读
0:00 / 0:59
DataHot 速览

dbt Labs 发布 dbt State，将原本无状态的 dbt 转为有状态：每次运行只构建有变更的部分，跳过未变更的模型。dbt 每天执行约159,000个作业，其中大量按小时运行，即使数据未变也重复计算。客户 Fanatics 通过该功能将模型复用率提升到25%，并有望节省30%的仓库计算开支。这减少了开发时等待100-200个模型构建的10-20分钟时间，也降低了维护20多个选择器的复杂度。

为什么值得关注：数据从业者应关注，因为 dbt State 通过增量构建解决大规模数据管道重复计算的成本与效率问题，是数据平台工程中成本治理的关键实践。

译文

AI 逐段翻译

每天我们大约看到 159,000 个 dbt 作业运行。其中大多数每小时运行一次。而且即使数据没有变化，大多数也每小时运行，因此成千上万个模型被重建以产生相同的结果。

长期以来，这是有道理的。云计算的单位成本不断下降，只需使用更多即可。

然后每个人都开始使用更多数据：更多仪表板，以及为机器学习模型和推荐引擎提供支持的更多管道。一旦代理出现，任何人都可以编写复杂的 SQL 查询，甚至创建 dbt 模型。

最初是运行管道的合理方式，现在变得昂贵。那些廉价的云成本开始飙升。

dbt State是我们的答案。它将原本无状态的引擎 dbt 变为有状态的：每次你运行 dbt run 或 dbt build，它只构建有变化的内容，并跳过所有未变化的内容。

我们反复提到的口号很简单：构建有变化的，跳过未变化的。下面是它的工作原理，以及我们的一位客户如何使用 dbt State 将模型重用率提高到 25%。

为什么我们构建 dbt State

对于我们所有的数据人员来说，这从来不仅仅是计算。在数据仓库账单上节省 30% 很棒，我们不会拒绝。但你每天感受到的是保持项目运行所需的时间、专注和信任。

想想摩擦：

  • 每次你开发一个新模型，你都必须问它属于哪些选择器。在 10,000 个模型中管理 20 个不同的选择器本身就成了一个问题。
  • 每次你在开发中运行，你都要等待 100 或 200 个模型构建，10 或 20 分钟，只是为了弄清楚你是否构建了正确的东西。这会消耗专注力。
  • 随着成本攀升而业务没有看到更多价值，因为数据没有更频繁地刷新，人们开始质疑这是否值得。

dbt State 始于我们上次的 dbt Summit，我们在那里将 状态感知编排 (SAO) 发布为预览版。反馈很明确。客户在数据仓库账单上节省了 30% 以上。

他们带回了两个问题。首先，为什么这只在生产环境中，而我想在暂存、持续集成 (CI)或开发中使用它来加快我的运行速度？其次，为什么只在 dbt 平台上的 dbt Fusion 引擎上可用，而我却想在任何地方运行它？

我们倾听了意见。我们吸取了 SAO 的最佳部分，并使其在任何地方都能工作。结果就是 dbt State。

dbt State 做什么

基本思想与 SAO 相同：构建有变化的，跳过任何未变化的。这解锁了三件事。

  • 优化成本。 团队通过仅构建上游有变化的内容并遵守您设置的 freshness 服务级别协议 (SLA)，平均减少 30% 的仓库计算，因此业务不会为比其使用频率更高的新鲜数据付费。
  • 自由运行。 当你启动 dbt run 或 dbt build 时，你可以确信你不会在只有 10 个模型发生变化时构建 100 个模型。你会构建 10 个。
  • 加速开发。 你可以在不采用诸如采样或在开发和生产中使用不同数据等自定义变通方法的情况下，提高每次运行的速度。你打开 dbt State，它就能正常工作。

在你运行 dbt 的任何地方运行它

dbt State 在 dbt 平台中原生可用，并在 dbt Core v2.0 中本地可用。如果你在 v2.0 上，你可以运行 dbt login 并立即设置 dbt State。

如果你在 v1，从 v1.7 到 v1.12，它可以作为插件使用：运行 pip install dbt-state 你可以在不到五分钟内跨开发和生产启动并运行。不需要平台升级。

任何地方确实意味着 任何地方。在诸如 Dagster 或 Airflow 这样的编排器中运行 dbt。将其添加到你在 EC2 上的 Python 环境中自己计划的设置中。如果你能运行 dbt，你就能运行 dbt State。

最后一点是最重要的。SAO 和 dbt State 建立在相同的前提上：在上游数据或代码未变化时跳过构建。

我们通过 dbt State 添加的是覆盖范围：不再需要 Fusion，不再局限于生产环境，以及一种重用已构建数据的方法，而不是付费重建。当相同的逻辑和数据已经存在于其他位置，例如暂存或生产环境中时，dbt State 会克隆它们而不是重建，你甚至不会注意到差异。

dbt State 如何工作

帮助区分两件事：数据平面，你在其中运行 dbt，和 控制平面，dbt State 在其中运行。

在数据平面中，每次 dbt run 针对你的仓库执行，在那里它可以访问你的数据并构建你的模型。控制平面是 dbt State 决定实际需要构建什么的地方。它保留你的表列表以及最后数据状态和代码状态的哈希。那里没有实际数据，只有状态的哈希。

所以每次运行时，dbt State 对每个模型都会询问一系列简短的问题。它是否实际发生了变化？如果是，是否已有某个版本存在于其他位置可以克隆？只有当两个问题的答案都是否时，我们才构建它。

有关 dbt State 实际运行的演示，请查看此按需网络研讨会。

只为重复使用付费

这一切从每个用户的 30 天试用开始。运行 pip install，在开发中尝试，在生产中运行，并告诉我们你的发现。

当你开始付费时，我们只想为产生价值的部分收费。我们的指标是每日活跃目标表 (DATT)：一个被 dbt State 重用的模型或测试。我们计算每天的独特重用次数，因此不会重复收费。

如果你的 fact_orders 和 dim_customers 模型每天重建六次但数据没有变化，你不会为每个模型支付六次重用费用。你只需支付两个，每个独特表一个，无论当天重用了多少次。

Fanatics Betting and Gaming 如何将 dbt State 投入使用

最早启用 dbt State 的团队之一是Fanatics Betting and Gaming，他们尝试的第一个项目就节省了两位数的计算成本。

Fanatics 的高级分析工程师 Alvin Chai 负责一个团队，负责构建和维护博彩和游戏业务中的黄金层数据模型，涵盖从体育博彩交易分析、产品洞察到监管和财务报告的所有内容。他们的技术栈是Snowflake作为数据仓库，dbt Core 和 Airflow 用于编排。

大约 18 个月前，他们迁移到 dbt 平台以消除瓶颈：刷新和回填过去需要特定的数据工程师来启动。如今他们运行约 11 个项目，每个分析域一个，其中 8 个在 Fusion 上，总共约数千个模型。

调度民主化让每个分析团队都能自由安排自己的刷新。Alvin 说，缺点是过度调度且可见性低：

"也许有一个分析团队将其模型设置为每 30 分钟运行一次，但构建该模型的源可能每小时才运行一次。"

dbt State 揭示了他们的模型重用率，并有效地为过度调度设置了护栏，仅在模型真正需要时才刷新，而不是一遍又一遍地重建相同的输出。这使得整个过程更加无需人工干预，团队不再需要因为成本过高而打扰其他分析域。

这一推广过程是获取 dbt State 价值的有用教训。Fanatics 从风险较低的工作开始。他们的试点是一个支持负责任博彩和反洗钱用例的治理项目，选择它是因为它通过dbt Mesh的下游依赖很少，并且易于回滚。然后他们按风险等级向下迁移，除了最关键的管理和财务报告之外，所有内容都迁移了。

在没有配置的情况下启用 dbt State，他们的模型重用率约为 0.2%，基本上为零。在配置了源新鲜度并声明了模型级 SLA（我们现在称之为滞后容忍度）之后，效果才显现出来。

他们的方法是根据每个模型当前的刷新频率为每个模型设置一个基线模型级 SLA，并在此基础上添加一个更积极的项目级 SLA，然后编写一个小脚本将其现有的调度标签转换为这些 SLA。例如，标记为"每日"的模型变成了 24 小时的刷新窗口。

这将试点项目的模型重用率从 0.2% 提高到大约 15%。从历史上看，过度调度的项目后来达到了高达 25% 的重用率。其他项目则接近 5%。在所有作业中，平均约为 8%。

计算成本的节省是实实在在的，但 Alvin 认为最大的长期收益是操作简单：

"问题从'这个模型应该属于哪个作业？'变成了'这个模型实际上需要多新鲜？'"

Fanatics 不再需要按节奏管理单独的作业和标签，而是可以转向基于 DAG 的作业：指向一个最终的消费模型，刷新它上游的所有内容，并让模型级 SLA 处理底层的不同新鲜度要求。

回报是团队时间的分配。他们不再需要绞尽脑汁考虑如何优化调度，而是可以专注于构建新模型，提供更多洞察和商业价值。

自己试试

dbt 的十年一直是将工程纪律带入分析领域。dbt State 将这种纪律扩展到计算本身：无论在哪里运行 dbt，都不要为重建未更改的内容付费。

你不必只听我们的一面之词。创建一个免费的 dbt 账户或运行 pip install dbt-state在您现有的项目上，您会发现开发运行速度加快，仓库账单减少。要查看 dbt State 的实际应用，请观看点播网络研讨会。
