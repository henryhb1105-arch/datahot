原文

Streaming tables and materialized views, read in place as Iceberg: the settings that matter, what the logs show, and the Snowflake errors I hit

Most guides to reading Databricks from Snowflake start with a plain Delta table. Mine are different: every table here is built by Lakeflow Declarative Pipelines (formerly Delta Live Tables), so they are streaming tables and materialized views, which an outside engine cannot read out of the box.

I got Snowflake to read all 13 of them in place, as Apache Iceberg, with no copy: three layers on AWS, each in its own Unity Catalog catalog. I tried two Snowflake features on them: Iceberg tables over Unity Catalog’s REST endpoint, and a catalog-linked database. This article covers how each works on Lakeflow tables, the Snowflake checks that confirm it, and the four Snowflake errors that cost me time.

In short: Lakeflow tables need one opt-in (pipelines.externalMetadata.enabled) to be readable from Snowflake; with it, both Iceberg tables over the REST endpoint (raw, curated) and a catalog-linked database (gold) read all 13 in place.

Disclaimer: This is my own work, not affiliated with or endorsed by Snowflake, Databricks or AWS. Parts were established by trial and error in one environment, so verify against the official documentation.

Why Lakeflow tables are different

A Lakeflow pipeline publishes streaming tables (incremental) and materialized views (recomputed queries). Both are Unity Catalog managed tables, but neither is a plain Delta table you can point another engine at. Three things follow, and they shaped everything below.

  1. They need an opt-in. Per Databricks’ documentation, they appear externally “as managed tables” with the same name, but only with pipelines.externalMetadata.enabled = 'true', UniForm for Iceberg and Iceberg v3 (Databricks Runtime 17.3 or later). Skip the property and Snowflake rejects the views (Error 2).
  2. The pipeline owns them. Its run-as identity owns every table, so everyone else, including Snowflake’s service principal, gets in through grants. By default only that identity can query the pipeline’s event log, which turns out to be the best change signal you can have.
  3. A full refresh can rebuild them, changing a table’s Iceberg identity (it did for all ten streaming tables I sync), which a Snowflake table object notices the hard way (Error 3).

The opt-in is a handful of table properties. This is a gold materialized view, with the lines that make it readable from Snowflake:

CREATE OR REFRESH MATERIALIZED VIEW
  driver_performance_summary
TBLPROPERTIES (
  'pipelines.externalMetadata.enabled' = 'true',
  'delta.columnMapping.mode' = 'name',
  'delta.enableRowTracking' = 'true',
  'delta.enableIcebergCompatV3' = 'true',
  'delta.universalFormat.enabledFormats' = 'iceberg'
)
WITH drivers_current AS ( ... )
-- the aggregation query follows, unchanged

Streaming tables carry the same properties through table_properties= in Python (plus enableDeletionVectors and enableIcebergCompatV2 = false, which come from a comment in my own code about Iceberg v3; I did not find them in the documentation). The capability is Public Preview per Databricks' June 2026 release notes.

Every table I checked through Unity Catalog’s Iceberg REST endpoint (the three views and two streaming tables) reports Iceberg format-version 3, so your Snowflake account must read v3. Snowflake documents v3 support, including for externally managed tables, but states no preview or GA status.

Three ways Snowflake can read Unity Catalog data

Databricks’ overview of external access lists the paths. Three let Snowflake read in place.

1. Iceberg tables over Unity Catalog’s REST endpoint. Snowflake gets table metadata and short-lived credentials from Unity Catalog and reads the S3 files. You create one Snowflake Iceberg table per Databricks table. It is read-only, and each table must be refreshed explicitly: the Databricks blog says automatic and manual refresh are incompatible. I use this for raw and curated.

2. A catalog-linked database. Same endpoint and credentials, but Snowflake discovers schemas and tables itself and re-syncs on a timer. You can allow or block whole namespaces (schemas), per the CREATE DATABASE reference, but not individual tables. It has been generally available since 17 October 2025. It is writable by default, and “Snowflake propagates table drops to the remote catalog, which removes the table and data from both systems.” I use this for gold, read-only.

3. Delta Sharing with the Iceberg REST option. The provider issues a credential file. It suits sharing with another organization, so I skipped it.

What I built

A Databricks notebook pulls race results from f1api.dev into a Unity Catalog volume, and three Lakeflow pipelines build driver, team and circuit summaries. Volumes are tiny, so I make no performance claims. Code: databricks-snowflake-iceberg-federation.

Each layer is its own catalog on the same S3 bucket:

  • f1_raw: 7 streaming tables, loaded by Auto Loader. Six are exposed as Iceberg tables; the quarantine table race_raw_quarantined is deliberately not.
  • f1_curated: 4 streaming tables (3 SCD Type 2 dimensions built with AUTO CDC, 1 fact), exposed as Iceberg tables.
  • f1_analytics: 3 materialized views, exposed through the linked database F1_ANALYTICS_LINKED.

That is 13 of 14 tables: 10 as individual Iceberg tables, 3 through the linked database.

Lakeflow pipelines
        | write
        v
S3 (Delta files + Iceberg metadata)
        ^
        | read with short-lived credentials
        |
Snowflake --catalog integration (OAuth)--> Unity Catalog
  ICEBERG TABLEs (raw, curated)            REST endpoint
  linked database (gold)                   (vends credentials)

Why a hybrid. I first built everything as individual tables. Per-layer catalogs made a split practical: an integration names one catalog, so Snowflake sees a whole layer.

  • Gold uses the linked database. Its catalog holds one schema with only the three views meant to be shared, so ALLOWED_NAMESPACES = ('analytics') is enough, Snowflake keeps it fresh, and the job needs no gold sync task.
  • Raw uses individual tables. The quarantine table shares a schema with shared tables and must stay out. A linked database filters by namespace, and neither the CREATE DATABASE nor the ALTER DATABASE reference offers a table-level list. A JSON list shares a table only when it is listed.
  • Curated uses individual tables too, but not for a technical reason. Nothing in it needs hiding, so a linked database would have worked; I kept the existing sync to keep the change small.

Choosing what to expose is not a security boundary: the service principal’s grants cover each entire catalog.

Step 1: Databricks-side prerequisites

Besides the table properties above, two things decide whether Snowflake can read anything.

A service principal. Snowflake authenticates to Unity Catalog as a service principal using OAuth. Reading through the REST endpoint needs EXTERNAL USE SCHEMA, and the pipelines page adds SELECT. I grant those plus USE CATALOG and USE SCHEMA at catalog level on all three catalogs. The same principal runs the Databricks job, so it holds more.

External data access on the metastore. Databricks says it must be enabled on the metastore as well as granting EXTERNAL USE SCHEMA. It is metastore-wide, so I kept it outside Terraform:

databricks metastores update <metastore-id> \
  --external-access-enabled=true \
  --profile <profile>

Without it you get Snowflake error 004174 (Error 1).

Step 2: One catalog integration per catalog

An integration defines how Snowflake reaches a catalog and which identity it uses. The statement follows Snowflake’s guide for Unity Catalog; VENDED_CREDENTIALS turns on credential vending:

CREATE CATALOG INTEGRATION IF NOT EXISTS
  uc_f1_analytics_iceberg
  CATALOG_SOURCE = ICEBERG_REST
  TABLE_FORMAT = ICEBERG
  REST_CONFIG = (
    CATALOG_URI =
      'https://<host>/api/2.1/unity-catalog/iceberg-rest'
    CATALOG_NAME = 'f1_analytics'
    ACCESS_DELEGATION_MODE = VENDED_CREDENTIALS
  )
  REST_AUTHENTICATION = (
    TYPE = OAUTH
    OAUTH_TOKEN_URI = 'https://<host>/oidc/v1/token'
    OAUTH_CLIENT_ID = '<client-id>'
    OAUTH_CLIENT_SECRET = '<client-secret>'
    OAUTH_ALLOWED_SCOPES = ('all-apis')
  )
  ENABLED = TRUE;

CATALOG_NAME is the Databricks catalog, and I set no default namespace, so each table supplies its own. Because an integration names one catalog, I run this three times (uc_f1_raw_iceberg, uc_f1_curated_iceberg, uc_f1_analytics_iceberg), deriving the name from the catalog name. Then I verify each with SYSTEM$VERIFY_CATALOG_INTEGRATION, which returns success: true when it works:

SELECT SYSTEM$VERIFY_CATALOG_INTEGRATION(
  'uc_f1_analytics_iceberg');

I run this from a Databricks notebook that reads the credentials from a secret scope Terraform populates, so no secret is typed by hand. The notebook ends with GRANT USAGE ON INTEGRATION uc_f1_analytics_iceberg TO ROLE SYSADMIN; so SYSADMIN can create the linked database next.

Two notes. The notebook is not a job task, so on serverless compute install snowflake-connector-python yourself or its first cell fails with ModuleNotFoundError. And I use a notebook rather than Terraform because these are one-time bootstrap steps and my Snowflake Terraform provider (1.2.3) has no catalog-integration resource.

Step 3: Create the catalog-linked database for gold

USE ROLE SYSADMIN;
CREATE DATABASE IF NOT EXISTS F1_ANALYTICS_LINKED
  LINKED_CATALOG = (
    CATALOG = 'uc_f1_analytics_iceberg',
    ALLOWED_NAMESPACES = ('analytics'),
    ALLOWED_WRITE_OPERATIONS = NONE,
    SYNC_INTERVAL_SECONDS = 60
  );
  • CATALOG names the integration (URL, catalog name, credentials).
  • ALLOWED_NAMESPACES limits discovery to analytics. The REST endpoint also lists information_schema, whose objects are not Iceberg tables and cause sync errors (Snowflake's tutorial blocks it).
  • ALLOWED_WRITE_OPERATIONS = NONE makes it read-only. With the default ALL, dropping a table in Snowflake also removes it and its data from the remote catalog.
  • SYNC_INTERVAL_SECONDS is how often it checks for new or dropped tables (30 to 86400, default 30). Once a table is discovered, its contents auto-refresh on the integration's REFRESH_INTERVAL_SECONDS, 30 seconds by default.
  • There is no EXTERNAL_VOLUME: the reference says it can be omitted with vended credentials.

Why a human runs this as SYSADMIN. My first design granted the sync role CREATE DATABASE through Terraform so a notebook could create it, and terraform apply failed with error 003102 (Error 4). SYSADMIN already holds CREATE DATABASE, so I had it create the database once. The catch: SYSADMIN owns it, the sync role cannot see it, other consumers need grants, and Terraform does not track it.

Snowsight lists all three views under F1_ANALYTICS_LINKED.analytics and previews their rows (below), and Snowflake's own status functions agree. Pass the database name as a quoted argument:

SELECT SYSTEM$GET_CATALOG_LINKED_DATABASE_CONFIG(
  'F1_ANALYTICS_LINKED');
SELECT SYSTEM$CATALOG_LINK_STATUS(
  'F1_ANALYTICS_LINKED');

The first returns "allowed_write_operations": "NONE", "allowed_namespaces": ["analytics"] and "sync_interval_seconds": 60; the second returns "executionState": "RUNNING" with an empty failureDetails. Check read-only this way rather than with a test DROP, which would delete the view in Databricks if the setting were wrong.

Step 4: Raw and curated Iceberg tables, refreshed only when they change

A JSON file lists every raw and curated table to expose, and a notebook creates an Iceberg table per entry, so sharing another table is one more entry:

{
  "layers": {
    "raw": [
      {
        "source_table": "raw_race",
        "target_schema": "RAW",
        "target_table": "raw_race"
      }
    ]
  }
}

raw has 6 entries and curated 4. There is no analytics key (gold comes through the linked database) and no entry for race_raw_quarantined, which should not be externally readable. For each entry the notebook creates the table if it is missing, then refreshes it if the source changed:

CREATE ICEBERG TABLE "<DB>"."RAW"."raw_race"
  CATALOG = 'uc_f1_raw_iceberg'
  CATALOG_TABLE_NAME = 'raw_race'
  CATALOG_NAMESPACE = 'raw';

ALTER ICEBERG TABLE "<DB>"."RAW"."raw_race" REFRESH;

Per Snowflake’s CREATE ICEBERG TABLE reference, CATALOG_TABLE_NAME cannot change after creation, and referencing an integration needs USAGE, not ownership. I omit EXTERNAL_VOLUME (the REFRESH reference says it is not required with vended credentials). Only the table owner may refresh, and one role does both.

Let the pipeline’s event log decide. This is where Lakeflow pays off. The notebook makes one event_log() query per layer to see whether a table's latest update changed anything, and skips REFRESH if not. For streaming tables the row counts are incremental, so a positive sum means new data. For materialized views num_output_rows is always the full recomputed count, so the notebook reads the refresh technique instead (MAINTENANCE_TYPE_NO_OP means unchanged), a branch now unused since gold moved to the linked database. New tables are always refreshed once, and an inconclusive status refreshes rather than skips.

What the notebook printed across three real runs (database name masked, long lines wrapped):

# run 1: created, then refreshed
f1_raw.raw.raw_race: streaming table
  rows written/upserted/deleted = 1
Creating Iceberg table "<DB>"."RAW"."raw_race"
Refreshing Iceberg table "<DB>"."RAW"."raw_race"

# run 2, no new data: skipped
f1_raw.raw.raw_race: streaming table
  rows written/upserted/deleted = 0
Skipping refresh for "<DB>"."RAW"."raw_race"
  - source unchanged since last update

# run 3, next round loaded: refreshed, not re-created
f1_raw.raw.raw_race: streaming table
  rows written/upserted/deleted = 1
Refreshing Iceberg table "<DB>"."RAW"."raw_race"

All 10 tables followed this pattern. SHOW ICEBERG TABLES IN DATABASE UC_ICEBERG_SYNC; (the database Terraform creates for them) lists them.

Step 5: Run it as a job

One Databricks job runs the three pipelines in sequence. The raw and curated sync tasks start right after their layer’s pipeline and run in parallel with the next layer’s, so syncing raw never waits for curated. There is no gold sync task.

Errors I hit, and how I fixed them

Errors 1 to 3 happened in my first version, when all three layers were schemas in one catalog, so their logs say f1_analytics.raw... and similar. Long messages have line breaks added for readability.

Error 1: “Please ensure that the catalog vends credentials” (004174)

Failed to retrieve credentials from the Catalog …
Please ensure that the catalog vends credentials.

The metastore’s external_access_enabled was false; catalog-level grants are not sufficient without it. My first guesses, an expired OAuth secret and a missing IAM permission, were wrong. After the Step 1 command, CREATE and REFRESH succeeded.

Error 2, specific to Lakeflow: “is not an Iceberg compatible table” (004177)

Creating the Iceberg table for a gold view failed. The message reads like an authentication error, but the cause is at the end:

Error: 004177 (42000): SQL Execution Error:
User provided authentication credentials or scopes
are invalid for catalog integration <integration name>
due to error: Malformed request:
Table 'f1_analytics.analytics.driver_performance_summary'
is not an Iceberg compatible table. [ErrorCode: 1000]

UniForm was enabled and the properties had persisted, but pipelines.externalMetadata.enabled was missing. My explanation, not found in the documentation: the Iceberg metadata attached to the view's internal backing table rather than the name Snowflake queries. Converting the views to Python @dp.table did not help, since it still produces a materialized view; adding the property did.

Error 3, specific to Lakeflow: “The UUID of Iceberg table does not match” (091391)

I ran a full refresh of all three pipelines. They succeeded, but every sync task then failed at REFRESH, each on its layer's first table:

ProgrammingError: 091391 (0A000): SQL compilation error:
The UUID of Iceberg table 'raw_race' does not match the
table UUID in metadata file
's3://<bucket>/f1_analytics/__unitystorage/catalogs/
<catalog-id>/tables/<table-id>/_external_metadata/
metadata/00002-<id>.metadata.json'.

My inference, not confirmed: the full refresh gave the Databricks table a new Iceberg identity while the Snowflake object stayed bound to the old one. Snowflake’s linked-database guide describes a comparable mismatch, where the table is dropped from a linked database, without saying whether it returns. The fix catches that specific error and recreates the table:

try:
    cur.execute(
        f"ALTER ICEBERG TABLE {table_fqn} REFRESH")
except snowflake.connector.errors.ProgrammingError as e:
    if "does not match the table UUID" in str(e):
        cur.execute(
            f"DROP ICEBERG TABLE {table_fqn}")
        # ...then re-run CREATE ICEBERG TABLE (Step 4)
    else:
        raise

The repaired run succeeded, and the fix has held up: I later ran another full refresh, all ten raw and curated tables hit the mismatch, the notebook recreated each one, and the job finished green. I did not test what a drop loses (such as grants issued directly on the table).

Gold behaved differently. In that second full refresh the three gold materialized views kept their Iceberg UUIDs while the streaming tables got new ones, so there was nothing for the linked database to drop. SYSTEM$CATALOG_LINK_STATUS stayed RUNNING with an empty failureDetails, and Snowflake showed no errors. Do not assume that always holds: in my first version a gold view did hit the mismatch.

Error 4: “Insufficient privileges” granting CREATE DATABASE (003102)

terraform apply created everything except one Snowflake grant, the one to the sync role UC_ICEBERG_READER, then failed:

Error: An error occurred when granting privileges
to account role
Id: "UC_ICEBERG_READER"|false|false|
CREATE DATABASE|OnAccount
Error: 003102 (42501): Grant not executed:
Insufficient privileges.

Terraform’s Snowflake login, acting as SECURITYADMIN, can grant an account-level privilege only WITH GRANT OPTION, which I had set up for CREATE INTEGRATION but not CREATE DATABASE. Rather than widen two roles, I removed the grant and had SYSADMIN create the database (Step 3).

A Databricks-side gotcha

The pipelines run as the service principal, so it owns every table they create. I deploy as a human who owns the catalogs and could list the tables but had no privilege on them (databricks grants get-effective table ... showed only the service principal); the bundle's permissions block is a workspace ACL, not a data privilege. A second grant giving the identity Terraform runs as ALL_PRIVILEGES fixed it. It is deliberately broad; narrow it if you only need to read.

What I would do differently

Two choices I made for speed are looser than they should be.

Let an admin own the integrations. The sync role UC_ICEBERG_READER creates and owns all three, because the notebook that creates them runs as that role. That forces it to hold account-level CREATE INTEGRATION, and SECURITYADMIN to hold it WITH GRANT OPTION. Yet Snowflake only requires USAGE to reference an integration, and the notebook never alters one. A tighter design has a human ACCOUNTADMIN create them once and grant USAGE, at the cost of handling and rotating the OAuth secret by hand.

Use narrower identities and grants. One service principal both authenticates Snowflake and runs the job, which gives a single identity external and internal reach. I would split it, and narrow ALL_PRIVILEGES for the identity Terraform runs as and the INSERT, UPDATE, DELETE and TRUNCATE that Terraform still gives the sync role (untested, and unnecessary on read-only tables).

Limitations and what I have not verified

  • Read-only, whole namespaces. External writes are not supported per the pipelines page, and I configured the linked database read-only. It exposes a whole schema, so anything added to the gold schema appears in Snowflake automatically.
  • Not tracked by Terraform. The linked database and integrations sit outside it. If a Terraform-managed object is dropped by hand (I dropped UC_ICEBERG_SYNC once), plan reports "has been deleted" with Marking the resource as removed warnings; those are expected, and apply recreates it.
  • Governance and cloud. Row-level security, column masking and time travel are unsupported for external reads, and vended credentials are documented for S3 only (a 2024 Databricks statement; verify elsewhere).
  • Status. External data access for pipeline tables is Public Preview; Snowflake lists linked databases as generally available. Confirm both in your account.

Where this fits

It works well when Snowflake users need to read tables that Lakeflow pipelines build, without a copy, on AWS S3. Freshness is conditional: raw and curated refresh when their pipeline completes, while gold is polled, with contents refreshed about every 30 seconds. It is a poor fit for writes from Snowflake, row-level security or masking on external reads, and sharing only some tables of a schema through a linked database. For another organization, use Delta Sharing.

Both features read the same Lakeflow tables through the same endpoint. Individual Iceberg tables give you control over exactly which tables Snowflake sees and when each one refreshes; a catalog-linked database gives you automatic discovery and refresh for a whole schema. Raw and curated used the first and gold used the second, so you can compare them side by side.
