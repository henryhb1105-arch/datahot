AI指数时代的产品管理：Claude Code产品主管分享

DataHot 速览

Claude Code的产品主管Cat Wu分享了在模型智能快速演进下，产品管理团队如何调整工作流程和路线图。她指出传统产品管理方法假设项目开始时与结束时技术能力大致相同，但指数级改进的模型打破了这一假设，团队需要围绕快速实验、持续发布并加码有效策略的新节奏进行重组。文章提及从2024年10月的Claude Sonnet 3.5到2025年6月的Opus 4，再到Opus 4.6，模型能力不断提升，使得现场演示成为可能。

为什么值得关注：文章揭示了AI产品管理在模型快速迭代下的新方法论，对数据Agent和平台产品经理具有借鉴意义。

译文

AI 逐段翻译

然后，随着Opus 4于2025年6月发布，Claude开始偶尔成功，足以让我们将这项练习转变为预先录制的演示，在Claude 4模型发布时展示最新模型所能实现的功能。

不到一年后，Opus 4.6能够可靠地一次性完成Excalidraw的功能请求，让我们有足够的信心在数千名专业开发者面前进行实时演示。

模型进步的速度不断拓展可能性的边界。传统产品管理手册建立在一个假设之上：项目开始时技术可行的东西，在项目结束时大致也是可行的。产品经理会在前期收集足够的信息，对未来做出有信心的押注，然后在数月内按计划执行。

指数级改进的模型打破了这一假设。你围绕设计约束条件可能在项目中途消失。你正在脚下上升的地基上建设，团队需要围绕这一现实进行重组。新的AI产品管理节奏是快速实验、持续发布，并针对行之有效的方案加倍投入。

毫不奇怪，作为Anthropic的产品经理，我最常被问到的问题之一就是我们的角色如何改变。以下是我学到的东西。

我的Claude Code产品管理之旅

我的职业生涯始于Scale AI和Dagster等初创公司的产品工程师，后来成为风险投资人，在那份工作中我仍然编写代码来自动化工作中繁琐的部分，比如扫描X以寻找新公司公告，或检测开源项目何时获得发展势头。

我于2024年8月加入Anthropic，担任研究产品经理团队的产品经理，该团队连接研究团队和真实世界客户，以交付更好的模型。当年秋天Claude Code在公司内部可用时，我用它来加速工作中更手工的部分，包括构建Streamlit应用以分析大规模用户反馈，以及运行评估以帮助公司找到值得信赖的新基准。低门槛的构建还让我能够探索超出常规职责的范围，比如创建强化学习环境以更好地理解训练。

这些项目花费了数百小时提示由Sonnet 3.5（新版）驱动的Claude Code，但没有手工编写一行代码。

设计新的产品管理工作流程

Claude Code并不是我的工作流程中唯一的工具。随着时间推移，我形成了三个产品之间的自然分工：一个聊天协作工具（Claude.ai）、一个代理式编码工具（Claude Code）和一个知识工作工具（Cowork）。

Claude.ai是我与Claude作为思维伙伴进行对话的地方，不需要它采取行动。我会在这里为战略文档、如何处理棘手情况等提供想法，并获得快速解答。

Claude Code是我构建原型、评估和脚本的地方，其中许多会调用Claude API。当输出是代码时，我会使用它。

Cowork是我处理所有其他事务的地方，从实现收件箱零未读、跟踪和处理待办事项列表、创建幻灯片、通过搜索Slack来理解决策背景，以及预订工作旅行。

我曾与业内产品经理交流，他们找到了自己的工作流程版本：

“Claude提高了优秀产品团队能够构建的上限，并大大缩短了从想法到原型之间的距离。过去，将实际可用的东西展示给客户需要数周的开发。现在，我会从Claude Cowork开始，从Slack、我们的代码库和文档中获取上下文，然后进入Claude Code，在几个小时内就能生成可演示的东西。优秀的产品团队一直用真实客户来测试想法，这种本能没有改变。改变的是我们能够真正投入循环测试的高质量想法的数量。”——Bihan Jiang，Decagon产品总监
“对我来说，在AI原生的世界当产品经理既是创造性的又是学术性的。每次新模型的发布都会改变可能性，在构建Datadog的Bits AI SRE代理时，我们通过离线评估真实生产事故来研究其优势和失败模式。我们还设计紧密的反馈循环，改进用户体验以揭示代理的困难之处，并将这些见解转化为产品改进。从这个意义上说，产品经理的技艺已从预先定义确定性转变为加速发现。”——Kai Xin Tai，Datadog高级产品经理

如今作为产品经理最激动人心的部分之一是这些工作流程在不断演变，并给我们带来更多杠杆效应。

顺应AI的指数级发展

METR 发现，大约一半的情况下，Opus 4.6能够完成人类需要近12小时的软件任务。当我们刚开始构建Claude Code时，Sonnet 3.5（新版）是前沿模型，METR测得其能完成人类大约需要21分钟的任务。这在16个月里大约提升了41倍。

Claude Code团队已经演进以适应模型改进的速度。我们的角色正在融合：设计师发布代码，工程师做出产品决策，产品经理构建原型和评估。这之所以有效，是因为清晰的战略和目标让每个人都能自主确定优先级。产品经理的工作是在快速模型进步带来的模糊性中创造清晰，推动团队更大胆地思考可能性，并扫清更快发布的障碍。

以下是我们已经接受的四个转变：

短期冲刺计划

传统产品经理思维将探索视为在路线图锁定之前发生的事情。你先做研究，写出PRD，然后交给工程团队构建。

我们鼓励团队中的每个人（工程师、产品经理、设计师）在长期路线图之外开展支线任务。支线任务是一种简短的自导式实验，你在官方路线图之外进行——花一个下午测试一个想法，验证一个你原本认为无法实现的能力，或者只是看看当你比预期更用力地推动模型时会发生什么。

Anthropic 最受欢迎的一些功能——Claude Code 桌面版、AskUserQuestion 工具以及待办事项列表——就是以这种方式诞生的。

鼓励用演示和评估取代文档

我们团队基本上已经用“先做原型”取代了“先写文档”的思维。我们不举行传统的站立会议，而是分享新想法的演示。内部用户试用这些演示，那些真正受到关注的演示会被打磨并更广泛地分享。因为你可以用一个下午就能做出原型，所以错误的赌注成本很低。

例如，当 Noah 向 Claude Code 分享他的插件规范时，返回的原型已经接近生产就绪。这个原型为团队最终发布的产品奠定了基础，因为它让团队能够快速验证用户体验。插件 使用Claude Code进行规范说明时，返回的原型几乎达到了生产就绪状态。这个原型锚定了团队最终发布的内容，因为它使团队能够快速验证用户体验。

专业提示：写完规范后，把它发给 Claude Code，看看它是否能构建出来。即使是一个粗糙的原型也能改变对话的走向。

除了演示之外，评估也有助于让抽象的产品更具体。例如，对于让用户协调多个 Claude Code 实例协同工作的智能体团队，Conner 手工制作了一组评估，以了解智能体团队在什么情况下能运作良好，什么情况下不能，以及需要修复什么。衡量功能是否有效有助于改进它。智能体团队 该功能允许用户协调多个Claude Code实例协同工作，Conner手工制作了一套评估来理解智能体团队何时工作良好，何时不佳，以及需要修复什么。衡量功能是否有效使得改进变得更加容易。

用新模型重新审视功能

现在，你发布了一个功能，然后一个更好的模型出现了，你的功能可能会因此大幅改进。每次模型发布都隐含着重新审视你已构建内容的意义。

抓住这些时机的最佳方法是成为日常活跃用户，并刻意要求它做你认为可能太难的事情。有时它会成功，这就表明产品需要跟上。

Claude Code 与 Chrome 集成就是这样发生的。我们注意到用户在用 Claude Code 构建 Web 应用，然后手动切换到 Chrome 中的 Claude 进行测试。用户手动提示并在两个工具之间复制粘贴指令。它运作得足够好，我们意识到这应该是一个内置功能。如果用户在某项临时解决方案上拼接，那就是你可以构建到产品中的脚手架。与Chrome集成的Claude Code 发生了。我们注意到用户使用Claude Code构建Web应用，然后手动切换到Chrome中的Claude进行测试。用户在这两个工具之间手动提示并复制粘贴指令。这工作得足够好，以至于我们意识到这应该是一个内置功能。如果用户正在临时拼凑某些东西，那就是你可以构建到产品中的脚手架。

在原型设计这些想法时，始终首先优化能力。使用比你认为需要的更多的令牌。过早削减令牌成本并因此交付一个能力大打折扣的产品是一个常见错误。你总是可以在更便宜的模型迎头赶上时降低成本，但首先你需要知道该功能是否可行。

做简单的事

在 Anthropic，我们每个团队都有一个指导原则：做简单且有效的事。

如果你的产品巧妙地绕过了模型限制，那么当下一个模型发布时，这种绕过就会成为不必要的复杂性。这就是为什么“做简单的事”很重要：你的实现越简单，就越容易在新功能出现时将其接入。

当我们首次在 Claude Code 中上线待办事项列表功能时，模型无法可靠地在完成任务后勾选事项。因此我们每隔几条消息就添加系统提醒，定期促使用户代理更新自己的待办事项列表。这奏效了，但这是一种临时解决方案。有了下一个模型，这种行为就自动出现了，我们完全移除了这些提醒。我们已经多次看到这种模式：我们的系统提示和工具描述曾经为了弥补模型限制而进行大量工程化调整，而随着每代模型的出现，我们已经能够削减提示，包括为 Opus 4.6 减少了 20% 的提示。

展望未来

许多产品经理习惯于对整个产品体验进行严格的控制，但 AI 迫使你放手才能快速前进。这种控制的直觉正是 AI 产品管理要求你摒弃的首要事项。

尤其在构建 AI 产品方面，感觉就像在冲浪，最重要的事情是待在浪头上。作为一个完美主义者，这是我最难适应的转变，但产品经理的角色现在变成了确定少数几个真正不可妥协的点，然后让其他事情顺其自然。

这些转变的最终效果是产品团队可以大大加快前进速度。当产品经理可以在一下午内从想法变成可工作的原型时，“如果我们试试……”和“来试试这个”之间的差距几乎消失了。

在 Anthropic，产品经理并不是唯一用 Claude 改变工作流程的人。我们的数据科学、金融、市场营销、法律和设计团队都自己采用了这些工具。整个组织以同样的速度前进，而不是等待交接。财务, 营销, 法律 和 设计团队 自行采用了这些工具。整个组织以相同的速度运作，而不是等待交接。

产品经理现在的角色是同时关注两件事：AI 如何改变你的工作方式，以及它如何改变你的产品中可能实现的功能。如果你做得好，当表格工具最终正常工作时，你就不会感到惊讶。你是那个预见到它的人。
