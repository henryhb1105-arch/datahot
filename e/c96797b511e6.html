如何在保留治理的同时将Genie Agents接地到结构化数据与文档

Databricks介绍如何让Genie Agents同时基于结构化数据（如Managed Tables、Views、Metric Views等）和非结构化文件（Unity Catalog Volumes）进行分析与回答，而无需在系统间桥接数据。其治理核心在于Genie Agents以最终用户身份运行，Unity Catalog通过AIM、对象权限、ABAC、行过滤器和列掩码自动执行权限控制。这样单一Agent即使访问大量数据，也不会向错误的人泄露错误信息，且无需额外设置即可继承现有治理体系。

摘要

- 将 Genie Agents 接地到结构化数据（托管表、外部表、外连表、视图、指标视图和物化视图）与非结构化文件（Unity Catalog Volumes）上，让同一个智能体能够跨所有这些数据回答问题。

- 智能体的治理位于 Catalog 层，而非模型层。治理会随着智能体一同扩展，而不会失控。

- 借助 Unity Catalog 中的自动身份管理（AIM）、对象权限、ABAC、行筛选器和列掩码，Genie Agents 以最终用户身份运行，每个答案都会按该用户的权限进行过滤。

构建一个自动化完成简单业务任务的智能体可能很容易。但创建一个真正理解你的业务、并尊重你现有数据治理策略的智能体，要困难得多。

过去很长一段时间，团队不得不使用相互孤立的系统来分别分析结构化数据和非结构化数据，常常要花数周时间才能将两者桥接起来。Genie Agents 通过直接对表和非结构化文件进行分析，简化了这一架构，让你可以用同一个智能体同时基于结构化数据和非结构化数据进行 grounding。

当你整合这些数据时，一个关键问题随之出现：如果某个智能体可以访问一切，那么是什么阻止它把错误的信息告诉错误的人？

好消息是，在 Databricks 中，答案已经存在于你现有的数据治理基础之中。你今天所依赖的那些 Unity Catalog 机制——身份同步、对象权限、ABAC、行筛选器和列掩码——会自动治理 Genie Agents，无需任何额外设置。这种无缝继承依赖于一个架构良好的治理策略，我们将在下文详细探讨。

为了让这些概念更具体，我们将以 Brickstore（一家虚构的全球砖块零售商）为例，使用其中的示例来走查这些场景。

治理契约：Genie Agents 以最终用户的凭据运行

核心架构原则很简单：Genie Agents 以最终用户的凭据运行。Unity Catalog 默认强制执行治理，确保对表和卷的访问直接绑定到最终用户现有的身份与权限。

这一点至关重要，因为许多自研系统会给智能体过宽的访问权限，并依赖提示工程在模型层过滤结果。这实际上就是把 LLM 当成你的安全边界——考虑到模型可能被操纵或绕过，这是一场危险的赌注。告诉审计师“我添加了指示，让它不要显示受限数据”，绝不是一种站得住脚的治理控制。

在本文概述的治理框架下，安全边界仍然是 Unity Catalog，而不是模型；这与 Databricks 其他部分的做法一致。尽管 Genie 决定如何查询数据，但它无法返回最终用户无权查看的任何记录，因为每个答案都会在数据层经过过滤，然后才会离开 Lakehouse。

第 0 步：从身份开始：自动身份管理（AIM）与即时（JIT）预配置

这一架构的起点是确保你的企业身份既准确又保持最新。访问控制的可靠性，本质上取决于它所评估的身份的可靠性。

如果 Databricks 中的组成员身份只是身份提供者中内容的陈旧、手工维护副本，那么“brickstore_apac 的成员只能查看 APAC 订单”这样的策略就毫无意义。针对 Microsoft Entra ID 和 Okta 的自动身份管理（Automatic Identity Management，AIM）弥合了这一差距。启用后，用户、组、组成员身份和服务主体会从这些身份提供者自动同步到 Databricks，无需 SCIM 应用。即时预配置（Just-in-time provisioning）始终开启，因此从未登录过 Databricks 的用户会在首次登录时被预配置，并且一到达就带着现有的组成员身份。流程如下：IdP 是事实来源。某人加入 APAC 销售组织；你的身份提供者将他们放入 brickstore_apac 组。AIM 将该信息同步到 Databricks——包括组成员身份。JIT 在用户首次打开 Genie One 时在 Databricks 上预配置该用户。Unity Catalog 策略以这些组为关键依据——对象权限、ABAC 策略、行过滤器和列掩码都在查询时评估组成员身份。用户向 Genie Agent 提问，答案恰好由其组权限所允许的范围决定，不多也不少。好处在于，治理是持续性的，而非一次性设置。当员工从 APAC 调往 AMER 时，IdP 会在组间移动他们，同步随之传播，他们向 Genie 提出的下一个问题就会返回 AMER 视图——无需任何人提交工单或修改 Genie Agent。当员工离开公司时，他们会从 IdP 中停用，对每个 Genie Agent 的访问也会立即被移除。

第一步：将结构化数据接地并控制四层访问

身份得到适当建立后，我们现在可以关注他们被允许看到什么。对于结构化数据，Genie Agent 可以访问任何 Unity Catalog 数据资产——表、视图、物化视图、指标视图、流式表，甚至是从外部系统联合的外部表。例如，Delta 表就是事实表和维度表。在 Brickstore 中，即 brickstore.sales.orders（每一笔订单，包含区域和 customer_email）和 brickstore.sales.products（砖块目录）。指标视图（Metric Views）是位于其上的受治理语义层——它们将业务指标的定义（例如“净收入”意味着什么、“已售砖块”如何计算、什么算作“最畅销砖块”）用 YAML 编码一次，因此每个消费者都以相同的方式计算它们。在这些资产之上，有四层访问控制，人们常常将它们混为一谈：

- **对象权限（Object Privileges）**：谁对什么资源拥有什么级别的访问？机制：对目录/架构/表执行 GRANT SELECT。

- **基于属性的访问控制（ABAC）**：哪条策略适用，适用于什么？机制：由治理标签驱动的策略，附着一次并传播（例如：任何带有“PII”标签的列只对某些组可用）。

- **行过滤器（Row Filters）**：用户能访问哪些行？机制：SQL 用户定义函数（UDF），在查询时对每一行求值（函数返回 FALSE 的行会从查询结果中排除）。

- **列掩码（Column Masks）**：哪些列应被掩码，如何掩码？机制：SQL UDF，将列值作为输入，返回原始值或掩码后的版本。

对象权限是第一层访问控制：没有 SELECT，Genie 就无法代表最终用户查询表。但授予对表的访问权限并不意味着你需要授予全部权限。

在这些授权之上，你再叠加行过滤器和列掩码。这样，区域经理可以查询订单表，但只能看到自己所在区域的行，且永远看不到原始的客户电子邮件。这些行和列的控制所依赖的，正是你的授权已经在使用的那些组——例如 `is_account_group_member('brickstore_apac')` 之类。接下来要讲的 ABAC 并不会取代这些机制；它只是用一种策略方式去附加同样的过滤器和掩码，而不是逐表附加。

ABAC：一次定义策略，让它自动传播

以往实现行级和列级安全的方式是逐表进行：写一个行过滤器，挂到 `orders` 表上；再写一个列掩码，挂到另一张表上；如此反复。这种方式仍然适合一次性逻辑，但在数百张表面前，它会变成一种容易出现漏洞的配置。ABAC 策略与受管标签、自动数据分类一起，现已在 Unity Catalog 中正式发布（GA），它扭转了这种局面。你用受管标签（账户级、受访问控制的键值对，如 `pii:email`）为敏感数据打标签，然后写一条策略：“无论这个标签出现在哪里，都应用此保护。” 新表一旦被标记，就立刻继承保护，因此无需逐表操作。一条列掩码 + ABAC 策略，用一条语句保护目录中所有 email 列；再加一条行过滤器 + ABAC 策略，让每位经理只看到自己区域的订单，由组成员身份驱动。最终效果是：APAC 经理询问订单相关问题，Genie Agent 只返回 APAC 行，且 `customer_email` 被掩码；AMER 经理查询同一张表，得到的是 AMER 行。

第 2 步：将同样的治理扩展到文档

从历史上看，团队在处理非结构化数据时，治理策略一直更具挑战性。结构化数据可以安全地管理在数据仓库或数据库中，而文档则常常存放在隔离的存储系统中，由独立的 ACL 管理。解决办法是让文件与结构化数据处于同一个治理平面。你可以把它们放入 Unity Catalog Volumes，它们就会像其他对象一样成为可保护对象。你对应该看到这些卷的组和用户执行 `GRANT READ VOLUME`，Genie 就在同一个身份契约下对它们进行推理。在设计你的 Agent 之前，有一个行为值得理解：当你把一个卷附加到 Genie Agent 上时，它会成为必需来源。这意味着，Agent 在加载时会验证对每个附加来源的访问权限，因此，如果用户对某个已附加卷没有 `READ VOLUME` 权限，就根本无法使用该 Agent。换句话说，卷授权将文档作为使用 Agent 的前提条件来治理，所以请确保将每个 Agent 的文档来源限定在应该使用该 Agent 的受众范围内。如果两类受众需要不同的文档，你可能需要给他们不同的 Genie Agent（每个 Agent 只挂载该用户能读取的卷）。同时要记住，Unity Catalog Volume 是最小的可保护单元，因此权限应用于整个卷，而不是单个文件。你不能挑选具体的文件来共享；你必须授予对整个卷的访问权，或者一个都不授予。考虑到这些因素，卷可以直接作为知识源附加到 Genie Agent 上，方式与表或视图相同。Genie Agent 的读取范围远不止 PDF——支持的格式包括 PDF、图像文件（JPG、JPEG、PNG、TIFF、TIF）和 Office 文档（DOC、DOCX、PPT、PPTX），以及纯文本文档和 Markdown。

配置 Volume 的最佳实践

实际上，这意味着扫描的合同、幻灯片和规格表都在支持范围内，而不仅仅是干净的 PDF。（完整列表和当前限制请参阅 Genie Agents volumes 文档。）为确保准确的路由和最佳性能，请遵循以下配置卷的最佳实践：

添加清晰描述：准确描述卷中包含的内容、组织方式以及 Agent 应如何使用它。不要使用通用占位符。例如，不要用“区域文件”，而要用“APAC 市场报告——APAC 区域的需求驱动因素、趋势和关注项”。Genie 依赖此描述来选择正确的卷。

避免重复内容：附加多个包含重叠信息的卷会使 Agent 更难以检索相关文档。对于卷内的单个文件也是如此。

避免无关文件：只包含与 Agent 领域相关的文件。无关文件会干扰 Agent。

使用清晰的文件名：使用描述性文件名，以便 Agent 区分不同文件。

第 3 步：生产环境中的 Genie Agents：相同问题，不同答案

至此，Genie Agent 已完全具备真正的领域专家能力——可以同时访问结构化和非结构化数据。底层知识库仍然通过行过滤器、列掩码和基于每用户权限的卷授权得到彻底保护。我们通过让两个不同用户提出完全相同的问题来对实现进行基准测试，这应产生两个各自正确且不同的响应。

考虑两个并发的 Genie Agent 会话，两者都基于相同的资产——orders 表、products 目录和 market_report 卷。一个请求者属于 brickstore_apac，另一个属于 brickstore_amer，但他们都提交了完全相同的查询：“本季度我们最畅销的产品是什么？是什么推动了这一需求？同时列出这些销售背后的主要客户及其电子邮件。”

这里有三点值得指出：

这种差异不需要任何按用户提示工程。没有人写“如果用户是 APAC，就隐藏其他区域”。Agent 的指令是完全相同的。Unity Catalog 在查询时完成了过滤——既在行级别，也在被掩码的列上。注意，电子邮件列被掩码以保护 PII。

结构化数据，经由非结构化知识而丰富。如果没有区域文档，Genie 也许能轻松识别“是什么”的问题，但很难想清楚哪些因素在推动需求。有了可用的非结构化数据，Genie 就拥有了完整的业务上下文。

需要留意的模式

在将本文的经验推向生产环境时，有几个模式值得留意：

先打标签，再定策略。不要逐表掩码。直觉是保护你面前的这三张表，但请抵制这种直觉。定义受治理的标签和 ABAC 策略，以让数据治理面向未来。

每个卷对应单一受众。由于卷是最小的可授权单位，请在卷的边界决定文档访问权限。如果两个文档需要不同的读者，它们就需要不同的卷和不同的 Genie Agents——请提前规划好布局。

当通过 MCP 或 API 在外部暴露 Genie One 或 Genie Agents 时，必须小心处理身份。与通过 Databricks UI 运行不同，你并不总是有权使用最终用户的身份（例如，使用服务主体进行身份验证时）。有一些需要采用的特定模式；Databricks 在《Access Genie everywhere》中详述了 U2M、M2M 和 OBO 配置。

用模拟（impersonation）来测试，而不是靠检查（inspection）。不要通过阅读策略并说服自己它是对的来验证治理——而是以每个组成员的身份提出同样的问题，并比较回答。把这一测试设为回归测试，并在策略或分组发生变化时运行。

要点

构建一个 agent 可能很容易，但治理它需要真正的设计工作。在 Databricks 中，企业身份从 IdP 同步，对象权限控制访问，ABAC 和治理标签在规模上应用保护，行过滤器和列掩码控制返回的内容，文档与数据保存在同一系统中。通过这种设置，Genie Agents 无需任何额外配置即可继承所有治理。

要开始构建你的第一个受治理的 Genie Agent，请访问 Genie 文档和 ABAC 策略文档。
