引言

任何大规模使用 LLM 生成文本的团队都会遇到同一个问题。你无法手动评估所有内容。你不知道哪些输出很好、哪些平庸、哪些有害，因为你根本无法全部读完。标准解决方案是 LLM-as-a-Judge，即用第二个模型为第一个模型的输出打分，作为人类评估者的替代。它快速、便宜且易于部署。然而，它引入了一个新的关键问题：谁来评估评估者？ 此外，如果评估者发生漂移，悄然退化并开始批准糟糕的输出，下游不会有任何机制发出警报。

本文讲述我们如何解决这个问题：通过构建、对齐并持续监控 LLM 评估者，使其随时间推移保持可信。我们的核心原则很简单：LLM 评估者绝不能独立运作。它必须以人类判断为锚点。 我们在生命周期的每个阶段都保留 人在回路（HITL）。人类定义什么是“好”，创建带标签的基准数据集来训练和验证评估者，在系统运行时监控其行为，并在任何更新推出之前进行审查和批准。

我们认为：

可靠的 LLM 评估者不是静态产物。它有一个生命周期。

它需要基于可信的人类标签来 构建，与人类偏好和推理 对齐，在人类设定的策略下 运行，并随着数据和使用模式的变化而 维护。每个阶段都有其人类负责人。在下面的章节中，我们将逐一介绍这四个阶段、每个阶段的关键设计决策，以及我们会与正在构建自己 LLM 评估者的团队分享的经验教训，并以一个具体任务作为贯穿全文的示例：推荐解释。

一个 推荐解释是伴随推荐条目的一段简短自然语言消息，它影响用户对推荐系统的感知和信任。在我们的工作中，解释是关于 为什么 基于会员此前观看的内容推荐某个标题的人类可读证据，展示在标题详情页上，即会员从主页选择某个标题后到达的屏幕。我们关注 基于相似度的解释，它将一个推荐标题与会员互动过的一个参考标题通过共享属性（如类型和基调）联系起来。例如，

一部关于爱与全新开始的幽默、真挚的假日爱情片，很像《我的秘密圣诞老人》。

质量在这里很重要，因为误导性或缺乏依据的解释会侵蚀解释本应建立的信任。

接下来的一切都来自我们在解释功能上运行的一系列受控的、面向用户的在线实验，包括在 Netflix 移动应用上为期一个月的实验。在这些测试中，我们使用 LLM 生成解释，在不断变化的目录上每周生成数十万条。在这个规模上手动审查是不可行的，因此我们部署了第二个 LLM 来评估它们。

什么算作好的解释是我们任务特有的。然而，我们构建、对齐和监控用于评估解释的 LLM 评估者的方式应该是可复用且可推广到不同任务的。

生命周期概览

图 1 总结了我们 LLM 评估者生命周期的四个阶段以及连接它们的数据流。

我们从 诞生：基准数据创建 开始，人类专家在此精心制作困难或接近边界的示例，人类评估者为其标注通过/不通过决策和书面理由。我们用 LLM 生成的灰色地带示例来扩充，以构建更丰富的基准数据集。

接下来，在第二阶段 训练：LLM 评估者开发 中，我们调整 LLM 评估者，使其与诞生阶段的人类标签和理由对齐，使用自我反思来识别评估者与人类之间的不匹配，并根据这些不匹配和锚点示例更新评分标准。我们在此阶段迭代，直到我们的指标显示评估者与人类评估者充分对齐。

在第三阶段，部署 中，我们将评估者作为把关者和批评者集成到解释生成系统中。LLM 生成器编写解释，LLM 评估者对其评分，要么放行，要么阻止并提供理由，生成器可用于自我完善和重试。通过的解释提供给会员，低质量的解释被拦截。

最后，在最后一个阶段，HITL 对齐与漂移监控 中，我们保持评估者随时间与人类对齐。这里的“人在回路”意味着一个人直接参与决策，而不仅仅是事后审查结果。我们以训练有素的评估者为基准来评测评估者，并且每一处变更在推出到系统之前都需经人工批准。在每次测试中，我们每周抽取一组解释（包括通过和拦截的，偏向较新的条目），让人类评估者审查并给出标签和理由，然后将评估者与这些人类评分进行比较。如果漂移超过阈值，我们触发重新训练和基准数据扩充。这通过将新的人工标注数据和更新的信号反馈到基准和开发阶段来闭合循环。

系统组件

四个自动化组件出现在所有阶段中，同时还有定义、验证和监督它们的人类角色。

  • 生成器： 生成解释文本，可选地将先前的评估者理由和轨迹作为其修订提示的一部分。
  • 评估者： 评估解释并返回通过/不通过标签以及书面理由。在部署的流水线中，它既充当护栏（拦截糟糕输出），又充当批评者（为自我完善提供反馈）。
  • 反思器： 在评估者犯错时修订其评分标准。它基于不匹配的示例、人类理由和锚点示例来更新评分标准。它调整评分标准，不直接评估解释。
  • 元评估者： 检查评估者是否因 正确的原因通过将评判器的理由与人类评分者的理由进行对比。
  • 人类专家和评分者：定义质量标准的人类专家；其标签和书面理由被用来调优和衡量评判器的评分者；在评判器运行期间监督它并在任何更改推出前明确批准的审查者。

第一阶段，诞生：建立基准真相

后续的一切都取决于知道“好”意味着什么，因此这是人力最密集的阶段。我们的内部写作专家定义了说明必须满足的必备标准，编写了详细的标注指南，并手工制作了棘手的对抗性示例。这些相同的指南承担双重职责。它们既是人类评分者的规则手册也是我们后续调优的LLM评判器的种子评分标准。

我们为何构建自己的基准

现成的LLM评判器基准侧重于通用文本评估，忽略了使我们的任务具有特殊性的因素。说明简短、针对具体条目且依赖上下文（每一条说明都与一个目标标题以及会员观看过的一到两个参考标题相关联）。我们还关心与自身编辑标准的对齐，而不仅仅是通用的语言质量。因此，我们从三个互补的来源构建了自己的定制基准：

  • 专家精心制作的对抗性案例：手工编写的、带有已知失败模式的通过/失败示例，是其他任何方式都无法可靠产生的边缘案例。
  • 边界示例：由LLM合成的说明，故意被推到接近通过/失败边界的位置，然后由人类评分。这些捕捉了从实时流量中采样很少能自行浮现的模糊案例。
  • 真实采样的说明：在测试运行期间从我们的LLM生成器输出中采样的说明。

两个重要的细节

  • 基准并非一成不变。一个 监控流水线（第四阶段）以每周一次的频率追加一批新的人工评分说明，因此在整个测试过程中，基准跟踪了当前的目录和新的使用模式，而不是变得过时。
  • 每个“失败”标签都附带一段自由文本理由解释为什么该说明失败了。这看起来像是一个小的记账细节，但它实际上对下一阶段至关重要，因为这些理由正是我们用来调优和审计评判器推理的依据。

第二阶段，训练：使评判器与人类对齐

失败模式：答案正确，理由错误

有一种失败模式根本不会出现在标签一致性指标中。评判器可以在标签上与人类一致——人类认为通过时它通过，人类认为失败时它失败——但却以错误的理由得出正确的结论。在仪表盘上它看起来完全对齐。但一旦你要求它解释一次拒绝——我们的流水线正是这样做的以引导自我修正——它就可能返回误导性的指导。

因此我们不仅关心标签一致性，还关心推理对齐。在我们的设置中，评判器总是被要求输出：

  • 一个标签（例如，通过/失败），以及
  • 一段简短的自然语言理由来说明该标签。

这里有一个说明性的例子。该会员观看了一部音乐剧，一部由年轻女主角和知名群星阵容出演的家庭奇幻片。我们推荐了一部同样是家庭奇幻片、同样有年轻女主角的冒险电影，这就是推荐系统将它们配对的原因。但它既没有相同的歌曲，也没有相同的群星阵容。

标签（失败）是正确的，所述理由乍看之下也合理。但事实证明，它以简单标签一致性无法检测的方式不完整，如下所示。

推理对齐评分标准调优

我们用一个称为推理对齐评分标准调优（RART）的流程来调优每个标准的LLM评判器。如上面的系统组件所介绍，评判器、元评判器和反思器是不同的组件。评判器根据评分标准对说明进行评分并给出理由，元评判器将该理由与人类书写的理由进行对比，反思器则编辑评分标准文本本身。RART就是这三者如何组合成一个训练循环。

每个评判器都是一个由评分标准参数化的固定提示模板，因此调优它并不意味着重新训练底层模型。相反，我们迭代地改进评分标准文本，直到评判器的行为与人类标签和人类理由都匹配。在第i次迭代时，评判器以当前评分标准文本为条件，将一条说明映射为一对输出——一个标签和一个理由。

在高层次上，每次RART迭代按如下方式进行。

  1. 用当前评分标准对训练数据进行评分。
  2. 在留出的验证集上评估加权对齐指标。如果所有各标准的指标都超过其阈值，则停止。
  3. 否则，构建一个由错误驱动的焦点集，包含未对齐的示例，并将其交给反思器，由反思器提出修订后的评分标准。

与标准循环的关键区别在于我们如何定义“错误”。大多数自我改进循环只关注标签分歧。RART增加了第二类错误。元评判器检查评判器和人类都判定为失败的情况，并将评判器所述的理由与人类的理由进行对比。当两者出现分歧时，这就是一个答案正确、理由错误的错误，它也会被送入反思器。具体而言，交给反思器的焦点集是两类错误的并集：

  • 标签不匹配：评判器的标签与人类不同的示例。
  • 标签正确、理由错误：评判器和人类都说失败，但元评判器发现他们的两个理由不匹配的示例。

因此，反思器基于普通标签错误和标签正确、理由错误这两类错误来修订评分标准。第二项是RART的核心。评判器不仅被推动去匹配人类的决策，还要以元评判器认可为与人类推理对齐的方式来论证这些决策。

回到之前的例子，LLM评判器说失败，人类也说失败，因此仅检查标签会记录为一致。将两个理由并排放置，就能显示这种检查遗漏了什么。

RART 将其路由到焦点集中，因此下一次评分标准修订必须将其考虑在内。

由于 Meta-Judge 本身也是一个 LLM，我们首先将其与人类进行了对照检查。训练有素的人类评审员对一组达成一致失败的理由对样本进行了标注，Meta-Judge 在几乎所有这些样本上的判定都与他们一致。

对齐指标

我们为每个标准运行一个 Judge，每个都有自己的评分标准，并各自独立调优和评分。因此，以下所有内容都是在每个标准上、在留出数据上测量的。对于每个标准，我们追踪三个指标。

  • 特异性（失败召回率）：Judge 正确拒绝不良解释的频率。这是我们最关心的指标，因为一个漏过闸门的不良解释是一个信任隐患。
  • 召回率（通过召回率）：它正确通过良好解释的频率，这能保持高覆盖率并降低修订成本。
  • 推理一致性：在两者都拒绝的解释上，它们以相同理由拒绝的频率。

每个标准的 Judge 都有各自的三项指标，一个可能表现健康而另一个可能下滑。这也是闸门严格的原因。一个解释必须通过每一个必备标准才能有资格被采用。

消融实验：推理信号有帮助吗？

为了隔离推理信号的影响，我们将 RART 与一个在其他方面完全相同的循环进行比较，后者仅使用标签分歧。我们称这个基线为vanilla：相同的 Reflector、相同的 Judge、相同的数据，但没有 Meta-Judge，也不使用人类理由。

图 2 显示了结果。在三个必备标准中的两个上，vanilla 和 RART 达到相同水平，因为起始评分标准已经接近上限，指标几乎没有提升空间。在第三个标准上，vanilla（仅标签）方法出现退化。vanilla 循环中的 Reflector 将评分标准重写为退化形式，特异性和推理一致性随每次迭代下降，最终比其起始的评分标准更差。RART 在同一标准上保持稳定并提升了这两项指标，召回率也有小幅提升。原因是 vanilla（仅标签）优化器可以通过不健全的推理达到正确的标签，而不健全的推理无法泛化到新数据。将信号锚定在理由上可以防止这一点。推理对齐在有提升空间的地方有帮助，在没有提升空间的地方也不会造成损害。

阶段 III，部署：让 Judge 发挥作用

部署后，Judge 位于生成流水线内部，在我们的测试中对生成过程中的解释进行把关和评判。

一个 Judge 的两种角色

一旦我们将 LLM Judge 与人类对齐，我们就会对每个生成的解释以两种不同的角色复用它：

  • 角色 1，闸门。Judge 根据必备标准对每个解释进行评分，并拒绝任何未通过的解释。
  • 角色 2，批评者。当一个解释失败时，我们不会直接丢弃它。Judge 的自由文本理由会被附加到 Generator 的提示中，Generator 再次尝试。

第二种角色将流水线转变为生成 → 评判 → 修订循环，由 Judge 的批评引导每次修订。

有界重试，以及为什么我们选择丢弃而不是采用

我们对重试次数设上限。每次修订都要多一轮生成和评判，而收益很快趋于平缓。图 3 显示了该循环实际带来的效果，基于 1,000 个生成的解释，使用四个生成器最多进行 12 次修订。每条曲线都在上升，这是 Judge 的批评在发挥作用，但陡峭的部分出现在早期，生成器之间的差距也很明显。修订放大的是一个有能力的生成器，而不是挽救一个弱的生成器。在我们的测试运行中，我们对最强的生成器使用了3 次重试的预算，而在此之后仍然失败的解释会被丢弃而不是采用。

“丢弃而不是采用”的规则是有意为之的。这两种结果并不对称。一个不良解释是一个信任隐患，而一个缺失的解释只是放弃了一个机会。当有疑问时，我们宁愿什么都不展示，而大多数解释在重试预算内就通过了标准。

Judge 批准的解释对会员有帮助吗？

通过 Judge 证明一个解释按我们的标准是好的，但这并不证明 Judge 批准的解释对会员是有用的。为了测试这种联系，我们在 Netflix 移动应用上进行了一次性对照实验，在标题详情页上对比有解释和无解释，持续约一个月，期间流水线每周生成并评判数十万个解释。

看到解释的会员将其观看转向了他们之前没看过的标题，并且更多浏览会话以有意义的播放结束。两种效应都具有统计显著性，并且我们在测试期间没有看到会员发起的下架或关于解释质量的升级。值得沿用的结果不是该效应的规模，而是与我们的评审员的离线一致性对于这些解释起作用是必要的，但从来不足以证明它们对会员有帮助。只有在线 A/B 测试才能确立与 Judge 对齐的解释不仅在质量上合规，而且真正有用。

阶段 IV，监控：保持 Judge 对齐

一个在启动时对齐良好的 Judge 不会一直保持那样。目录会变化，高质量的定义也会变化。生命周期必须闭环。

每周人工审查

在测试运行的每一周，我们抽取大约300 个生成的解释进行人工审查，按 Judge 的决策分层（已采用、已修订、已丢弃），并侧重于较新的目录条目，也就是最容易出现漂移的地方。分层在每周之间保持固定，因此连续的各周具有可比性。由至少三名评分者组成的小组审查每条解释，多数标签就是我们的基准真值。这些标签承担了两项工作。它们告诉我们评判者与人类的一致性是否在下滑，并且它们扩充了基准。

以人类分歧设定标准

该小组还告诉我们评分者彼此之间的分歧有多大，而这正是评判者的合适标尺。我们不是用固定阈值来要求它，而是将评判者和每位评分者都对照同一个 多数标签打分，并要求评判者落在评分者自身的分布范围之内。

以某一项标准及其某项指标 M 为例。那一周的样本给出评判者的一个值 M(J)，以及小组中三名或更多评分者的一组逐评分者值 M(H)。我们要求

因此评判者的得分不得低于平均评分者两个标准差以下。更困难的一周会扩大人类分歧，也会随之扩大该区间，因此评判者不会因为人类也感受到的难度而受到惩罚。

在任何指标-标准对上低于该区间即为一次漂移事件，这会触发在扩充后的基准上重新调优（回到第二阶段）。重新调优后的评分标准绝不自动上线。团队中会有人在它进入运行中的流水线之前阅读提议的变更并签字确认，同时我们保留之前的评分标准以便即时回滚。

指标无法捕捉、而人工审查能捕捉到的问题

除了询问评判者是否仍与人类评分者一致之外，每周审查还回答第二个问题。当前的指南是否仍在要求正确的东西？

在每周审查流程中，审查者发现了评判者-评分者一致性中没有显现的问题。一条解释可以使用准确的属性，却仍然夸大两个标题实际上有多相似。一个含糊的形容词（“exciting”、“fun”、“emotional”）从技术上讲可以满足评分标准，却几乎什么也没说明。有时参考本身就是问题所在，某个会员根本不会认为它是可比的标题，因此无论属性如何对齐，这种比较都显得很奇怪。某些类型在规模上表现出同样的问题。单口喜剧特辑可能共享相似的元数据标签，但在语气和文化语境上完全不同，因此一种比较在纸面上可能看似合理、也没有糟糕到让评分者判定不通过，却仍然无法让会员满意。还有些解释满足了每一项必备标准，却仍然读起来像泛泛的“词语堆砌”，对用户帮助不大。

当反复出现的模式不断出现时，我们更新了第一阶段的指南，这些指南同时作为评分者的说明和评判者的评分标准的种子，因此一次修订会同时更新两侧。其他时候，我们在评判者之外添加产品规则，例如阻止某些标题类型被用作参考。

漂移检测能捕捉到已经不再与人类一致的评判者。只有持续的人工审查才能告诉我们，我们对“好解释”的定义何时过于狭窄或不完整。两者都需要。

  • 漂移检测让评判者与当前评分标准保持一致。
  • 持续的人工审查让评分标准与真正对会员有效的东西保持一致。

我们学到了什么

我们认为有五条经验可以迁移到任何交付 LLM 评判者的团队：

  1. 在评判者之前先投资于基准。一个适度的、带有理由标注的基准胜过大型的仅含标签的基准。那些写下的理由正是使推理对齐调优成为可能的关键。如果你从未写下人类的推理，你就无法纠正评判者的推理。
  2. 基于推理调优，而不仅仅是标签。评判者可能因错误的原因得出正确的结论，这在仪表盘上看起来没问题，但会给出误导性的反馈，并且在新数据上站不住脚。在我们的消融实验中，仅标签的循环使评分标准退化，而推理感知的循环则使其保持稳定。
  3. 一个对齐的评判者可以承担多种角色。将同一个评判者同时复用为门控和批评者，可以分摊对齐成本，并使生产行为在各角色之间保持一致。对齐是昂贵的部分，所以要把一个评判者做对，并多次使用它。
  4. 从第一天起就规划监控。推荐平台的物品和会员从不停下变化，因此 LLM 评判者，和任何 ML 模型一样，必须被观察并在需要时重新调优，而不是部署后就遗忘。
  5. 从设计上就让人类留在环路中，而不是作为例外。自动化评估并不等同于把责任委托出去。在我们的生命周期中，人类设定标准（第一阶段），提供评判者所对齐的理由（第二阶段），决定丢弃而非提供可疑输出的保守默认做法（第三阶段），并审查实时决策的常设样本、在每次评分标准变更上线前予以批准（第四阶段）。一旦评判者已经在自行做决策，这些检查点就很难事后补上。常设审查还告诉我们评分标准缺少什么，而不仅仅是评判者何时出现了下滑。

综合来看，评判者扩展了我们审查者的触达范围，而这些审查者正是信任评判者的基础。正是这种关系使得在规模上运行该系统是负责任的。一个无人审计的自动化评估器无法为其正在做出的决策提供任何保证。
