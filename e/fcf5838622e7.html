IP 数据就是数仓数据

每一台防火墙、负载均衡器、VPN、CDN 边缘节点、DNS 解析器、Kubernetes 集群和应用服务器都会输出一串记录，而这些记录都以同一样东西为键：一个 IP 地址。对于大型企业而言，这些数据流合计每天生成数百亿条事件，并且是组织所运行的一些最有价值的分析的基础，包括威胁检测、欺诈调查和网络可观测性。历史上，业界将这些网络可观测性用例视为需要专用技术栈的专门用例，从而导致了孤岛、碎片化治理和厂商锁定。

这一切现在改变了。今天，IP Functions 已正式发布（Generally Available）。通过此次发布，IP 地址分析成为湖仓上的一等公民、高性能 SQL 工作负载，让安全团队能够在其其余分析工作旁边，在同一套治理模型下，解析、丰富和分析其最高容量的 IP 数据。

为什么网络分析过去如此痛苦

过去，IP 地址在 SQL 中处理起来出乎意料地困难。一个 IPv4 地址看起来像字符串，但行为却像 32 位整数；IPv6 则是 128 位。像 10.0.0.0/8 这样的 CIDR 块根本不是一个值——它是 1600 万个地址的区间。问“这个 IP 是否在该子网内？”实际上是一个隐藏在一段文本背后的区间包含问题。

在没有原生支持的情况下，团队被迫采用几种脆弱的模式之一——每一种都要在正确性、性能或可维护性上做出牺牲：

常见变通方案你所付出的代价
正则解析 从字符串中提取各段八位组缓慢、脆弱，在格式错误或 IPv6 输入上会静默出错
手工位运算 将地址转换为整数只有作者才能读懂的不堪入目的 SQL；在 v4/v6 边界上会出错
自定义 UDF 用于 CIDR 包含判断扼杀向量化和查询优化器感知；成为规划器无法下推或广播的黑盒
预先将 CIDR 展开为区间 在外部管道中需要维护另一条独立管道
完全放弃 IPv6整类现代流量被静默排除在分析之外

结果是双输。只会 SQL 的分析师被挡在基本的 IP 过滤之外，因为它需要过程式代码。数据工程师耗费大量精力维护 UDF 库和 CIDR 展开作业。最重要的是，关键工作负载，例如将数十亿条事件与威胁情报和地理位置 IP 表进行丰富，会运行超过一个小时，而业务需要几分钟内得到答案。在 PB 级规模下，这个差距就是正在发生的入侵被当场捕获，与事后在复盘报告中读到它之间的区别。

内置于 SQL 的原生 IP 函数

Databricks 推出一整套内置的IP 函数，使网络数据成为湖仓的一等公民。它们统一处理IPv4 和 IPv6，同时接受人类可读的STRING和紧凑的BINARY表示形式，原生理解 CIDR 记法，并且是在引擎本身中实现的，因此优化器和 Photon 可以加速它们。

下面的示例用威胁情报丰富原始网络流日志，然后识别正在扫描大量目标与端口可疑的源网络。过去需要自定义解析逻辑和定制 IP 库才能做到的事情，现在可以直接使用原生 IP 和 CIDR 操作在 SQL 中表达。

没有 UDF。没有正则。没有整数体操。它读起来就像分析师实际提出的问题。

这些函数

此次 GA 版本提供了解析、规范化、检查和连接 IP 数据所需的完整工具集：

包含判断与连接

  • ip_cidr_contains(cidr, needle) - 测试一个 IP 地址或另一个 CIDR 块是否落在一个 CIDR 块内。这是 CIDR 块连接和高容量过滤背后的单一谓词，也是整个优化工作所围绕的函数。

解析与规范化

  • ip_host(ip) - 将 IPv4 或 IPv6 地址规范化为其标准形式（例如，将 2001:0db8:0000::1 折叠为 2001:db8::1）。
  • ip_cidr(cidr) - 生成 CIDR 块的规范表示。

检查 CIDR

  • ip_network(cidr) / ip_network_first(cidr) - 返回 CIDR 块的第一个（网络）地址。
  • ip_network_last(cidr) - 返回 CIDR 块的最后一个地址。
  • ip_prefix_length(cidr) - 返回前缀长度（斜杠后面的数字）。
  • ip_version(ip_or_cidr) - 返回 4 或 6，因此可以在无需特殊处理的情况下对混合协议地址进行分支判断

表示形式转换 - 用于性能

  • ip_as_binary(ip_or_cidr) - 将地址或 CIDR 转换为其规范、紧凑的二进制形式（IPv4 为 4 字节，IPv6 为 16 字节）。以 BINARY 存储和连接可跳过重复解析并缩小存储。
  • ip_as_string(ip_or_cidr) - 将二进制表示形式转换回人类可读文本，用于报告。

用于脏数据的安全变体

  • try_ip_host(ip)、try_ip_cidr(cidr)、try_ip_as_binary(ip_or_cidr)、try_ip_as_string(ip_or_cidr) - 与其对应函数相同，但在无效输入时返回 NULL 而不是报错。在摄取原始日志时至关重要，因为总有一小部分记录是格式错误的，这样一行坏数据永远不会让一个十亿行的作业失败。

这些原生函数可与其余 SQL 自然地组合使用，它们对每个 SQL 用户都可用，无需任何设置，并且优化器能够理解它们，这正是性能表现得以实现的原因。

Rearc 帮助企业开发 GenAI、数据和云平台，它正利用 IP Functions 为大规模客户构建网络可观测性用例。

我们为一家大型金融公司构建了一款产品，该公司每天处理超过 30TB 的数据，性能和成本效率至关重要。借助 Databricks 引擎原生的 IP 函数，我们能够直接在 SQL 中解析、验证和连接 IP 数据，用更优雅、更易维护的方案取代了之前的临时实现。由于这些函数内置于引擎中，我们在实现这一点的同时，并未牺牲此规模下工作负载所要求的性能。他们让湖仓上的网络分析对我们来说变得更简单、交付更快。”——Dara Kharabi，Rearc 的 AI 与数据实践负责人

为 PB 级规模而构建：以秒计，而非以分钟计

一个常见的 IP 分析挑战是在一个大得多的范围中查找单个地址或子 CIDR，这对于大规模快速检测威胁、调查欺诈和监控网络活动至关重要。该用例代表一种范围连接，而引擎历来难以处理这种连接，因为标准连接算法依赖于相等性。Databricks 的引擎通过 ip_cidr_contains 支持针对 IP 地址的优化范围连接。

Databricks 的 ip_cidr_contains 在各种规模的探测表（即“针”）和块表（即“干草堆”）上，在价格和速度方面均优于传统数仓。我们在五个代表性场景中对 ip_cidr_contains 进行了基准测试：

场景探测表大小 （即针的数量）CIDR 块表大小 （即干草堆的数量）
某团队的每日访问日志与精选拒绝名单进行连接1000 万 IP1000 个块
某大型客户的每日活动与中级威胁情报进行连接10 亿 IP10 万个块
将一个季度的防火墙和 VPN 日志与已知云提供商范围集合进行关联100 亿 IP100 万个块

一周的流量与更大型威胁情报进行连接100 亿 IP1000 万个块

结果表明，Databricks 的 IP 函数性能远强于竞争对手，即使在规模不断扩大的情况下也是如此。一旦探测数量超过 100 亿个 IP 地址且块数量超过 100 万个 CIDR，查询速度开始趋于平缓。

成本差距同样明显。即使工作负载规模扩大，Databricks 仍然便宜 2 倍到高达6.4 倍。

Stanby 很快就看到了直接在湖仓上运行其网络监控用例的价值，而不是在外部系统上运行：

“Databricks 的原生 IP 函数让我们能够直接在 SQL 中处理 IP 和 CIDR 数据。我们不再依赖脆弱的字符串解析或手动位运算逻辑。能够将 IP 数据的解析、验证和连接作为一等 SQL 操作，使这项工作对我们的团队来说更简单、更易维护。对于在湖仓上将网络和流量分析与其余数据一起运行而言，这是一种自然的契合。”——Stanby，数据工程负责人

最终，这些高性能的 IP 函数使得一整类网络工作负载可以直接构建在湖仓上。

这解锁了什么

借助快速、原生的 IP 函数，以前无法在湖仓上运行的整体工作负载现在可以迁移到湖仓上：

  • 大规模 CIDR 富化连接 - 在数秒内为每个事件打上 GeoIP、ASN、威胁情报或所有权元数据标签，从而使下游检测和调查查询能够针对富化后的数据运行。
  • 高吞吐量实时过滤 - “向我展示过去 24 小时内来自这个可疑 /16 的所有连接”变成了交互式查询，而不是批处理作业。
  • 统一 IPv4 和 IPv6 分析 - 混合协议表开箱即用，因此现代流量会被分析，而不是被丢弃。
  • CIDR 在 CIDR 中的匹配 - 以与 IP 在 CIDR 中相同的性能检查整个子网是否位于另一个子网内，用于网络拓扑和策略分析。
  • 一等 SQL 可访问性 - 分析师只需使用普通 SQL 即可获得 IP 过滤和连接，无需过程式代码或 UDF 库。

借助湖仓上原生支持的这些函数，这些网络工作负载与企业其余部分共享同一份受治理的数据副本——无需单独的专业系统来许可、保护和保持同步。

立即开始

原生 IP 函数现已可用 正式发布 于 Databricks Runtime 18.3 及更高版本。

请参阅 IP 函数参考文档以获取完整函数列表和签名。网络数据洪流一直是您最大的数据集之一——现在它终于可以存在于您其余分析所在的地方了。
