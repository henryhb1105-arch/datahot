从分析工程师到上下文工程师

dbt Labs 发文探讨企业 AI 部署从“为仪表盘建模数据”转向“为 Agent 建模上下文”。文章以自身为例，起初直接使用供应商 MCP 连接 Gong 等数据源，导致单次通话分析消耗高达 5 万 Token（约 0.25 美元），总数据量超 5 亿 Token。他们随后将原始数据摄入数仓并通过建模总结，以降低成本和掌控上下文层。

dbt Labs 近日发文指出，大多数企业在企业级 AI 部署中正在走捷径，并陷入数据团队早已熟悉的经典陷阱。所谓“捷径”，就是将 AI 直接接入供应商提供的 MCP（模型上下文协议），再连到源数据提供方。这种方式正在让企业付出高昂的 token 消耗、供应商 API 费用，并导致数据所有权和可移植性的缺失。

dbt Labs 自己最初也不例外。他们使用了供应商 MCP，直到发现这些隐性成本远超预期。他们意识到，将 AI 连接到数据的最高效、可扩展的方式，其实正是他们一直倡导的路线：将数据集中到数据仓库中，直接在数仓内工程化上下文。这让他们有机会掌控 AI 的上下文层，并扩展数据团队的职责边界。

故事始于 Claude 在组织内部推广。销售团队成为最高频的用户群之一，他们连接 Gong、Salesforce 等丰富上下文来源来剖析交易。当 GTM 团队提出客户洞察需求，希望防止流失并识别高价值客户时，dbt Labs 起初同意了，并允许他们通过原生 MCP 将 AI Agent 直接连接到 Gong 数据进行分析。

成本很快失控。数百名销售人员每天多次使用这些数据，分析单个通话最多消耗 50,000 个 token，相当于 AI 读取一次通话记录就要花费 0.25 美元。而他们可调用的 Gong 通话转录数据总量超过 5 亿 token。大量销售人员在一天中运行多次 Claude 会话，AI 总支出在规模效应下显著上升。

于是 dbt Labs 决定采取新方法：将原始 Gong 数据摄入数据仓库，并通过数据建模来总结每一通通话。这种方法把 AI 读取的原始内容转化为结构化、精炼的上下文，从而大幅降低 token 消耗，同时让数据团队重新掌握对数据资产的控制权。

这一转变标志着数据团队的角色正在从“为仪表盘建模”演进为“为 Agent 建模上下文”。dbt Labs 称其为从 analytics engineer 到 context engineer 的转变，并计划以此为开篇，系列探讨企业如何构建可扩展、可拥有的 AI 上下文层。
