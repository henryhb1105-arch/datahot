译文

AI 逐段翻译

实时事件管道很少能处理统一模式。无论是物联网指标、电子商务点击流还是金融定价向量，每种事件类型都有各自的模式。例如，股票交易和利率交易携带的字段几乎完全不同。摄取这些多模式流历来迫使人们做出次优的架构选择。你要么为每种事件类型构建单独的表，要么维护一个宽的 STRUCT，其中必须预先声明所有事件类型中的每个可能字段（读取快，但稀疏且僵化）。另一种选择是将所有内容扁平化为一个包含数百列笨拙的模式。为了避开这种维护负担，许多团队将事件转储到一个普通的 JSON 字符串列中，这带来了显著性能损失。查询单个嵌套字段需要你的引擎为每一行反序列化整个 JSON 大对象。在大规模情况下，你耗费计算和预算扫描数 TB 的原始文本以提取少量字节的数据。

另一个挑战是，这些管道通常需要混合处理速度。你需要一个实时路径（而非近实时）以亚秒级延迟标记异常或高风险事件，同时将这些相同的事件推送到分析存储中进行批量深度历史分析。

使用 AWS Glue 6.0，你可以通过单个管道解决所有这些挑战（模式异构性、JSON 扫描开销和混合延迟需求）。AWS Glue 6.0 基于 Apache Spark 4.1 和 Apache Iceberg v3 支持，将 Variant 列、Variant 碎片化、Spark 实时模式 (RTM) 以及 Arrow 原生用户定义函数 (UDF) 引入全托管无服务器环境中。

在本文中，我们将演示如何使用金融服务用例构建这种多层架构：处理交易定价向量的市场风险管道。虽然案例是金融领域，但该模式适用于任何涉及异构模式、昂贵 JSON 解析以及混合实时/批量需求的场景，例如物联网设备群、多租户 SaaS 平台、物流跟踪等。我们将展示如何以亚秒级延迟标记高风险交易、将所有内容以 Variant 形式流式传输到 Iceberg v3 数据湖，以及使用 Arrow 原生 UDF 高效地运行批量风险价值风险 (VaR) 计算。

解决方案概述

银行的市场风险团队从前台系统接收持续不断的交易定价向量流。每笔交易事件携带：

  1. 交易 ID 和账簿/交易台 ID。
  2. 定价向量为半结构化数据。模式因资产类别而异（例如，股票携带称为 Greeks 的风险敏感度，如 delta/gamma；外汇携带波动率表面；利率携带曲线敏感度）。
  3. 区域 ID 用于司法管辖区报告（使用 DEFAULT 值，因此省略它的行会自动填充）。

团队需要从该流中获得三样东西，每样速度不同。我们构建三层管道，每层通过 AWS Glue 6.0 专用能力满足不同需求。

第 1 层：实时交易头寸违规检测（亚秒级延迟）

头寸必须在亚秒级时间内更新，而非传统微批流式处理的秒级。对于监控头寸限额的团队来说，这些秒意味着交易可能在该系统响应前就打破限额。Spark 实时模式 (RTM) 完全消除了微批边界，让记录连续流过管道，从而高风险交易在到达亚秒级内触发警报。

第 2 层：近实时分析湖仓（秒级延迟）

每笔交易必须在几秒内落地到可查询的数据湖中，异构定价向量存储而无需预先声明固定模式。Iceberg v3 Variant 类型原生处理此需求。原始半结构化负载进入单一列，无论资产类别模式如何。写入时，Variant 碎片化自动将数据中观察到的字段提取到类型化 Parquet 列中，因此下游分析查询只读取所需列，无需反序列化完整大对象。交易修改和取消通过 删除向量（读时合并）以更低成本处理，列 DEFAULT 值减少摄取代码中的样板内容。

第 3 层：批量风险计算（分钟到小时级延迟）

风险指标（如风险价值 VaR）必须在 Python 中对数百万笔交易进行计算。传统上，Java 虚拟机 (JVM) 与 Python 之间逐行的 pickle 序列化是瓶颈。Arrow 原生 UDF 以向量化列式批次处理数据，消除序列化开销并加速基于 Python 的风险计算。

该解决方案使用三个独立的 AWS Glue 6.0 作业，每个作业可独立扩展：

  • 实时路径（Scala、gluestreaming）：从 Amazon MSK 读取交易，丰富风险评分和违规标志，并将警报写入下游 Kafka 主题。它使用固定工作线程常驻运行。下游欺诈检测和头寸限额系统消费告警主题以进行实时阻断决策。
  • 近实时路径（PySpark、gluestreaming）：从同一 MSK 主题读取并将完整交易历史落地到 Iceberg v3 表。它使用 Glue 自动扩展，可在批次之间缩减，保持较低成本。
  • 批量分析（PySpark、glueetl）：从 Iceberg v3 表读取，使用 variant_get 提取字段，计算组合 VaR，并将聚合风险报告写入下游汇总表。

先决条件

要遵循本文操作，您需要以下内容：

  1. 一个 AWS 账户，位于 AWS Glue 6.0 可用的区域。
  2. 一个 AWS Identity and Access Management (IAM) 角色，具有部署 AWS CloudFormation 堆栈和创建资源（包括 AWS Glue, Amazon MSK, AWS Lambda, Amazon Simple Storage Service (Amazon S3), 以及 AWS Glue Data Catalog。）

部署 CloudFormation 堆栈

我们提供一个 AWS CloudFormation 模板，用于预置本次演练所需的所有资源。

该堆栈预置以下资源：

  • 一个 Amazon MSK 集群，包含两个主题：trade-risk-vectors（输入）和 trade-alerts（实时警报输出）。
  • 一个 Amazon S3 存储桶，用于 Iceberg 表存储和流式检查点。
  • 一个 AWS Glue 数据库（risk_analytics_<account-id>_glue6b1）。
  • 一个 IAM 角色（GlueRole-<account-id>-glue6b1），具有 Glue、MSK、S3 和 CloudWatch 的权限。
  • 虚拟私有云（VPC）网络：一个 Glue 网络连接（connection-<account-id>-glue6b1）、S3 网关端点和 Glue 接口端点。
  • AWS Glue 作业 rtm-alerts-<account-id>-glue6b1（Scala）：此作业从 MSK 读取交易，使用 Spark RTM 实时进行风险评分，将警报写入 trade-alerts 主题。
  • AWS Glue 作业 nrt-ingestion-<account-id>-glue6b1（PySpark）：此作业从 MSK 读取交易，写入启用了 Variant + 分片功能的 Iceberg v3 表。
  • AWS Glue 作业 batch-var-<account-id>-glue6b1（PySpark）：此作业从 Iceberg v3 表读取数据，使用 Arrow UDF 计算 VaR，并演示删除向量。
  • AWS Glue 作业 producer-<account-id>-glue6b1-helper（PySpark）：此作业生成示例交易事件（股票、外汇、利率）到 trade-risk-vectors 主题。

部署 CloudFormation 堆栈：

  1. 从 GitHub 仓库下载 CloudFormation 模板。
  2. 登录到 AWS CloudFormation 控制台
  3. 选择 Create stack > With new resources > Upload a template file，并上传下载的模板。
  4. VpcId：您的 VPC ID。
  5. SubnetIds：至少两个位于不同可用区的子网。
  6. SecurityGroupId：一个专用安全组，允许来自自身的所有入站 TCP 流量（自引用规则）。
  7. RouteTableId：您的 VPC 的主路由表。

确认 IAM 功能，然后选择 Create stack。堆栈创建大约需要 20 分钟。

堆栈完成后，打开 AWS Glue 控制台，并按以下顺序启动作业：

  1. 启动 rtm-alerts-<account-id>-glue6b1 和 nrt-ingestion-<account-id>-glue6b1。
  2. 两者都显示 RUNNING 后，启动 producer-<account-id>-glue6b1-helper。
  3. 生成器完成后（约 3.5 分钟），运行 batch-var-<account-id>-glue6b1 进行风险聚合。

消费者必须在生成器启动前运行，以便交易能实时评分并在到达时落入 Iceberg 表。批处理作业最后运行，因为它读取的是近实时路径填充的 Iceberg 表。

了解 Iceberg v3 表设计

CloudFormation 堆栈预置的 Glue 作业将创建两张 Iceberg v3 表：trade_risk_vectors（主交易存储）和 daily_risk_summary（批量 VaR 输出），并使用新的数据类型和功能：

  1. VARIANT：存储半结构化的定价向量，无需固定 schema。
  2. DEFAULT 值：当未提供字段时自动应用给定的默认值。
  3. 删除向量（合并时读取）：支持快速的按行更新和删除。

在 AWS Glue 控制台中，打开 Data Catalog > Tables > trade_risk_vectors。

图 2：AWS Glue Data Catalog 中的 trade_risk_vectors 表

以下是 Create Table 命令：

CREATE TABLE {TABLE} (
    trade_id STRING, book_id STRING, desk STRING,
    asset_class STRING DEFAULT 'UNKNOWN',
    execution_time STRING,
    pricing_vector VARIANT,
    var_contribution DOUBLE DEFAULT 0.0,
    risk_weight DOUBLE DEFAULT 1.0,
    trade_date DATE, region STRING DEFAULT 'EMEA'
) USING iceberg
TBLPROPERTIES ('format-version'='3', 'write.delete.mode'='merge-on-read',
    'write.update.mode'='merge-on-read',
    'write.parquet.shred-variants'='true')
PARTITIONED BY (trade_date, asset_class)

注意对 DEFAULT值的使用，用于 asset_class, var_contribution, risk_weight 和 region。这是 Iceberg v3 的功能，在写入时未提供值时自动应用默认值，减少了摄取代码中的样板。 pricing_vector 列定义为 Variant 类型，而 write.parquet.shred-variants='true' 在写入时自动将 Variant 字段提取为单独的带类型 Parquet 列，以加快下游查询速度。

使用 Spark 实时模式摄取交易

传统的 Spark Structured Streaming 使用微批处理：收集记录、调度作业、处理、提交、等待。即使批处理很小，规划和调度的固定开销也会增加每批的明显延迟。对于监控仓位限额的风险团队，延迟可能在系统响应之前就导致交易突破限额。

以下Scala作业从Amazon MSK读取交易事件，根据事件中直接可用的数据应用轻量级风险规则，并将警报写入Kafka主题，所有操作都在亚秒级延迟内完成。实时路径刻意避免外部查询（市场数据、波动率曲面）以保持高速。完整的VaR计算稍后在批处理层执行，在那里延迟不那么关键。

您可以在AWS Glue控制台的rtm-alerts-<accountid>-glue6b1作业下查看完整作业代码。此外，所有脚本都可以在GitHub存储库中获取。

图5：Scala实时作业，对交易进行评分并写入警报

这是它与传统微批处理的区别所在：Trigger.RealTime("1 minute")记录在管道中连续流动。记录在到达的瞬间即被处理。1分钟参数控制Spark多久检查一次进度以进行恢复，而不是控制记录的处理频率。RTM在AWS Glue 6.0上目前支持Kafka源、无状态、Scala工作负载，使用固定worker（无自动扩缩）且仅支持更新输出模式。这使得它非常适合需要亚秒级延迟的无状态转换，例如这里展示的过滤、丰富、评分和路由模式。较重的计算（VaR、聚合）在微批处理/批处理层运行，在那里亚秒级延迟不那么关键。

实时路径充当断路器：名义金额超过5000万美元的交易被标记为CRITICAL，超过2500万美元的标记为HIGH。下游系统消费trade-alerts主题，并可以在下一笔交易执行之前阻止或升级。详细的VaR计算（需要市场数据、波动率曲面和完整的定价向量）在延迟不那么敏感的批量消费层中运行。

分片工作原理

在写入过程中，Spark会在写入时自动将其观察到的Variant字段提取到单独的Parquet类型列中，此功能称为分片（shredding）。在每次写入开始时，引擎会缓冲行样本（由write.parquet.variant-inference-buffer-size控制），推断出哪些字段及其类型，然后使用该模式对文件中的所有后续行进行分片。样本中观察到的每个字段都有自己的类型列，包括嵌套对象。缺少特定字段的行仅在该分片列中存储NULL。对于我们的风险表，诸如$.greeks.delta、$.dv01和$.model这样的字段都位于它们自己的Parquet类型列中，即使只有一种资产类别带有特定字段。结果是：查询性能更快，因为查询只访问它们需要的类型列，完全跳过文档的其余部分。分片对查询是透明的。variant_get()调用无论字段是否被分片都以相同方式工作。查询引擎在可用时自动路由到分片列，对于不属于推断模式的字段，回退到二进制Variant blob。

注意：分片会增加写入延迟，因为引擎必须推断模式并写入额外的类型列。在此流水线中，我们在近实时路径上启用分片并承担该成本，因为下游读取的好处（批处理VaR、即席查询、审计）远大于写入惩罚。对于写入路径上每毫秒都很重要的延迟敏感流水线，您可以在流式表上禁用分片，而是在单独的批处理作业中写入分片数据，该作业从非分片表读取并插入到分片副本中。这种方法以降低架构简单性为代价来降低摄取延迟。

图9：计算历史VaR的Arrow原生UDF

该@arrow_udf装饰器是Spark 4.1中的新特性。你的函数直接接收和返回pyarrow.Array，一次性操作整批行。没有pickle序列化，没有逐行调用，也没有Pandas转换。数据在JVM和Python之间以原生Arrow列式数组流动。对于跨数十万行的计算密集型操作（如VaR），这比传统的标量UDF要快得多。此外，你可以使用内置的UDF分析器来识别计算密集型UDF（如VaR计算）中的性能和内存瓶颈。

使用删除向量处理迟到的交易修正

在金融市场中，交易修正和取消很常见。批处理VaR作业在完成风险计算后演示了这一点。它修改了一笔交易并取消了另一笔。

图10：使用读时合并修改和取消交易

在Iceberg v3之前，行级删除要么需要重写整个数据文件（写时复制），要么需要维护单独的位置删除文件，这些文件以Parquet行的形式存储(file_path, row_position)对（读时合并）。这两种方法在大规模场景下成本很高。写时复制为单次修改重写数GB数据，而位置删除则随着删除文件的累积而降低读取性能（每次读取都必须解析所有删除记录并与数据文件进行哈希连接）。

由于我们配置表时使用了write.delete.mode='merge-on-read'，UPDATE和DELETE操作会写入删除向量，而不是Iceberg v2中使用的的位置删除文件。删除向量是存储在Puffin文件（.puffin）中的Roaring Bitmap，每个受影响的文件一个，标记哪些行位置被删除。读取时，引擎加载单个位图，并通过位检查跳过标记的位置。无需文件连接，也不需线性扫描多个删除文件。无论删除多少行，位图都很紧凑，并且随着修改累积，读取性能保持可预测。

批处理作业还验证了删除向量是否已创建。你可以在作业的输出日志中看到结果。

图11：验证创建了删除向量的输出

清理

为避免产生额外费用，请删除CloudFormation堆栈。这将移除本文中配置的所有资源，包括S3存储桶、Glue作业、Iceberg表、MSK集群和IAM角色。

结论

在本文中，我们使用AWS Glue 6.0构建了一个多层市场风险管道（实时警报、近实时摄取和批量分析）：

  • 实时路径上的Spark实时模式（RTM）提供亚秒级的交易评分和违规警报，消除了微批处理边界，从而在下一次交易执行前强制执行持仓限额。
  • 近实时路径上的Iceberg v3 Variant无需展平模式即可存储异构定价向量。一个表可处理股票、外汇和利率，每行有不同的模式。
  • Variant碎片化在写入时自动将字段提取到单独的Parquet类型列中，无需手动调整即可加速读取。
  • Arrow原生UDF消除了基于Python的风险计算的pickle序列化开销，在批处理层以向量化列批处理数据。
  • 删除向量使用紧凑的Roaring Bitmaps处理交易修改和取消，而无需昂贵的数据文件重写，避免累积位置删除文件。
  • 默认值减少了摄取代码中的样板代码。

要开始使用AWS Glue 6.0，请参阅AWS Glue文档。有关Apache Iceberg v3的更多信息，请参阅Iceberg规范。
