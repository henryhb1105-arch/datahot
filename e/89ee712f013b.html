pg_clickhouse 与 chdb 更新：编码、嵌套与类型

RSS ClickHouse Blog AI 逐段翻译 发布 2026-10-01 00:29
DataHot 速览

pg_clickhouse v0.11.0 和 chdb extension v0.1.2 发布，继续提升 ClickHouse 与 Postgres 之间的跨库兼容性，涉及字符编码、interval、嵌套数据、JSON 和类型映射。pg_clickhouse 新增 check_encoding 外部服务器选项，chdb_hook 也可在 COPY/CREATE TABLE 中设置，支持 fail/remove/replace/truncate 四种处理无效编码字节的方式。默认 fail 会报错，replace 在 UTF-8 下用 � 替换非法字节，其他编码则删除。更新来自官方博客与 GitHub/PGXN 发布。

为什么值得关注：面向 Postgres 与 ClickHouse 跨库查询和数据接入的工程实践，提供编码校验、类型映射和错误处理的可操作细节，对构建跨库数据链路的数据工程师有直接参考价值。

译文

AI 逐段翻译

现已在 GitHub 和 PGXN 上发布，pg_clickhouse v0.11.0 和 chdb 扩展 v0.1.2 延续了我们对跨数据库兼容性的执着关注。这些增强中有许多源自我们的仅头文件 C 库，clickhouse-c 和 pg-clickhouse-c。让我们来看看这些版本中仅有的三项更改。

真是个字符

首先是字符编码。在为 chdb 扩展文章开发基准测试的过程中，我发现 pg-clickhouse-c 没有验证文本列的字符编码。我的同事 Philip 迅速修补了该库，使其在任何基于文本或 json 的1 类型包含违反数据库编码的字节时抛出异常。

此修复已在 chdb v0.1.1 中发布，但我们推迟了 pg_clickhouse 一段时间，以避免对任何拥有读取无效编码数据的现有外部表的人造成错误。pg_clickhouse v0.11.0 新增了一个 外部服务器 选项，check_encoding，它提供编码错误处理器。选项包括：

  • fail（默认）：抛出错误
  • remove：移除无效字节
  • replace：在 UTF-8 编码下，将无效字节替换为 Unicode 替换字符（�）；对于其他编码与 remove 相同
  • truncate：在第一个无效字节处截断文本

chdb_hook v0.1.2 为其 COPY 和 CREATE TABLE 命令提供相同的选项。两者都允许你处理类似以下的错误：

1ERROR:  invalid byte sequence for encoding "UTF8": 0x81

更改 pg_clickhouse 服务器配置中的 check_encoding 以消除错误。最易读的将是 replace：

1ALTER SERVER ch_server_name OPTIONS (ADD check_encoding 'replace');

对于 chdb_hook，将其作为 COPY 或 CREATE TABLE 选项传入：

1CREATE TABLE logs () WITH (2    copy_from      ='s3://chdb-lakedata-public/logs/logs-2026-08-26.csv',3    format         ='CSVWithNames',4    check_encoding ='replace'5);

对于 UTF-8 编码的数据库，无效字节将被替换为 �，

1try=# SELECT * FROM ch_table ORDER BY id;2id |   name3----+---------4  1 | Barrack5  2 | Ale�y6  3 | Leopold7  4 | An�n�e

对于其他数据库编码，有问题的字符将直接被移除：

1try=# SELECT * FROM ch_table ORDER BY id;2id |   name3----+---------4  1 | Barrack5  2 | Aley6  3 | Leopold7  4 | Ann

另一方面，如果你需要保留字节兼容性，则需要将有问题的列映射到 bytea，改为：

1ALTERFOREIGNTABLE ch_table ALTER name TYPE bytea;

这将保留逐字节的二进制数据：

1try=# SELECT * FROM ch_table ORDER BY id;2id |      name3----+------------------4  1 | \x4261727261636b5  2 | \x416c6500796  3 | \x4c656f706f6c647  4 | \x416e006e81658(4 rows)

但请注意，转换为文本将会失败。

间隔有效

ClickHouse 支持种类繁多的 间隔类型：IntervalNanosecond、IntervalHour、IntervalDay、IntervalYear，以及介于其间的所有类型。在之前的版本中，pg_clickhouse 不支持这些类型；尝试 导入 使用其中之一的 ClickHouse 表会返回错误。

不再如此。pg_clickhouse v0.11.0 和 chdb_hook 0.1.2 将这些类型导入为 Postgres interval 列。因此，给定一个使用例如 IntervalMillisecond 的 ClickHouse 表，如这里的 duration 列：

1CREATE TABLE logs (2    req_id    Int64                NOT NULL,3    start_at  DateTime64(6, 'UTC') NOT NULL,4    duration  IntervalMillisecond  NOT NULL,5    resource  Text                 NOT NULL,6method    Enum8('GET'=1, 'HEAD', 'POST', 'PUT', 'DELETE', 'PATCH') NOT NULL,7    node_id   Int64                NOT NULL,8    response  Int32                NOT NULL9) ENGINE = MergeTree10ORDERBY start_at;

在导入时，pg_clickhouse 创建一个具有 duration interval 列的表：

列类型可空
req_idbigintnot null
start_attimestamp(6) with time zonenot null
durationintervalnot null
resourcetextnot null
methodtextnot null
node_idbigintnot null
responseintegernot null

当然，下推也适用。假设你想统计所有在昨天结束前 完成 的事务。只需将持续时间加到开始时间上：

1try=# EXPLAIN (VERBOSE, COSTS OFF)2 SELECT COUNT(*)3   FROM logs4  WHERE start_at + duration < date_trunc('day', now());5                                                QUERY PLAN6-----------------------------------------------------------------------------------------------------------7 Foreign Scan8   Output: (count(*))9   Relations: Aggregate on (logs)10   Remote SQL: SELECT count(*) FROM "default".logs WHERE (((start_at + duration) < toStartOfDay(now64())))11(4 rows)

该 EXPLAIN (VERBOSE) 输出显示了在 ClickHouse 上执行的远程查询，它显然下推了 start_at + duration 以在 ClickHouse 中执行（当然，连同 COUNT() 聚合2）。

相同的模式适用于 chdb_hook v0.1.2：它将 chDB 的 间隔类型 导入为 Postgres interval 值。两个扩展也都允许将间隔类型导入为 bigint，改为只需创建具有 duration bigint 的外部表或复制目标表，扩展将完成其余工作。

嵌套本能

pg_clickhouse http 驱动程序自 v0.1 起就支持 JSON 类型，二进制驱动程序自 v0.3 起也支持。然而，尽管它会下推 JSON 属性访问器，例如，

1SELECT*FROM things ORDERBY data ->>'name';

ClickHouse 会返回错误：

1DB::Exception: Data types Variant/Dynamic are not allowed in ORDER BY keys, because it can lead to unexpected results.2Consider using a subcolumn with a specific data type instead

此错误源于 ClickHouse JSON 对象的实现：ClickHouse 想要知道 JSON 属性存在以便排序。ClickHouse 25.3+ 参数化子列确保属性存在。例如：

1CREATE TABLE things (2    id    Int32 NOT NULL,3    data  JSON(4      id      UInt32,5      name    String,6      size    Enum('small', 'medium', 'large'),7      stocked Bool8    ) NOT NULL9) ENGINE = MergeTree PARTITIONBY id ORDERBY (id);

以前，pg_clickhouse 无法导入参数化 JSON 列，但 v0.11.0（以及 chdb_hook v0.1.2）简单地将其映射为 jsonb（或 json），现在对属性进行 ORDER BY 可以正确地下推：

1try=# SELECT * FROM things ORDER BY data ->> 'name';2id |                              data3----+-----------------------------------------------------------------4  4 | {"id": 4, "name": "doodad", "size": "large", "stocked": false}5  3 | {"id": 3, "name": "gizmo", "size": "medium", "stocked": true}6  2 | {"id": 2, "name": "sprocket", "size": "small", "stocked": true}7  1 | {"id": 1, "name": "widget", "size": "large", "stocked": true}8(4 rows)

类似地，pg_clickhouse v0.11.0 和 chdb_hook v0.1.2 改进了对未展平的 Nested 类型 的支持，如本示例所示：

1CREATE TABLE visits(2    visit_id  UInt64,3    user_id   UInt64,4    goals     Nested(5        serial    UInt32,6        order_id  String7    )8) ENGINE = MergeTree ORDERBY visit_id SETTINGS flatten_nested =0;

该 flatten_nested=0 指示 ClickHouse 创建一个单一的 goals 列，格式为 Tuple(serial UInt32, order_id String) 的数组（而不是为每个字段单独创建数组列）。以前，两个扩展都不支持此结构。现在它们提供两种映射。

默认情况下，IMPORT FOREIGN SCHEMA 和 chdb_hook 的 COPY 和 CREATE TABLE 命令将未展平的 Nested 列映射为二维文本数组：

列类型
visit_idnumeric(20,0)
user_idnumeric(20,0)
goalstext[][]

这将 Nested 值中的每一项映射为每种类型的文本表示的数组：

1try=# SELECT * FROM nest_bin.visits WHERE visit_id < 3 ORDER BY visit_id;2 visit_id | user_id |      goals      3----------+---------+-----------------4        1 |       1 | {{1,xx},{2,yy}}5(1 row)

该 goals 数组包含两个数组，每个数组有两个文本值，第一个用于 serial，第二个用于 order_id。此结构以牺牲数据类型为代价保留了数据，尽管对 pg_clickhouse 表的 INSERT 会在插入 ClickHouse 之前正确转换类型：

1INSERT INTO visits2VALUES (2, 2, ARRAY[ ['3', 'aa'], ['4', 'bb'] ]);

但我们可以做得更好。pg_clickhouse v0.11.0 还允许将 Nested 值映射到自定义 复合类型，只要顺序、类型和命名完全一致。给定为 goals 定义的 Nested 类型：

1Tuple(serial UInt32, order_id String)

我们可以创建一个具有对应名称和类型的类型，并将其插入外部表：

1CREATE TYPE goal_type AS (serial bigint, order_id text);2ALTERFOREIGNTABLE visits ALTER goals TYPE goal_type[];

现在 Nested 元组转换为复合类型：

1try=# SELECT * FROM nest_bin.visits WHERE visit_id < 3 ORDER BY visit_id;2 visit_id | user_id |        goals        3----------+---------+---------------------4        1 |       1 | {"(1,xx)","(2,yy)"}5        2 |       2 | {"(3,aa)","(4,bb)"}

当然，我们也可以按此格式 INSERT 数据：

1INSERT INTO visits2VALUES (3, 3, ARRAY[row(5, 'jj'), row(6, 'zz')]::goal_type[]);

相同的模式适用于 chdb_hook v0.1.2：在处理从 ClickHouse 或 chDB 导出的嵌套数据时，Postgres 目标表可以使用多维值数组或适当结构化的复合类型数组：

1CREATE TYPE event_status AS ENUM ('new', 'done');2CREATE TYPE event_point AS (x integer, y integer);3CREATE TYPE event_label AS (key text, valuebigint);4CREATE TYPE event_item AS (id integer, name text);56CREATE TABLE events (7    status event_status,8    point  event_point,9    labels event_label[],10    items  event_item[]11);

然后使用 COPY 查询中相应的数据类型定义（或依赖 *WithNamesAndTypes 格式之一）来导入数据。

1COPY events FROM's3://chdb-lakedata-public/examples/events.parquet' (2    structure $$3        status Enum8('new'=1, 'done'=2),4        point  Tuple(Int32, Int32),5        labels Map(String, Int64),6        items  Array(Tuple(id Int32, name String))7    $$8);

这里我们为嵌套类型使用了 Array()；如果数据是从 ClickHouse 以未展平（flatten_nested=0）结构导出的，你可以改用 Nested，改为：

1COPY events FROM's3://chdb-lakedata-public/examples/events.parquet' (2    structure $$3        status Enum8('new'=1, 'done'=2),4        point  Tuple(Int32, Int32),5        labels Map(String, Int64),6        items  Nested(id Int32, name String)7    $$8);

  • 正如眼尖的读者无疑已经注意到的，除了 interval 映射 之外，大整数类型现在映射到适当的 Postgres numeric 类型，还有许多其他 ClickHouse 数据类型现在映射到适当的 Postgres 对应类型： 相同的映射也适用于 chdb 扩展 v0.1.2。
  • 原始的 clickhouse_raw_query() 函数已在 v0.10.0 中弃用，现已被移除。请更新你的代码，使用 clickhouse_query(server, sql) 来读取行，并使用 CALL clickhouse_perform(server, sql) 来运行不返回任何内容的语句。
  • 此版本放弃了对 PostgreSQL 13 的支持，Postgres 社区自 2025 年 9 月起已不再支持该版本。
  • 一项 社区贡献为 PostgreSQL 的 sha224()、sha256()、sha384() 和 sha512() 函数添加了下推，以及对 pgcrypto 扩展的 digest() 函数的受支持常量算法调用的下推。
