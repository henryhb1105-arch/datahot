DataHot 速览

ClickHouse Cloud 运行在 AWS、GCP、Azure 上数千个 Kubernetes 节点，许多节点故障（如 NVMe 磁盘损坏、内核卡死、网络半失效）表面上仍显示 Ready，导致副本写缓存失败或查询超时。团队因此启动 Compute Layer Reliability 项目，自行掌控节点的检测与处置。方案由三部分组成：Node Problem Detector 作为传感器，将内核与系统日志及主动探测转为节点 Condition；Node Problem Mitigator 作为执行器，按 taint、drain、terminate 的顺序受控摘除节点；Node Debug Collector 在节点失联前抓取日志与系统状态用于取证。起因是一起 EC2 上 RAID 阵列单盘故障导致缓存盘持续写失败的线上事故。

为什么值得关注：这是一线云数仓厂商公开的基础设施可靠性工程实践，讲清了故障检测、受控摘除和现场取证的完整机制与边界，对构建数据平台运维体系有直接借鉴价值。

AI 逐段翻译

ClickHouse Cloud 运行在 AWS、GCP 和 Azure 上数千个 Kubernetes 节点上。在这种规模下，磁盘损坏、内核任务卡死或网络半可用的节点是每天都会发生的事。这些故障大多一开始看起来并不像节点故障。Kubernetes 仍将节点报告为 Ready。云服务商控制台显示实例正在运行。而你实际看到的是：某个 ClickHouse 副本无法写入其缓存磁盘，某个 Pod 一直停留在 ContainerCreating，或者某个查询在一个副本上超时而在其他副本上正常。

虽然云服务提供商（CSP）有时会尝试检测并修复这些问题，但他们并不能 100% 成功。此外，“修复”行为在不同云服务商之间有所不同，而且并不总是针对特定问题的最优解决方案。我们希望在各 CSP 之间拥有更多控制权和一致性。因此，我们启动了一个名为 Compute Layer Reliability 的项目。

本文解释了我们研究各云上节点健康处理方式时的发现、为什么决定自己掌控检测和响应，以及我们为实施它而构建或采用的三个组件：

  • Node Problem Detector（NPD），即传感器。云原生组件按我们的需求采用。它在每个节点上运行，将内核和系统日志行以及少量主动探测转化为 Kubernetes 节点 Condition 和 Event。
  • Node Problem Mitigator（NPM），即执行器。它是一个控制器，监视这些 condition 并以受控方式将节点移出服务：taint、drain，然后终止实例。
  • Node Debug Collector（NDC），即取证工具。它在节点消失之前从节点捕获日志和系统状态，即使节点已不可达。

我们为什么开始、学到了什么，以及我们决定了什么

引发这一切的事件

我们发现一个 EC2 节点上，软件 RAID 阵列后面的两块 NVMe 驱动器之一已故障。内核记录了 raid0 array has a missing/failed member，随后是一连串的 EXT4 错误和缓存文件系统上的 I/O 错误。该节点上的 ClickHouse Pod 长时间写入失败。没有数据丢失，但系统处于降级状态，值班操作员花了大量时间试图找出根本原因。

没有人因为节点本身不健康而被传呼。Kubernetes Node 对象一直处于 Ready 状态。云服务商也没有标记该实例。故障唯一可见的地方是 VM 本身的内核环形缓冲区。

该集群上确实运行着 Node Problem Detector。NPD 是用于这项工作的标准 Kubernetes 工具：一个 DaemonSet，跟踪内核和系统日志，将其与规则匹配，并在 Node 对象上报告问题。当我们检查其日志时，它已匹配到 EXT4 错误。但上游的 EXT4 错误规则被标记为“临时”。临时规则会产生一个 Kubernetes Event，该 Event 在一小时后过期。它不会设置 Node condition，我们的技术栈中也没有任何东西对其做出反应。

还有其他情况，仅仅 drain 节点就解决了各种问题。每一次都是人工通过阅读日志发现问题，而每一次的修复方式都相同。

Kubernetes 提供了什么，以及它在哪里止步

Kubernetes 内置了 Node condition：Ready、MemoryPressure、DiskPressure、PIDPressure 和 NetworkUnavailable。kubelet 设置它们，Kubernetes 内置控制器对它们做出反应。当 Ready 变为 false 时，节点会被加上 taint，Pod 会从该节点上被驱逐。

这些 condition 覆盖的是 kubelet 自身对节点的视图。它们不覆盖降级的 RAID 阵列、变为只读的文件系统、卡在挂起内核任务上的容器运行时，以及许多其他故障模式——在这些情况下，kubelet 持续报告 Ready，而 VM 已经降级。

Kubernetes v1.37 附带了对 Lifecycle Conditions 的支持，这在一定程度上改善了对节点状态的监控和对 drain 过程的控制。我们启动项目时这还不可用，而且至今仍不够成熟，无法用于生产环境。

项目开始前各云为我们如何处理这一问题

我们在三个云上运行着一个机群，每个云都有不同的答案。我们对每个云进行了广泛研究，并从某些云服务商随附的内置 VM 代理中提取了实际运行配置。以下是我们发现的情况。

在 AWS 上，我们有意禁用了节点自动修复，因为我们看到磁盘碎片启发式规则不断将节点标记为不健康的情况。自动修复行为还会影响卷如何挂载和卸载到节点。简单地将 Pod 从不健康节点上驱逐比等待自动修复完成更快。在大多数情况下，自动修复是就地重启节点，这意味着运行中的容器会短时间宕机。重启后的节点经常会再次出现同样的问题。

在 GCP 上，服务商在每个节点上部署了自己的 NPD，带有一长串检查，包括若干自定义插件。自动修复因类似原因被禁用。内置 NPD 检查未覆盖我们所关心的重要信号。

在 Azure 上，服务商还以主机进程方式运行 NPD，同样带有很多检查。Azure 没有内置机制对 NPD 发布的 condition 采取行动。无法控制这些 VM 的自动修复机制。对于 Azure 检测到的问题，VM 可以被 重启、重新镜像或重新部署。这意味着该过程结束后仍可能带回之前的问题，而且它仍未覆盖我们所关心的信号。

决定

我们决定选择自己的道路：在全部 3 个云服务商上实现一致的检测、响应和调试信息收集。

  1. 自主掌控 检测。我们在三个云上都运行自己的 node-problem-detector NPD 配置。我们根据实际见过的故障自行编写检查。伤害过我们的故障会成为永久 condition，而不是一小时后过期的 event。
  2. 自主掌控 响应。我们不会尝试就地修复节点。报告硬件或内核问题的节点会被退出服务，在健康节点上重新调度工作负载。我们编写了一个控制器，node-problem-mitigator（NPM），它监视 NPD 发布的条件，并对每个条件应用一个配置好的响应，从仅观察一直到终止实例。
  3. 保留 证据。在这个项目之前，从不健康节点收集诊断信息是一场与 drain 过程赛跑的手动操作，而且节点往往已经不再响应。运维人员必须记住针对不同 CSP 的不同步骤，并执行相同的命令序列，将收集到的数据上传到共享存储以供分析。我们创建了 node-debug-collector 来解决这些问题。

节点问题检测器：向 Kubernetes 暴露不健康节点

Kubernetes 无法看到节点内部

如上所述，某些节点故障永远不会传到 Kubernetes。内核软锁定或 NVMe 缓存磁盘挂载失败会让节点保持 Ready 状态，同时影响工作负载。我们需要节点内部的传感器，将这些故障转化为 Kubernetes 能够理解的信号。我们选择了上游的 Node Problem Detector（NPD），而不是编写我们自己的代理。它是一个小型 DaemonSet，正在积极维护，并且会发出标准的 Node Conditions 和 Events。我们原样部署上游镜像。我们添加的一切都是配置，因此我们跨三个云的所有集群都使用同一份检查目录运行相同的检测器，添加或调整检查只是配置变更和一次滚动发布。

从内部进行监控

NPD 自带多种监控器类型。我们使用其中两种。

日志监控器：NPD 会跟踪内核环形缓冲区或某个 journald 单元，并用正则规则匹配每一行。它们成本低廉，能覆盖任何在日志中留下痕迹的情况。下面这条规则可以捕获 ext4 文件系统上的错误：

1{2"type":"permanent",3"condition":"Ext4Error",4"reason":"Ext4HasError",5"pattern":"EXT4-fs error .*"6}

日志监控器的主要缺点是其粘性：匹配到日志模式后，产生的 Node Condition 会无限期保持活跃。自定义插件监控器会反复运行检查，并根据最新结果更新条件。

自定义插件监控器：按计划运行脚本并读取其退出码和 stdout。当日志中没有任何内容或一行日志不够时，我们会使用它们。一个例子是 NVMe 超时检查，它仅在至少两个设备在同一分钟内超时时触发，因为单个设备超时通常是可自愈的短暂异常，而两个几乎总是意味着主机侧的故障。另一个例子是一个检查本地 NVMe 磁盘是否正确挂载的脚本。

无论采用哪种检测方法，在我们的设置中检测到的每个问题都会成为发布在 Node 对象上的 Condition。这让我们能够了解节点问题并对其采取行动。

更少的误报胜过更快的检测

很大一部分工作投入到了调查生产中的节点问题，将每个问题转化为一项检测，然后进行调整以避免误报。迁移客户工作负载成本高昂且可能造成一定干扰，因此每项检查都需要表明节点本身存在问题，而不仅仅是某一个 pod 或一次短暂故障。我们还要避免对集群范围的问题采取行动，比如错误的网络策略或 CNI 配置错误，因为迁移工作负载无法修复这些问题，反而可能使影响更严重。

正因如此，上述 NVMe 超时检查会对受影响的设备进行计数。网络检查是一个很好的监控信号，但我们不会对它进行缓解：区域范围的故障会让每个节点都未通过相同的探测，而迁移 pod 也无济于事。pod 创建检查会忽略启动后的最初几分钟，此时节点 CSI/CNI 仍在初始化，失败是正常的。意外情况会由常规值班流程进行调查和处理。

同一组检查部署在每个云上。GCP 和 AKS 会部署它们自己的 NPD 守护进程，并且无法禁用它们。如果某个提供商托管的 NPD 已经报告了某个条件，我们会关闭自己的检查，而不是将同一个问题报告两次。

节点问题缓解器：不是包管理器

缓解问题

能力越大责任越大，这意味着没有现有工具愿意为杀掉错误节点承担责任。因此，它们对于我们的目的来说往往形同虚设：当我们确信节点有问题时，我们需要它消失。考虑到这一点，终止任务变得相当抗拒被“行业标准化”：不存在放之四海而皆准的解决方案。问题不在于现有工具不够复杂，而在于“终止阈值”可能因以下因素而大不相同：

  • 工作负载类型（有状态/无状态）
  • 集群中运行的软件的成熟度（PDB、SIGTERM 纪律、超时保证等）
  • 组织中的开发者文化 / 集群运维人员的 YOLO 程度

在决定行动方案之前，我们考察了现有的开源控制器：

  • Medik8s node-healthcheck-operator 和 self-node-remediation。功能强大，但需要安装和配置 CustomResources。从一行内核日志到被 drain 的节点，这条链路要经过 NPD、一个 condition、一个 operator、一个自定义资源以及第二个 DaemonSet。对于我们所需而言，活动部件太多，同时又无法在需要时轻松实现自定义逻辑。
  • Draino。已被废弃，最后一次提交大约在六年前。只执行 drain。
  • Cluster API MachineHealthChecks。相对于问题本身，这是一次大得多的架构变更。
  • 新的上游 node-readiness-controller 与 descheduler 相结合。零自定义代码，并且复用了我们已经在运行的组件。但耦合是松散的：如果 descheduler 配置错误，节点会被打上污点并且永远不会被 drain。它也没有让我们控制后续步骤，例如终止实例。此外，Node Readiness Controller 本身在我们启动项目时还不成熟。
  • Karpenter 自带的节点自动修复我们不在 GCP 和 Azure 集群中运行 Karpenter。该功能本身依赖于 AWS 节点代理，不允许跨云一致性。

我们自己的 NPM

因此我们构建了自己的控制器，其使命很简单：以期望的激进程度杀死坏节点。该控制器只销毁/移除节点，从不判断节点是好是坏；这项任务被委托给 node-problem-detector。

控制器监视节点的状态和状况，每个状况都配置了缓解节点的步骤（从最不激进到最激进）：

  • 评估：试运行以监控情况
  • 排空：在遵守 PDB 的前提下优雅地移除 Pod
  • 终止：排空（带超时），然后终止实例/VM。

这些步骤可以在持续缓解过程中被更改（如果另一个带有更激进步骤的状况被触发），但方向只有一个：朝着更激进的步骤。无论选择何种步骤，都可以先通过预缓解 Job 收集节点调试信息（参见下一节关于 NDC 的内容）。调试包收集默认是尽力而为的；它不会阻塞缓解操作，以确保我们尽快摆脱不健康的节点。

安全性 当你将这样的东西部署到生产集群时，首先想到的是“万一呢？”万一它开始一次删除太多节点怎么办？万一有些工作负载我们希望人工验证后再杀死怎么办？Node-problem-mitigator 使用各种安全门来降低缓解风险：

  • 终止开关：停止任何控制器活动的 ConfigMap 值
  • 试运行/评估模式：预览将要执行的缓解操作而不实际执行它们
  • 排除项：工作负载的命名空间、节点污点、注解和标签；我们可以过滤并跳过这些节点
  • 全局节点缓解冷却时间：节点可以被多快缓解。例如，可以配置为每 15 分钟最多缓解一个节点（每个集群）。
  • 暴露各种指标，并对卡住的缓解、异常高的缓解数量等进行告警。

推出

推出这样一个“危险”的工具是一项重大责任。幸运的是，我们团队足够勇敢，一步一步地承担了下来：

  • 从评估状况及其模式开始。用传感器和告警充分覆盖该过程；起初手动监控仪表板。
  • 对于我们确信的状况，逐步配置更激进的缓解措施。
  • 从开发环境和预发布环境开始，并使其领先生产环境一步。
  • 保持配置粒度细致；有些状况比其他状况风险更高。

Node-problem-mitigator 是开源的，欢迎贡献： https://github.com/ClickHouse/node-problem-mitigator

节点调试收集器：从节点获取证据

当我们检测到可疑节点时，我们想做的第一件事就是从它那里获取一些遥测数据：日志、指标、系统状态等。当节点被删除时，我们会丢失可能有用的诊断信息。如果能在替换坏节点之前就获得它的调试包，岂不是很好？

不同的云服务提供商有不同的调试包收集方法（EC2RL、AKS periscope），但它们都是云特定的，并且大多为其支持量身定制。调试收集变得很麻烦：不同云有不同的授权和收集方法，以及将节点与其云实例表示进行匹配。这是相当多的工作，尤其是在事件期间。

在我们支持的三个 CSP 中，GCP 使用的是最符合我们要求的工具：sosreport。它高度模块化、开源且云无关。实际上，它的插件数量巨大，我们不得不筛选所有支持的收集器，并将包精简为仅包含与我们集群相关的收集器。

很好，我们有了收集器。现在唯一剩下的就是将其交付到坏节点、运行它并收集结果。事实证明，这实际上是调试收集中更困难的部分：由于我们使用 3 个不同的云提供商，再加上节点是坏的，交付和执行可能是一个挑战。坏节点可能坏到无法正常发出遥测数据或响应遥测收集，或者可能完全无响应。

我们对这个问题的处理方式：

  • 尝试使用 kubectl cp 和 kubectl run。
  • 如果 kubelet 已死，则回退到 SSM/S3 作为传输方式（以及它们在 GCP/Azure 中的等效方式）。
  • 可选地，以 快照 模式运行：离线收集调试信息。通过快照克隆根卷，创建临时实例/VM，挂载根卷，并收集任何可离线获取的内容。

快照模式也可用于“脆弱”节点：即我们对收集器本身引入的最小影响有所担忧的节点。

该工具可供开发者使用，也可由 node-problem-mitigator 自动触发。在两种情况下，CSP 特定细节都被安全地抽象掉，因此可以通过单个命令执行收集，云特定细节将从 ProviderID 等节点属性中推断出来。为了遵守我们的数据隐私政策，不会从节点转储任何敏感数据。

结论

自 NPD+NPM+NDC 系统推出以来，我们每月都在修复大量不健康的节点。对这些问题的可见性得到改善，使我们能够发现新的故障模式，并在 VM 配置变更部署到生产环境之前对其进行验证。我们会自动收集诊断信息，并可以无延迟地将其提供给 CSP 支持。

与任何其他“可靠性改进”一样，它也有代价：系统复杂度的增加。新的自动化会引入新的故障模式，而我们一直在努力确保理解并准备好应对这些新挑战。检测规则过于宽泛可能会在不解决问题的情况下耗尽健康节点；缓解器缺陷可能一次耗尽过多节点，或者反过来，在不采取行动的情况下抑制错误。我们接受这种权衡，因为安全门（终止开关、试运行、速率限制和排除项）会将每一种故障模式转变为有界且可观测的事件，也因为一个在三个云上以相同方式运行的控制器比三个我们无法完全控制的特定于提供商的修复机制更容易推理。

值得注意的是，该系统不会对外部关于虚拟机问题的信号做出反应。AWS 发布 EC2 实例的状态检查，GCP 有 屏蔽节点的完整性监控，而 Azure 发布关于自动修复节点失败尝试的 Kubernetes 事件。你也可以希望对那些看起来完全无响应的节点采取行动，以至于 NPD 因为无法获得 CPU 或网络资源份额而不会发布任何 Conditions。我们将在未来的文章中涵盖这些情况的处理。
