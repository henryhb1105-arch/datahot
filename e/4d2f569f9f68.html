PostgreSQL 19 监控与可观测性新特性概览

DataHot 速览

PostgreSQL 19 即将发布，默认开启 log_lock_waits，锁等待超过 1 秒即记录日志，方便发现锁竞争。log_min_messages 支持按进程类型分别设置日志详细级别，例如可单独为 checkpointer 开启 DEBUG2、为 autovacuum 开启 DEBUG1。这些改进降低了数据库监控和问题排查的门槛。

为什么值得关注：数据库可观测性是数据平台运维的关键，PostgreSQL 19 的监控增强能帮助从业者更高效地定位锁等待和日志问题。

译文

AI 逐段翻译

PostgreSQL 19 即将到来，我将在即将举行的 PostgreSQL 欧洲会议 上谈论可观测性改进。我还作为 社区活动日 的一部分共同组织了 PostgreSQL 可观测性峰会，该活动在会议的最后一天，即 10 月 23 日星期五举行。所以，我认为这是整理思绪的好时机，写一篇博客文章。

免责声明： 在我撰写本文时，PostgreSQL 19 仍处于测试阶段，因此以下一些细节可能在最终版本发布前发生变化。发布说明 将是 19.0 正式发布后的最终定论。

话不多说，让我们看看 PostgreSQL 19 中我认为最有用和最有趣的监控和可观测性改进。

锁争用现在默认可见

log_lock_waits 控制当会话等待超过 deadlock_timeout（默认 1 秒）获取锁时是否记录消息。检查死锁相对昂贵，因此建议设置一个等待时间，然后再进行该检查，理想情况下应长于您的常规事务时间。这就是 deadlock_timeout 和 log_lock_waits 之间的关系（Robert Haas 甚至 建议 将两者分开）。简而言之，启用 log_lock_waits 为 Postgres 提供了一个廉价的锁争用检测器，但直到现在它默认是关闭的。

PostgreSQL 19 将默认值翻转为 开启（提交 2aac62be8，Laurenz Albe）。我喜欢提交消息中的推理：

如果有人被锁阻塞超过一秒钟，这几乎总是一个值得记录日志的问题。

每个进程类型的不同日志详细程度

log_min_messages 一直是一个单一的全局旋钮。如果您想要 DEBUG2 输出来自检查点进程，您会从所有内容获得 DEBUG2 输出，祝您找到您关心的那一行。

从 PostgreSQL 19 开始，log_min_messages 接受逗号分隔的 进程类型:级别 对列表，外加一个适用于未列出所有进程类型的必需级别。裸级别仍然有效，因此旧语法继续工作。

1-- DEBUG2 for the checkpointer, DEBUG1 for autovacuum, WARNING for everything else2ALTERSYSTEMSET log_min_messages ='warning, checkpointer:debug2, autovacuum:debug1';

识别出的进程类型是 archiver、autovacuum、backend、bgworker、bgwriter、checkpointer、checksums、ioworker、postmaster、slotsyncworker、startup、syslogger、walreceiver、walsender、walsummarizer 和 walwriter。请注意，autovacuum 涵盖启动器和工作者。

autoanalyze 的单独日志记录

到目前为止，log_autovacuum_min_duration 控制 autovacuum 执行的 VACUUM 和 ANALYZE 的日志输出。这些是非常不同的操作：autoanalyze 运行通常短得多，因此针对捕获慢 VACUUM 而调整的阈值会静默丢弃几乎所有 ANALYZE 活动。

PostgreSQL 19 添加了 log_autoanalyze_min_duration，它控制 ANALYZE 的日志输出。log_autovacuum_min_duration 现在只控制 VACUUM 日志记录。两者默认值为 10分钟，接受 0（记录所有内容）和 -1（禁用）。您还可以设置每表覆盖：

1-- For this table log every autoanalyze, regardless of the global setting2ALTER TABLE events SET (log_autoanalyze_min_duration =0);

升级说明： 如果您的工具解析 autovacuum 日志，请记住升级后 log_autovacuum_min_duration 单独不再报告 analyze 运行。如果您在界面中显示日志参数，请考虑使 log_autoanalyze_min_duration 也可见。

WAL 整页写入字节到 VACUUM 和 ANALYZE 日志记录

整页映像通常是 WAL 量的主要部分，VACUUM 产生大量整页映像。如果您不熟悉原因，我将尝试解释一下。检查点后第一次修改页面时，Postgres 将整个 8kB 页面写入 WAL，而不是仅写入小的更改，这样崩溃恢复就永远不必信任磁盘上可能损坏的页面。这意味着，如果碰巧是自上次检查点以来对该页面的首次触碰，对 50 字节行的一次微小更新可以产生约 8kB 的 WAL。VACUUM 爬行并弄脏许多冷页面，因此会触发大量此类事件，这就是为什么清理大且冷的表可能产生比实际更改的数据量多得多的 WAL。

Postgres 报告整页映像计数（wal_fpi）但不报告其大小，因此如果您想要实际字节数，您必须通过 pg_waldump 或 pg_walinspect 深入挖掘 WAL。

PostgreSQL 19 添加了一个新的 wal_fpi_bytes 计数器，由 Shinya Kato 的一系列补丁添加。您可以在集群范围的 pg_stat_wal（您的指标收集器轮询的内容）中看到它，通过 pg_stat_get_backend_wal() 按会话查看（当您想知道哪个连接产生所有 WAL 时，方便与 pg_stat_activity 连接），在 EXPLAIN (ANALYZE, WAL) 中按查询查看，以及在 VACUUM 和 ANALYZE 日志输出中按操作查看，现在看起来像这样：

1WAL usage: 2841 records, 1904 full page images, 15735621 bytes,2           15242880 full page image bytes, 3 buffers full

比较 wal_fpi_bytes 与 wal_bytes 告诉您 WAL 中整页映像的比例，以及 wal_compression、检查点间隔或维护调度是否是关键所在。

新的等待事件：WAL LSN 和 COPY I/O

Postgres 19 添加了几个新的等待事件，使以前难以看到的等待在 pg_stat_activity 中可见。

作为新 WAIT FOR 命令（我计划在另一篇博客文章中进一步解释）背后的基础设施的一部分，PostgreSQL 现在可以报告会话何时等待 WAL 达到特定日志序列号 (LSN)。一个新的 WaitForWalWrite 等待事件涵盖等待 WAL 写入，现有的 WaitForWalFlush（以前仅主库）现在也涵盖备库。与 WaitForWalReplay（顾名思义，等待 WAL 重放）一起，它们可以判断会话正在等待 WAL 处理的哪个阶段（写入 → 刷新 → 重放）。

Postgres 19 还填补了围绕 COPY 的类似可观测性空白。以前，COPY FROM/TO 对文件、管道或程序的操作进行读写时没有等待事件，因此当后端卡住时我们无法可见。现在，新的 CopyFromRead 和 CopyToWrite 等待事件使这些路径可观察。COPY 通过有线协议的已被 ClientRead/ClientWrite 覆盖，因此这填补了批量加载和 ETL 管道常用的文件、管道和程序路径。

更好地记录来自远程 Postgres 服务器的消息

这一点很微妙，但任何运行逻辑复制或重度使用FDW的人都会感激它。来自远程服务器（通过复制、postgres_fdw 或 dblink 连接）的NOTICE、WARNING及类似消息过去直接打印到本地服务器的stderr。因此，它们没有获得通常的日志格式，例如log_line_prefix，这使得它们更难与附近的日志条目关联起来。

PostgreSQL 19 现在将这些消息通过ereport() 路由，就像本地服务器消息一样。它们获得正常的日志格式，并带有来源前缀：received message via replication 或 received message via remote connection。这使得跨服务器日志关联变得容易得多。

通过 pg_get_multixact_stats() 查看多事务活动

多事务（Multixacts）在多个事务锁定同一个元组时创建（想想外键检查和 SELECT ... FOR SHARE），长期以来一直是可观测性的盲点。当 pg_multixact/members/ 开始占用磁盘时，你的选择只能是检查文件系统和有依据的猜测。

PostgreSQL 19 新增了 pg_get_multixact_stats()：

1SELECT*, pg_size_pretty(members_size) AS members_size_pretty2FROM pg_get_multixact_stats();34 num_mxids | num_members | members_size | oldest_multixact | members_size_pretty5-----------+-------------+--------------+------------------+---------------------6311740299|2785241176|13926205880|2|13 GB

这让我们直接看到多事务活动：num_mxids 显示当前正在使用的多事务ID数量，num_members 显示它们包含的条目数，members_size 显示这些成员占用的磁盘空间。oldest_multixact 帮助追踪集群仍需要的最旧多事务有多远。

当 num_mxids 激增时，表明存在并发的行锁工作负载；oldest_multixact 保持不变而 num_members 增长，则表明有长事务在阻塞清理。该函数需要 pg_read_all_stats 权限，因此可以直接用于监控角色。

更长的环绕（wraparound）预警时间

最后，事务ID和多事务ID的环绕警告阈值已从距离环绕前4000万提高到1亿个事务。4000万这个数字来自事务速率低得多的时代：每秒消耗10,000个XID的系统大约一小时就能通过这个阈值，这没有多少时间来注意到、反应并让激进的vacuum完成。

重要的是，这并不会改变环绕发生的时间；它只是让Postgres更早地开始警告你。如果你的 age(datfrozenxid) 告警阈值是根据旧警告点推导的，请重新审视。

这对工具意味着什么：升级检查清单

我知道信息量很大，所以我决定用一系列可操作的事项来结束这篇博客。如果你维护可观测性工具，升级前请检查这些事项（或者把这份清单交给你的代理🙂）：

免责声明： 这份清单对我来说也不是理论性的：我们维护 pg_stat_ch，一个开源扩展，将查询统计信息从Postgres流式传输到ClickHouse，支持PostgreSQL 19意味着要逐一处理这份清单：新的WAL字段、新的等待事件等等。

日志解析器

  • 更新VACUUM/ANALYZE日志行的模式；它新增了一个字段：... bytes, N full page image bytes, N buffers full。
  • 添加 log_autoanalyze_min_duration 到读取自动vacuum日志的任何地方，log_autovacuum_min_duration 单独不再报告analyze运行。
  • still waiting for lock 消息在从未记录它们的集群上出现。
  • received message via replication / received message via remote connection 条目（后者始终以本地 LOG 级别记录，因此基于严重级别的过滤器不会捕获远程WARNING）

指标收集器

  • 开始收集 wal_fpi_bytes 从 pg_stat_wal 并跟踪其与 wal_bytes 的比例。
  • 添加 pg_get_multixact_stats() 到你的查询中；监控角色需要 pg_read_all_stats 权限，没有它函数会返回NULL而不是错误，导致指标静默为空。

等待事件字典

  • 添加 CopyFromRead, CopyToWrite 和 WaitForWalWrite；注意 WaitForWalFlush 现在也出现在备机上。

配置验证和用户界面

  • 接受新的 type:level 列表语法用于 log_min_messages，并展示 log_autoanalyze_min_duration 在其autovacuum对应项旁边。

告警

  • 重新校准 age(datfrozenxid) 告警阈值以适应新的1亿警告点，以便你的告警仍然在服务器开始抱怨之前触发。

PostgreSQL 19 还引入了新的系统视图（pg_stat_lock, pg_stat_recovery, pg_stat_autovacuum_scores）并改进了几个现有的视图。我计划在另一篇博客文章中介绍这些，但最好还是先熟悉一下。

结语

就我个人而言，可观测性正是我的Postgres世界和日常工作交汇的地方。在ClickHouse，我们正在构建一个 托管Postgres服务，而ClickHouse本身是许多工程团队用来存储和分析像Postgres这样的系统产生的日志、指标和追踪的工具。所以，我得以从两方面思考可观测性：发出信号的数据库和存储并分析它们的数据库。

如果你想讨论这些内容，请在10月20-23日到巴伦西亚的 PGConf.EU 找我！
