Snowflake 用 Workload Identity Federation 强化 S3 存储集成隔离

DataHot 速览

Snowflake 推出基于 OIDC 的 Workload Identity Federation（WIF），目前处于 Private Preview，用于连接 Amazon S3。WIF 为每个存储集成提供独立的联合身份，取代传统单一 AWS IAM 角色共享模型。该机制旨在改善最小权限隔离、降低跨集成越权风险，并增强云审计可观测性与细粒度撤销能力。

为什么值得关注：数据平台安全隔离与细粒度权限管理是平台工程的关键问题，WIF 提供了一种不改变用户 SQL 工作流的强化方案，值得数据平台负责人关注。

许多客户将Snowflake与Amazon S3的存储集成用于各种用例。了解如何通过工作负载身份联合（WIF）加强Snowflake与Amazon S3之间的集成隔离——一种新的、基于OIDC的简化存储集成认证模型。

Bonny Mahajan，Snowflake产品经理

引言

您是否是注重安全的客户，试图按工作负载、数据域或租户隔离存储访问？WIF为每个存储集成提供自己的联合身份，因此您可以在不改变用户使用Snowflake阶段和SQL方式的情况下加强这些边界。

传统存储集成面临的挑战

传统模型使用单个AWS身份和访问管理（IAM）角色，该角色在Snowflake账户中的所有存储集成之间共享。虽然这通过AssumeRole使用临时凭据，但共享主体可能使执行每个集成的边界变得更加困难：

最小权限：财务集成和营销集成可能需要完全不同的访问权限，但共享身份可能使这些边界更难执行。

隔离：新集成可以从已授予共享身份的权限中受益，而无需新的云侧授权检查点。这造成一种风险，即一个集成可以访问为另一个集成批准的某个位置。

可观测性：云审计记录将活动归因于同一主体，使得更难了解哪个存储集成对某个操作负责。

合规性：安全团队越来越需要短期凭据、明确的授权边界，以及在更细粒度级别撤销访问的能力。

WIF：基于OIDC的认证

工作负载身份联合（WIF）目前处于私人预览阶段，为客户提供了一种连接Snowflake到S3的不同方式。

使用WIF，Snowflake充当OpenID Connect（OIDC）工作负载身份提供者。Snowflake不再通过单个IAM角色路由所有集成，而是为每个存储集成颁发一个范围限定的签名身份令牌。AWS验证该令牌，并为客户配置的IAM角色返回临时凭据。

身份范围限定为存储集成：

  • 颁发者标识客户的Snowflake账户。
  • 主体标识该账户中的特定存储集成。
  • IAM角色定义该集成可以访问哪些S3存储桶和前缀。

这为客户提供了一种实用方式，以为不同工作负载创建独立的信任边界。例如，组织可以将一个集成绑定到财务存储桶，将另一个绑定到营销存储桶，而无需通过一个共享的云主体授予两个集成访问权限。

WIF还保留了人们已经拥有的Snowflake阶段体验。信任配置在云侧发生变化，但客户继续以相同方式使用阶段、COPY INTO、目录表、外部表和其他存储工作流。

工作原理

以下每次Snowflake通过启用WIF的存储集成访问S3时会发生的情况：

  1. 请求签名JWT — 一个阶段操作触发（LIST、COPY INTO、SELECT FROM @stage）。Snowflake的内部OIDC提供者准备令牌请求。
  2. 返回签名JWT — OIDC提供者生成包含iss（特定于您账户的颁发者URL）、sub（特定于存储集成的主体）和aud（sts.amazonaws.com）的签名JWT。令牌返回给Snowflake引擎。
  3. AssumeRoleWithWebIdentity — Snowflake连同IAM角色ARN将JWT发送到AWS安全令牌服务（AWS STS），调用AssumeRoleWithWebIdentity。
  4. 获取JWKS并验证 — AWS STS从JWKS端点获取Snowflake的公共签名密钥，并验证JWT签名。它检查iss、sub和aud声明是否与IAM角色的信任策略条件匹配。
  5. 返回公钥 — Snowflake的JWKS端点返回用于验证令牌签名的公钥。
  6. 颁发临时凭据 — 验证后，STS返回一个访问密钥ID、秘密访问密钥和会话令牌，范围限定为IAM角色的权限。
  7. GET/PUT对象 — Snowflake使用临时凭据执行实际的S3操作（GetObject、PutObject、ListBucket、DeleteObject）。
  8. 返回数据 — S3返回请求的数据（或确认写入）。当凭据过期时，下一个请求自动重复该循环。

这取代了基于外部ID的信任模型，使用OIDC主体声明，提供等效的混淆代理保护，同时简化初始设置。

优势：WIF与传统方式对比

WIF的价值不仅仅在于使用OIDC。它让客户对存储访问如何分离、审查和治理拥有更多控制权。

对于运行多租户平台或管理独立业务数据域的客户，差异是显著的。新集成不能再仅仅因为另一个集成导致共享主体获得该权限而继承访问权限。云侧IAM策略再次成为明确的授权检查点。

WIF还解决了常见的合规性问题：访问权限是静态的、宽泛的且难以归因。客户可以在自己的云环境中撤销或更改IAM角色及其权限，而Snowflake在运行时使用短期凭据。

分步设置（AWS）

先决条件

  • 具有IAM管理员权限的AWS账户
  • 供Snowflake访问的S3存储桶
  • 启用WIF私人预览功能的Snowflake账户
  • ACCOUNTADMIN角色（或CREATE INTEGRATION权限）
重要： WIF用于存储集成目前处于私人预览阶段。您的Snowflake账户必须启用此功能，才能使用AUTH_TYPE = WORKLOAD_IDENTITY_FEDERATION。请联系您的账户团队请求访问权限。

第1步：获取Snowflake的OIDC签发者URL

SELECT SYSTEM$GET_WORKLOAD_IDENTITY_ISSUER_URL();
-- Example output: https://identity.snowflake.com/oauth2/3130xxxx/3130xxxx/56504238333xxxx

第2步：在AWS中注册OIDC提供方

在AWS管理控制台中：IAM → Identity providers → Add provider

  • 提供方类型：OpenID Connect
  • 提供方URL：来自第1步的签发者URL
  • 受众：sts.amazonaws.com

或通过CLI：

aws iam create-open-id-connect-provider \
  --url "https://identity.snowflake.com/oauth2/..." \
  --client-id-list "sts.amazonaws.com" \
  --thumbprint-list "0000000000000000000000000000000000000000"
指纹值是占位符——AWS不再验证OIDC提供方指纹（自2023年6月起），因此任何40字符的十六进制字符串都有效。
注意：每个Snowflake账户只需一个OIDC提供方，无论创建多少个集成。

第3步：创建IAM角色

创建一个带有Web身份信任策略的角色：

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::<ACCOUNT>:oidc-provider/identity.snowflake.com/oauth2/..."
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "identity.snowflake.com/oauth2/...:aud": "sts.amazonaws.com"
      }
    }
  }]
}
注意： 此初始信任策略只检查aud（受众）声明，这意味着您Snowflake账户中的任何存储集成都可以假定此角色。唯一标识特定集成的sub（主题）值将在第4步创建集成后生成。在第5步中，您应在生产中使用该集成之前，使用sub条件更新此信任策略。这确保每个集成恰好映射到一个IAM角色——这种按集成隔离正是WIF的价值所在。

现在附加一个S3权限策略（内联或托管），授予Snowflake所需的访问权限：

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:GetObjectVersion", "s3:DeleteObject", "s3:DeleteObjectVersion"],
      "Resource": "arn:aws:s3:::<BUCKET>/<PATH>/*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": "arn:aws:s3:::<BUCKET>",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["<PATH>/*"]
        }
      }
    }
  ]
}

或通过CLI：

# Create the role with the trust policy
aws iam create-role \
  --role-name my-role \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<ACCOUNT>:oidc-provider/identity.snowflake.com/oauth2/..."
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "identity.snowflake.com/oauth2/...:aud": "sts.amazonaws.com"
        }
      }
    }]
  }'

# Attach an inline S3 policy
aws iam put-role-policy \
  --role-name my-role \
  --policy-name s3-access \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": ["s3:PutObject", "s3:GetObject", "s3:GetObjectVersion", "s3:DeleteObject", "s3:DeleteObjectVersion"],
        "Resource": "arn:aws:s3:::<BUCKET>/<PATH>/*"
      },
      {
        "Effect": "Allow",
        "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
        "Resource": "arn:aws:s3:::<BUCKET>",
        "Condition": {
          "StringLike": {
            "s3:prefix": ["<PATH>/*"]
          }
        }
      }
    ]
  }'

第4步：在Snowflake中创建存储集成

CREATE OR REPLACE STORAGE INTEGRATION my_s3_wif
    TYPE = EXTERNAL_STAGE
    STORAGE_PROVIDER = 'S3'
    STORAGE_ALLOWED_LOCATIONS = ('s3://my-bucket/path/')
    STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::<ACCOUNT>:role/my-role'
    AUTH_TYPE = WORKLOAD_IDENTITY_FEDERATION
    ENABLED = TRUE;

这里的关键区别是AUTH_TYPE = WORKLOAD_IDENTITY_FEDERATION。这告诉Snowflake使用OIDC而不是传统的IAM用户方法。

第5步：使用主题更新信任策略

此步骤通过添加sub条件来完成您在第3步中创建的信任策略。没有它，您Snowflake账户中的任何存储集成都可以假定此IAM角色——这直接破坏了WIF旨在提供的按集成隔离。

即使没有sub条件，WIF也能正常工作，但我们强烈建议在生产中使用该集成之前添加它。sub条件是将一个IAM角色绑定到一个特定集成的东西。

创建后，DESC INTEGRATION my_s3_wif会显示自动生成的sub：

WORKLOAD_IDENTITY_FEDERATION_SUBJECT = identity_external_stage_integration_<hex>

您应向IAM信任策略添加sub条件以增强安全性，以便每个集成恰好映射到一个角色。您可以通过在AWS管理控制台（IAM → Roles → 选择角色 → Trust relationships → Edit trust policy）或通过CLI更新角色的信任策略来实现：

aws iam update-assume-role-policy \
  --role-name my-role \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<ACCOUNT>:oidc-provider/identity.snowflake.com/oauth2/..."
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "identity.snowflake.com/oauth2/...:aud": "sts.amazonaws.com",
          "identity.snowflake.com/oauth2/...:sub": "identity_external_stage_integration_<hex>"
        }
      }
    }]
  }'

同时包含aud和sub的更新条件块如下所示：

"Condition": {
  "StringEquals": {
    "identity.snowflake.com/oauth2/...:aud": "sts.amazonaws.com",
    "identity.snowflake.com/oauth2/...:sub": "identity_external_stage_integration_<hex>"
  }
}

第6步：创建暂存区并验证

CREATE OR REPLACE STAGE my_wif_stage
    STORAGE_INTEGRATION = my_s3_wif
    URL = 's3://my-bucket/path/';

LIST @my_wif_stage;  -- Should return empty (no files) with no error

如果遇到访问被拒绝的错误，请等待一两分钟再重试。AWS OIDC提供方的传播可能需要最多60秒。

用例：为什么这现在很重要

组织在S3中拥有合同、发票、索赔、图像和其他非结构化数据。挑战通常不在于Snowflake能否处理这些文件——而是安全与合规团队是否会批准访问模型。单个共享的云身份可能使按业务部门、租户或数据领域隔离存储库变得困难，这可能使高价值工作负载无法进入Snowflake。

WIF改变了这一局面。客户可以为每个集成创建单独的联合身份和IAM边界——例如，一个用于财务文档，一个用于法律记录，一个用于特定租户的存储库。然后，他们可以使用这些文件进行文档解析、提取、分类、搜索和RAG，同时将访问权限限制在他们授权的存储桶和路径内。

这种新方法使客户能够以安全团队所需的隔离和治理方式，将更多数据连接到Snowflake。

1. AI文档处理（S3上的非结构化数据）

企业正在将合同、发票、表单和其他非结构化文件引入Snowflake进行处理。这些文件通常位于业务部门或租户特定的S3位置，并具有严格的访问要求。

WIF允许客户为每个数据域创建一个单独的集成，并将IAM角色范围限定为仅所需的存储桶和前缀。Snowflake工作流保持不变。以下是一个演示此用例的示例。

-- Parse PDFs on S3 into structured text with layout preservation
SELECT
    relative_path,
    AI_PARSE_DOCUMENT(
        TO_FILE('@my_wif_stage', relative_path),
        {'mode': 'LAYOUT'}
    ) AS parsed
FROM DIRECTORY(@my_wif_stage)
WHERE relative_path LIKE '%.pdf';

-- Extract structured fields from invoices
SELECT
    relative_path,
    AI_EXTRACT(
        file => TO_FILE('@my_wif_stage', relative_path),
        responseFormat => {
            'vendor_name': 'What is the vendor name?',
            'invoice_date': 'What is the invoice date?',
            'total_amount': 'What is the total amount?'
        }
    ) AS extracted
FROM DIRECTORY(@my_wif_stage)
WHERE relative_path LIKE 'invoices/%.pdf';

-- Classify documents by type
SELECT
    relative_path,
    AI_CLASSIFY(
        AI_PARSE_DOCUMENT(
            TO_FILE('@my_wif_stage', relative_path),
            {'mode': 'LAYOUT'}
        ),
        ['invoice', 'contract', 'receipt', 'resume']
    ) AS doc_type
FROM DIRECTORY(@my_wif_stage);

价值不在于调用AI_PARSE_DOCUMENT的新方法，而在于能够处理敏感文件，而无需跨不相关的文档存储库扩展共享云主体的权限。

2. Cortex Search与RAG（基于S3数据的AI代理）

构建搜索和RAG体验的客户通常合并来自多个团队或租户的文档。这使得在保持源数据分离的同时，给Snowflake提供一致的处理和索引方式变得重要。

启用了WIF的暂存区可以限定到一个知识库或数据域的来源位置。客户可以在将文件索引到Cortex Search之前进行解析和分块。

WIF保护对源文件的访问。解析、分块、索引和检索仍然是客户已经使用的相同Snowflake操作。以下是一个演示此用例的示例。

-- Create a chunked table from S3 documents for RAG
CREATE OR REPLACE TABLE doc_chunks AS
SELECT
    relative_path AS source,
    c.value::STRING AS chunk
FROM DIRECTORY(@my_wif_stage),
    LATERAL FLATTEN(input =>
        SPLIT(
            AI_PARSE_DOCUMENT(
                TO_FILE('@my_wif_stage', relative_path),
                {'mode': 'LAYOUT'}
            ):content,
            '\n\n'
        )
    ) c
WHERE relative_path LIKE '%.pdf';

-- Create a Cortex Search Service over the chunks
CREATE OR REPLACE CORTEX SEARCH SERVICE my_knowledge_base
    ON chunk
    ATTRIBUTES source
    WAREHOUSE = my_wh
    TARGET_LAG = '1 hour'
    AS (SELECT chunk, source FROM doc_chunks);

-- Query it using SEARCH_PREVIEW
SELECT PARSE_JSON(
    SNOWFLAKE.CORTEX.SEARCH_PREVIEW(
        'my_knowledge_base',
        '{
            "query": "What is the cancellation policy?",
            "columns": ["chunk", "source"],
            "limit": 5
        }'
    )
)['results'] AS results;

3. 数据加载与摄取

对于批处理和持续摄取，客户希望获得Snowflake管道的便利性，而不需要跨额外存储位置扩展共享主体的权限。

启用了WIF的暂存区可用于常见文件格式，包括CSV、Parquet、JSON、Avro和ORC。以下是一个演示此用例的示例。

-- Bulk load Parquet from S3
CREATE OR REPLACE TABLE my_table (id INT, name STRING, amount NUMBER);

COPY INTO my_table
    FROM @my_wif_stage/data/
    FILE_FORMAT = (TYPE = PARQUET)
    MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;

-- Set up Snowpipe for continuous auto-ingest
CREATE OR REPLACE TABLE my_events (event_id STRING, event_type STRING, ts TIMESTAMP);

CREATE OR REPLACE PIPE my_pipe
    AUTO_INGEST = TRUE
    AS COPY INTO my_events
    FROM @my_wif_stage/incoming/
    FILE_FORMAT = (TYPE = JSON)
    MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;

Snowpipe可以继续支持持续摄取。WIF保护Snowflake到S3的访问路径；自动摄取的事件通知配置仍然适用。

4. 数据卸载与导出

一些客户需要Snowflake将结果写回S3，以供下游应用程序、数据湖处理或归档使用。同样的按集成边界适用于写入：IAM角色可以仅允许访问该工作流所需的导出位置。以下是一个演示此用例的示例。

-- Export query results as Parquet to S3
COPY INTO @my_wif_stage/exports/monthly_report/
    FROM (SELECT * FROM my_table)
    FILE_FORMAT = (TYPE = PARQUET)
    HEADER = TRUE
    OVERWRITE = TRUE;

这为团队提供了更清晰的数据出站和入站授权边界。

5. 外部表与数据湖查询

外部表让客户无需先将数据加载到Snowflake表中即可查询S3中受支持的数据。这对于希望保留现有数据湖布局的大型或不常访问的数据集非常有用。以下是一个示例，用于演示此用例。

-- Create an external table over Parquet files on S3
-- Columns are auto-inferred from the Parquet schema
CREATE OR REPLACE EXTERNAL TABLE events_ext
    WITH LOCATION = @my_wif_stage/events/
    FILE_FORMAT = (TYPE = PARQUET);

-- Query directly (no data loaded into Snowflake)
SELECT event_type, COUNT(*)
FROM events_ext
WHERE event_date > '2026-01-01'
GROUP BY event_type
ORDER BY 2 DESC;

使用WIF时，外部表会继承阶段每个集成的信任和S3权限。客户可以将对一个数据湖区域的访问与对另一个区域的访问分开。

当前限制

此功能处于私有预览阶段，需要由您的Snowflake账户团队启用账户。有关限制和注意事项的完整列表，请参阅官方文档。

总结

用于存储集成的工作负载身份联合使Snowflake的S3访问模型与现代零信任原则保持一致。短期加密签名的OIDC令牌取代了共享主体模型，改用每集成的联合身份。设置过程得到简化：一次OIDC提供商注册即可取代手动交换IAM角色ARN和信任策略配置。 由于每个集成都使用自己范围的身份和短期OIDC令牌运行，因此安全态势更强，更容易在集成级别审计和撤销访问。并且它与团队已经用于Kubernetes、GitHub Actions和其他联合工作负载的现有IAM OIDC身份提供商自然集成。

如果您已经在AWS中为其他服务管理OIDC提供商，那么将Snowflake添加到该信任模型中是自然而然的事。
