Amazon EMR on EKS 推出 Apache Spark 故障排查 Agent

AWS 宣布将 Apache Spark 故障排查 Agent 扩展至 Amazon EMR on EKS，帮助数据工程师用自然语言诊断 Spark 作业失败。该 Agent 自动从 S3 或 CloudWatch 拉取日志及 Spark History Server 事件日志，定位根因并给出修复建议。它可显著缩短平均故障恢复时间（MTTR），从数天降至几分钟，且对 EMR on EKS 客户免费。

在 Amazon EMR on EKS 上调试失败的 Apache Spark 应用，通常需要同时关联多个信号源，包括 Spark driver 和 executor 的 Pod 日志、Spark event logs、以及以 Pod 退出码形式出现的容器终止信号。例如，一次简单的内存溢出可能表现为 Kubernetes 退出码 137，而且很难直接关联到导致问题的代码行或配置。这种跨系统排查可能让单次事件的 MTTR 延长到数天，并且要求工程师具备很深的 Spark 和 Kubernetes 知识。

AWS 近日宣布，Amazon EMR on EKS 现已支持 Apache Spark 故障排查 Agent，将原本适用于 Amazon EMR on EC2、Amazon EMR Serverless 和 AWS Glue 的智能诊断能力扩展到 EKS 环境。该 Agent 此前已帮助数据工程师通过自然语言提示诊断 Spark 故障，现在你可以在失败的 EMR on EKS 作业上使用相同的工作流。

使用过程中，你只需输入一个自然语言提示，Agent 就会自动从 Amazon S3 或 Amazon CloudWatch（根据作业日志配置）拉取 Spark 日志，同时结合 Spark History Server 的事件日志数据，识别故障根因；如果故障与代码相关，它还会推荐修复方案。这一过程能将故障平均恢复时间从数天缩短到分钟级。

对 Amazon EMR on EKS 客户来说，该 Agent 无需额外付费，你只需为现有的 EMR on EKS 资源买单。AWS 官方博客演示了如何为 EMR on EKS 配置该 Agent，并完整走查一个失败作业的排查流程，同时展示了从 Amazon EMR 控制台和某个支持 Model Context Protocol（MCP）的 AI 助手中操作该 Agent 的两种方式。MCP 是一个开放标准，用于将 AI 助手连接到外部工具和数据。

该功能尤其适合那些同时使用 Spark 和 Kubernetes、但缺乏专门运维团队的组织。通过把日志采集、事件关联和根因分析自动化，工程师可以更快恢复正常业务，并把精力集中在代码和配置优化上。
