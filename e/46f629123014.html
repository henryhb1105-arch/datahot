原文

Preparing data while it is already in memory keeps the overhead low. ClickHouse also accelerates that work by parallelizing its execution.

ClickHouse is built to push hardware to its limits

ClickHouse uses as much compute as the underlying infrastructure will provide. Its engine parallelizes both data preparation and query execution across nodes, CPU cores, and SIMD lanes. We’ll begin with data preparation, then show how the same approach carries through to query execution.

Different nodes can process different inserts concurrently with zero synchronisation required. In ClickHouse, concurrent insert operations are isolated from each other. Each insert writes new data parts, each with its own sparse primary index and metadata. Nodes can therefore prepare data without rewriting existing data or updating a shared table-wide index.

Within each node, ClickHouse parallelizes sorting and pre-aggregation across CPU cores. Aggregation uses mergeable partial aggregation states: each CPU core can aggregate its own subset of rows, and the states can be combined into a correct result. ClickHouse uses this model for its 200+ aggregate functions and their combinators. During ingestion, the states are written to the summary table. Our GROUP BY walkthrough shows concrete examples.

Within each core, ClickHouse processes columnar data in batches (vectorized execution) and uses SIMD instructions to perform supported operations on multiple values at once.

The animation below zooms from the ingest nodes into one node’s CPU cores, then into one core’s SIMD lanes.

Alongside ongoing inserts, ClickHouse runs multiple background part merges concurrently across CPU cores. In summary tables, these merges continue the pre-aggregation started at insert time by combining partial aggregation states from different batches, progressively shifting aggregation work from query time to background merge time. They also consolidate raw and summary data into fewer, larger parts while preserving each table’s ORDER BY order. Queries combine the remaining states to return a current answer, without scanning recent raw events to catch up. Our VLDB architecture paper describes this design.

What this delivers in practice

In CostBench, ClickHouse kept summaries current with ingested raw data at the lowest preparation cost. Ordered, compressed history and compact summaries leave less work for subsequent queries, so applications can answer recurring questions from current data and still investigate individual events.

The fastest query results at the lowest cost

Efficient preparation reduces the work behind each query. To measure the payoff, CostBench tested the whole path under load, running the same four interactive aggregate queries every ten minutes and the same two selective drill-down queries every hour on every system while fresh quotes were ingested and prepared. ClickHouse’s lead in query processing

ClickHouse Cloud accumulated the least query runtime and the lowest query cost across all four comparisons.

Query-result caching was disabled on every system, so every measured query executed. Underlying data caches were allowed to remain warm, reflecting continuous operation.

For aggregate queries, Snowflake and BigQuery had extra work at query time because their pre-aggregations lagged behind the raw data. They combined their summaries with newer raw rows to return current answers. Databricks and Redshift read their last completed summaries, so their answers could miss more recent quotes. Inside the engine behind that lead

Preparation reduces the data each query needs to process. Pre-aggregation lets aggregate queries read compact summaries, while ordering helps queries with suitable filters skip irrelevant ranges. As with data preparation, ClickHouse makes queries fast by parallelizing the remaining work.

Across nodes, a single query can use CPU cores on multiple nodes. Participating nodes can process different subsets of rows concurrently and combine their partial results into one answer.

Within each node, ClickHouse divides the rows to process among available CPU cores, so each core can process its own portion concurrently.

ClickHouse uses mergeable partial aggregation states for its 200+ aggregate functions and their combinators: each CPU core can aggregate its own subset of rows, and the states are combined into the correct answer. Raw-data drill-downs build these states at query time; queries over summaries combine states already prepared during ingestion and background merges. Our GROUP BY walkthrough explains the mechanics with concrete examples.

Within each core, ClickHouse processes columnar data in batches through vectorized execution, improving CPU-cache locality. SIMD instructions perform supported operations on multiple values at once.

The animation below follows the same data as it is divided across nodes, then across one node’s CPU cores, and finally across SIMD lanes within one core.

The aggregation work on each core also benefits from low-level choices. ClickHouse selects from 30+ specialized hash-table variants based on the grouping keys and data. Alexey’s Building for Fast discussion illustrates the experimentation behind such choices, including predicting hash-table capacity.

How ClickHouse further reduces query work (click to expand) Over the years, ClickHouse has introduced a series of layered optimizations to aggressively reduce I/O. These techniques form the foundation of its speed and efficiency.

The ordering of raw and summary data established during preparation lets ClickHouse’s sparse primary index skip irrelevant ranges. Projections extend this approach with alternative data orderings and their own indexes.

Skipping continues during execution. PREWHERE applies filters before additional columns are loaded. Optimizations for common query patterns such as Top-N further reduce the work required by ORDER BY … LIMIT, skipping data that cannot improve the result. Lazy materialization can defer reading output columns until the result rows are known.

ClickHouse also uses caches at several levels to avoid repeatedly fetching metadata and data, decompressing and decoding columns, or evaluating the same filters.

These are only some of ClickHouse’s query optimizations. Statistics guide query planning, and query rewrites eliminate redundant calculations before execution. Other techniques include just-in-time compilation of frequently used expressions and using existing data order to satisfy ORDER BY without an additional sort or to simplify aggregation. Our VLDB research paper describes these techniques and the wider engine architecture in more detail.

How does parallelized query throughput scale with CPU cores? (click to expand) To test how this parallel execution model scales with CPU cores, we reran the two raw-data drill-down queries with 2, 4, 8, 16, 30, and 59 CPU cores available to each query. All 113.2 billion quotes were already loaded and prepared. This was a separate experiment from the continuous-ingestion measurements above.

At 59 cores, throughput reached about 15.56 GB/s with hot caches and 9.85 GB/s with cold caches. Hot permits ordinary data caches and the query-condition cache; cold bypasses data caches and disables the query-condition cache. Query-result caching remains disabled in both cases. Speedups are not perfectly linear: combining partial results adds work, even when that merging work is parallelized, and some query stages cannot be fully parallelized.

Source: Measurements and methodology

Parallelized execution on NVIDIA Vera: The same parallel execution model also automatically takes advantage of larger machines. On a dual-socket NVIDIA Vera system with 176 CPU cores, the ClickHouse engine delivered the fastest ClickBench result we had ever measured. Our Vera performance walkthrough shows a CPU-intensive aggregation running about 164× faster with 176 cores than with one. That is close to the 176× speedup of perfectly linear scaling: combining partial results adds overhead, and some query stages cannot be fully parallelized. A separate filtering test processed about 900 GB/s, with further scaling limited by memory bandwidth. The walkthrough also shows how SIMD accelerates supported operations within each core.

Those advantages compound at scale

The ClickHouse engine prepares fresh data batches efficiently, leaving less work for every query, and executes that remaining work efficiently.

Efficient preparation and fast query execution both improve end-to-end performance per dollar, so their benefits compound.

Preparation and query execution reinforce each other

The earlier query-side comparison started with data already prepared and measured a 23×–101× performance-per-dollar advantage for ClickHouse. CostBench tested the broader, continuous-ingestion path and measured a 412×–1,996× advantage with preparation and query serving running together.

Source: Measurements and methodology

Scaling ingest and query compute independently

ClickHouse Cloud adds elasticity and workload isolation to that efficient engine. SharedMergeTree separates table storage from compute, the Shared Catalog centralizes database metadata, and a distributed cache makes hot data reusable across compute changes. This foundation lets stateless compute nodes access the same tables without redistributing stored data as capacity changes.

Compute-compute separation lets ingestion, dashboards, and investigations run on independently sized services, each with its own CPU Cores and memory. CostBench used this separation for its ingest and query services.

Beyond the CostBench setup, On-Demand Compute lets eligible queries request temporary stateless workers through the existing service. These workers provide additional query capacity without permanently increasing the service’s size.

The shared-data architecture also supports several ways to distribute query work:

  • Parallel replicas distribute reads and aggregation across nodes.
  • Index sharding distributes index analysis across nodes.
  • Multi-stage execution dynamically spreads large joins and high-cardinality aggregations across nodes.

Ingest nodes, read nodes, and temporary stateless query workers all run the same ClickHouse engine.

One engine integrates the full analytical path (click to expand) Data preparation (including insert-time transformations), parallelized query processing, and the distributed execution mechanisms described above are built into it.

ClickHouse Cloud can scale compute independently by workload while retaining common SQL functions, data types, and execution machinery. For developers, this provides a consistent set of building blocks for understanding and debugging the full analytical path. Improvements to shared engine code can benefit every role that uses it.

What this enables for real-time applications

Efficient data preparation and parallelized query execution let applications get answers based on the latest ingested data in milliseconds, and use those answers to decide what to do next. Those answers must arrive within the application’s response budget and remain economical when requested repeatedly as the history grows.

CostBench’s stock-market quote dataset provides a concrete illustration. Imagine a trading application checking risk before approving a trade. A recent market move could change the decision, so the analytical query needs the latest ingested quotes. Suppose that query has a 100 ms budget: the deadline stays fixed even as the quote history grows.

The animation below brings together CostBench’s measured summary freshness and aggregate-query latency, comparing response times against this illustrative deadline while new quotes arrive. For the illustrated aggregate query, only ClickHouse combined current data with an answer inside the 100 ms budget at 100 billion quotes.

Source: Measurements and methodology

At 100B rows, ClickHouse Cloud returned the query in approximately 15 ms, with daily summaries current with the ingested raw data. Together, freshness and low latency provide the analytical evidence an application needs before making its next decision.

The economics matter when those decisions trigger queries repeatedly, across users and workflows. Current summaries make recurring questions inexpensive to answer, while ordered raw history supports detailed investigation. Low preparation and query costs help keep both practical as the application grows.

Real-time decisions in practice: At Buildkite, analytical queries help determine how the next CI build runs. The platform ingests results from a trillion test executions a year and uses ClickHouse Cloud for intelligent test splitting, flaky-test detection, and interactive analysis of test history. Materialized views maintain statistics for recurring questions, while raw data remains available for detailed investigation. Those queries sit on the critical path: getting answers quickly helps thousands of machines finish their tests sooner and accelerates the next build.

Built for the age of agent-facing analytics

Agents increasingly ask database questions on people’s behalf, with each answer helping determine what they investigate next.

Database researcher Andy Pavlo, VP of ClickHouse Labs, anticipates “potentially a 10 to 100x increase in volume and the number of queries that are going to hit databases.”

That growth puts pressure on the whole analytical path. Incoming events must keep becoming query-ready while agents ask follow-up questions and run investigations concurrently.

Consider an agent helping a security team investigate an ongoing incident. It might compare recent activity with historical patterns, identify affected accounts, and inspect individual events. The situation can change during the investigation, so each follow-up query needs access to newly ingested evidence.

ClickHouse’s continuous preparation keeps summaries current with ingested raw data, while ordered raw history supports detailed investigation. The agent can move between summaries and individual events as new evidence arrives.

Each answer can determine the next question, putting database latency directly in the investigative loop. In typical ClickHouse workloads, each query takes less time than the model’s typical time to first token. That means agents don’t really have to wait for the database.

The database cost also includes every query needed to reach a conclusion. Those costs accumulate across follow-up questions and concurrent investigations, making efficient query execution increasingly valuable as agent usage grows.

At ingestion volumes of a petabyte a day or more, agents still need current evidence and fast, affordable follow-up queries. ClickHouse’s continuous preparation reduces the work behind each answer, while ClickHouse Cloud lets ingest and query capacity scale independently as event volumes and investigative demand grow. ClickHouse does this right.

Agent investigations in practice: Artemis uses ClickHouse Cloud to continuously examine incoming security logs while investigative agents explore suspicious activity against historical data. Extracting frequently queried fields through materialized views reduced one investigative lookup from 12 seconds to 200 milliseconds. Separately, combining detection rules into shared scans lets production batches of more than 100 rules execute in under a second. Preparing data efficiently and reducing repeated query work support both timely investigations and continuous detection.

Real-time analytics, cost-efficient at scale

Keeping incoming data query-ready, answering efficiently, and scaling with demand are connected requirements across the whole analytical path. Together, efficient preparation and query execution delivered unmatched end-to-end performance per dollar for ClickHouse Cloud in CostBench: 412×–1,996× better across the four comparisons. For real-time applications and agents, that efficiency becomes increasingly valuable as requests multiply.
