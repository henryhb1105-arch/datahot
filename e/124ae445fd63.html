以下关键承诺之一现代数据湖在于开放表格式能够支持任意查询引擎。先进的多引擎转换意味着负责数据建模的团队绝不会被锁定在任何特定引擎上，从而能够构建统一的数据架构，并具备在每个使用场景中就地处理数据的互操作性。

问题所在

由于各引擎的 SQL 方言不同，轻松转译 SQL 的能力对于确保数据资产的互操作性、可移植性和可复用性至关重要。

SQLGlot 是一个纯 Python 的 SQL 解析器、转译器和优化器。它支持 34 种 SQL 方言，且零依赖。它为越来越多的开源和商业项目提供支持，例如 SQLMesh、Apache Superset 以及许多其他项目，这些项目合计处理数百万条查询。人们喜欢它是纯 Python，因为它易于安装、易于修改，并且可在任何地方运行，但“纯 Python”和“快速”通常不会出现在同一句话中。

对于大多数用例，SQLGlot 已经足够快。但当你在数据管道中解析数百万条查询，或对数百条 TPC-H 查询运行优化器时，那些毫秒会累积起来。我们想让它更快，同时不放弃使它出色的特性。

为什么不选 Cython、Rust 或 PyPy？

在最终选择 mypyc 之前，我们考虑了那些常见选项。

  • Cython 可以在“纯 Python”模式下工作，但在实践中，你仍然会得到 Cython 特定的注解和构建问题。我们的目标是维护一个单一、100% 纯 Python 的代码库，不包含特殊语法或模式。
  • 我们最初尝试了 Rust。SQLGlot 有一个基于 Rust 的分词器（sqlglotrs），已经运行了一年多。它有效，但带来了实际缺点。我们需要一个单独的构建和测试流水线来与 Rust 互操作，每当出现故障或需要升级包时，都需要 Rust 专业知识，而且版本管理令人头疼，因为 sqlglotrs 有独立于 sqlglot 的发布周期。
  • PyPy 很棒，但它完全是一个不同的运行时。用户需要切换他们的 Python 安装，这对大多数生产环境来说是不可行的。

我们真正想要的是保持代码库原样，同时以某种方式让它更快。

mypyc 登场

mypyc 是一个转译器，可将带有类型注解的 Python 代码转换为 C 扩展模块。它构建在 mypy 之上，因此它理解你的类型注解，并利用它们生成高效的 C 代码。

mypyc 将 CPython 的 C API 与原生操作尽可能结合起来。当你的类型注解足够严格时，它会绕过解释器的动态分派，并为属性查找、方法调用和整数运算等操作生成直接的 C 调用。如果你已经有良好的类型注解（我们确实有，因为我们已经运行了 mypy），你可以在完全不更改源代码的情况下获得显著加速。

为什么我们仍然发布纯 Python 版本

mypyc 编译的类是 C 扩展类型，而不是常规的 Python 类，这在实践中带来了重要的限制。

你不能猴子补丁编译后的类，也不能在运行时向其添加属性，因为类型命名空间在类创建后就被冻结了。你不能在未使用特殊装饰器选择加入的情况下从常规 Python 自由地子类化它们，即使如此，也存在边缘情况。编译后的实例没有 __dict__（类似于带有 __slots__ 的类），因此只有类体中声明的属性存在。编译后的函数不暴露 __code__，因此任何在运行时检查函数签名的代码都需要一个回退路径。

我们自己的一些测试会创建表达式类型的临时子类或为测试而补丁方法，我们的用户也在他们的代码中这样做。编译版本更快，但它不能支持所有使用模式，因此纯 Python 应保持为一等选项。我们在两种模式下运行完整的测试套件，它们之间的任何差异都是我们要调查的 bug。

打包与分发

我们将编译后的扩展作为名为 sqlglotc 的单独包发布。用户通过 pip install "sqlglot[c]" 安装它。如果安装了 sqlglotc，SQLGlot 会自动加载编译后的模块；如果没有安装，一切以纯 Python 速度完全相同地工作。

我们使用 cibuildwheel 为 Python 3.9 到 3.14 在 Linux、macOS 和 Windows 上构建预编译的 wheel，因此大多数用户永远不需要自己编译任何东西。这比旧的基于 Rust 的 sqlglotrs 设置是一个巨大的改进，当时我们必须在 CI 中维护单独的 Rust 工具链并处理交叉编译的麻烦。

我们目前的状态

今天，我们将 100 多个模块编译为 C 扩展：核心分词器、解析器和生成器；构成 AST 的所有约 950 个表达式类；所有 33+ 种方言解析器；所有 32+ 种方言生成器；schema 模块；以及性能最关键的优化器通道（类型注解和表达式简化）。我们有意将一些模块保留为纯 Python，例如使用频率较低的优化器通道和执行器，因为它们经常变化，且运行频率不足以证明编译开销的合理性。

当我们在 mypyc 源代码中修复 bug 并且 mypyc 逐渐成熟时，我们也能够回头移除之前添加的变通方法。例如，我们最初不得不用手动类注册来绕过 __init_subclass__ bug，但一旦我们的修复进入 mypyc，我们就移除了该变通方法并回到了更干净的方法。

SQLGlot 主要组件的加速包括：

解析（分词器 + 解析器） ~5x
SQL 生成 ~2.5x
优化器（annotate_types、simplify） ~2x 到 2.5x

解析的加速最为显著，因为分词器受益于我们贡献的所有字符串原语，而解析器受益于哨兵模式、原生整数和内联热路径。生成器和优化器的改进较为温和但仍然显著，主要来自更紧凑的分派和消除动态开销。

我们针对广泛的查询形态进行基准测试，以确保持续的加速效果，而非单一模式的偶然产物。测试套件包含 TPC-H 查询、20,000 项的 IN 子句、500 层嵌套算术、200 个 JOIN、500 个 UNION、1,000 分支的 CASE 语句等等。

我们学到了什么

过程中有几件事让我们感到意外。

我们原本已有不错的类型注解以供 mypy 检查，但 mypyc 推动我们把它们做得更严密。更好的类型意味着更快的编译代码，而 mypyc 严格的运行时强制检查抓到了真实的 bug——我们的注解与现实不符：生成器方法的表达式类型写错、变量可能为 None 却未标记为 Optional。起初作为正确性工具的东西，也变成了性能工具。

我们花了大量时间调试 mypyc 内部实现、编写测试用例并提交补丁。本可以很诱人地只在自身这边绕过每个问题。但通过在 mypyc 本身中修复问题，我们让编译器对所有人更好，并且不用背负未来版本中可能失效的变通做法。我们提交到 Python/mypy 的 PR 修复了任何大型 mypyc 项目最终都会遇到的真实问题。

编译版本更快，但它永远不能是唯一选项。有些用户无法构建 C 扩展，有些想要 monkey-patch 内部实现，还有些环境被锁定。将纯 Python 视为一等路径让我们对编译的约束保持诚实，也意味着我们始终有一个可用的基线可供测试。

mypyc 不是玩具，但它也不是“拨动开关就变快”的工具。对于大型代码库，你需要理解它的工作原理、阅读其源代码，并且很可能修复一两个 bug。如果你对此感到自如，它非常合适。从最热的模块开始，让它们编译通过，然后逐步扩展。

对于有类型标注、CPU 密集、非数值型的 Python 代码，mypyc 非常值得一试。加速是真实的，但最好的部分也许是你在过程中对自己代码的发现。

让它编译通过

SQLGlot 遵循经典的编译器架构：分词器、解析器、AST（表达式）、优化器和生成器（将 AST 转回查询）。我们的目标是尽可能多地编译这些部分。

还记得我们说过无需更改源代码就能获得显著加速吗？关于这一点：让如此规模的代码库通过 mypyc 本身就是一项工程。我们遇到了编译器 bug，碰到了意想不到的设计约束，最终为 mypyc 贡献了修复以解除自身阻塞。

阻碍我们的编译器 bug

mypyc 并非为处理约 950 个类的模块而设计。我们的 AST 定义位于单个模块中，当编译器尝试处理它时，其某个内部编译阶段对每条指令都在做冗余工作。在如此大的模块上，它会耗尽所有可用内存，即使在 64 GB 机器上也会因 OOM 而死掉。我们不得不深入 mypyc 内部并优化该阶段，才让编译得以完成（python/mypy#20897）。

这只是第一个阻碍。我们在 mypyc 的代码生成中发现并修复了另外五个 bug，每个都会导致崩溃或静默的错误行为：

  • 包含 lambda 的字典推导式会完全使编译器崩溃（#21009）
  • 方法解析在深层继承层次下会静默失效（#20917）
  • 属性 getter 和 setter 在生成的虚表中会混淆，因此调用 getter 可能实际运行 setter（#21010）
  • 在同一主体中引用其他类变量的类变量会生成错误的初始化代码（#21011）
  • __init_subclass__ 钩子在类级常量设置之前运行，因此任何依赖这些常量的逻辑都会看到垃圾值（#20916）

我们本可以在 SQLGlot 一侧绕过其中大部分问题，但那意味着拆分文件、把每个 lambda 提取为具名函数、重构类层次，以及移除 __init_subclass__ 改用更手动的方式。相反，我们深入 mypyc 代码库，理解代码生成，编写修复并让它们合并到上游。这花费了真实的时间和精力，但替代方案是永远维护 mypyc 的分支，或者把 SQLGlot 的大部分重写成不那么自然的东西。

适配 SQLGlot

即使在修复编译器 bug 之后，我们也不得不调整部分代码库以适应 mypyc 的模型。这些改动单独来看都不大，但合在一起触及了大量文件。

最大的类别是类属性注解。SQLGlot 的方言系统构建在类级字典之上，子方言会扩展它们。每个 Parser 和 Generator 都会覆盖诸如 FUNCTIONS、TRANSFORMS 和 KEYWORDS 之类的东西。在普通 Python 中这没问题，但 mypyc 对类属性处理方式不同：没有 ClassVar 注解时，访问 Parent.FUNCTIONS 会返回一个底层描述符而非实际的字典（基本上，你会得到关于该属性的元数据而不是它的值）。修复很简单（用 ClassVar 注解，mypyc 就不会动它），但我们不得不遍历整个代码库，在所有需要的地方加上这些注解。

除此之外，还有一堆较小的适配。我们用 __init_subclass__ 替换了元类（mypyc 只支持 ABCMeta），将方法内部的惰性 from X import Y 导入改为限定访问（mypyc 不支持编译函数中的 from 导入），并把实例变量声明移入 __init__，以便 mypyc 生成更快的属性访问。

我们还不得不修复 mypyc 严格运行时强制检查标记为错误的类型注解。这实际上是个不错的惊喜：mypyc 抓到了我们一直携带而不自知的真实 bug，比如生成器方法注解了错误的表达式类型，或变量可能为 None但并未被标记为Optional。

让解析器的热循环更快

在一切都能编译且测试通过之后，我们转向帮助 mypyc 生成尽可能最好的代码。你对 Python 代码书写方式的小改动，可能会对编译输出产生超乎预期的影响。

解析器是 SQLGlot 中对性能最敏感的部件之一，我们发现了两种模式，它们对 mypyc 编译它的方式产生了真正的差异。

第一个是消除对None的检查。解析器通过_curr、_next和_prev字段维护指向 token 流的游标。最初，这些字段是Optional[Token]，这意味着每次访问都需要处理None的情况，而在编译后的代码中，这会带来真正的开销，因为 mypyc 必须在每个边界处将值包装和解包为 Python 对象。我们用哨兵 token 替换了None，这是一个特殊的TokenType.SENTINEL值，其Token.__bool__返回False。你仍然可以写if self._curr:，它的工作方式相同，但这些字段现在始终是Token而不是Optional[Token]，这让 mypyc 可以完全跳过对None的处理。

第二个是使用原生整数。解析器的索引字段（_index、_tokens_size）在解析过程中会被递增和比较数百万次。Python 整数带来的开销比你预期的要多，因为它们支持任意大小，但 mypyc 支持一种特殊的i64类型注解，它告诉编译器改用普通的 64 位整数。每次操作的差异很小，但会在数百万次迭代中累积。

内联热路径

mypyc 无法像优化普通循环那样优化通过生成器产生值的代码。嵌套生成器在树遍历代码中很常见，它们尤其昂贵，因为每一层都增加了编译器无法看穿的额外开销。我们在分析优化器的作用域遍历时发现了这一点，该遍历使用了expression.walk()，一个基于生成器的树遍历器。通过将遍历重写为直接循环，我们在作用域分析上获得了

1.8 倍的加速。

同样的原则也适用于分词器和解析器。将分词器的空白跳过逻辑内联到其内部的_scan方法中（绕过常规的_advance()调用）对包含大量空白或字符串字面量的查询产生了

显著差异。在解析器中，我们为列引用和简单表名等常见 token 模式添加了快速路径，当下几个 token 就能让答案显而易见时，避免完整递归下降的开销。其中一条快速路径将嵌套函数调用解析减少了 41%。

生成器中更快的分派

SQLGlot 的生成器通过对表达式类型进行分派来将 AST 节点转换为 SQL 字符串。原始代码通过字符串拼接（expression.key + "_sql"）以及在每个节点上使用getattr()来实现。我们将其替换为一个

预构建的分派字典，它将表达式类型直接映射到其生成方法，构建一次并重复使用。这使我们在 SQL 生成上获得了 6-23% 的加速，具体取决于查询复杂度，查询访问许多小节点时收益最大。

积少成多的小提示

还有一些较小的模式补全了全貌。用typing.Final注解模块级常量，可以让 mypyc 将值直接内联到生成的 C 代码中，而不是在运行时查找它们。我们还发现并修复了分词器关键字扫描中的 O(n^2) 字符串拼接问题，将其替换为列表累积和单次 join。在我们向 mypyc 贡献原生字符串原语之前（详见下文），我们在分词器中使用了预构建的查找表进行字符分类，因为在编译代码中字典查找比 Python 方法调用更便宜。

向 mypyc 贡献性能原语

SQLGlot 的分词器是库中最热的代码路径。它逐字符扫描 SQL 字符串，检查每个字符是否为空白、数字、字母数字等等。在大规模处理查询时，这些字符串操作会发生数百万次，而在我们的工作之前，mypyc 没有它们的优化原生版本；相反，它会回退到通过 C API 调用常规 Python 方法，这虽然可行，但留下了性能潜力。

我们向 mypyc 贡献了五个字符串操作原语：

原语加速比PR
str.isspace() ~1.3x #20842
str.isalnum() 最高 3.2x #20852
str.isdigit() 最高 3.5x #20893
str.lower()/str.upper() 最高 2.6x #20948
str[i] 索引（ASCII 缓存） 3.9x #21035

字符串索引优化值得仔细研究。分词器不断用self.sql[i]对 SQL 字符串进行索引。在 CPython 中，单字符 ASCII 字符串在内部被缓存，因此"hello"[0]总是返回同一个预先存在的"h"对象，而不分配任何新内容。但 mypyc 的字符串索引在每次访问时都会创建一个全新的字符串对象。一旦我们在 mypyc 中增加了对 CPython 缓存 ASCII 字符的支持，我们就在可以说是整个分词器中最频繁的单一操作上获得了 3.9 倍的加速。
