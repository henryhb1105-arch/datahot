Tradeoffs You'll Hit, At Scale

If I just show you the clean picture, if I show you, these are the things that work in production, these are the things that you need to do in production, I'm not going to help you. We talked about one token per work. We talked about one token per session. For example, if that call is lengthier than you expect, then token may or may not get expired within the work, and at that time, your AI agent workflow can be broken.

At that time, you need to think about, either I need to stop the agent, I need to kill the agent, or I need to let it run. The third tradeoff is fail-open versus fail-close, and that is where only you and your team can decide what sort of mechanism or thing that you need to put in fail-open versus fail-close. This is where only you can decide what sort of operations that you want to allow in case of failure and what sort of operations that you want to just pass in case of failure.

The fourth point for tradeoff is cardinality, where per-session identity explodes label cardinality in traces and metrics, and this is something that usually surprised me most. The last one is policy as single point of failure. Guardrails

Guardrails and identity and tools. Before we talk about guardrails, why do we need guardrails? Every AI agent needs some boundaries so that they can work within that boundary and also you have some control over it. The first guardrail which is very important is least privilege at the tool layer. What we do is we implement least privilege control at the prompt layer, but that is the wrong start. You cannot control user to enter the prompt. You can control the keywords that they can enter, but that is bad practice because it should happen at the tool layer because that is where the blast radius lives. The prompt can say anything. The prompt can do anything, but the tool layer is where you enforce what the agent is actually allowed to do. The second is scoped tokens only. We already talked about that each agent should only use token till that work is done, that per agent, per token, per session, per token.

Token should be scoped to current tasks only. LLMs should not ask nicely, can I please use this token because I need to do this and that? Can I please extend this token? That's not going to help. That's not going to work in the production environment. The third thing is tool output is untrusted input, because each tool will give you something in form of output. It can have malicious information. It can have malicious data, and that is where you need to control before it gets to the next stage. Those are the tradeoffs that we have seen in a production environment. Guardrails, these are the action, context, and kill switches. First is allowlist destructive actions, tier them by blast radius. You can reduce the blast radius. You can define what actions you want to put in each individual blast radius. You can have dry run. You can have explicit conform or human in the loop as well, depending on the tier.

The second is rate and budget limits per agent identity. Cost is security control as well. You need to also think about the sudden cost spikes when that agent is running. The third is bounded context. Hard caps on retrieval count, recency, and sensitivity class. Unbounded context is a data leakage surface for bounded context. Kill switch, this is another important aspect. You need to implement kill switch not after you are in incident, but before you even actually go and implement that AI agent, because you need some sort of control. If your logs or if your observability is saying that something is going south, something is not going as per the plan, or something is not going accordingly, then you need to stop that agent. You need to revoke that token immediately, rather than thinking about it later, rather than being an incident. This is something that you need to implement beforehand, not afterhand.
