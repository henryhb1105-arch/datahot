译文

AI 逐段翻译

在 Databricks，我们知道你的数据是你最宝贵的资产。Databricks 已与数千家客户合作，安全部署 Databricks 数据 + AI 平台，并配备适当的功能以满足他们的安全、隐私和监管要求。

现代网络攻击并不总是从边界被突破开始；它始于一次合法的登录。一旦攻击者获取了泄露的会话 Cookie、个人访问令牌（PAT）或服务主体凭据，最初的入侵就已经完成。从那一刻起，他们的全部目标就是融入环境，并以你被入侵的用户或服务的身份进行操作。

但拥有钥匙并不意味着你熟悉这栋大楼。想象一个入侵者刷卡进入一间安全办公室。他们可能已经通过了旋转门，但他们仍然需要绕过保安、猜测自己有权进入哪些楼层，并弄清楚金库在哪里。由于攻击者缺乏你实际员工的深入、本地化背景，他们的行为最终会暴露自己。发现这些异常正是抓住他们的方法。

在本文中，我们将介绍基于凭据的攻击如何在 Databricks 平台上展开，如何使用 Databricks 详细审计日志和 Genie 检测身份行为的转变，在确认入侵后如何响应，以及哪些控制措施从一开始就限制了被盗凭据能做什么。

一个跟踪基于凭据攻击的模型

当通过合法凭据建立访问时，攻击者与安全从业者一样，也明白一旦他们的行为过于偏离该身份的预期行为，他们的访问随时可能被撤销。攻击者依赖非线性的攻击序列，例如验证一组凭据来映射你的环境，然后获取另一组凭据，通过一个新的身份或工作区返回，而该身份或工作区没有与之关联的侦察活动。此外，攻击者可能在未建立持久性的情况下收集信息，或在完成目标之前建立返回你 Databricks 平台的途径。

这在实践中是什么样子

设想一位数据工程师的个人访问令牌从配置错误的持续集成和交付（CI/CD）日志中被复制。几分钟内，该令牌从一个新 IP 被用来列出工作区中的机密范围、目录和仓库，而这位工程师从未这样做过。一个保存服务主体凭据的机密被读取。一小时后，该服务主体（而非该工程师）创建了一个函数，将自己添加到一个管理员组中，并导出了几个初始化脚本。这些事件中的每一个都可能被当作例行的平台使用，但综合来看，它们显示了一次入侵正在穿越攻击链。

在 Databricks，我们预期与基于凭据的攻击相关的非线性事件序列，并使用此模型将单个事件连接成一次调查，而不是将它们视为不相关的事件。

基于凭据攻击的六个阶段

当攻击者在平台即服务（PaaS）环境（如 Databricks）中利用被入侵的凭据时，他们的活动可以分为六个阶段，尽管他们很少以直线方式依次进行。下面的每个阶段都描述了攻击者试图做什么，以及在 Databricks 审计日志表 中要查找什么。请将此指南视为起点，并根据你环境的正常自动化进行调整。

注意：事件写作 service_name.action_name，例如 secrets.getSecret。

1. 攻击者使用有效凭据获得访问权限

登录本身很少看起来不寻常。由于凭据是真实的，身份验证会像合法所有者那样成功。然而，该身份在登录后的几分钟内所做的活动往往与其正常活动大不相同，而这种变化正是响应人员可以检测到的。在数据工程师的例子中，被盗令牌成功通过身份验证，登录时唯一的区别是工程师从未使用过的源 IP。随后的活动才是引人注目的。

攻击者目标： 使用有效凭据访问工作区，无论是被盗的浏览器会话、重放的 PAT 还是服务主体凭据，并融入控制措施旨在允许的活动之中。

要查找什么：

  • 使用身份验证事件作为你时间线的起点。仅凭登录很少足以触发警报，但其 user_identity、source_ip_address、user_agent、sessionId、request_id 和 workspace_id 让你能够跟踪该凭据接下来做了什么。
  • 标记 accounts.tokenLogin 事件，这些事件在短时间内从陌生客户端突然涌入，随后同一令牌从不同的源 IP 被使用。这种模式可能表明有人在测试被盗令牌，而 requestParams.tokenId 让你能够将这些事件关联到同一令牌。
  • 标记从预期网络铸造但用户代理异常的服务主体 OAuth 令牌，尤其是当来自新源 IP 的活动在一分钟内随之出现时。

2. 攻击者映射环境

接下来，攻击者需要在访问被撤销之前了解该凭据能触及什么。因此，被入侵的身份可能在几秒内从日常活动转变为列出数据、机密、代码和网络控制。这种侦察通常同时跨越多个服务，并且比人工在 UI 中导航的速度更快。在我们的场景中，这个阶段是在令牌被使用后几分钟内大量调用列出机密范围、目录和仓库，而这是该工程师以前从未执行过的活动。

攻击者目标： 构建一张可访问的数据、凭据、仓库和防护措施的地图，以便在访问被撤销之前规划一条更深入环境的路径。

要查找什么：

  • 查找单个身份在工作区和账户平面上进行快速的列表调用，例如 secrets.listScopes / listSecrets、unityCatalog.listMetastores / listCatalogs / listSchemas / listExternalLocations / listStorageCredentials、repos.listRepos，以及账户级别的 accountsManager.listWorkspaceConfigurations / listNetworkConfigurations / listStorageConfigurations。例如，一个人在一分钟内调用五个或更多不同的发现 API，不太可能是在浏览平台。
  • 将活动与该身份的正常基线进行比较。一个已建立身份首次进行密钥枚举，或一个 SQL 会话从业务查询转向针对访问控制和配置架构的 SHOW TABLES，比大量调用更有意义。启用详细审计日志记录后，commandSubmit 会将查询保留在 commandText 中。
  • 在搜索中包含失败请求。调查某个身份首次出现的 IpAccessDenied，尤其是当它出现在 accounts.oidcTokenAuthorization 之后，或跨工作区重复出现时。在这种情况下，授权已成功，但请求来自被阻止的网络，这通常是从不受信任的位置重放凭证的最早记录。

3. 攻击者收集更多凭证

收集凭证通常需要几个步骤。攻击者列出密钥范围，列出其中的密钥，然后读取看起来有用的密钥。他们获取的值使他们能够以另一个身份（通常是权限更高的身份）返回。因此，可疑身份读取的每个密钥都值得跟进。在数据工程师示例中，攻击者读取了一个保存服务主体凭证的密钥。从那时起，调查必须跟踪两个身份：工程师和服务主体。

攻击者目标：获取令牌、API 密钥或服务主体密钥，将初始立足点升级为以新身份在整个环境中访问。

要查找的内容：

  • 对调用进程发出警报。secrets.listScopes 单独出现很常见，且会产生噪声。然而，listScopes 之后是 listSecrets，然后是 getSecret，并在多个范围中快速连续重复，表明正在进行收集。listSecrets 记录范围，getSecret 记录范围和键。
  • 将被拒绝的读取与后续成功的读取关联起来。对严格控制范围的 getSecret 被拒绝，随后对限制较少的范围中相同或相关键的读取成功，表明该身份正在寻找它可以访问的副本。
  • 除密钥 API 外，还要监控计算端访问。启用详细审计日志记录后，笔记本的 submitCommand 和 Databricks SQL 的 commandSubmit 事件可以显示调用密钥工具的代码，或对包含凭证的路径运行 read_files()。请记住，提交的文本显示运行了什么，但并不能确认返回了值。
  • 将每次密钥读取与后续发生的事件关联起来，例如新的 accounts.tokenLogin、首次出现的服务主体活动、IP 或用户代理发生变化，或 generateTemporaryTableCredential / generateTemporaryVolumeCredential 调用。在响应期间，轮换该身份可能访问过的每个凭证，并检查每个凭证在何处被使用，以及它存储在何处。

4. 攻击者找到可用的执行路径

一旦建立访问权限，攻击者就会寻找运行自己代码的方法。在 Databricks 上，这通常通过用户定义函数（UDF）和作业实现。函数可以将有效载荷包装在看起来普通的代码中，并且可以被重复调用；作业可以跨不同的计算按计划运行该代码。因此，检测的关键问题是某个身份是否开始执行它以前未执行过的操作。回到数据工程师的示例，在密钥被读取一小时后，服务主体创建了一个函数。由于执行此操作的是服务主体而不是工程师，仅针对工程师活动范围的搜索会遗漏它。

攻击者目标：建立一种可靠、可重用的有效载荷执行方式，并在某条计算路径被阻止时提供回退方案。

要查找的内容：

  • 优先处理来自没有创建函数历史的身份、IP 或目录的 createFunction 事件，尤其是当短时间内出现多个此类事件时。在可获得函数定义的情况下，标记执行进程、动态评估代码、访问实例元数据、打开出站网络连接或写入云存储的代码。同时追踪函数之间的引用，因为看起来无害的包装器可以调用风险更高的 UDF。请注意，function_info 在 system.access.audit 中除账户管理员和 databricks_pii_access 外均被屏蔽，因此请将审计数据与函数清单结合使用。
  • 按身份、IP 以及作业或运行 ID 追踪作业路径。典型序列是 importNotebook，然后是 changeJobAcl、Jobs create、runNow 和 getRunOutput。这些事件很少保留笔记本正文，因此请同时保留笔记本版本和作业配置。来自同一来源的重复导入和运行活动比任何单一操作都是更强的信号。
  • 查找在失败后切换计算资源的身份。例如，集群创建失败或 submitRun 之后不久出现 startWarehouse，或在不同计算资源上出现新作业，可能表明攻击者正在绕过被阻止的路径。响应代码和事件之间的短暂间隔是将此序列与常规错误区分开来的关键。无服务器计算是一种常见的回退方案。

5. 攻击者建立持久性

有了运行代码的途径后，攻击者接下来会设法确保在原始凭据被撤销后仍能返回。常见的持久化方法包括访问授权、新建令牌、更改组和工作区成员资格，以及控制平面编辑。最有用的信号是由不熟悉的身份或执行上下文做出的敏感变更。例如，从作业内部发起的权限变更比管理员在控制台中做出的相同变更更值得仔细审查。在接下来的场景中，服务主体将自己添加到管理员组。即使工程师的令牌被撤销，该组成员资格仍会使攻击者的访问权限得以保留。

攻击者目标： 创建持久的、独立的访问路径，使其在受损凭据被撤销后仍能存活。

需要关注的内容：

  • 对来自意外上下文的权限和身份授予告警，例如机密范围上的 putAcl、updatePermissionAssignment、addPrincipalToGroup 或 setAdmin。当服务主体向另一身份授予访问权限，或在短时间内发生多次分配时，要特别注意。
  • 将试图更改安全控制的行为视为高严重性，即使这些尝试失败。这包括 setSetting / deleteSetting、IP 访问列表编辑和 createPrivateAccessSettings。在得出控制是否实际被绕过的结论之前，请审查所请求的变更、响应和来源。还要审查来自预期 IdP 之外任何来源的 SCIM 组变更。
  • 标记来自不熟悉来源或在作业运行期间发起的 generateDbToken 调用。每个生成的令牌都是需要撤销的独立凭据。
  • 留意自行持续运行的工作负载。将控制平面事件与 run_by、run_as 以及预期运行窗口进行关联。如果某个作业在攻击者的交互活动停止后仍继续修改组、权限或设置，它可能正在自行维持访问。在终止它之前，请保留作业定义和工件。

6. 攻击者收集数据并清理访问

数据收集可能小到只是几次有针对性的导出，而清理可能不止于删除文件。留意有针对性的导出、临时凭据请求、清除短期使用的工具，以及使活动难以还原的混淆命令。其中任何单个事件都可能看起来是常规操作，因此它们周围的序列比单个导出或删除更重要。最后，我们场景中的服务主体导出了一些 init 脚本。单看这是一次小规模导出。然而，由于它跟随同一服务主体的机密读取和新函数之后发生，应将其作为同一次入侵的一部分进行调查。

攻击者目标： 取走重要数据并清除最明显的工具，同时保留更隐蔽的访问。

需要关注的内容：

  • 关注每次导出的上下文，而不是导出的数量。workspaceExport 记录路径、格式以及是否为直接下载。优先关注由不熟悉身份发起的、导出到异常路径或使用异常格式的、来自此前未见网络的，或跟随机密访问或新执行之后的导出。对 init 脚本进行小规模、有针对性的导出，可能比批量 SOURCE 转储泄露更多信息。
  • 保留短期对象的记录。在同一个会话中对同一函数先 createFunction 后 deleteFunction，或反复进行创建、删除和重新创建的循环，可能表明试图清除证据。在还原任何内容之前，请保留定义和时间信息。存活下来的对象通常比被删除的对象被赋予更合理的名称。
  • 将临时凭据和数据读取突发（generateTemporaryTableCredential、generateTemporaryVolumeCredential、Delta Sharing、云存储读取）与先前的侦察关联起来。编码或脚本化的命令本身过于常见，不足以单独告警，因此要将其与不熟悉的用户代理、类似自动化的时序、机密访问或新函数关联起来。

使用 Genie 调查凭据驱动的攻击

以凭据驱动的攻击链为指南，你可以引导 Genie 逐一处理攻击阶段，而无需从头编写每个查询。本文中的每项检测都运行在你已有的遥测数据上。Databricks 将控制平面活动写入 system.access.audit 系统表。

要开始使用，请安装 Detection App，它会添加一个用于 Databricks 审计日志的 Genie agent。你可以通过两种方式从 Genie One 使用它：

  • 用自己的话提问，例如 “user@example.com 昨天导出了哪些笔记本？” Genie 会为你编写并运行 SQL。
  • 使用内置检测。Detection App Genie agent 包含 30 多项检测，涵盖从令牌滥用到管理员授权。询问“上周谁创建了个人访问令牌？”，Genie 会运行匹配的检测，而不是编写新的 SQL。给它一个目标，例如“我们在过去 90 天内是否遭到入侵？”，它会逐项运行检测。

请记住两个限制。第一，空结果并不意味着什么都没发生。事件可能在你时间窗口之外，或者 verbose audit logging 可能被禁用。第二，审计日志记录了什么发生了变化以及是谁更改的，但通常不记录旧值或新值。

从检测到响应

一旦狩猎发现某个身份不符合其正常模式，重点就转向攻击者仍拥有哪些访问权限。由于凭据驱动的攻击是非线性的，你发现的第一个访问权限很少是唯一的访问权限。在数据工程师示例中，撤销工程师的令牌会留下服务主体的凭据、其管理员组成员资格及其创建的函数。完整的响应既要移除原始凭据，也要移除攻击者此后创建的每条路径，包括授权、令牌、函数以及在用户被禁用后仍继续运行的作业。

对于疑似工作区入侵，响应人员应：

  1. 禁用该身份。 停用该用户在账户级别，这会阻止所有工作区。没有 API 可以结束用户的浏览器会话，但停用会阻止它们。对于服务主体，删除其 OAuth 密钥并使用账户 SCIM API 将其停用。服务主体已持有的 OAuth 令牌最长仍有效一小时。
  2. 撤销他们的个人访问令牌。停用用户不会删除其令牌，如果用户被重新激活，令牌会再次生效。使用令牌管理 API或账户控制台中的令牌报告。
  3. 保存你需要的内容，然后停止计算。首先导出作业定义和笔记本版本。然后取消作业运行、终止集群并停止 SQL 仓库。在无服务器上，取消运行或语句。停用用户不会停止已在运行的计算。
  4. 轮换该行为者读取过的每一个密钥。在源头更改它，然后更新存储的值。同时轮换攻击者用于进入的凭据。
  5. 撤销行为者创建的持久化机制。移除密钥范围 ACL、工作区分配和组成员身份。删除这些函数并撤销这些授权。从你自己的记录中恢复基于上下文的入口策略（以及 IP 访问列表，如果你仍在使用它们）。
  6. 检查该身份可能更改的代码，例如云存储中的初始化脚本和 ETL 代码。
  7. 确认它已停止。对该行为者的活动进行搜索。如果详细审计日志处于关闭状态，请将其打开。命令文本仅在其开启时才会被记录。

防御凭据驱动的攻击

回到办公楼：基于上下文的入口决定谁能通过旋转门，而最低权限决定他们的徽章能打开哪些楼层。早期检测能争取响应时间，但预防性控制能限制被盗凭据能做什么。以下控制措施按它们从攻击者手中夺走的内容分组，大致按照它们打断攻击链的顺序排列。

将被盗凭据挡在外面

针对凭据重用最有力的预防性控制是基于上下文的入口控制。它评估谁在发出请求、请求来自哪里以及请求的目的，而不是依赖单一的网络边界。随着越来越多组织不再使用 VPN，这尤其有用。即使没有可依托的企业网络，你也可以将被盗令牌限制在其所有者实际使用的上下文中。例如，你可以将特权服务主体限制为仅接受来自可信网络的 API 请求，同时对人类用户应用不同的策略。

  • 将策略同时应用于工作区和账户请求。工作区策略不覆盖账户控制台或账户级 API。
  • 从试运行模式开始。在system.access.inbound_network中查看拒绝和试运行违规记录，优先保护特权服务主体，并在你已考虑合法自动化和合作伙伴集成后再强制执行。
  • 在广泛强制执行之前测试无服务器和私有连接工作流，因为它们遵循单独的策略规则。记录任何例外并监控其使用情况。
  • 将 IP 访问列表视为额外的一层。在两者都适用的情况下，请求必须同时通过两者。如果你仍在使用工作区和账户控制台列表，请配置它们。

降低被窃取凭据的价值

  • 为服务主体凭据、集成凭据和个人访问令牌设置过期和轮换要求，并停用不再使用的凭据。休眠凭据对攻击者特别有吸引力，因为其泄露可能数月不被察觉。
  • 对密钥范围强制执行最低权限。避免将强大凭据的副本存储在具有不同 ACL 的范围中，并审查谁可以列出范围内容以及谁可以检索值。

限制凭据可以运行或更改的内容

  • 限制高影响操作。将 UDF 创建、密钥范围 ACL 更改、工作区权限更改、作业管理和入口策略更改限制为经批准的身份和受控自动化。
  • 将管理路径与计算路径分离。普通作业运行时不应能够修改账户和网络控制，任何此类尝试都应生成警报。
  • 保护云执行环境。在适用的情况下使用强化的元数据服务配置，并限制计算出口，使工作负载无法自由访问凭据端点或未经批准的目的地。
  • 限制哪些身份可以管理账户身份、分配工作区访问权限和创建作业。

保留证据

  • 为潜在的安全入侵保留可供调查的遥测数据。
  • 保留审计日志、笔记本和作业版本历史、UDF 定义和依赖项、权限更改历史、云存储写入事件以及基于上下文的入口拒绝日志，保留时间足以重建一次攻击活动。

请记住，被盗凭据的爆炸半径仅取决于分配给它的权限。通过采取以下步骤来减少这种暴露并能够搜寻异常活动：

  • 查看Databricks 安全最佳实践以强化你的工作区和账户。
  • 开启详细审计日志并设置基于上下文的入口控制，以便两个平面都得到覆盖。
  • 部署检测应用以开始你的搜寻，并向 Genie 提出你的第一个问题：“我们在过去 90 天内是否遭到入侵？”
