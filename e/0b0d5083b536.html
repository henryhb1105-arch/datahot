SAP：Agent进生产失效，因业务语义断层

SAP在TechEd 2026上指出，企业AI Agent在POC阶段表现亮眼，但进入生产环境后常因数据分散、业务语义不一致、系统异构集成等问题失效。SAP提出需先做好Clean Core（数据与流程标准化、主数据治理）和语义就绪，并正将ERP积累的700多万字段、50多万张表、15000多个业务流程构建为知识图谱，为Agent提供企业上下文。Joule Work的财务预算案例展示了模型结合成本中心、审批流程等企业数据完成分析的能力。SAP认为Agent会改变ERP使用方式，但不会取代ERP。

AI摘要

AI Agent在企业落地面临业务语义断层、系统异构集成与生产环境鲁棒性三大瓶颈。

关键观点：企业数据孤岛与规则不一致导致Agent难以理解真实业务上下文；行业大模型缺乏企业级微观知识，无法支撑具体决策；POC成功不等于生产可用，工程化需解决异常处理与跨系统协调。

适合AI平台工程师、企业架构师、SaaS产品技术负责人阅读。

“POC 非常成功，领导都非常高兴，说我们就去干吧。可真正做起来，效果完全不一样，数据不准确，其他问题也都出来了。”蔡彦斌在谈及企业部署 AI Agent 的实际情况时直言。

企业的业务系统往往经过多年建设，数据分散在不同平台，系统之间存在复杂的依赖关系，业务规则也并不总是一致。AI Agent 接入这些系统后，如何理解业务上下文、协调不同系统，以及应对生产环境中的异常情况？这些问题决定了 Agent 能否真正承担业务任务。

在日前落幕的 SAP TechEd 2026 上，AI Agent 进入企业核心业务流程成为重要议题。但从技术演示到真正投入生产，仍有不少工程问题需要解决。

围绕这些问题，InfoQ 专访了 SAP 全球高级副总裁、SAP 全球研发网络总裁柯曼博士（Prof. Dr. Clas Neumann），以及 SAP 中国研究院院长、SAP 全球副总裁、HCM 产品全球化研发负责人蔡彦斌博士。

模型能够理解行业知识，却未必知道一家企业究竟如何经营。蔡彦斌举了一个例子：他的一位朋友经营着一家自行车贴牌加工厂，曾让两个 Agent 制定未来几个月的产品定价策略。模型给出的分析看起来相当完整，却无法直接使用，因为它不了解具体产品，也不清楚企业的客户情况。

在小范围测试中，企业可以为模型准备数据、设定明确任务。但进入生产环境后，Agent 需要面对分散在不同系统中的业务数据、长期积累的管理规则，以及大量无法提前穷举的实际情况。

柯曼认为，企业 AI 的目标应该是能够根据业务意图自主采取行动。例如，一家供应商的关键零部件延迟交付，系统不仅要及时识别风险，还要判断对生产和供应链的影响，并采取相应的补救措施。

在这一思路下，SAP 提出了“自主运营企业”（Autonomous Enterprise）愿景，希望让 AI 从辅助工具逐渐进入企业核心业务，承担更多流程编排和执行工作。

不过，对于已经运行着大量 ERP、财务和供应链系统的企业，Agent 要真正接手这些工作，仍需要解决数据、流程、权限和系统集成等问题。

模型很聪明，却不知道企业的规则

“企业里面有两个系统，到底应该遵循哪一个系统的规则？这个事情，智能体自己解决不了。”蔡彦斌说道。

相比按照固定规则执行任务的机器人流程自动化（RPA），Agent 能够根据环境变化进行判断，选择不同工具和执行路径。但企业内部的数据往往分布在多个系统中，不同部门甚至可能对同一个业务概念采用不同定义。

例如，某个系统中的“客户”可能指签订合同的主体，另一个系统则按照实际收货或结算对象管理。如果没有统一的业务语义，Agent 即使能够读取两套系统，也可能在执行任务时产生错误判断。

蔡彦斌认为，企业部署 Agent 首先需要做好“干净的数字化核心” （Clean Core），包括数据标准化、流程标准化和主数据治理。在此基础上，还要实现“语义就绪”，让 AI 理解不同数据所对应的业务含义，以及它们之间的关联。

为此，SAP 正在将长期积累的业务数据和管理流程整合进知识图谱。据悉，其 ERP 系统积累了 700 多万个字段、50 多万张数据表和超过 15000 个业务流程。知识图谱的作用，是将这些数据及其业务关系提供给 AI，使其能够结合企业自身情况进行分析和执行。

以财务预算为例，模型需要了解的不只是某个部门的预算金额，还包括成本中心归属、支出规则、审批流程和相关系统接口。具体地，财务人员向 Joule Work 提出一个任务：第四季度电价预计上涨 20%，需要分析哪些部门的剩余预算可能不足。系统随后调用企业后台数据，找出六个成本中心，识别其中三个可能出现预算缺口，并提出进一步核实电价生效时间、部门用电量和追加预算的处理建议。

这个体现了企业上下文的重要性。模型可以理解电价上涨的含义，但要判断哪些部门受到影响、预算如何调整，还需要调用企业已有的数据和流程。

Agent 会改变 ERP，但不会取代 ERP

那么，随着 Agent 开始理解业务意图、调用系统和执行流程，传统 ERP 未来会变成什么样？

蔡彦斌认为，企业软件的使用方式肯定会改变。过去，员工需要熟悉不同的事务代码和功能界面，在 ERP 或 SaaS 系统中找到相应模块才能完成工作。未来，用户可能只需要向 Joule Work 提出需求，由 AI 协调后台系统完成操作。

但传统界面不会因此完全消失。“特别是在人需要干预的时候，或者某一个点有突发情况时，人还是需要跑到后台找到对应的事务代码、对应的屏幕。”蔡彦斌表示。

他预计，通过 AI 入口完成工作的比例会逐渐提高，传统界面的使用频率相应下降。但在可预见的阶段，两种方式仍将并存。

SAP 也据此调整了企业软件架构。在其提出的体系中，Agent 负责理解用户意图、编排任务；原有应用继续承载财务、人力资源、供应链等业务流程；数据层则提供企业知识和业务语义。

蔡彦斌透露，SAP 目前已经发布了 300 多个智能体，希望通过 Agent 重新组织现有 ERP 流程，逐步覆盖更多端到端的企业业务。但这些智能体不会直接取代底层应用。

具体到产品，Joule Work 承担用户交互和任务协调，Joule Studio 则用于构建智能体。后者允许业务人员通过自然语言描述需求，由系统结合企业已有流程、数据和接口，生成相应的 Agent。

这种开发方式也在改变企业 IT 团队与业务部门的关系。蔡彦斌认为，业务人员可以更多参与技术开发，技术人员则需要更加理解具体业务。对于 SAP 而言，原来负责传统 SaaS 应用的部分研发人员，也开始将积累的业务知识用于智能体开发。

不过，Agent 越容易构建，后续管理就可能越复杂。

企业有几百个 Agent 后，谁来负责升级？

蔡彦斌预计，随着开发门槛降低，未来各个业务部门都可能利用类似 Joule Studio 的工具创建自己的 Agent。一家企业同时运行几百个智能体，并非难以想象。

但数量增长之后，新的问题会逐渐出现。“智能体 1、2、3 协同完成了一个流程，智能体 2 版本更新了，你到底能不能和 1、3 协同？”

蔡彦斌提出的这一问题，涉及多 Agent 系统的版本兼容、依赖关系和持续维护。对于单个 Agent，企业可以在修改后重新测试；但如果多个 Agent 共同完成采购、审批、财务结算等流程，其中一个组件升级，可能影响整个业务链路。

企业因此需要知道自己拥有多少个 Agent、分别负责哪些流程、哪些只在部门内部使用、哪些已经进入集团级系统，以及它们之间存在怎样的调用关系。

SAP 希望通过统一的智能体目录和版本管理机制，记录不同 Agent 的功能、权限和运行状态。对于需要跨系统协作的 Agent，还需要管理 A2A、MCP、API 等协议连接，并通过网关控制访问范围。

蔡彦斌强调，企业必须在 Agent 上线前建立完整的测试流程，包括功能、性能、安全、准确率和合规验证。部署之后，还要持续监控运行情况，并在业务变化时维护相应版本。“不能等到有 300 个智能体在跑的时候，再考虑这个问题，那就有点太晚了。”

Agent 到底能获得多大的自主权？

Agent 数量增加之后，企业还需要解决另一个问题：什么时候可以放心让 AI 自己做决定？

柯曼认为，企业要利用 AI 实现自主运营，就必须给予系统一定程度的信任。但这种信任有明确边界。机器可以承担自主编排和执行工作，人负责设定规则，并对结果承担责任。

蔡彦斌则从企业实际工作出发，将自主性进一步划分为不同层级。

企业的工作可以分为执行层、管理层和策略层。现阶段，AI 更适合承担执行层任务。随着技术可靠性提高，未来某些业务场景中，可能有 70%至 80%的执行工作交给 Agent 完成；但越往管理层和策略层走，需要理解的上下文越多，能够自主完成的工作比例也会下降。而不同层级的业务，也需要相应的控制机制。

蔡彦斌介绍，SAP 希望将 ERP 现有的用户授权体系延伸到 Agent。智能体执行任务时，应当受到对应用户权限的约束，不能随意读取数据或修改业务信息。

同时，企业需要追踪 Agent 执行的每一步，包括读取了哪些数据、依据什么信息作出判断、修改了哪些内容。如果操作出现错误，还要具备相应的回溯和回滚机制。

蔡彦斌特别提到，回滚不一定发生在数据库层面，不同业务需要采用不同的技术手段。SAP Business AI Platform 承担了相关运行治理和追踪能力，Joule Studio 则将测试与验证纳入 Agent 开发、发布流程。

对于管理者而言，能够看到 Agent 完成了多少工作还不够，还需要判断它是否遵循了业务规则，以及出现异常时能否及时干预。

在蔡彦斌看来，随着更多执行工作交给 Agent，人的职责可能逐渐向管理和策略层转移。但具体能放开多少权限，需要根据不同业务场景的风险和可靠性要求决定。

从软件走向机器人，业务指令直接进入工厂

SAP 的自主运营企业愿景，也开始向物理 AI（Physical AI）延伸。

蔡彦斌认为，中国在制造业、仓储物流和机器人产业方面具有较好的基础。一些 SAP 客户已经在仓库中使用机器人拣货、配货，随之产生了将机器人与仓库管理系统、业务智能体连接起来的需求。

在 SAP 与英特尔成都工厂的合作中，仓库管理系统中的拣配任务可以通过业务智能体传递给机器人。机器人完成零部件拣选与配送后，执行结果再反馈给企业业务系统。其中，SAP 负责理解和协调企业业务指令，机器人合作伙伴负责将任务转化为具体的物理动作。

SAP 方面介绍，相关方案针对原有人工拣配、安检和跨区域配送流程进行了优化，并给出了可减少约 90%人工工作量的测算。

对 SAP 而言，Physical AI 延续了其在企业软件领域的思路：机器人可以来自不同厂商，但需要接入企业原有的仓储、制造和管理流程，避免形成新的独立系统。

蔡彦斌表示，SAP 并不打算开发通用大模型，而是希望将对企业业务和行业的理解，融入可治理的 AI 框架，再与本地模型和技术生态结合。

中国研发团队也在这一过程中承担新的角色。过去，SAP 在中国的重要工作之一是将全球软件进行本地化。如今，中国研究院除了承担数据、应用、智能体和平台层面的研发，还希望将中国市场形成的 AI 实践引入全球产品体系。

柯曼认为，SAP 分布在德国、中国、美国和印度等地的研发网络，有助于理解不同市场的数据、业务流程和监管要求。对于大量开展国际业务的中国企业，AI 如果要参与供应链管理和跨国业务执行，还必须理解不同国家和地区的规则。

技术跑得很快，但企业全面融入“还有很长的路要走”

实际上，企业的准备程度仍然制约着 AI 落地。在 SAP 此前发布的《2026 年 SAPAI 价值报告》显示，目前仅有 6%的中国受访企业表示已为智能体 AI 做好充分准备。对此，柯曼指出，一些企业尚未找到真正能够产生业务价值的 AI 应用场景，另一些则因模型技术迭代过快而选择观望，担心过早投入后很快面临新一轮技术升级。

蔡彦斌也认为，中国企业要把 AI 全面融入核心业务，还有相当长的路要走。企业多年来积累的数据和流程资产，将在这一过程中发挥重要作用，但前提是先把这些资产整理成 AI 能够理解、调用和执行的业务体系。

SAP 希望通过 Agent 改变企业软件的使用方式，同时保留 ERP 承载核心业务规则和流程的作用。对企业来说，接下来需要解决的，是如何让越来越多的 Agent 在真实业务中协同运行，并在明确的权限和责任边界内完成工作。
