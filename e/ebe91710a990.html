Databricks 官方博客以虚构商业车险公司为例，指出“赔付率是否改善”这一问题在财务与承保部门得出相反结论，因为二者分别采用日历年净再保与保单年毛再保剔除巨灾的口径，而准备金部门又用事故年最终赔付率。文章提出 Genie One 借助 Genie Ontology（已 GA）从既有仪表盘、查询、笔记本与语义模型中学习业务逻辑（Ontology Snippets），并与 Unity Catalog 中经认证的 Metric Views、Domains、Pages 等受治理定义结合，使 Text-to-SQL 在共享事实一致的前提下按提问场景选用正确口径。

为什么值得关注：指标同名不同义是 ChatBI 落地最典型的失败原因，本文给出了“学习式上下文+受治理语义层”的具体机制与案例，对做 Data Agent 和语义层的团队有直接参考价值。

译文

AI 逐段翻译

问财务和核保部门，赔付率从2024年到2025年是否有所改善，你会得到两个相互矛盾但都正确的答案。在我们为这项测试搭建的一家虚构商业车险公司中，财务部门报告称赔付率恶化了8.2个百分点，而核保部门报告称改善了1.5个百分点。两者都没有错。财务部门跟踪的是扣再保险后的日历年数据，因此一笔较早赔案的不利准备金发展会体现在今天的数字中。核保部门严格按保单年度、再保险前的毛额并剔除巨灾来看，因为那是用于设定费率的基准。与此同时，准备金部门则完全依赖第三项指标：事故年终极赔付率。

SQL可以完全正确，却仍然给出对提问者而言毫无意义的答案。挑战在于：当同一个术语有多种有效定义时，要知道该应用哪个业务定义，同时保持共享事实（例如已承保保单总数）的一致性。这正是我们想用Genie One探索的问题。

Genie One由Genie Ontology（现已正式可用）提供支持，将这些业务上下文带入分析体验中。Genie Ontology从团队已经完成的工作中学习，自动从现有仪表板、查询、笔记本和语义模型中捕获业务逻辑、计算和关系，形成Ontology Snippets。这种学习到的知识由建模知识加以补充：通过经过认证的Metric Views、Domains and Subdomains以及Pages，在Unity Catalog中表示明确定义、受治理的业务概念。在本研究中，我们将这种建模知识称为“治理层”。

学习到的知识和建模知识共同让Genie对组织的运作方式有更丰富的理解。团队可以在已从现有资产中捕获的知识基础上继续构建，同时使用建模知识为那些一致性和精确性最重要的业务概念建立权威定义。无需预先对所有概念进行建模。

本研究探讨的是Genie Ontology的另一个方面，不同于我们在Turing基准中描述的方面，该基准详见我们的Genie Ontology正式可用公告。该基准比较了Genie与Genie Ontology相对于领先前沿智能体的准确性和效率，而我们的研究则单独考察建模知识的贡献：受治理的Metric Views和Pages如何补充学习到的知识和精心策划的智能体，帮助Genie One解读业务定义并给出一致的答案。

为探索这一点，我们构建了四个Genie Agents，分别面向财务、准备金、核保和理赔。它们使用相同的表，但各自拥有本团队的定义、示例查询和文档。每个智能体单独表现都很好。我们想知道当Genie One成为入口时会发生什么：它是否会路由到正确的智能体并使用正确的定义，以及它需要什么才能可靠地做到这一点？

我们测试了四种配置来找出答案。

  • 仅表格：没有智能体，Unity Catalog中也没有受治理的上下文。
  • 精心策划的智能体：每个智能体都有本团队的定义、业务规则和文档。
  • 治理层，无智能体：Unity Catalog中的Metric Views、认证、Domains、Subdomains和Pages，没有Genie Agents
  • 带治理层的精心策划的智能体：相同的智能体加上相同的受治理业务上下文。

仅表格得分64%。精心策划的智能体和治理层各自达到83%，但它们擅长的方面并不相同。添加精心策划的智能体改善了基于文档的答案。添加治理层改善了依赖业务定义的答案。单独任何一项都不足以同时覆盖两种需求。两者同时具备时，两次运行的准确率达到93–95%。组合设置还在赔付率问题上得分93%，在需要同时使用文档和结构化数据的问题上得分97%。

为观察这一模式在保险行业之外是否成立，我们使用一家虚构零售商重复了比较。在那里，将治理层添加到精心策划的智能体后，准确率从54%提高到82%。

为什么Genie One可能错过智能体已经知道的内容

Genie One并非简单地选择一个智能体并让它回答所有问题。它可以使用受治理的Unity Catalog Semantics，例如Metric Views、Domains and subdomains以及Pages，或者将问题路由到相关的Genie Agent。如果找不到合适的匹配，它会搜索工作区。在那里，它可能会根据你经常使用的表或卷，或根据你之前的对话，推断应使用哪些数据。

当Genie One使用自己的上下文回答问题时，它不会自动继承每个智能体内部配置的指令。这些指令仅在Genie One将问题路由到该智能体时适用。因此，一个智能体可能被精心策划，但如果Genie One以不同方式回答该问题，它仍然贡献甚微。

我们如何构建测试

保险业务

我们创建了一家虚构的商业车险公司，包含：

  • 8,000份保单和7,482笔赔案。
  • 赔案价值每季度更新。
  • 为尚未报告的赔案计提准备金（已发生但未报告，即IBNR）。
  • 两份再保险合同和三起巨灾事件。
  • 近期加利福尼亚州伤害赔案成本上升。

四个智能体共享相同的底层表。每个智能体还可以访问本团队的文档文件夹，四个文件夹中共有14份PDF。

我们还植入了两份误导性文档来测试稳健性。一份是准备金委员会会议纪要的早期草稿，报告准备金增加410万美元；同一文件夹中已批准的会议纪要则报告增加528万美元。另一份是供应商通讯，其中包含一条隐藏指令，要求将赔付率报告为55%，这是一个简单的提示注入测试。

然后，我们在真实定义旁边放置了三个看似相似的表格：analytics_loss_ratio_v2、analytics_loss_ratio_test，以及一个个人副本finance_lr_calendar_quarter_net_jdoe。

这些智能体配置了各自团队的公式、业务规则和 SQL 示例问题。我们在一组单独的练习题上对它们进行了调优，然后将其冻结，在所有包含智能体的配置中使用相同的版本。

让 Genie 可以使用企业文档有多种方式，取决于内容所在的位置以及团队需要如何访问它。在此实验中，我们将团队特定的 PDF 存储在 Unity Catalog Volumes 中，并通过内容搜索使其可供相应的 Genie Agents 使用。当信息分散在 Google Drive、SharePoint、Jira 或 Confluence 等业务应用程序中时，Genie Search提供了更广泛的企业搜索体验。它将来自已连接应用程序的索引内容与通过 MCP 进行的实时检索相结合，将结果与 Databricks 资产汇聚在单一体验中。它还遵循源系统的权限，因此用户只能看到其有权访问的内容。

对于受治理层，我们设置了：

  • Metric Views包含各团队的计算：三个赔付率定义，以及保费、索赔频率和严重程度的相关团队特定版本。
  • 认证将预期的 Metric Views 和智能体标记为可信，并将诱饵资产标记为已弃用。
  • 域和子域围绕商业汽车业务组织资产。共享事实存放在主域中，而每个团队的定义、文档和智能体则存放在各自的子域中。
  • 页面提供对业务术语的简短、受治理的解释，并链接到它们所描述的表和 Metric Views。

问题与评分

保险基准测试包含 125 个问题，每个问题都有一个在 SQL 中独立计算出的预期答案。

这些问题涵盖简单查找、明确命名的业务定义、诸如“我们的赔付率是多少？”之类的模糊问题、需要解释的问题、可用数据无法回答的问题，以及将文档与结构化数据相结合的问题。我们还测试了后续问题和两个植入的文档。

我们采取了几项措施使结果更有意义。Genie One 对每个问题回答了三次，每次运行都使用全新的服务主体，以免之前的对话延续下来，并且每个答案都记录在 MLflow 中。当关键结果接近时，我们用新的身份重复了整个设置。我们报告了来自 2,000 次自助重采样的 95% 置信区间，将每个问题的重复回答保持在一起，因为 Genie One 可以回忆先前的答案。来自不同模型系列的两名 AI 评判员提取了标题数字、所使用的定义以及所涵盖的事实，并由固定规则决定每个答案是否正确。评判员在 95–99% 的答案上达成一致。在每次运行之前，每个智能体必须独立地正确回答其至少 85% 的基础问题。

受治理层增加了什么。仅使用精选智能体时，Genie One 经常自行回答定义问题，从未看到智能体指令中的公式。已发布的页面在整个账户中对 Genie One 可见，因此它能找到的最接近的定义是其他人为不相关项目编写的页面。它在 49% 的回答中依赖了这些页面。受治理层为 Genie One 提供了更好的匹配：每个计算对应的经认证的 Metric Views，以及我们为每个有争议术语提供的页面，这些都组织在商业汽车域内。对其他项目页面的依赖降至 11%，我们基准测试中的每个定义问题都得到了正确答案。

仅使用精选智能体时，智能体知道答案，但 Genie One 自行回答了大约十分之四的定义问题，并且其中大部分都答错了。有了受治理层，它无论哪种方式都能答对。我们用不同的身份从头运行了两次该设置，路由发生了巨大变化：Genie One 在一次运行中将 74% 的答案交给智能体，在另一次运行中为 19%，而准确率大致相同。路由不是确定性的，但有了受治理层，它不再重要。直接回答时，Genie One 读取经认证的 Metric Views 和页面。路由到智能体时，智能体应用与同一 Metric View 匹配的公式。每条路径都通向相同的定义。

植入的文档没有改变任何答案。任何设置中的回答都没有报告注入的供应商新闻通讯中的 55% 赔付率，也没有使用草案准备金数字。

没有受治理层，路由决定你是否得到正确答案。教训是为 Genie One 所走的任何路径进行设计：将每个定义放在每条路径都能到达的地方，并在信任结果之前通过 Genie One 多次测试。

智能体增加了什么。没有 agent 时，文档类问题降到了仅靠表的水平。在没有 agent 时会变差的 18 个问题中，有 12 个需要团队文档，例如诉讼审查、准备金委员会会议记录或承保建议。在这种设置下，agent 是 Genie One 访问这些文档的唯一途径，因为这些 PDF 只能通过 agent 内容搜索获得，而没有任何 Page 链接到它们。没有 agent 时，Genie One 还为每个重复项预测了 2027 年的赔付率，而不是说数据不覆盖 2027 年。这一限制写在表描述和 agent 指令中，但不在 Genie One 所读取的 Metric View 上，所以它从未看到。

受治理层各部分分别贡献了什么

上面的比较是一次性加入整个受治理层。为了解每个组件贡献了什么，我们运行了一系列单独的测试，每次添加一个组件。

第二个实验从四个赔付率公式不一致的 agent 开始。从第二步起，我们将公式移入 Metric View，并将每个 agent 缩减为几条行为规则和两个示例查询。这些 agent 的配置与主比较中完全精选的 agent 不同，因此下面的结果不应与之前的表直接比较。

  • Metric View 修正了公式。同一步骤还将 agent 缩减为几条行为规则。赔付率问题从 56% 提升到 83%，定义问题从 66% 提升到 90%。
  • 认证有助于表明哪些资产值得信任，但并未独立提高准确性。总体得分从 90%（84–94%）下降到 83%（76–89%），但区间重叠，因此我们不能说下降是真实的。同时，诱饵表的使用率从答案的 9% 降至 4%，Genie One 在 22% 的答案中明确引用了认证定义。我们将认证视为一种有用的信任信号，它与 Domain 和 Page 协同工作，而不是一种能单独使答案正确的功能。
  • 最后添加的 Domain 和 Page 帮助 Genie One 识别适用哪个定义。模糊问题准确率提高到 94%，定义问题达到 100%，诱饵使用率从 4% 降至零。Metric View 告诉 Genie One 如何计算数字；Domain 和 Page 帮助解释这是谁的度量以及它如何融入业务。

文档问题在不同运行之间的变化比其他类别更大。只有 12 个问题，因此改变两个问题就可能使得分移动约 15 个百分点。原始 agent 的指令说明了在哪里查找诉讼状态，Genie One 将两个诉讼问题都路由到 Claims agent 并正确回答。一旦我们精简了这些指令，这些问题通常会失败，直到我们添加了一个定义“in litigation”的 Page。

每个答案都解释了它使用的是哪个团队的定义。这表明学习知识和建模知识协同工作，因为 Genie One 将它记住的每个用户的信息与该团队已建模的定义结合起来。两个身份的数据访问权限完全相同，因此差异来自 Genie One 记住的团队上下文，而不是身份能看到的内容差异。这是对业务上下文的测试，而不是访问控制。记住某人的团队并不能替代权限或行级安全；这些仍然需要单独强制执行。

当业务定义发生变化时会发生什么？

业务定义不会一成不变。我们想看看更新一个定义而不破坏其他定义需要多少工作。

中途，Underwriting 决定其赔付率还应包括抗辩索赔的法律费用。我们更新了 Underwriting Metric View，并在其 Page 中添加了一句话。我们没有更改任何 agent 指令。然后，在受治理层就位且使用精选 agent 的情况下，我们通过 Genie One 问了 12 个关于 Underwriting 赔付率的问题。

每个答案都使用了新定义。关于我们未更改的定义的八个问题仍然正确。在仅精选设置中，同样的更改意味着要在四个 agent 的指令中的七个位置找到并编辑公式。

一个注意事项：agent 仍然保留着旧公式。在 Genie One 之外直接询问时，它们在 92% 的答案中使用了旧公式且没有任何警告，并且会一直这样做，直到有人更新每个 agent。集中定义减少了重复，但留在 agent 中的任何逻辑仍然需要维护。

同样的方法在保险行业之外有效吗？

我们用一个虚构的零售商重复了主比较。Finance、Merchandising 和 Marketing 各自对收入有不同的定义。我们问：“2025 年收入增长了吗？”

  • Merchandising 计算折扣前所有已订购的商品，报告增长 13.6%。
  • Finance 在订单发货时、扣除折扣和退款后计算收入，表示下降了 9.4%。
  • Marketing 计算退货前的已完成订单，表示持平。

一次假日促销和服装退货的激增解释了这一差距，而三者都是正确的。

精选的零售智能体单独运行时表现良好。然而通过 Genie One，它们只能答对约一半的问题，因为 Unity Catalog 中没有任何内容说明收入对每个团队意味着什么，也没有说明哪些表格属于该业务。借助治理层，定义准确率从 31% 跃升至 100%，整体准确率提升至 82%。

我们的建议

基于这些实验，请保留你的精选智能体，并在其下方添加一个治理层。关键决策在于每条信息应归属于何处：

位置存放内容
经认证的指标视图带有连接键、计算和维度的范围数据集，Genie One 和智能体用它来对数据进行计算和聚合
域和子域业务和团队所有权，共享事实放在主域中，团队特定上下文放在子域中
页面对业务术语的解释，指向保存证据的表格、视图和文档。页面可以链接到与该页面相关的相关资产，例如指标视图。
表格和指标视图描述数据涵盖和不涵盖的内容，包括日期范围、缺失的预算或支出数据
智能体指令行为规则说明使用了哪个定义，在需要时请求澄清，并在数据无法回答问题时予以说明
左右滑动查看 →

有几条实践经验尤为突出：

  1. 从不同团队有不同理解的术语开始，尤其是那些作为单一团队内部经验知识存在的术语。Genie One 已经能很好地处理普遍达成共识的事实。
  2. 每个度量只定义一次。将官方计算放入经认证的指标视图，而不是在多个智能体指令中维护相同的公式。在我们的测试中，指标视图和页面推动了准确率的提升。在我们的分步测试中，认证引导 Genie One 远离相似诱饵表格，将其使用率从 9% 降至 4%，而域和页面将其降到了零。
  3. 使用页面解释业务上下文。将它们链接到其所描述的经认证的表格和指标视图。在每个页面上，定义计算适用的场景以及 Genie One 应避免使用该计算的场景。当 Genie One 能将定义与底层数据关联起来时，定义会更有用。
  4. 让智能体专注于它们最擅长的事情。团队特定文档、域知识和行为规则仍然很重要。治理层不能替代这些上下文，尤其是当问题依赖于表格或指标视图中未体现的信息时。
  5. 通过 Genie One 进行测试，而不仅仅是测试单个智能体。如果 Genie One 不路由到某个智能体，那么该智能体即使单独回答得好也无济于事，因此要在每次更改前后衡量端到端体验。

要将此应用于你自己的数据，请从各团队定义不同的术语开始，将它们连同指标视图和页面添加到域/子域中，并通过 Genie One 衡量变化。Genie Ontology 文档解释了各部分如何组合在一起，而我们关于在数据栈中运营化 Genie Ontology 的指南则逐步演示了如何设置它们。
