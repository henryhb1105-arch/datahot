ClickHouse 26.8 引入管道式 SQL 语法

DataHot 主播约 1 分钟精华朗读
0:00 / 0:56
DataHot 速览

ClickHouse 26.8 新增基于 |> 运算符的管道式 SQL，让多阶段查询可以写成一系列清晰的变换序列，简化原本需要嵌套子查询或 CTE 的复杂查询。官方文章以英国房产价格数据集为例，对比了传统 SQL、FROM 前置（自 22.12 起）与管道式写法的差异，并展示伦敦各行政区 2024 年以来房产中位价 Top10 的查询结果。该语法延续了 ClickHouse 对 FROM 优先写法的支持，进一步提升了复杂分析 SQL 的可读性。

为什么值得关注：ClickHouse 是实时分析场景的重要数据平台，管道式 SQL 直接影响复杂分析查询的编写与维护方式，值得数据分析工程师和 BI 开发者关注。

在后台运行查询

由 Miсhael Stetsyuk 贡献

现在可以在后台运行查询了。查询会立即返回，然后运行直至完成，无论你的连接发生什么情况。

此功能适用于将数据摄入 ClickHouse 或从中导出数据的长时间运行查询，使它们即使客户端断开连接也能继续运行。

我们运行着一个 ClickHouse 服务器，其中导入了 英国房产价格数据集，然后使用以下查询复制了几次：

1ALTER TABLE uk_price_paid2ATTACH PARTITION ID 'all'3FROM uk_price_paid;

这样我们就得到了略多于 2.4 亿行数据：

1SELECTcount() FROM uk_price_paid;
1┌───count()─┐2│ 243619704 │3└───────────┘

接下来，我们可以运行以下查询，将 uk_price_paid 表中的数据写入本地 HTTP 服务器上的一个文件。

1INSERT INTOFUNCTION url('http://localhost:8080/uploads/london-sales.parquet', 'Parquet')2SELECT*FROM uk_price_paid3SETTINGS run_query_in_background =1;
1Query id: 59eabb9f-33f4-412b-b2f3-b090fe7b4bbf23Ok.450 rows inset. Elapsed: 0.001 sec.

我们可以查询 system.processes 来检查后台查询的进度：

1SELECT query_id, query,2      round(elapsed, 2) AS elapsed_seconds,3      read_rows, written_rows4FROM system.processes5WHERE query NOT ILIKE '%system.processes%'6ORDERBY elapsed DESC;
1Row 1:2──────3query_id:        59eabb9f-33f4-412b-b2f3-b090fe7b4bbf4query:           INSERT INTO FUNCTION url('http://localhost:8080/uploads/uk.parquet', 'Parquet')5SELECT * FROM uk_price_paid6SETTINGS run_query_in_background = 1;7elapsed_seconds: 8.528read_rows:       179243204 -- 179.24 million9written_rows:    179243204 -- 179.24 million

1SELECT event_time, type, query_duration_ms,2      read_rows, result_rows3FROM system.query_log4WHERE query_id ='59eabb9f-33f4-412b-b2f3-b090fe7b4bbf'5ORDERBY event_time;

PostgreSQL 风格的正则表达式运算符

由 Alexey Milovidov 贡献

ClickHouse 现在支持以下 PostgreSQL 风格的正则表达式运算符：

  • ~ 当字符串与正则表达式匹配时返回 1，使用区分大小写的匹配。
  • ~* 当字符串与正则表达式匹配时返回 1，使用不区分大小写的匹配。
  • !~ 当字符串与正则表达式不匹配时返回 1，使用区分大小写的匹配。
  • !~* 当字符串与正则表达式不匹配时返回 1，使用不区分大小写的匹配。

以下查询展示了如何使用所有运算符来匹配术语 Baker Street 的各个部分：

1SELECT2'Baker Street'~'street$'AS matchesCaseSensitively,3'Baker Street'~*'street$'AS matchesCaseInsensitively,4'Baker Street'!~'street$'AS doesNotMatchCaseSensitively,5'Baker Street'!~*'street$'AS doesNotMatchCaseInsensitively6FORMAT Vertical;
1Row 1:2──────3matchesCaseSensitively:        04matchesCaseInsensitively:      15doesNotMatchCaseSensitively:   16doesNotMatchCaseInsensitively: 0
一个小免责声明： 这些运算符附带了实现者 Alexey 的免责声明：他并不喜欢它们，并认为它们让 SQL 看起来太像 Bash 或 Perl 了。PostgreSQL 兼容性这一轮胜出。同样的变更意味着 psql 命令，例如 \d、\dt 和 \dv，现在通过 PostgreSQL 线协议连接到 ClickHouse 时也能正常工作。但是，\d <table> 仍然使用一些 ClickHouse 尚不支持的 PostgreSQL 语法。

数组作为数组下标

由 folly 贡献

下标运算符现在接受一个索引数组，并返回所有给定位置上的元素。这使得可以在单个表达式中收集、重排或采样数组元素，与 arraySort 和 topK 风格函数一起使用时非常方便。

让我们看一个简单的例子：

1WITH arrayMap(x -> rand(x), range(1, 10)) AS random_values2SELECT random_values[[1, 3, 5]];
1┌─arrayElement(ran⋯ues, [1, 3, 5])─┐2│ [344408953,1157293782,407846805] │3└──────────────────────────────────┘

一个更现实的用法是从月度时间序列中选择季度检查点。以下查询构建每个地区月度中位价格的有序数组，然后在一个表达式中选择一月、四月、七月和十月：

查询转 JSON 再转查询

由 Alexey Milovidov、Nikita Fomichev 贡献

现在可以将查询转换为其 JSON 格式的抽象语法树，并使用 JSON 格式的抽象语法树查询 ClickHouse。

这个 parseQueryToJSON 函数返回 JSON 格式的抽象语法树。我们将使用一个简单的 count() 来演示这个函数，因为其输出极其冗长：

1SELECT parseQueryToJSON($sql$2SELECTcount() FROM uk_price_paid3$sql$)::JSON4FORMAT Vertical;
1{2"type":"SelectWithUnionQuery",3"union_mode":"UNION_DEFAULT",4"list_of_selects":{5"type":"ExpressionList",6"children":[7{8"type":"SelectQuery",9"select":{10"type":"ExpressionList",11"children":[12{"type":"Function","name":"count",13"arguments":{"type":"ExpressionList"}}14]15},16"tables":{17"type":"TablesInSelectQuery",18"children":[19{"type":"TablesInSelectQueryElement",20"table_expression":{21"type":"TableExpression",22"database_and_table_name":{23"type":"TableIdentifier","name":"uk_price_paid"}}}24]25}26}27]28}29}

该 JSON 将查询描述为一棵由带类型节点组成的树：标识符、字面量、函数和子句。

由于它就是普通的 JSON，任何带有 JSON 库的语言都可以分析、验证、重写或生成查询，而无需嵌入 SQL 解析器。

转换是双向的：formatQueryFromJSON 会将树转换回 SQL，因此你始终可以读回你所构建的内容：

1SELECT formatQueryFromJSON(parseQueryToJSON($sql$2SELECTcount() FROM uk_price_paid3$sql$));
1┌─formatQueryFromJ⋯_price_paid\n'))─┐2│ SELECT count() FROM uk_price_paid │3└───────────────────────────────────┘

ClickHouse 26.8 还添加了一个实验性方言，clickhouse_json，它允许你发送 JSON AST 而不是 SQL。它被 enable_json_ast_dialect 设置所控制，然后像任何其他方言一样选择：

1SET enable_json_ast_dialect =1, dialect ='clickhouse_json';

如果我们粘贴之前创建的 SELECT count() FROM uk_price_paid 的 AST，我们会得到：

1┌───count()─┐2│ 243619704 │3└───────────┘

我们并不期望你开始将查询编写为 JSON 语法树！此功能更多是面向机器而非人类。

任何生成查询的东西都可以生成 JSON 语法树而不是 SQL，这意味着不需要字符串拼接，不再有可怕的转义错误，也许最重要的是，没有 SQL 注入面。

CREATE USER ... VALID FOR

由 Alexey Milovidov 贡献

在 ClickHouse 26.8 之前，已经可以使用 VALID UNTIL 语法创建有时间限制的用户：

1CREATEUSER mark2IDENTIFIED WITH no_password3VALID UNTIL '2026-10-04';

ClickHouse 26.8 添加了 VALID FOR INTERVAL 语法，它从当前时间开始计算截止时间。因此，要让用户从现在起两周内有效，我们会运行以下查询：

1CREATEUSER mark2IDENTIFIED WITH no_password3VALID FORINTERVAL2 WEEKS;

然后我们可以检查该用户的有效期到什么时候：

1SHOWCREATEUSER mark2FORMAT LineAsString;

此查询的输出会全部在一行上，因此我们为了便于阅读手动进行了格式化：

1CREATE USER mark 2IDENTIFIED WITH no_password 3VALID UNTIL '2026-09-18 10:06:29'

我们也可以在修改用户时使用此语法。要让用户改为从现在起一周内有效，我们会运行以下查询：

1ALTERUSER mark VALID FORINTERVAL1 WEEK;
1CREATE USER mark 2IDENTIFIED WITH no_password 3VALID UNTIL '2026-09-11 10:08:34'

原子 POPULATE

由 Alexey Milovidov 贡献

一个 增量物化视图 等同于一个触发器，它在数据块插入表时对数据块运行查询。

在创建增量物化视图并在创建时填充它时，一个竞态条件会导致它跳过在填充期间插入的记录。在 ClickHouse 26.8 中，此问题已修复。

当你调用 CREATE MATERIALIZED VIEW ... POPULATE 时，视图会订阅源表上的新插入，并且现有数据的快照会一并捕获，在源表上短暂持有排他锁，这样每一行与填充并发插入的行都会被恰好传递一次。

此功能默认启用，但我们可以通过将 materialized_views_populate_atomically 设置为 0 来禁用它，这样我们可以演示之前的行为。

首先，让我们创建一个包含 100,000 行的源表：

1CREATE TABLE src (id UInt64) 2ORDERBY id;3INSERT INTO src 4SELECT number FROM numbers(100000);

再创建一个目标表：

1CREATE TABLE dst (id UInt64) 2ORDERBY id;

接下来，我们将让一个查询插入 50 行，另一个查询创建一个填充 dst 表的物化视图。

要让一行掉进间隙，它的 INSERT 必须在 POPULATE 获取源表快照时仍处于进行中。大多数插入完成得太快，不会出现这种情况，因此我们使用 sleepEachRow 将 50 行分散到大约两秒半内，并在该插入仍在运行时启动 CREATE。

我们还将 POPULATE 与 TO 一起使用，这在 26.8 之前是语法错误。该视图会从 dst 表中已有的数据回填现有的 src 表。

1./clickhouse client -q "2  INSERT INTO src SELECT number + 100000 FROM numbers(50)3  WHERE sleepEachRow(0.05) = 0;" &45sleep 0.567./clickhouse client -m -q "8  SET materialized_views_populate_atomically = 0;9  CREATE MATERIALIZED VIEW mv TO dst10  POPULATE AS SELECT id FROM src;"1112wait

一旦此操作运行完成，我们可以将源表与目标表进行比较：

1SELECT (SELECTcount() FROM src) AS sourceRows,2       (SELECTcount() FROM dst) AS dstRows,3       (SELECT uniqExact(id) FROM dst) AS dstDistinct,4       sourceRows - dstRows AS lost,5       dstRows - dstDistinct AS duplicated6FORMAT PrettyCompact;
1┌─sourceRows─┬─dstRows─┬─dstDistinct─┬─lost─┬─duplicated─┐2│     100050 │  100000 │      100000 │   50 │          0 │3└────────────┴─────────┴─────────────┴──────┴────────────┘

所有 50 条记录都在源表中，但目标表中一条也没有。该插入在 mv 存在之前就开始了，所以它没有推送到该视图，并且它在填充快照获取之后才提交，所以回填也没有看到它。

正好是 50 条，因为插入在查询开始时一次性决定哪些视图将接收其数据，而不是按行或按块决定。因此整个插入要么到达，要么不到达。

如果我们删除 mv、src 和 dst，然后重新创建 src 和 dst，我们可以创建物化视图，但这次将 materialized_views_populate_atomically 设置为 1：

1./clickhouse client -q "2  INSERT INTO src SELECT number + 100000 FROM numbers(50)3  WHERE sleepEachRow(0.05) = 0;" &45sleep 0.567./clickhouse client -m -q "8  SET materialized_views_populate_atomically = 1;9  CREATE MATERIALIZED VIEW mv TO dst10  POPULATE AS SELECT id FROM src;"1112wait

而这次，当我们统计每个表中的记录数时，会得到以下输出：

1┌─sourceRows─┬─dstRows─┬─dstDistinct─┬─lost─┬─duplicated─┐2│     100050 │  100050 │      100050 │    0 │          0 │3└────────────┴─────────┴─────────────┴──────┴────────────┘

日语和中文分词器支持

由 Robert Schulze、Amos Bird、Jimmy Aguilar Mena 贡献

ClickHouse 中的默认分词器（被 tokens、hasAllTokens 和 hasAnyTokens 函数使用）是 splitByNonAlpha，它按空白和标点字符将字符串拆分为子字符串数组。与英语和其他印欧语言不同，中文和日文文本词之间没有空格，因此需要专门的分词器。

26.8 通过两个专门构建的分词器解决了这个问题：

  • japanese - 日语分词器依赖于 MeCab 形态分析器，并且需要在服务器配置中指定外部 MeCab 词典
  • chinese - 一个 jieba 风格的分词器，结合词典与 HMM（隐马尔可夫模型）来切分未知序列，例如将 ClickHouse是一个快速的开源数据库 拆分为 ClickHouse、是、一个、快速、的、开源、数据库，而不是一整块或单个字符。

日语

要使用日语分词器，你首先需要配置一个词典。在此示例中，我们将使用 UniDic。从网站下载 .zip 归档后，你需要获取该归档的 SHA256，ClickHouse 会在加载词典之前用它来验证词典：

1sha256sum /var/lib/clickhouse/unidic-cwj-202512.zip
1d94216b589d15d05c408ed59abc5259086703ebbac14e225b5314e4cd106c4db

在 /etc/clickhouse-server/config.d/tokenizers.xml 中添加一个新的分词器，以定义自定义配置，该配置会在服务器启动时合并到你的主 config.xml 文件中。

1<clickhouse>2<tokenizer>3<japanese>4<dictionary_location>file:///var/lib/clickhouse/unidic-cwj-202512.zip</dictionary_location>5<dictionary_sha>d94216b589d15d05c408ed59abc5259086703ebbac14e225b5314e4cd106c4db</dictionary_sha>6</japanese>7</tokenizer>8</clickhouse>

注意

你也可以通过 HTTP/HTTPS URL 或 S3 兼容存储指定词典

如果你的服务器已经在运行，请务必重启它，以便配置生效。现在你可以创建文本索引并像这样查询它：

新的 tokenizer：icu 和 splitByRegexp

由 Jimmy Aguilar Mena 贡献

虽然 Jieba 是为简体中文和繁体中文设计的，而 MeCab 主要面向日语——ICU（International Components for Unicode）是一个通用的、基于规则的多语言库，使用标准的边界分析算法，那么我们或许可以合理地问：如何为其他不在单词之间放置空白字符的语言（例如泰语、老挝语、高棉语或缅甸语）进行文本分词？

26.8 版为 ClickHouse 新增了一个 icu(locale) tokenizer，它使用该库的 Unicode 单词切分将字符串拆分为单词词元。对于不在单词之间放置空白字符的文字系统，ICU 会应用基于词典的分词，确保文本被拆分为有意义的多字符单词，而不是单个字符。

在 26.8 之前，如果你尝试使用像 asciiCJK 这样的非 ASCII tokenizer 为泰语、老挝语、高棉语或缅甸语文本分词，你会遇到单字符碎片化问题，因为 asciiCJK 将每个非 ASCII 字符视为其自身的词元。以泰语词 บ้าน（“house”）为例：

1SELECT tokens('บ้าน', 'asciiCJK');
1┌─tokens('บ้าน', 'asciiCJK')─┐2│ ['บ','้','า','น']          │3└───────────────────────────┘

บ 和 น 是辅音，้ 是声调符号，า 是元音符号，因此分词将该词拆成了四个无意义的片段。 hasAllTokens 只检查每个 needle 片段是否存在于该行中的某处，因此两个完全无关的真实泰语词可以各自贡献一个片段，并在针对“house”的搜索中，对像“The horse is on the mountain”这样完全无关的句子产生假阳性：

1-- "ม้าอยู่บนภูเขา" = "The horse is on the mountain" (no usage of "house")2SELECT tokens('ม้าอยู่บนภูเขา', 'asciiCJK');
1┌─tokens('ม้าอยู่บนภูเขา', 'asciiCJK')──────────────────────┐2│ ['ม','้','า','อ','ย','ู','่','บ','น','ภ','ู','เ','ข','า'] │3└───────────────────────────────────────────────────────┘
1SELECT hasAllTokens('ม้าอยู่บนภูเขา', 'บ้าน', 'asciiCJK');
1┌─hasAllTokens⋯'asciiCJK')─┐2│                        1 │3└──────────────────────────┘4-- false positive

将其与使用 icu tokenizer 且将 locale 设置为 th 时发生的情况进行比较：

1SELECT tokens('ม้าอยู่บนภูเขา', 'icu', 'th');

对于需要更多控制的情况，26.8 引入了 splitByRegexp tokenizer，它允许你使用正则表达式作为分隔符，将文本拆分为词元。

ClickHouse 的默认 tokenizer splitByNonAlpha 会在每个非字母数字 ASCII 字符处拆分，这意味着像 C++、C# 和 F# 这样的文本都会坍缩为同一个裸字母：

1SELECT2    tokens('C++', 'splitByNonAlpha'),3    tokens('C#', 'splitByNonAlpha'),4    tokens('F#', 'splitByNonAlpha')5FORMAT Vertical;
1tokens('C++'⋯yNonAlpha'): ['C']2tokens('C#',⋯yNonAlpha'): ['C']3tokens('F#',⋯yNonAlpha'): ['F']

在实践中，这意味着搜索“C#”可能会返回像“I am an expert in C++”这样的假阳性：

1SELECT hasAllTokens('I am an expert in C++', 'C#', 'splitByNonAlpha');
1┌─hasAllTokens⋯yNonAlpha')─┐2│                        1 │3└──────────────────────────┘

此外，hasToken 会拒绝包含分隔符字符的 needle，因此使用 C++ 或 C# 根本无法在 splitByNonAlpha 下搜索字面术语。

使用 splitByRegexp，你可以显式定义分隔符模式，使字符 # 和 + 被视为单词的一部分：

1CREATE TABLE hold_my_beer2(3id UInt64,4description String,5INDEX idx description TYPE text(tokenizer = splitByRegexp('[^\p{L}\p{N}#+]+'))6)7ENGINE = MergeTree ORDERBY id;89INSERT INTO hold_my_beer VALUES10    (1, 'I am an expert in C++'),11    (2, 'I am an expert in C#'),12    (3, 'I use Arch');1314SELECT id, description FROM hold_my_beer WHERE hasAllTokens(description, 'C++') OR hasAllTokens(description, 'C#');

在 Iceberg 中预取清单文件

在从 Iceberg 表读取数据之前，ClickHouse 会读取描述其数据文件和删除文件的清单文件。获取和处理这些元数据可能会增加明显的启动时间，尤其是当它需要对对象存储发起许多请求时。

在 26.8 中，ClickHouse 在解析当前清单文件的同时预取下一个清单文件，使存储读取与 CPU 工作重叠。

删除清单也会被并发读取和解码。由于这些必须在读取数据文件之前处理，这有助于对具有许多删除文件的表的查询更快启动。iceberg_delete_manifest_decode_concurrency 设置控制一次解码多少个删除清单，默认值为 4。

此版本还修复了数据湖目录的 S3 存储桶区域缓存，避免重复请求以确定存储桶的区域。

原生 Parquet 改进

由 Alexey Milovidov 和 Vasily Chekalkin 贡献

ClickHouse 26.8 为 Parquet 读取带来了多项改进，帮助查询跳过不必要的数据。

对于带有 ORDER BY 和 LIMIT 的查询，ClickHouse 可以先读取排序和过滤所需的列，然后仅对通过限制的行获取其余列。此优化默认启用。

让我们在一个公共 Parquet 数据集中查找最近的十条事件，使用 WatchID 来打破平局：

1SELECT URL, Title2FROM s3(3'https://clickhouse-public-datasets.s3.amazonaws.com/hits_compatible/hits.parquet',4    NOSIGN5)6ORDERBY EventTime DESC, WatchID DESC7LIMIT 108SETTINGS query_plan_optimize_lazy_materialization_for_object_storage =1;

我们可以将其与通过将 query_plan_optimize_lazy_materialization_for_object_storage 设置为 0 禁用惰性读取的情况进行比较。在 ClickHouse 26.8.2.7 上的重复检查中，禁用该优化时查询从 S3 读取了大约 6.6–6.7 GB，启用时读取了 1.5 GB，返回了相同的十行。

基于字典的过滤也有助于 ClickHouse 为等值和 IN 条件跳过数据。让我们查找与特定手机型号匹配的行：

1SELECTcount()2FROM s3(3'https://clickhouse-public-datasets.s3.amazonaws.com/hits_compatible/hits.parquet',4    NOSIGN5)6WHERE MobilePhoneModel ='GT-C3262';
1┌─count()─┐2│     200 │3└─────────┘

当列块完全采用字典编码时，如果请求的值不在字典中，ClickHouse 可以跳过其行组。即使 min/max 统计信息无法排除匹配且 Bloom 过滤器不可用，这也有帮助。

启用字典过滤后，此查询处理了 12 个数据页，而禁用时处理了 226 个。两个查询都返回了 200。input_format_parquet_dictionary_filter_push_down 设置默认值为 1048576（1 MiB 字典页限制）；将其设置为 0 会禁用该优化。

GeoParquet 查询也得益于空间剪枝。ClickHouse 使用边界框信息跳过不相关的行组和页，并在行读取期间应用空间谓词。

GROUP BY 性能改进

由 Nihal Z. Miaji、Dmitriy Terenichev、Konstantin Bogdanov、Harikrishnan Prabakaran 贡献

26.8 版本还为 GROUP BY 带来了一系列性能改进，包括：

  • 一种新的并行 GROUP BY 算法，它自适应地结合了合并聚合器和拆分聚合器所使用的方法。
  • 26.7 版本为按键排序的表将 GROUP BY 与 ORDER BY LIMIT 融合。26.8 对任何读取顺序都这样做，剪除不可能出现在结果中的分组。
  • GROUP BY 使用单字符串键时，现在使用更小的哈希表单元。
  • 并行 GROUP BY 查询中的最终合并步骤现在使用多个线程，防止其成为单线程瓶颈。

我们将在单独的文章中更详细地介绍这些优化。

连接

由 Han Fei、Anton Popov、Robert Schulze、Alexey Milovidov、Vladimir Cherkasov、Alexander Gololobov 贡献

与每个版本一样，我们在连接方面有更多改进，包括：

  • 列统计信息现在在 INSERT默认对小表使用，在全部 TPC-H 基准测试中实现了 29% 的提升。
  • 条件为两个不等式的 JOIN 过去被执行为带过滤的 CROSS JOIN。它们现在将改用基于排序的 IEJoin 算法。
  • 一种新的合并连接算法 parallel_full_sorting_merge，可在所有核心上运行。输入按键的哈希分片为独立的每分片合并连接。
  • 面向分布式查询计划的基于成本的优化器。新的基于成本的优化器使用基数估计来选择分布式连接、聚合、排序和数据移动应如何执行。
