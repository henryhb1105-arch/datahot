亚马逊云科技开发者布道师Darko Mesaroš在北京分享Strands开源家族进展，指出AI Agent从写代码走向端到端任务后，生产落地受制于安全边界、决策成本与长时运行三大工程挑战。Strands Box在操作系统隔离之上叠加Dogwood策略语言，实现文件写入、网络访问、命令执行的细粒度与顺序化控制，并隔离云凭证；Strands Decider用小模型在候选项中做选择，替代大模型完成重复简易决策；同时提出Agent需支持状态持久化与任务接力，而非单次对话。

AI摘要

AI Agent正从辅助编码转向自主完成端到端开发任务，但其在生产环境的落地受制于安全边界、长时上下文管理与持续运行机制三大工程挑战。

安全边界需重定义：Agent访问生产系统必须具备细粒度权限控制与操作审计能力；决策成本须降低：通过Strands等工具链压缩推理-执行循环延迟；长期运行需新范式：Agent应支持状态持久化与任务接力，而非单次对话。

适合SRE、平台工程师、AI基础设施工程师阅读。

Agent 开始接管软件开发，亚马逊想先解决三个难题

AI Agent 正在改变软件开发的工作方式。

过去，开发者使用 AI 编程工具，通常是输入一段需求，让模型生成代码，再由人检查、修改和部署。但随着 Agent 能力增强，开发者开始尝试把更完整的目标交给 Agent：让它持续处理代码、调用工具、维护代码仓库，甚至在开发者离线时继续推进任务。

这也带来了新的工程问题：Agent 能否安全地访问生产环境？长时间运行时，如何管理上下文？多个 Agent 之间又该如何分工？

近日，在亚马逊云科技北京办公室举行的一场开发者主题媒体沟通会上，亚马逊云科技杰出开发者布道师 Darko Mesaroš围绕 Strands 开源家族、Kiro Crew 等工具进行了分享，并展示了亚马逊云科技对 Agent 开发和运行方式的一些探索。

从他的分享来看，亚马逊云科技正在尝试解决三个问题：如何给 Agent 划定安全边界，如何降低 Agent 工作流中的决策成本，以及如何让 Agent 从一次性对话变成能够长期运行的工作单元。

Agent 进入生产环境，安全边界需要重新定义

在 Darko 看来，Agent 开发面临的一个突出问题，是开发者无法完全信任 Agent。

与传统软件不同，Agent 需要处理大量开放式、非确定性的任务。开发者很难提前将所有操作写成固定规则，因此必须赋予 Agent 一定的自主性。但自主性越强，潜在风险也越大。

例如，一个 Agent 可能访问生产系统、删除文件，或者执行开发者并不希望它执行的操作。传统沙箱的思路，是将 Agent 限制在一个隔离环境中，阻止它访问某些系统资源。但问题在于，实际工作中，开发者并不可能完全禁止 Agent 访问外部资源。Agent 仍然需要调用工具、访问网络、读写文件，甚至连接云服务。

如何在允许 Agent 完成工作的同时，限制它不应该做的事情？

这是亚马逊云科技推出 Strands Box 的重要出发点。

Strands 本身是一个面向 Agent 构建和运行的开源家族，不再局限于单一的开发工具，而是覆盖 Agent 运行所需的多个环节。Darko 重点介绍了其中的 Strands Box 和 Strands Decider。

Strands Box 的核心思路，是在传统操作系统隔离之外，再增加一层策略控制。具体而言，它结合了操作系统层面的隔离机制，以及基于 Dogwood 策略语言构建的策略层。前者负责限制 Agent 能够触及的系统资源，后者则进一步判断 Agent 在允许访问的范围内，究竟可以执行什么操作。例如，开发者可以允许 Agent 访问指定网站、连接特定网络地址、运行某些 Python 命令，或者读取特定文件，但不允许它修改其他文件。

更重要的是，这套策略不仅能判断某个操作是否被允许，还能考虑操作发生的顺序、执行次数以及时间条件。举个例子，只有在测试通过之后，Agent 才能执行 git push；或者限制 Agent 每小时调用某个工具的次数，这些规则通过 Dogwood 策略语言定义，并在内核层面执行。

现场演示中，Darko 让 Agent 尝试在 README 文件中添加一行文字。由于策略没有授予文件写入权限，Agent 的操作被 Strands Box 直接拦截。随后，他修改策略文件，允许相应的写入操作，再次执行任务后，Agent 便成功完成了操作。这意味着，开发者不必完全依赖 Agent 自身的判断来保证安全，而是可以在执行层面建立确定性的约束。

Darko 还提到，Strands Box 可以将安全凭证与 Agent 本身隔离。Agent 不直接接触亚马逊云科技的访问凭证，而是在网络出口时由 Box 附加相应凭证，从而降低凭证暴露风险。

在他看来，Agent 安全的关键不是简单地限制其所有访问权限，而是让开发者能够精确控制 Agent 可以做什么、不能做什么。

小模型做决策，大模型负责复杂任务

除了安全问题，Agent 工作流中的另一个成本来自大量重复、简单的决策。在执行任务过程中，当用户提出一个需求时，Agent 可能需要判断应该加载哪个 Skill、调用哪个工具，或者将任务交给哪个执行单元，这些工作并不一定需要调用一个大型语言模型。

Darko 介绍的 Strands Decider，正是为这类场景设计的开源决策模型。

与传统大语言模型通过生成 Token 回答问题不同，Decider 主要负责在给定的选项中做出选择。开发者提供问题和候选项，模型直接判断哪个选项更合适，而不是生成一段完整文本。

Strands Decider 目前基于 Qwen 系列的 20 亿参数模型构建，同时也提供基于 Google Gemma 的模型版本。

Darko 举例称，如果需要根据用户的问题判断应该由账单团队、技术团队还是销售团队处理，可以让 Decider 直接从三个选项中进行判断，而不必把完整任务交给大型语言模型处理。在 Agent 工作流中，这类能力尤其适合 Skill 选择、任务分类和工具路由等环节。

他还提到，亚马逊内部有团队使用 Strands Decider 替代原先由大型模型承担的部分决策任务。在一个案例中，相关成本降低了约 98%，效果仍然符合预期。按照他引用的相关案例，这项调整预计每年可以节省数百万美元的 Token 成本。

这背后的思路是：并不是 Agent 工作流中的每一个环节，都需要最强大的模型。如果只是进行简单分类、路由和选项判断，使用小型专用模型可能更加经济、高效。大型模型则可以将更多计算资源集中在复杂推理、内容生成和真正需要智能判断的任务上。

Darko 认为，未来行业还会出现更多专用模型。随着企业越来越重视 Token 使用效率，没有必要为了一个简单问题，就将完整上下文发送给大型语言模型。

从单次对话到长期运行，Agent 开始拥有自己的目标

如果说 Strands Box 解决的是 Agent 能做什么的问题，Strands Decider 解决的是如何更高效地做决策，那么 Kiro Crew 则试图改变 Agent 执行工作的组织方式。

Darko 将 Kiro Crew 称为一个开源 Agent 工作空间。它基于 Kiro 的 AI 编程能力构建，但并不局限于单一编程助手，而是能够协调多个 Agent，处理软件开发中的不同任务。与开发者在一个对话窗口中反复提出指令不同，Kiro Crew 引入了 Bot 机制。

一个 Bot 拥有自己的目标，可以持续运行，不需要开发者每次都重新发出指令，例如，开发者可以让一个 Bot 负责维护某个代码仓库。它会定期检查未解决的 Issue、Pull Request、项目指标和可观测性信息，并根据设定的目标持续推进工作。

如果任务比较复杂，Bot 还可以调用其他 Agent 作为 Worker，将研究、分析等子任务分配出去，再把结果汇总回来。

Darko 认为，单个 Agent 更适合处理一个明确的任务，例如编写某个功能；多 Agent 则更适合承担一个完整目标，例如维护一个项目、处理跨多个代码库的复杂任务。原因在于，单个 Agent 通常是单线程工作方式，一次只能处理一件事情。面对复杂目标时，不仅容易出现上下文过载，也难以同时推进多个相互独立的工作。多 Agent 协作则可以将不同环节拆分给不同的 Agent，各自使用独立的上下文，并行处理后再汇总结果。

这也是他所理解的软件工厂（Software Factory）的一个方向：开发者交给 Agent 的，不再只是写代码的具体任务，而是一个更大的工作目标。

为了让这些 Bot 能够持续工作，Kiro Crew 还设计了独立的记忆系统。

Darko 介绍，Kiro Crew 不会完全依赖当前对话上下文，而是会定期回顾历史会话，提炼经验和知识点，并通过 Embedding 模型建立本地索引。这样，即使进入新的会话，Agent 也能够找回此前积累的关键信息，而不必将所有历史对话重新塞进上下文窗口。此外，Kiro 本身也支持上下文自动压缩。例如，当上下文使用量达到设定阈值时，可以自动压缩已有内容。

在 Darko 看来，长周期 Agent 的上下文管理，主要有两条路径：一是通过压缩减少上下文占用，二是通过多 Agent 任务委派，将不同任务的上下文分开管理。

值得注意的是，Kiro Crew 不仅可以在本地运行，也支持远程运行。开发者可以通过自己的设备连接远程工作空间，继续管理 Bot 和项目，而不必始终依赖本地笔记本。

Darko 还强调，Kiro Crew 是开源项目，不要求开发者必须使用 Kiro 订阅。它可以与 Strands、Claude Code、OpenAI 以及 OpenCode、Pi 等不同 Harness 配合使用，多数 Harness 均可支持 Kiro Crew 的绝大部分功能。

AI 可以写代码，但不能替工程师承担责任

在这场沟通会上，Darko 反复强调的一个观点是：AI 时代，开发者的价值不会因为代码生成自动化而消失，但工作重心正在发生变化。

他坦言，当 AI 编程工具快速发展时，自己也曾经产生过职业焦虑：如果 Agent 已经能够写代码，开发者的技能是否还有意义？

他的答案是肯定的。

在他看来，写代码只是软件开发的一部分。一名优秀的软件工程师，还需要理解客户需求、系统扩展性、运维和可观测性，以及软件在真实生产环境中的运行方式。

Agent 可以生成代码，但它并不意味着能够替工程师承担所有责任。

Darko 特别提醒开发者，不要成为 Agent 背后的“肉身代理”（Meat Proxy），即只负责不断批准 Agent 操作，却不理解它究竟在做什么的人。尤其当开发者构建的是面向客户、涉及个人信息或敏感数据的产品时，工程能力仍然不可或缺。

他建议开发者建立 T 型能力结构：在一个领域具备足够深入的专业能力，同时理解其他相关领域的基本知识。

他以云计算的发展作类比。云出现之前，企业通常有网络管理员、数据库管理员和存储管理员等不同角色；云计算普及之后，基础设施逐渐抽象化，工程师需要具备更综合的平台工程能力。而今天，AI 正在进一步抽象代码编写工作，开发者同样需要扩大自己的能力边界。

这也解释了为什么他对 Agent 时代的软件开发持乐观态度：开发者不应该只关注代码，而应该对最终交付的软件质量负责。

从 Strands Box 的策略控制，到 Strands Decider 的小模型决策，再到 Kiro Crew 的多 Agent 长期协作，亚马逊云科技正在探索的，其实是 Agent 从辅助工具走向生产级工作系统之后，需要补齐的工程基础设施。

当 Agent 开始拥有更大的自主权，真正重要的已经不只是它能生成多少代码，而是它能否在明确的权限、可靠的记忆和可控的协作机制下，持续完成一项工程任务。
