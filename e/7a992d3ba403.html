原文

Another month goes by, which means it’s time for another release!

The ClickHouse 26.10 release contains 104 new features 🎃 225 performance optimizations 🍂 and 739 bug fixes 🦉.

This release brings function composition for more readable SQL, more flexible JOIN conditions, and new ways to work with text and SQLite files.

We also have faster GROUP BY queries, disk spilling for IN subqueries, and an experimental columns cache that saves repeated reads from decompressing and deserializing the same data.

Function composition operator

Contributed by Ivan Esipov and Alexey Milovidov

If you’ve used ClickHouse’s higher-order functions, like arrayMap and arrayFilter, you’ll know that the lambda you pass in can quickly turn into a series of nested function calls. ClickHouse 26.10 adds a function composition operator, which means we can now create a pipeline of functions joined with the | operator, making these lambdas easier to read.

Let’s see how the two styles compare when extracting site names from some URLs. We're going to lowercase the URL, strip the www prefix, take the first significant subdomain, and then uppercase it.

1WITH [2'https://WWW.ClickHouse.com/docs',3'https://GitHub.com/ClickHouse/ClickHouse',4'https://www.anthropic.com/news'5] AS urls6SELECT7    arrayMap(x ->upper(firstSignificantSubdomain(domainWithoutWWW(lower(x)))), urls) AS with_lambda,8    arrayMap(lower | domainWithoutWWW | firstSignificantSubdomain | upper, urls) AS with_composition9FORMAT Vertical;
1Row 1:2──────3with_lambda:      ['CLICKHOUSE','GITHUB','ANTHROPIC']4with_composition: ['CLICKHOUSE','GITHUB','ANTHROPIC']

Both columns give the same result, but the composed version reads more like a list of steps. Each function here can be called with just the value passed along, so we didn’t need to say where it should go.

To pass additional arguments to a function, use _ to mark where the value from the pipeline goes. For example, substring(_, 1, 3) takes the first three characters of the string passed along:

1WITH ['ClickHouse', 'Anthropic', 'OpenAI'] AS companies2SELECT3    arrayMap(x ->substring(upper(x), 1, 3), companies) AS with_lambda,4    arrayMap(upper |substring(_, 1, 3), companies) AS with_composition5FORMAT Vertical;
1Row 1:2──────3with_lambda:      ['CLI','ANT','OPE']4with_composition: ['CLI','ANT','OPE']

Higher-order functions can also take several arrays of the same length, which they process position by position. In that case, use _1 for the element from the first array, _2 for the matching element from the second, and so on. Let’s work out the line totals for an order by multiplying each price by its quantity, and then format the results as prices:

1WITH2    [49.99, 189.00, 19.50] AS prices,3    [2, 1, 4] AS quantities4SELECT5    arrayMap(multiply(_1, _2) | toString | concat('$', _), prices, quantities) AS line_totals;
1┌─line_totals─────────────┐2│ ['$99.98','$189','$78'] │3└─────────────────────────┘

Placeholders also work on their own, without |, as a shorter way of writing a lambda. For example, _1 * _2 means the same thing as (price, quantity) -> price * quantity, as shown in the following example:

1WITH2    ['Keyboard', 'Monitor', 'Mouse'] AS products,3    [49.99, 189.00, 19.50] AS prices,4    [2, 1, 4] AS quantities5SELECT6    arrayMap(_1 * _2, prices, quantities) AS line_totals,7    arrayMap(concat(_1, ' x', toString(_2)), products, quantities) AS order_lines8FORMAT Vertical;
1Row 1:2──────3line_totals: [99.98,189,78]4order_lines: ['Keyboard x2','Monitor x1','Mouse x4']

Under the hood, ClickHouse turns the pipeline into an ordinary lambda during query analysis. We can see this by running EXPLAIN SYNTAX with run_query_tree_passes = 1, which shows the query after the analyzer has rewritten it:

1EXPLAIN SYNTAX run_query_tree_passes =12SELECT arrayMap(3    lower | domainWithoutWWW | firstSignificantSubdomain | upper,4    ['https://WWW.ClickHouse.com/docs']5) AS sites;
1SELECT arrayMap(lambda(tuple(__composed_arg_1), upper(firstSignificantSubdomain(domainWithoutWWW(lower(__composed_arg_1))))), _CAST(['https://WWW.ClickHouse.com/docs'], 'Array(String)')) AS sites2FROM system.one AS __table1

The | chain has become a lambda with the same nested expression we started with, so the two styles run in exactly the same way and you can use whichever one you prefer.

Quotas on inserted rows

Contributed by Alexey Milovidov

Quotas let you limit how much a user can do in a given time interval. ClickHouse 26.10 adds a written_rows counter, so you can cap ingestion by the number of rows a user writes.

Let’s create a table and an ingest user who can write at most 100,000 rows, across no more than 250 inserts, per minute:

1CREATE TABLE events (id UInt64) 2ORDERBY id;
1CREATEUSER ingest IDENTIFIED WITH no_password;2GRANTINSERT, SELECTON default.events TO ingest;
1CREATE QUOTA ingest_limit2FORINTERVAL1minute MAX written_rows =100000, query_inserts =2503TO ingest;

The first insert of 60,000 rows goes through without any problems:

1INSERT INTO events 2SELECT number 3FROM numbers(60000);

But if we run the same insert again within that minute, it takes us over the limit:

1Received exception:2Code: 201. DB::Exception: Quota for user `ingest` for 60s has been exceeded: written_rows = 120000/100000. Interval will end at 2026-10-23 14:00:00. Name of quota template: `ingest_limit`. (QUOTA_EXCEEDED)

The rejected insert doesn’t write any data, so the table still contains 60,000 rows. As with other quotas, you can see how close each user is to their limits in system.quotas_usage:

1SELECT quota_name, written_rows, max_written_rows, query_inserts, max_query_inserts2FROM system.quotas_usage3WHERE quota_name ='ingest_limit'4FORMAT Vertical;
1Row 1:2──────3quota_name:        ingest_limit4written_rows:      1200005max_written_rows:  1000006query_inserts:     27max_query_inserts: 250

New Array and Map functions

Contributed by Minh Vu, Jimmy Aguilar Mena, UnamedRus, and Alexey Milovidov

This 26.10 release also brings a handful of new functions for working with arrays and maps.

arrayMinIndex and arrayMaxIndex return the position of the smallest and largest element, optionally after applying a lambda to each one. arrayRemoveAt removes the element at a given position, and negative positions count back from the end.

Let’s see what each of them returns on some small arrays:

1WITH [2,5,10,9,7] ASvalues23SELECT4    arrayMinIndex(values) AS min_index,5    arrayMaxIndex(values) AS max_index,6    arrayMaxIndex(x -> length(x), ['a', 'abc', 'ab', 'abcd']) AS longest_index,7    arrayRemoveAt(values, 2) AS remove_second,8    arrayRemoveAt(values, -1) AS remove_last9FORMAT Vertical;
1Row 1:2──────3min_index:     14max_index:     35longest_index: 46remove_second: [2,10,9,7]7remove_last:   [2,5,10,9]
Array indexes in ClickHouse start at 1, so the smallest value, 2, which is in first position in the array, has an index of 1

We could then can pass the results straight into another array to look up a matching value. In the following example, we find the coldest and warmest days of the week, and then drop Friday from the list:

1WITH2    ['Mon', 'Tue', 'Wed', 'Thu', 'Fri'] AS days,3    [18.5, 21.2, 16.9, 24.3, 22.0] AS temps4SELECT5    days[arrayMinIndex(temps)] AS coldest,6    days[arrayMaxIndex(temps)] AS warmest,7    arrayRemoveAt(days, -1) AS without_friday;
1┌─coldest─┬─warmest─┬─without_friday────────────┐2│ Wed     │ Thu     │ ['Mon','Tue','Wed','Thu'] │3└─────────┴─────────┴───────────────────────────┘

For maps, mapRemove drops a key, mapEntries returns the key-value pairs as an array of tuples, and mapContainsKeyValue checks whether a map contains a specific key-value pair:

1WITH map('env', 'prod', 'region', 'eu-west-1', 'team', 'payments') AS labels2SELECT3    mapRemove(labels, 'team') AS without_team,4    mapEntries(labels) AS entries,5    mapContainsKeyValue(labels, 'env', 'prod') AS is_prod6FORMAT Vertical;
1Row 1:2──────3without_team: {'env':'prod','region':'eu-west-1'}4entries:      [('env','prod'),('region','eu-west-1'),('team','payments')]5is_prod:      1

mapContainsKeyValue can also use text indexes, which makes filtering on labels a lot quicker when you have plenty of rows.

Finally, the -Map combinator no longer needs a Map column. You can pass the key as the last argument instead, which makes it easy to aggregate per key directly from rows:

1SELECT2    sumMap(views, country) AS views_by_country,3    argMaxMap(page, views, country) AS top_page_by_country4FROMVALUES('country String, page String, views UInt32',5    ('UK', '/docs', 120), ('UK', '/blog', 340),6    ('US', '/docs', 910), ('US', '/pricing', 450),7    ('DE', '/blog', 75));
1┌─views_by_country─────────────┬─top_page_by_country──────────────────────┐2│ {'DE':75,'UK':460,'US':1360} │ {'DE':'/blog','UK':'/blog','US':'/docs'} │3└──────────────────────────────┴──────────────────────────────────────────┘

SQL-compatible integer division

Contributed by Ilya Yatsishin

In ClickHouse, dividing one integer by another has always returned a floating-point number, so 7 / 2 gives you 3.5. PostgreSQL, SQL Server, and SQLite all truncate that to 3 instead.

Alexey’s take on the release call was that ClickHouse is right and everyone else is wrong, but if you’re porting queries from another database and need them to be wrong in the same way, there’s now a setting for that. Here’s the default behaviour:

1SELECT7/2, -7/2, 7/2.0, toTypeName(7/2);
1┌─divide(7, 2)─┬─divide(-7, 2)─┬─divide(7, 2.)─┬─toTypeName(divide(7, 2))─┐2│          3.5 │          -3.5 │           3.5 │ Float64                  │3└──────────────┴───────────────┴───────────────┴──────────────────────────┘

And if you prefer the PostgreSQL way, you can enable sql_compatible_division_for_integers:

1SET sql_compatible_division_for_integers =1;23SELECT7/2, -7/2, 7/2.0, toTypeName(7/2);
1┌─divide(7, 2)─┬─divide(-7, 2)─┬─divide(7, 2.)─┬─toTypeName(divide(7, 2))─┐2│            3 │            -3 │           3.5 │ UInt8                    │3└──────────────┴───────────────┴───────────────┴──────────────────────────┘

The result is truncated towards zero and keeps an integer type, while dividing by a floating-point number still gives you a float. With the setting enabled, dividing by zero throws an error rather than returning inf:

1SET sql_compatible_division_for_integers =1;23SELECT1/0;
1Received exception:2Code: 153. DB::Exception: Division by zero: In scope SELECT divideExact(1, 0) AS `divide(1, 0)`. (ILLEGAL_DIVISION)

The setting is disabled by default. Views and other stored definitions keep the division behaviour they were created with, so enabling it won’t change the results of your existing views.

IN subqueries can spill to disk

Contributed by Nihal Z. Miaji

When we use IN with a subquery, ClickHouse builds a set of the values returned by that subquery and checks the outer query’s rows against it. A large set can use a lot of memory. ClickHouse 26.10 adds the ability to spill this set to disk, allowing the query to complete with a smaller memory limit.

Let’s try it with the UK property prices dataset, which contains property sales in England and Wales since 1995. We want to count sales in 2024 at addresses that also have a recorded sale before 2024. We’ll match on the postcode and the two address fields, addr1 and addr2, which identify the building and, where applicable, the flat. This is an address-based match rather than a permanent property identifier, and we’re counting sales rather than distinct properties.

First, let’s give the query a 4 GiB memory limit and leave spilling disabled:

1SELECTcount() AS repeat_address_sales_20242FROM uk_price_paid3WHEREdate>='2024-01-01'4ANDdate<'2025-01-01'5AND (postcode1, postcode2, addr1, addr2) IN6  (7SELECT postcode1, postcode2, addr1, addr28FROM uk_price_paid9WHEREdate<'2024-01-01'10  )11SETTINGS max_threads =2,12         max_memory_usage ='4Gi',13         max_bytes_before_external_set =0;
1┌─repeat_address_sales_2024─┐2│                    558458 │3└───────────────────────────┘451 row in set. Elapsed: 5.777 sec. Processed 60.90 million rows, 966.34 MB (10.54 million rows/s., 167.27 MB/s.)6Peak memory usage: 1.96 GiB.

The subquery reads 29.3 million earlier sales to build its set of addresses. On ClickHouse 26.10, this query used 1.96 GiB of peak memory. Let's see what happens if we reduce the memory limit to 512 MiB:

1SELECTcount() AS repeat_address_sales_20242FROM uk_price_paid3WHEREdate>='2024-01-01'4ANDdate<'2025-01-01'5AND (postcode1, postcode2, addr1, addr2) IN6  (7SELECT postcode1, postcode2, addr1, addr28FROM uk_price_paid9WHEREdate<'2024-01-01'10  )11SETTINGS max_threads =2,12         max_memory_usage ='512Mi',13         max_bytes_before_external_set =0;
1Elapsed: 0.978 sec. Processed 7.93 million rows, 122.04 MB (8.10 million rows/s., 124.75 MB/s.)23Received exception:4Code: 241. DB::Exception: Query memory limit exceeded: would use 537.51 MiB (attempt to allocate chunk of 63.96 MiB), maximum: 512.00 MiB: While executing CreatingSetsTransform. (MEMORY_LIMIT_EXCEEDED)

ClickHouse runs out of memory. We can now enable spilling by setting max_bytes_before_external_set. Let’s use a threshold of 128 MiB, keeping the query’s overall memory limit at 512 MiB:

1SELECTcount() AS repeat_address_sales_20242FROM uk_price_paid3WHEREdate>='2024-01-01'4ANDdate<'2025-01-01'5AND (postcode1, postcode2, addr1, addr2) IN6  (7SELECT postcode1, postcode2, addr1, addr28FROM uk_price_paid9WHEREdate<'2024-01-01'10  )11SETTINGS max_threads =2,12         max_memory_usage ='512Mi',13         max_bytes_before_external_set ='128Mi';
1┌─repeat_address_sales_2024─┐2│                    558458 │3└───────────────────────────┘451 row in set. Elapsed: 3.185 sec. Processed 60.90 million rows, 966.48 MB (19.12 million rows/s., 303.44 MB/s.)6Peak memory usage: 203.11 MiB.

This time we have a peak memory usage of 203 MiB. That’s above our 128 MiB spill threshold, which tells ClickHouse when to start spilling rather than imposing a hard memory limit. The query also needs memory to read and process data, so we set the spill threshold below the overall 512 MiB limit.

If we look at profile events, by pressing the space bar while the query's running, we'll see that ClickHouse spilled one set to disk and wrote four parts:

1SetsSpilledToDisk:          12ExternalSetWritePart:       43ExternalSetCompressedBytes: 470342352

The following table summarizes the various configurations we used:

Faster GROUP BY with LowCardinality columns

Contributed by artemkulyk, Samuel Krempaský, and Alexey Milovidov

ClickHouse 26.10 improves grouping by multiple LowCardinality columns. It can serialize the grouping keys directly from their dictionaries and cache aggregate-state lookups for repeated combinations of keys.

Let’s reuse our uk_price_paid table to count sales and calculate the average price for each combination of county, district, town, and outward postcode. All four grouping columns have a column type of LowCardinality(String):

1SELECT2    county,3    district,4    town,5    postcode1,6count() AS sales,7avg(price) AS average_price8FROM uk_price_paid9GROUPBY county, district, town, postcode110SETTINGS use_query_cache =011FORMAT Null;

We use FORMAT Null to run the query without printing its 15,409 result rows, so terminal output doesn’t affect the comparison.

Let’s run the query three times on ClickHouse 26.9:

10 rows in set. Elapsed: 0.289 sec. Processed 30.45 million rows, 331.39 MB (105.20 million rows/s., 1.14 GB/s.)2Peak memory usage: 170.67 MiB.340 rows in set. Elapsed: 0.269 sec. Processed 30.45 million rows, 331.39 MB (113.29 million rows/s., 1.23 GB/s.)5Peak memory usage: 171.81 MiB.670 rows in set. Elapsed: 0.255 sec. Processed 30.45 million rows, 331.39 MB (119.19 million rows/s., 1.30 GB/s.)8Peak memory usage: 177.98 MiB.

And now three times on ClickHouse 26.10, using the same data and table layout. Both versions use the default 12 threads on my machine:

10 rows in set. Elapsed: 0.242 sec. Processed 30.45 million rows, 331.39 MB (125.90 million rows/s., 1.37 GB/s.)2Peak memory usage: 128.49 MiB.340 rows in set. Elapsed: 0.181 sec. Processed 30.45 million rows, 331.39 MB (168.49 million rows/s., 1.83 GB/s.)5Peak memory usage: 124.16 MiB.670 rows in set. Elapsed: 0.171 sec. If we take the best time from each version, the query took 255 milliseconds on 26.9 and 171 milliseconds on 26.10, meaning 26.10 is just over 30% quicker.

Top-K dynamic filtering for GROUP BY

Contributed by Alexey Milovidov and Konstantin Bogdanov

ClickHouse 25.12 introduced dynamic filtering for ORDER BY … LIMIT queries, using the current Top-K boundary to avoid unnecessary column reads and skip granules through minmax indexes. ClickHouse 26.10 extends this approach to GROUP BY queries and adds granule skipping through the primary index.

Let’s reuse our UK property data to find the ten most recent dates with recorded sales, along with the number of sales and their average price. We’ll create a separate table containing the two columns used by the query, sorted by date. This layout lets ClickHouse use both mechanisms: filter older sales before reading their prices, and use the primary index to skip granules whose dates are all older than the cutoff.

1CREATE TABLE uk_price_paid_by_date2ENGINE = MergeTree3ORDERBYdate4ASSELECTdate, price FROM uk_price_paid;56OPTIMIZE TABLE uk_price_paid_by_date FINAL;

This copies all 30m sales and merges the new table into a single part. We’ll run the query on ClickHouse 26.10 so we can see what the output looks like:

1SELECT2date,3count() AS sales,4    round(avg(price)) AS average_price5FROM uk_price_paid_by_date6GROUPBYdate7ORDERBYdateDESC8LIMIT 109SETTINGS10    enable_group_by_top_k_dynamic_filtering =0,11    use_query_condition_cache =0,12    use_query_cache =0;

The query returns the following ten dates:

Columns cache

Contributed by Alexey Milovidov

ClickHouse 26.10 introduces an experimental columns cache, which keeps deserialized column data in memory, saving subsequent queries from decompressing and deserializing it again.

Let’s reuse our UK property dataset to count sales where the first address field contains HOUSE. We'll create a copy containing the price and address columns, keeping the original sort order:

1CREATE TABLE uk_price_paid_columns_cache2ENGINE = MergeTree3ORDERBY (postcode1, postcode2, addr1, addr2)4SETTINGS min_bytes_for_wide_part =0,5         min_rows_for_wide_part =06ASSELECT postcode1, postcode2, addr1, addr2, price FROM uk_price_paid;

The cache currently supports wide MergeTree parts. Setting both size thresholds to 0 forces this format.

First, let's run the query with the columns cache disabled:

1SELECTcount() AS house_sales2FROM uk_price_paid_columns_cache3WHERE addr1 LIKE'%HOUSE%'4SETTINGS use_columns_cache =0,5         use_query_cache =0,6         use_query_condition_cache =0,7         log_queries =1,8         log_profile_events =1,9         log_comment ='sorted-columns-cache:off-1';
1┌─house_sales─┐2│      904871 │3└─────────────┘

After one unmeasured run to warm the filesystem cache, we'll run this query three times, using sorted-columns-cache:off-1, sorted-columns-cache:off-2, and sorted-columns-cache:off-3 as the log comments.

Then we'll change use_columns_cache to 1 and run it three more times, using comments sorted-columns-cache:on-1, sorted-columns-cache:on-2, and sorted-columns-cache:on-3. The first enabled run populates the columns cache, and the next two reuse it.

With caching enabled, the query caches addr1. It doesn't read price, for example, so that column isn't cached. But, if we added a condition on price, any data read from that column would also be cached.

With query logging enabled, we can retrieve the timings and cache counters from system.query_log, using the following query:

The run in which the cache gets populated takes 37 milliseconds, and the next two runs that use the cache each take 12 milliseconds, with all 3,718 granules of addr1 read from the columns cache.

SelectedRows stays the same: ClickHouse still evaluates the filter against all 30.45 million rows, but it can reuse the decoded address data. The cache stores column data rather than the query result, so other queries reading the same data can benefit too.

LATERAL JOIN

Contributed by Dimitri König and Alexey Milovidov

ClickHouse 26.10 adds experimental support for LATERAL JOIN, which lets a subquery reference columns from a table that appears before it. We can enable it by setting allow_experimental_lateral_join = 1.

We'll use the IMDb dataset from our joins examples to find the three highest-rated films for each of three actors. The actors table contains their names, movies contains film details and ratings, and roles connects actors to the films they appeared in.

1SELECT2    concat(a.first_name, ' ', a.last_name) AS actor,3    top_titles.name AS title,4    top_titles.year ASyear,5    round(top_titles.rank, 1) AS rating6FROM actors AS a7JOINLATERAL8(9SELECT m.id, m.name, m.year, m.rank10FROM roles AS r11INNERJOIN movies AS m ON r.movie_id = m.id12WHERE r.actor_id = a.id13AND m.rank ISNOT NULL14GROUPBY m.id, m.name, m.year, m.rank15ORDERBY m.rank DESC, m.year DESC, m.id16    LIMIT 317) AS top_titles ONtrue18WHERE (a.first_name, a.last_name) IN19    (('Tom', 'Hanks'), ('Meryl', 'Streep'), ('Denzel', 'Washington'))20ORDERBY actor, rating DESC, yearDESC, top_titles.id21SETTINGS allow_experimental_lateral_join =1;

Line 12 is the important one: WHERE r.actor_id = a.id. The a.id value comes from actors AS a in the outer query. The LATERAL lets our inner query use that value, which means we find the top three films for this actor. LIMIT 3 applies per actor, rather than selecting three films across the whole dataset.

For each selected actor, the inner query finds their roles, joins them to the film details, and excludes films without a rating. The GROUP BY removes duplicate films where an actor has multiple role records. It then sorts by rating, using the year and film ID to break ties, and returns the top three.

1┌─actor─────────────┬─title──────────────────┬─year─┬─rating─┐2│ Denzel Washington │ Glory                  │ 1989 │    8.1 │3│ Denzel Washington │ Much Ado About Nothing │ 1993 │    7.5 │4│ Denzel Washington │ Antwone Fisher         │ 2002 │    7.4 │5│ Meryl Streep      │ Manhattan              │ 1979 │    8.2 │6│ Meryl Streep      │ Deer Hunter, The       │ 1978 │    8.1 │7│ Meryl Streep      │ Adaptation.            │ 2002 │    7.9 │8│ Tom Hanks         │ Saving Private Ryan    │ 1998 │    8.3 │9│ Tom Hanks         │ Green Mile, The        │ 1999 │    8.1 │10│ Tom Hanks         │ Toy Story 2            │ 1999 │    8.1 │11└───────────────────┴────────────────────────┴──────┴────────┘

We get nine rows: three films for each actor.

JOINs with arbitrary conditions

Contributed by Vladimir Cherkasov and Alexey Milovidov

ClickHouse 26.10 also supports JOINs with arbitrary ON conditions, including those without an equality condition between the tables. Let's use this to categorize website traffic using URL patterns.

First, we'll create a table containing page view counts:

1CREATE TABLE page_views2(3    path String,4    views UInt645);67INSERT INTO page_views VALUES8    ('/docs/getting-started', 1200),9    ('/docs/sql-reference/functions', 850),10    ('/blog/clickhouse-release-26-10', 2400),11    ('/pricing', 600),12    ('/about', 300);

We'll store the categorization rules in a separate table. The % wildcard matches any sequence of characters:

1CREATE TABLE page_categories2(3pattern String,4    category String5);67INSERT INTO page_categories VALUES8    ('/docs/%', 'Documentation'),9    ('/blog/%', 'Blog'),10    ('/pricing', 'Pricing');

We can now join the tables using LIKE to match each path to a category:

1SELECT p.path, p.views, c.category2FROM page_views AS p3LEFTJOIN page_categories AS c ON p.path LIKE c.pattern4ORDERBY p.views DESC;
1┌─path───────────────────────────┬─views─┬─category──────┐2│ /blog/clickhouse-release-26-10 │  2400 │ Blog          │3│ /docs/getting-started          │  1200 │ Documentation │4│ /docs/sql-reference/functions  │   850 │ Documentation │5│ /pricing                       │   600 │ Pricing       │6│ /about                         │   300 │               │7└────────────────────────────────┴───────┴───────────────┘

Keep in mine that the flexibility of arbitrary joins can be expensive: the block nested loop join checks every pair of rows, so it can be as slow as a cross join and is used as a last resort by the query planner.

Freeform input format

Contributed by Tri Dao and Alexey Milovidov

ClickHouse 26.10 also adds the Freeform input format, which infers columns and their types from consistently structured text.

Let's see how it works by piping the output of ls -l into clickhouse-local. The piped input will be available as table and can be queried the same way as any other table. The following query desribes the output of ls -l:

1ls -l **/*.parquet | 2./clickhouse --input-format Freeform --query "DESCRIBE TABLE table"
1c0	String2c1	Int643c2	String4c3	String5c4	Int646c5	Int647c6	String8c7	Int649c8	Int6410c9	String

We can see from this output that ls -l outputs 10 columns, which are named c0 to c9. We can query table to return all columns with the following query;

1ls -l **/*.parquet | 2./clickhouse --input-format Freeform --query "FROM table FORMAT Vertical"

SQLite import and export

Contributed by Yue Ni and Alexey Milovidov

ClickHouse already supports querying SQLite databases through a database engine, table engine, and table function. Version 26.10 adds SQLite as an input and output format, letting us export query results directly into a SQLite database file, ready to open with SQLite tools or share with someone else.

Let's reuse our IMDb movies table to count films and calculate their average rating for each year of the 1990s:

1SELECT2year,3    toInt64(count()) AS films,4    round(avg(rank), 2) AS average_rating5FROM movies6WHEREyearBETWEEN1990AND19997GROUPBYyear8ORDERBYyear9INTO OUTFILE 'films.sqlite'10SETTINGS output_format_sqlite_table_name ='films_by_year';

ClickHouse uses the SQLite format becaues of the .sqlite extension of the output file, but we can also specify the output explicitly by specifying FORMAT SQLite after the file name. We write ten results in a table called films_by_year.

We can open the file with the sqlite3 command-line tool and query it:

1sqlite3 -header -column films.sqlite \2'SELECT * FROM films_by_year ORDER BY year LIMIT 5;'

ClickHouse can also read the file back, inferring the column names and types:

1SELECT*2FROM file('films.sqlite')3ORDERBYyear4LIMIT 5;

String filtering during the scan

Contributed by Alexey Milovidov

ClickHouse 26.10 can check string filters such as LIKE, startsWith, and endsWith while deserializing a column, avoiding copying non-matching strings into memory. The optimization is enabled by default through apply_string_filters_during_scan.

Let's try it with the Amazon reviews dataset. We'll load the 2010 and 2011 Parquet files from our Freeform example into a MergeTree table, giving us 9.98 million reviews:

1CREATE TABLE amazon_reviews2ENGINE = MergeTree3ORDERBY tuple()4ASSELECT*5FROM file('benchmarks/amazon-columns-cache/data/amazon_reviews_{2010,2011}.snappy.parquet');

We want to count reviews containing the word disappointed. First, let's disable the optimization, along with the columns cache, query cache, and query condition cache:

1SELECTcount() AS matching_reviews2FROM amazon_reviews3WHERE review_body LIKE'%disappointed%'4SETTINGS apply_string_filters_during_scan =0,5         use_columns_cache =0,6         use_query_cache =0,7         use_query_condition_cache =0;
