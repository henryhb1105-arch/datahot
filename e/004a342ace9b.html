AI Discover 智能层背后的挑战与决策

作者： Varun Khaitan， Peng Ren， Gary Tang， Itay Teller， Atif Faheem， Nipun Kumar， Donnie DeBoer， Eduardo Lundgren， Matteo Rinaldi， Raghav Bakshi

我们最近推出了 AI Discover，这是我们电视应用中的一个新标签页，一小部分会员可以在这里尝试新方式来找点可看的内容。多年来，我们的推荐一直在后台默默运作，从会员的观看历史中推断他们可能喜欢什么。AI Discover 从那种无声的排序转向可操控的发现。会员选一个主题，比如“Quick Watches”，就会得到一行匹配的标题、一段关于它们为何契合的简短说明，以及几个可以接着尝试的更窄主题。从那里开始，他们可以继续收窄、前往新的方向，或者调整自己看到的内容。

构建 AI Discover 引出了一个许多团队都会认出的问题：如何在电视上用生成式 AI 提供更好的会员体验，同时不牺牲速度、可靠性或安全性？我们的答案是一个新的智能层，即 AI Discover 背后的智能体运行框架（agent harness）。对于每个请求，它决定如何将 LLM 与我们的推荐系统结合起来。它建立在多年来理解会员喜好的工作之上，也建立在我们近期将 LLM 应用于推荐和生成式体验的工作之上。该层自身负责规划每个请求、在这些系统上运行请求、提供结果，并在离线环境中进行评估。

本文涵盖我们针对设计的挑战以及在此过程中做出的关键决策。

为什么需要智能层？

每个 Netflix 页面都将推荐与规则结合在一起。我们挑选会员可能喜欢的标题，而资格、成熟度和安全规则决定哪些内容可以出现。基于 LLM 构建的体验需要同样的规则，还需要决定何时调用 LLM 以及如何处理其输出的代码。那段代码被称为智能体运行框架（agent harness），它是我们智能层的核心。

最简单的实现方式是将整个请求交给 LLM，让它挑选标题、撰写标签并决定接下来发生什么。然而，这让我们在需要受控结果的地方依赖概率性输出，因为 AI Discover 中的每一轮最终都会落在某个人客厅里的屏幕上。在我们的规模下，即使是罕见的故障每天也会发生很多次。会员会看到每一次缓慢的调用、每一个不可用的标题或每一句不符合品牌调性的文案。七个挑战塑造了我们的设计：

  1. 将 LLM 融入并非为其设计的产品和架构中。 传统推荐器根据过去的行为对标题进行排序。LLM 可以做更多：理解会员在要求什么，并规划如何回应。我们现有的体验会让其中大部分能力闲置。
  2. 让推荐有据可依。 每一个选择都必须是来自我们不断变化的目录中的真实、可用的标题。检索和排序器与 LLM 协同工作，以选择符合会员品味和意图的标题。
  3. 应对缓慢且不可预测的 LLM。 LLM 调用是系统中最慢、最昂贵的部分。尾部延迟可能飙升，输出也可能不是你所要求的。因此我们有选择地使用 LLM，将其返回的内容视为不可信输入，并在任何东西上线前测试性能和质量。
  4. 适应快速变化的模型、工具和提示词。 建模和工程解决方案不断演进，因此产品不能依赖任何单一的模型、工具或提示词。
  5. 为电视而构建。 在电视上打字很难，所以会员依赖遥控器，而应用应该在差异巨大的硬件上对每一次按键立即响应。电视应用更新也很慢，因此变更必须在没有应用版本发布的情况下上线。典型的电视请求在片刻内返回，而多步生成可能需要数秒。
  6. 在规模下坚守安全与可靠性标准。 即使 LLM 调用失败或产生糟糕的结果，会员也总能得到一个页面。他们的选择和我们的内容标准在每次请求中都得到遵守，当出现故障时，结构化记录会说明原因。
  7. 从会员所说的内容以及我们已知的内容中学习。 推荐一直在从观看行为中学习。AI Discover 还让会员告诉我们他们想要什么，而这必须影响他们接下来看到的内容。

系统架构

当会员选择一个主题时，电视应用将请求发送到 页面服务器，它为所有 Netflix 应用构建页面，并将请求异步交给智能层。在高层面上，这个新层有两个组件：一个控制器和一个执行器。

控制器决定要运行什么。它收集每个请求所需的上下文，包括诸如一天中的时间等实时信号。然后它确定一个计划，要么是既定的计划，要么是其规划器起草的新计划，对其进行验证，并仅从 Memory Hub（我们的每位会员记忆存储）中检索该计划所需的会员详细信息。这些详细信息可能包括由 MemberLLM（我们用于个性化推荐的内部语言模型）生成的会员品味摘要，或会员分享的反馈。我们稍后会更多地讨论 Memory Hub 和会员品味摘要。

计划是一个已批准步骤的图，每个步骤运行一个能力。能力是一个命名的工作单元，可以有多个版本，并属于检索、排序、生成或打包等家族。它声明其输入和输出、它可以看到的上下文以及失败时会发生什么。

能力声明使计划可验证。在执行之前，控制器验证该图：每个步骤都已获批准，每个输入都有生产者，没有任何循环，并且计划恰好以一个页面结束。之后，控制器在结果被提供之前对其进行检查。

执行器运行该计划。各步骤通过声明的契约在彼此之间传递带类型的输出，因此每个步骤收到的正是它所要求的。独立步骤并行运行，各自拥有自己的截止时间和适当的回退行为。有些步骤是经过优化的 LLM 调用，每个只承担一项任务，例如编写行标题或建议下一个主题，并且它们只在经过验证的计划范围内行动。运行前的检查和运行期间的契约赋予我们受治理的执行，其中每项操作都停留在代码所设定的限制之内。

两个部分都会写入请求记录，也就是我们在离线状态下用来评估和改进系统的追踪记录。

关键决策

每个挑战都促成了一项决策。以下是我们所做的选择以及它为我们带来的收益。

1. 围绕 LLM 设计产品和架构

我们围绕 LLM 重新构想了这一体验。更省事的做法是把它们作为排序器插入，维持当前的延迟预算，并在必要时进行预计算。AI Discover 建立在会员可以引导的往返式交互之上，这赋予了 LLM 只有它们才能完成的工作：生成主题、解释行内容、总结品味，以及帮助选择契合会员和当下时刻的标题。会员用遥控器选择主题，因此无需打字。在电视上，这些主题和解释拥有各自的原生 UI 元素。在屏幕之后，LLM 可以起草计划，而异步服务为多步骤的智能体编排提供了所需的时间。

这开辟了我们传统技术栈无法独自支持的体验。

2. 让现有系统可组合

让推荐保持有据可依，意味着要构建在那些已经了解我们内容目录和会员的系统之上。大多数能力封装了复杂且经过验证的 Netflix 系统，例如搜索、大规模排序和内容目录元数据访问。其中一些系统未来可能会运行自己的智能体。

重塑这些系统需要细致的工作，因为智能体编排挑战了分布式系统的许多长期假设。一项能力现在必须能在无人设计过的组合中工作，服务于一个在运行时选择调用它的调用方。每项能力都需要有明确的目的和语义接口，而塑造它意味着决定将多少内容合并到单个步骤中、将多少内容留给规划器。过细，规划器就更容易出错；过粗，它就失去了组合更丰富计划的空间。

作为回报，规划器获得了可以用新方式混合的构建模块，连接服务所需的手动接线也大大减少。由于计划只能使用这些模块，即使是在运行中临时起草的计划，也仍然立足于我们的内容目录和会员品味。

3. 先规划，后执行

为了控制 LLM 的延迟和错误，我们在任何内容运行之前先规划每个请求。让智能体使用工具的一种常见方式是循环：推理、调用工具、读取结果、再次推理。这种方式灵活，但你无法预先知道它会走多少步，也无法知道它是否走了错误的路径。用智能体的术语来说，我们的是规划-执行型智能体：LLM 可以提出路径，但由代码决定它是否运行。

计划来自两个地方：我们已经测试过的既定计划，以及 LLM 在运行中起草的计划。由我们控制的路由器决定提供哪一个。无论哪种方式，计划在运行之前都要通过相同的检查。如果规划器速度慢或其计划未通过检查，我们就回退到经过测试的计划。

这允许自适应规划。规划器可以找到服务请求的新方式，我们可以为每项任务平衡成本、延迟和质量，从精简的单次调用计划到更丰富的多步骤计划。

4. 保持模型和能力无关

今天对某项任务而言最好的模型或能力，几个月后可能变成次优或过度。因此我们构建了系统以在它们之间切换。我们将每项任务分配给适合它的模型或能力版本。目前这是一个可按任务设置、可以在线覆盖的配置。请求中只有部分步骤使用 LLM。

只有切换容易，这一点才能成立。我们使用的所有 LLM 都位于一个公共接口之后。在切换之前，每个候选者都会在同一批任务上通过自动化检查和 LLM 评判员进行评分，因此每次替换都是一次经过测量的变更。

系统的大部分行为存在于服务端提示词和配置中，因此我们无需新代码或发布电视应用即可更换模型、工具和能力。

升级变得廉价，实验变得容易。迁移到更好的模型、排序器或检索系统是计划或设置的变更，而不是迁移，因此每个组件都能持续改进，而无需大量投入。

5. 让页面生成异步化

推理一直在变快，但会员的期望也同样迅速上升：更丰富的响应、更多上下文，以及更多由 LLM 塑造的页面。感觉即时与值得等待之间的界线会不断移动，因此我们将异步路径构建为一等的服务方式。

电视应用的大部分是同步的：按下按钮，获得页面。生成式工作打破了这一模式。让一个请求在多个服务之间保持打开许多秒会占用太多线程。因此涉及生成的请求是异步的。按下按钮会立即返回一个确认，电视切换到思考状态，说明正在准备什么。与此同时，执行器在后台运行计划。当结果准备好时，服务器通知电视，电视随后获取结果。

缓慢的生成不再拖慢其他任何东西。无论一轮交互耗时多长，服务路径都保持健康，每次按键仍然能在屏幕上获得即时反馈。

6. 在代码中强制执行安全

有些规则无论 LLM 写出什么都必须成立：内容和分级标准、每个步骤可以访问什么，以及会员要求我们不要向他们展示什么。将那些规则放进提示词会使它们变成概率性的，因此我们在代码中强制执行。生成的文本在到达屏幕之前会被清理。规划器看到的是精简过的请求，会员的详细信息仅限于经过验证的计划所需的内容。

例如，规划器决定每个步骤需要哪些输入，例如用于检索的档案成熟度评级。它不直接编写参数值，而是使用占位符。在计划通过验证后，控制器用请求中的值填充它们，并按声明的类型进行匹配。这也能防止提示注入。

每个请求还会留下一条结构化记录：计划、每个步骤及其结果，以及应用了哪些规则。当页面未命中时，我们可以判断问题出在计划、数据、规则还是模型上。同样的记录也会用于我们的离线评估和回放。

这些规则和记录共同确保实验在发布时达到与产品其他部分相同的安全和隐私标准。

7. 记住会员告诉我们的信息

品味摘要是对会员所喜爱内容的简短画像，例如最喜欢的类型、基调和反复出现的主题。MemberLLM 会根据会员的观看历史提前生成它，从而将这项 LLM 工作移出请求路径。它帮助我们进一步个性化他们的页面，而撰写主题和说明的步骤会将其作为上下文接收，因此它们的措辞能反映该会员。我们将在后续文章中更详细地介绍 MemberLLM。

在 AI Discover 中，会员还可以调整他们的推荐，并直接告诉我们他们想要什么。这些选择会立即生效，并会跨访问保留，它们在我们已经了解的品味信息之外为我们提供了一个新信号。这是朝着记住每位会员更多信息迈出的第一步，从他们的偏好到随着时间显现的习惯，再到他们喜欢探索的目录角落。我们将所有这些都保存在 Memory Hub 中，这是我们持久、低延迟的记忆存储，与他们的品味摘要放在一起，并且我们可以根据需要添加新类型的记忆。我们会在后续相关请求中，将这些记忆与实时上下文一起应用。

会员掌握着遥控器

在这个版本中，会员通过选择主题和使用诸如“不要推荐”之类的调整选项来进行交互。没有自由文本输入或开放式聊天。这在设计上让 LLM 的工作保持狭窄。

  • 常规的保护措施仍然适用。 档案设置以及我们的安全和隐私政策在这里和其他任何地方一样适用。
  • 生成的文本在发布前经过了测试。 我们对主题标签、行标题和说明进行了安全评估，以确保它们符合我们的标准。

下一步是什么

让一个 LLM 完成所有工作并就此止步本会更快。智能层为我们提供了一个 AI 原生产品，包括有依据的构建模块、自适应规划、更快的实验、异步生成、受治理的执行以及用于可调个性化的智能体记忆。虽然 AI Discover 是它的第一个体验，但我们在设计时考虑了更多。

我们组织工作以回答两个问题：

  • 会员在多大程度上希望塑造他们的推荐？ 他们更愿意主动引导还是被动依赖，以及程度如何，哪些类型的主题有帮助，以及我们应如何将会员告诉我们的信息与现有个性化系统相结合。
  • 这项技术会带来哪些权衡？ 随着流量增长，成本与延迟在生产环境中表现如何，会员愿意等待生成结果多久，以及错误是来自模型、框架还是我们现有系统。多轮会话也需要与单次请求不同的评估和可观测性。

从更长远来看，我们的目标是构建一个能够自我改进的系统，从每个请求留下的记录开始。今天，我们会针对新的提示、模型或规则回放过去的请求，以观察有哪些变化，并通过自动化检查、LLM 评判器和人工评估来评判每项变化。最终，我们希望系统能够在我们的隐私和数据使用政策范围内提出改进、安全地测试它们，并只保留被证明更好的改进。随着 LLM 的进步，更多工作可能会转移到它们之中，而智能层让我们能够有意识地移动这条界线。

这是更大转变的一部分。推荐系统长期以来一直默默地从会员观看的内容中学习，并以排序后的行作出回应。LLM 让它们能够倾听并回应，会员可能会越来越期待这一点。我们将继续探索这对 Netflix 上的发现意味着什么。
