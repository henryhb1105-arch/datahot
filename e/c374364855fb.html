原文

Amazon S3 Tables, a capability of Amazon Simple Storage Service (Amazon S3), deliver a cloud object store with built-in Apache Iceberg support and streamline storing tabular data at scale. When you integrate them with dbt and AWS Glue, you can run SQL-based data transformations with the reliability and performance of a modern lakehouse, bringing software engineering best practices to the data space.

This post demonstrates how to configure and implement dbt transformations using Amazon S3 Tables with the dbt-glue adapter. Starting with version 1.12.4, the dbt-glue adapter adds incremental merge support for S3 Tables, which the patterns in this post build on. We cover the specific configuration requirements for the dbt-glue adapter and practical implementation patterns built on S3 Tables incremental models: the merge strategy to keep the latest state per record and the append strategy to build an audit-friendly change history.

Example scenario

In this walkthrough, we simulate an ecommerce system that tracks customer profiles and their orders. We first run the pipeline against an initial dataset, then simulate an update to the upstream source data and run it again to demonstrate incremental updates.

Our example scenario follows a data pipeline architecture that uses S3 Tables throughout. Raw ecommerce data (customers.csv and orders.csv) lands in a regular S3 bucket as comma-separated values (CSV). dbt then transforms it through two layers of S3 Tables. A staging layer cleanses and standardizes each source, and a mart layer produces analytics-ready dimension and fact tables. You can query the resulting mart data from a variety of analytics and business intelligence (BI) tools such as Amazon Athena and Amazon Quick Sight. In this post, we query it from Athena.

The mart layer demonstrates two incremental strategies side by side: the fact_orders model uses merge to keep the latest state per order, while fact_order_history uses append to accumulate a full change history.

The data pipeline flow looks like the following chart:

Source Data (Regular S3 - CSV)
    └─ customers.csv, orders.csv
    ↓
Staging Models (S3 Tables)
    ├─ stg_customers
    └─ stg_orders
    ↓
Mart Models (S3 Tables)
    ├─ dim_customers
    ├─ fact_orders                (incremental with merge --- latest state per order)
    └─ fact_order_history         (incremental with append --- change history)
    ↓
Consumption Layer (Athena, Quick Sight, BI tools)

The following diagram shows the architecture behind this pipeline: dbt-glue submits each model as a Spark SQL statement to an AWS Glue interactive session, which reads from the raw S3 bucket and writes the staging and mart tables as S3 Tables within the same data lake.

Prerequisites

Before you begin, make sure that you have the following prerequisites:

  • AWS Account.
  • An AWS Identity and Access Management (IAM) role that dbt-glue assumes to run the AWS Glue interactive session, with permissions for AWS Glue, the AWS Glue Data Catalog, Amazon S3, and Amazon S3 Tables. See Setting up IAM permissions for AWS Glue.
  • dbt-glue 1.12.4 or later (required for S3 Tables incremental models).
  • Python 3.10, 3.11, or 3.12. See the Python compatibility matrix to find supported Python versions for each dbt-core version.
  • AWS Glue 6.0 or later.
  • AWS Command Line Interface (AWS CLI) version 2.x.
  • Integrate Amazon S3 table buckets with AWS analytics services.

Create S3 Tables namespace and AWS Glue databases

In this section, you set up the AWS infrastructure that dbt-glue needs: an S3 table bucket and namespace to hold your dbt models, and an AWS Glue database for your source data.

First, set your environment variables. Replace YOUR_ACCOUNT_ID, YOUR-REGULAR-BUCKET, and YOUR_Glue_Role_ARN with your data:

export DBT_GLUE_REGION="us-east-1"
export AWS_ACCOUNT_ID="<YOUR_ACCOUNT_ID>"
export S3_TABLES_BUCKET_NAME="dbt-glue-s3-tables-bucket"
export DBT_ROLE_ARN="<YOUR_Glue_Role_ARN>"
export DBT_S3_LOCATION="s3://<YOUR-REGULAR-BUCKET>/glue/data/"
export DBT_S3_TABLES_BUCKET="${AWS_ACCOUNT_ID}:s3tablescatalog/${S3_TABLES_BUCKET_NAME}"

The DBT_S3_TABLES_BUCKET format is AWS_ACCOUNT_ID:s3tablescatalog/BUCKET_NAME, not an Amazon Resource Name (ARN).

Second, create an S3 table bucket and namespace:

aws s3tables create-table-bucket \
  --region $DBT_GLUE_REGION \
  --name $S3_TABLES_BUCKET_NAME
aws s3tables create-namespace \
  --region $DBT_GLUE_REGION \
  --table-bucket-arn "arn:aws:s3tables:${DBT_GLUE_REGION}:${AWS_ACCOUNT_ID}:bucket/${S3_TABLES_BUCKET_NAME}" \
  --namespace dbt_glue_s3_tables
aws glue get-database \
  --region $DBT_GLUE_REGION \
  --catalog-id "$DBT_S3_TABLES_BUCKET" \
  --name dbt_glue_s3_tables
aws glue create-database \
  --region $DBT_GLUE_REGION \
  --database-input Name=raw_ecommerce,Description='Raw e-commerce data'

Configure dbt profile

The dbt profile configuration is critical for S3 Tables integration. In this section, you create a dbt profile that connects to AWS Glue Interactive Sessions and configures Spark to read and write S3 Tables through the Iceberg catalog, then validate the connection with dbt debug.

dbt_glue_s3_tables:
  target: dev
  outputs:
    dev:
      type: glue
      glue_version: "6.0"
      role_arn: "{{ env_var('DBT_ROLE_ARN') }}"
      region: "{{ env_var('DBT_GLUE_REGION') }}"
      workers: 2
      worker_type: G.1X
      schema: dbt_glue_s3_tables

      # S3 Tables Spark configuration (space-delimited format)
      conf: "spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions --conf spark.sql.catalog.spark_catalog=org.apache.iceberg.spark.SparkSessionCatalog --conf spark.sql.catalog.spark_catalog.type=glue --conf spark.sql.catalog.glue_catalog=org.apache.iceberg.spark.SparkCatalog --conf spark.sql.catalog.glue_catalog.warehouse={{ env_var('DBT_S3_LOCATION') }} --conf spark.sql.catalog.glue_catalog.catalog-impl=org.apache.iceberg.aws.glue.GlueCatalog --conf spark.sql.catalog.glue_catalog.io-impl=org.apache.iceberg.aws.s3.S3FileIO --conf spark.sql.catalog.glue_catalog.glue.id={{ env_var('DBT_S3_TABLES_BUCKET') }} --conf spark.sql.defaultCatalog=glue_catalog"

Create dbt models

In this section, you build out the full model layer: a sources.yml that registers your raw AWS Glue tables, two staging models that clean and prepare the customer and order data, and three mart models that turn those staged data into a dimension table and two fact tables, one using incremental merge and one using incremental append.

First, create sources.yml defines your raw data tables:

version: 2

sources:
  - name: raw_ecommerce
    description: "Raw e-commerce data in regular S3 buckets"
    schema: raw_ecommerce

    tables:
      - name: customers
        description: "Customer master data"
        columns:
          - name: customer_id
            tests:
              - unique
              - not_null
          - name: email
            tests:
              - unique
              - not_null

      - name: orders
        description: "Order transactions"
        columns:
          - name: order_id
            tests:
              - unique
              - not_null
          - name: customer_id
            tests:
              - not_null
              - relationships:
                  arguments:
                    to: source('raw_ecommerce', 'customers')
                    field: customer_id
          - name: updated_at
            tests:
              - not_null
-- Staging model as S3 Tables with incremental merge
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='customer_id',
    on_schema_change='sync_all_columns',
    file_format='s3tables'
) }}

SELECT
    customer_id,
    LOWER(TRIM(email)) AS email,
    first_name,
    last_name,
    CAST(registration_date AS DATE) AS registration_date,
    customer_segment
FROM spark_catalog.{{ source('raw_ecommerce', 'customers') }}
WHERE customer_id IS NOT NULL
-- Staging model as S3 Tables with incremental merge
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='order_id',
    on_schema_change='sync_all_columns',
    file_format='s3tables'
) }}

SELECT
    order_id,
    customer_id,
    CAST(order_date AS DATE) AS order_date,
    CASE
        WHEN LOWER(TRIM(order_status)) = 'completed'  THEN 'completed'
        WHEN LOWER(TRIM(order_status)) = 'shipped'    THEN 'shipped'
        WHEN LOWER(TRIM(order_status)) = 'processing' THEN 'processing'
        WHEN LOWER(TRIM(order_status)) = 'cancelled'  THEN 'cancelled'
        ELSE 'unknown'
    END AS status,
    CAST(order_amount AS DECIMAL(10,2)) AS total_amount,
    EXTRACT(YEAR  FROM CAST(order_date AS DATE)) AS order_year,
    EXTRACT(MONTH FROM CAST(order_date AS DATE)) AS order_month,
    CAST(updated_at AS TIMESTAMP) AS updated_at
FROM spark_catalog.{{ source('raw_ecommerce', 'orders') }}
WHERE order_id IS NOT NULL
-- Dimension table using S3 Tables
{{ config(
    materialized='table',
    file_format='s3tables',
    partition_by=['registration_year'],
    table_properties={
        'format': 'iceberg',
        'write.format.default': 'parquet'
    }
) }}

SELECT
    customer_id,
    email,
    first_name,
    last_name,
    registration_date,
    YEAR(registration_date) as registration_year,
    customer_segment,
    CASE
        WHEN customer_segment = 'Premium' THEN 1
        WHEN customer_segment = 'Regular' THEN 2
        ELSE 3
    END as segment_priority,
    CURRENT_TIMESTAMP() as dbt_updated_at
FROM {{ ref('stg_customers') }}
-- Fact table using S3 Tables with incremental merge
{{ config(
    materialized='incremental',
    file_format='s3tables',
    incremental_strategy='merge',
    unique_key='order_id',
    partition_by=['order_year', 'order_month'],
    table_properties={
        'format': 'iceberg',
        'write.format.default': 'parquet'
    }
) }}

SELECT
    o.order_id,
    o.customer_id,
    o.order_date,
    YEAR(o.order_date)  AS order_year,
    MONTH(o.order_date) AS order_month,
    o.status,
    o.total_amount,
    c.customer_segment,
    c.segment_priority,
    CURRENT_TIMESTAMP() AS dbt_updated_at
FROM {{ ref('stg_orders') }} o
LEFT JOIN {{ ref('dim_customers') }} c
  ON o.customer_id = c.customer_id
-- Fact table using S3 Tables with incremental append
{{ config(
    materialized='incremental',
    file_format='s3tables',
    incremental_strategy='append',
    partition_by=['event_year', 'event_month'],
    table_properties={
        'format': 'iceberg',
        'write.format.default': 'parquet'
    }
) }}

SELECT
    order_id,
    customer_id,
    status,
    order_date,
    total_amount,
    updated_at,
    CURRENT_TIMESTAMP() AS recorded_at,
    YEAR(updated_at)    AS event_year,
    MONTH(updated_at)   AS event_month
FROM {{ ref('stg_orders') }}

  1. Run the following command.

By running without --full-refresh, dbt runs its normal incremental logic instead of rebuilding the tables from scratch. In the staging layer, stg_customers and stg_orders apply the changes with a MERGE INTO statement that updates customer_id=1 and order_id=1004 in place and inserts customer_id=6 and order_id=1006. Downstream, fact_orders (merge) reflects the 1004 update and the 1006 insert as the latest state, while fact_order_history (append) records both 1004 and 1006 as new history rows.

Clean up

To avoid ongoing charges, clean up the resources you created during this walkthrough. Complete these steps in the specified order to facilitate proper resource deletion.

  1. Drop the tables dbt created in the S3 Tables namespace.
  2. Remove the namespace from the table bucket.
  3. Delete the table bucket.
  4. Delete the Data Catalog database.
  5. Delete the data this walkthrough wrote to your S3 bucket: the dbt warehouse data under s3://<YOUR-REGULAR-BUCKET>/glue/data/ and the sample CSV files under s3://<YOUR-REGULAR-BUCKET>/raw/. Leave the bucket itself in place if you use it for other workloads.
  6. (Optional) Remove the local dbt project directory (dbt_glue_s3_tables) and the sample customers.csv / orders.csv files.

Conclusion

In this post, we showed how to build an end-to-end dbt transformation pipeline on Amazon S3 Tables with AWS Glue 6.0, using a staging and mart architecture. At the core of this pipeline are incremental models on S3 Tables, which let us transform and maintain data incrementally with SQL. We demonstrated two incremental strategies working together: the merge strategy to keep the latest state per order in fact_orders, and the append strategy to build an audit-friendly change history in fact_order_history.

S3 Tables support in the dbt-glue adapter is currently experimental (as of version 1.12.4) and will continue to evolve in upcoming releases. As with any experimental feature, we recommend thoroughly testing it in your own environment before use.

To learn more, see Amazon S3 Tables and the dbt-glue adapter.
