AI 逐段翻译

为数据迁移构建代理工厂：用 Snowflake 做一个小测试

我如何用并行 AI 代理、脚本化检查和一个独立的 AI 审查员，把 PostgreSQL 数据库的视图和函数迁移到 Snowflake，以及这个过程中出了什么问题。

简短版

我构建了一个用于 SQL 迁移的“代理工厂”小型概念验证（PoC）：AI 翻译器并行工作，脚本用真实数据测试每一个翻译，以及一个第二个、独立的 AI，其唯一职责就是找出测试遗漏的问题。测试用例：Pagila，一个公开的 PostgreSQL 示例数据库，迁移到 Snowflake。

这个架构的目标是迁移数据库的逻辑（视图、函数、过程），而不仅仅是它的数据，并且要达到一种规模——在这个规模上“一个 AI 加一个人类审查员”不再奏效，同时绝不让 AI 给自己的作品打分：

  • 规模： 按依赖顺序并行翻译许多对象。
  • 信任： 脚本用真实数据和边界情况证明每一个翻译，然后由一个独立审查员寻找脚本遗漏的问题。
  • 只在关键之处投入人工时间： 人们回答工厂无法决定的明确问题，并且每个答案都会被复用。

为什么做 PoC： 在将其用于真实迁移之前，我想在一个小而公开的东西上了解哪些部分有效、代理在哪里失败、脚本必须捕获什么。最有用的教训：数据匹配并不等同于逻辑正确。 有些翻译在真实数据上“匹配”PostgreSQL 纯粹是运气。

如果你从未用 AI 代理构建过任何东西，这篇文章就是为你写的。我会解释每一个部分。

1. 问题：复制表很容易，复制逻辑并不容易

数据库迁移有两个部分：

  1. 数据：表和行。无聊、机械，由工具解决。
  2. 代码：用源数据库的 SQL 方言编写的视图、函数和过程。每一个都必须为重写以适配目标数据库，并且必须被检查。

代码这一半正是项目停滞的地方。如今常见的配置是“一个 AI 助手加一个人”：AI 翻译一个对象，人来审查，如此重复。这对 20 个对象有效。对 2,000 个对象则无效。而且它有一个隐藏缺陷：编写 SQL 的 AI 同时也是说“看起来不错”的那个。没有任何独立方检查它。

研究支持了这种担忧。LLM 评判者给自己的输出打分高于其他人同样好的输出（Panickssery 等人，NeurIPS 2024），而当检查者来自不同的模型家族时，验证效果更好（Lu 等人，2025/26）。

2. 别人写了什么，以及空白之处

在构建任何东西之前，我阅读了大约 15 个原始资料。简短版本如下：

  • 大型迁移使用工厂，而不是聊天。 Airbnb 在 6 周内迁移了约 3,500 个测试文件，方法是将每个文件推过一个带重试的脚本化检查状态机（Airbnb）。Google 发现人工审查，而不是代码生成，才是瓶颈（Google，2025）。
  • 把工作分发给许多代理，但要给每个代理一份清晰的简报。 Anthropic 的多代理研究系统使用一个主导代理和并行子代理，并认识到模糊的任务描述会让代理重复工作（Anthropic）。
  • 测试就是规格说明。 当 16 个并行代理构建一个 C 编译器时，教训是“任务验证器几乎完美，否则 Claude 会解决错误的问题”（Carlini, Anthropic）。
  • 在一个数据集上匹配数据并不能证明查询是正确的。 一个缺少 WHERE 子句的查询可以在一个数据库上返回正确答案（Zhong 等人）。更新的工具会构建针对性的测试数据来暴露这类错误（LASSO，2026）。
  • 厂商将基于规则的转换、AI 修复和数据比较结合起来（Snowflake SnowConvert AI，Databricks Lakebridge）。Microsoft 的 Horizon 警告说，修复循环内部的 LLM 评判者可能导致“回归螺旋”，并且真实数据经常产生空结果，因此比较通过了却没有证明任何东西（Horizon，VLDB 2025）。

空白之处。 在我找到的厂商工具中，同一个代理负责翻译、读取差异并修复。没有人公布按对象划分的数字（首次尝试通过率、重试次数、每个对象的成本、审查员发现了差异所遗漏的什么内容）。而 SnowConvert 的 AI 验证将 PostgreSQL 列为“计划中”。因此我构建了一个小型、公开、可复现的版本并对其进行了测量。

3. 架构

数据存放在三个地方：只读的 PostgreSQL 源、一个仅用于测试的 PostgreSQL 副本，以及 Snowflake（RAW 模式用于复制的表，SANDBOX 用于试用，临时的 EDGE_* 模式用于边界情况测试）。设计规则很简单：脚本完成一切可以机械决定的事情；代理只负责翻译和评判。 代理从不接触数据库。只有关卡脚本会接触，而且只在一次性模式中。

4. 逐步讲解

所有代码都是 Python；仓库中有完整版本。下面的片段是真实代码，经过删减。

步骤 1：源数据库，放在 Docker 中

当前的 Pagila 需要 带 pgvector 的 PostgreSQL 18（它使用 uuidv7() 和一个向量列），所以普通的 Postgres 16 无法加载它。

docker run -d --name pagila-factory -p 127.0.0.1:55432:5432 \
  -e POSTGRES_PASSWORD="$(cat ~/.config/pagila_factory/pg_admin)" pgvector/pgvector:pg18
docker exec pagila-factory psql -U postgres -c "CREATE DATABASE pagila"
docker exec -i pagila-factory psql -U postgres -d pagila < pagila-schema.sql
docker exec -i pagila-factory psql -U postgres -d pagila < pagila-data.sql

然后是两种角色：一个只能读取源数据库，另一个拥有一个用于测试的副本。

CREATE ROLE pagila_ro LOGIN PASSWORD '...';
GRANT pg_read_all_data TO pagila_ro;
ALTER ROLE pagila_ro SET default_transaction_read_only = on;   -- the source can never change
CREATE DATABASE pagila_scratch TEMPLATE pagila OWNER factory_scratch;

连接测试证明了这一点：以 pagila_ro 身份执行 CREATE TABLE 会失败，报错为 "cannot execute CREATE TABLE in a read-only transaction"。

步骤 2：Snowflake，采用最小权限

一个角色、一个 60 秒后挂起的超小仓库、一个数据库。管道从不使用管理员角色。

CREATE ROLE IF NOT EXISTS PAGILA_FACTORY_ROLE;
CREATE WAREHOUSE IF NOT EXISTS PAGILA_FACTORY_WH WAREHOUSE_SIZE = XSMALL
  AUTO_SUSPEND = 60 AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE STATEMENT_TIMEOUT_IN_SECONDS = 300;
GRANT USAGE, OPERATE ON WAREHOUSE PAGILA_FACTORY_WH TO ROLE PAGILA_FACTORY_ROLE;
CREATE DATABASE IF NOT EXISTS PAGILA_FACTORY;
GRANT OWNERSHIP ON DATABASE PAGILA_FACTORY TO ROLE PAGILA_FACTORY_ROLE;
-- as the project role: schemas RAW, SANDBOX, MIGRATED

每个会话还会执行 USE SECONDARY ROLES NONE，因此会话永远无法获得未授予它的管理员角色。

步骤 3：复制表并证明无误

表不是代理的工作。一个脚本用 COPY ... TO STDOUT（在只读会话中允许）导出每个表，将其上传到表暂存区并用 COPY INTO 加载。然后它读回双方数据并比较每列的概况：行数、非空计数、不同值计数、总和、最小值/最大值。

结果：15/15 张表，352/352 项检查通过。 第一次试点实际上失败了：时间戳偏差不到一秒。数据本身没问题；是我的检查在 Snowflake 上使用整秒（epoch_second），而在 PostgreSQL 上使用微秒。教训一：检查你的检查。

步骤 4：清单和波次

清单从目录读取定义。视图很容易（pg_get_viewdef 加上 pg_depend）。函数则不然：PostgreSQL 不追踪函数体依赖什么，因此脚本会解析文本。我的第一个版本报告说每个函数都依赖一个名为 language 的表，因为它匹配到了 LANGUAGE plpgsql 子句。用一行代码修复了。

然后对象被排序进波次。film_in_stock 调用 inventory_in_stock，所以它必须等待：

wave 1  actor_info, customer_list, film_list, ... inventory_in_stock, rewards_report (11 objects)
wave 2  film_in_stock  ← depends on inventory_in_stock
PASS  37/37 checks · inventory.json

步骤 5：智能体

每个智能体都是通过 Claude Agent SDK 发起的一次调用，带有一份工作描述、材料，以及一个答案必须匹配的 JSON schema。重要的部分是智能体不会获得的东西：

opts = ClaudeAgentOptions(
    model=model,
    tools=[], allowed_tools=[],        # no shell, no files, no web: it can only write text
    setting_sources=[],                # none of my personal settings or memory
    max_turns=4,
    system_prompt=system_prompt(role),
    output_format={"type": "json_schema", "schema": schema},
)
result = None
with anyio.fail_after(timeout_s):      # 5 minutes per call, configurable
    async for m in query(prompt=user_prompt, options=opts):   # the Claude Agent SDK call
        if isinstance(m, ResultMessage):                       # the final message of the session
            result = m
answer = result.structured_output      # the JSON that matches the schema
cost = result.total_cost_usd           # logged per call

query() 启动一个 Claude 会话并回流其消息；代码只保留最后一条，其中包含结构化答案、成本和轮次数量。运行超过时限的调用会被取消，该对象被升级处理，而不是重试。

没有设置 setting_sources=[] 时，我的第一个测试智能体以 --- 开头作答：它加载了我自己的 Claude Code 指令。对于一个必须独立且可重复的审查者来说，这是一个 bug。

翻译器返回 {sql, trace, assumptions, confidence}。验证器看到源、翻译后的 SQL 和比较结果，但永远看不到翻译器的推理。

智能体如何并行运行。 这些调用是异步的：当一个智能体等待 Claude 时，Python 切换到另一个，全部在单线程上。一个线程就足够了，因为它本身几乎不做任何工作：每个智能体在自己的 Claude Code 进程中运行，Claude 在 Anthropic 的服务器上进行思考，Python 只发送提示并在回复到达时做出反应。编排器为波次中的每个对象启动一个任务，并限制同时运行的数量：

limiter = anyio.CapacityLimiter(concurrency)          # 3 objects at a time by default
async with anyio.create_task_group() as tg:
    for obj in wave:
        tg.start_soon(process, obj, limiter)          # translate → gates → verify, per object
# inside process(): database checks use blocking drivers, so they run on a worker thread
gate = await anyio.to_thread.run_sync(gates.deploy_and_diff, obj, sql)

在一个对象内，步骤按顺序运行（翻译，然后测试，然后验证）。跨对象时，它们重叠进行。一个波次只有在前一个波次完成后才开始，依赖项未通过的对象会被标记为阻塞，而不是继续翻译。

步骤 6：关卡

智能体输出是不可信的文本。在运行之前，守卫会检查它：

head = re.match(r"CREATE\s+OR\s+REPLACE\s+(SECURE\s+)?(VIEW|FUNCTION|PROCEDURE)\s+SANDBOX\.(\w+)\b", s, re.I)
...
if ";" in outside_body:  findings.append("more than one statement")
bad = FORBIDDEN.findall(no_strings)   # DROP, GRANT, INSERT, EXECUTE, USE, ...

然后对象在 SANDBOX 中创建，并在两个系统上运行。视图按逐行比较（作为多重集，在规范化数字、时区和 JSON 之后）。函数用脚本选择的参数集调用，以命中已知情况，例如从未被租用过的、当前已租出的或不存在的库存物品：

"inventory_in_stock": FunctionSpec(arg_query="""
  (select inventory_id from inventory order by inventory_id limit 15)
  union (select distinct inventory_id from rental where return_date is null order by 1 limit 15)
  union (select i.inventory_id from inventory i where not exists
         (select 1 from rental r where r.inventory_id = i.inventory_id) order by 1 limit 10)""", ...)

两条规则直接来自 Horizon 论文：

  1. 两边都为空不是证据。 如果每次调用都不返回任何内容，该对象只能通过一个能产生行的边界测试来通过。
  2. 只有证据才能把工作送回去。 仅凭审查者的意见永远不会触发重试；一个显示差异的已执行测试才会。

步骤 7：验证器和边界情况测试

验证器将小测试写成数据：要插入的行，以及要用来调用的参数。

{"name": "mixed_returned_and_open",
 "purpose": "Inventory 4583 has one returned rental and one open rental, so it should return FALSE.",
 "rows": [
  {"table": "inventory", "values": {"inventory_id": 4583, "film_id": 1, "store_id": 1}},
  {"table": "rental", "values": {"rental_id": 87562, "rental_date": "2022-05-01T10:00:00+00:00",
     "inventory_id": 4583, "customer_id": 1, "staff_id": 1, "return_date": "2022-05-03T10:00:00+00:00"}},
  {"table": "rental", "values": {"rental_id": 87563, "rental_date": "2022-05-31T23:59:59+00:00",
     "inventory_id": 4583, "customer_id": 1, "staff_id": 1, "return_date": null}}],
 "call_args": [4583]}

运行器将它们插入 PostgreSQL 中一个总是回滚的事务内，以及一个由零拷贝克隆组成、之后会被删除的 Snowflake schema 中。它在两边运行该对象并进行比较。运行后的检查确认临时副本未被更改。

步骤 8：诊断器和决策卡

我的第一次完整运行把一半对象升级处理，并将原始 JSON 转储作为“问题”。不可读，而且智能体在它永远无法修复的问题上浪费了重试。因此我添加了一个诊断器，对每个失败进行分类。有一个标签需要定义：测试框架是我围绕智能体编写、用于运行和检查它们的一切：关卡脚本、比较 PostgreSQL 和 Snowflake 结果的代码、边界测试设置和翻译规则。当测试框架有 bug 时，一个正确的翻译看起来像是坏的。

决策卡看起来是这样的：

问题： 如果任一阈值参数为 NULL，Snowflake 存储过程应该像 Postgres 那样抛出错误，还是返回空结果？
根本原因： source_bug。Postgres 用 || 构建动态 SQL；NULL 会使整个字符串变为 NULL，EXECUTE 意外失败。1. 对 NULL 参数抛出错误。2. 返回空结果。
建议： 抛出错误；它保持两个系统一致。

答案进入决策日志，并在后续简报中被引用，因此同一个问题永远不会被问两次。 在 UI 中，每张卡片以一句平实的话开头说明问题，然后是原因、选项和建议：

当源有缺陷时，“接受建议”不足以作为证据。对于 get_customer_balance，我将已批准的逻编写为临时副本中的修正参考函数（绝不写入源），关卡将 Snowflake 与之比较：24 次调用中 24 次匹配。

步骤 9：状态 UI

一个本地页面（绑定到 127.0.0.1，只读取日志文件）显示每个流水线、每个波次和每个对象，包含开始/结束时间，并在每个阶段有一个 ⓘ 解释其作用。

5. 结果

第一次尝试就通过的内容： 简单视图（customer_list、staff_list、sales_by_store、sales_by_film_category、rental_by_category）和两个库存函数。验证器仍然为每个编写了 2–4 个边界测试，它们全部一致。

验证器捕获到而数据差异遗漏的内容：

  • 幸运匹配。 film_list 和 nicer_but_slower_film_list 用一个自定义 group_concat 构建演员列表，该函数没有 ORDER BY，因此 PostgreSQL 的顺序是未定义的。翻译器产生的顺序碰巧在真实数据上匹配。验证器插入了几行，PostgreSQL 改变了计划，顺序在每一部电影上都变了。真实数据的匹配曾是好运。修复方式是一个决策，而不是代码：当源顺序未定义时，比较时忽略顺序（决策 D-1，此后自动应用）。
  • 源中的一个合并键 bug。 actor_info 构建一个以类别名称为键的 JSON 对象。验证器插入了两个同名的类别：PostgreSQL 静默丢弃其中一个，翻译则合并它们。哪个正确是一个业务问题，所以交给了人工。
  • NULL 参数。rewards_report 在 PostgreSQL 上因 NULL 输入而失败，这是它构建动态 SQL 的方式偶然导致的；Snowflake 版本则不返回任何行。它被交给人工处理，并附带了建议。
  • 一个从未成功运行的源。get_customer_balance 调用了 IF()，这是一个 PostgreSQL 没有的 MySQL 函数。它在全部 24 次调用中都失败。诊断器根据函数自身注释提出了预期逻辑，因此人工只需确认即可。

三个人工决策（每个只需一行即可回答）：

因我而失败的部分。大多数失败并非糟糕的翻译。它们是我测试框架（我的测试脚本、比较代码和规则）中的缺陷，让正确的 SQL 看起来像是错的：

  1. 时间戳以不同精度比较（步骤 3）。
  2. language 被解析成了一张表（步骤 4）。
  3. PostgreSQL JSON（一个 Python dict）与 Snowflake JSON（一个字符串）比较：actor_info 因我的缺陷被错误归咎了三次。
  4. 边界测试：PostgreSQL 填充了列默认值 rating = 'G'，Snowflake 没有默认值。修复方法：在 PostgreSQL 中用 RETURNING * 插入，并将 已存储的 行复制到 Snowflake。
  5. 来自早先尝试的一个函数阻止了创建同名的过程。
  6. Python 驱动将 5.99 作为 double 发送，因此 PostgreSQL 找不到 rewards_report(integer, numeric)。
  7. 测试副本的 payment 表按月分区且只覆盖 2022 年，因此“最近三个月”的测试无法插入行。仅在副本中用默认分区修复。
  8. 我自己的翻译规则写着“numeric → NUMBER”。在 Snowflake 中，裸 NUMBER 只保存整数，所以 0.01 变成了 0，rewards_report 在三次独立运行中都在第一次尝试时失败。反复出现的缺陷应写入规则，而不是再重试一次。

诊断器自己发现了缺陷 3–8，并将它们标记为 harness_issue（或指出了确切的类型）。这是我主张加入它的最有力论据。

评估：它可重复吗，它能发现缺陷吗？

一次通过的运行可能是运气：智能体每次都会给出不同的答案。因此我将 12 个已验证对象视为黄金集，并测量了两件事。

可重复性。 我从头完整重跑了整个工厂 3 次，使用相同的提示和模型。每次运行都会重新翻译并测试每个对象；它从不会看到同一对象早先的翻译，且它产出的任何内容都不会覆盖已验证的 SQL。

更便宜的翻译器。 额外一次运行使用 Sonnet 作为翻译器（验证器仍使用 Opus），同样通过了 12/12，首次尝试即达 92%，每个对象 $0.11 而非 $0.16。一次运行并非证明，但它表明质量更多地由检查而非翻译器模型承载。

植入缺陷。 然后我故意破坏已验证的翻译，一次一个已知缺陷，让每一个都经过相同的检查，之后再把已验证版本放回去：

数据差异漏掉了 5 个中的 3 个，因为真实数据中没有无影片的演员、没有恰好处于截止时间的付款、也没有落在报告日期窗口内的行。边界测试抓住了全部 5 个。这是本文中最清晰的证据，说明独立审查者存在的必要性。这也是一个小样本：五个缺陷，每个只测试一次。

对你自己迁移的要点

  • 让脚本决定一切它们能决定的事。 智能体负责翻译和判断；脚本负责检查。
  • 绝不要让翻译器给自己的作品打分。 在这个测试中，一个全新的、持怀疑态度的审查者发现了数据差异漏掉的每一个问题。
  • 匹配的差异是证据，不是证明。 在你信任它之前，先查找空结果和未定义的排序。
  • 让升级成为决策，而不是倾倒。 一个问题、两三个选项、一个建议，以及一份日志，这样它只会被问一次。
  • 衡量工厂，而不只是迁移。 我自己的测试框架造成的失败比 AI 更多，而我知道这一点只是因为每次尝试都被记录了下来。
