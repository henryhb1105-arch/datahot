为什么用 TCP，它有何不同？

为什么需要原生客户端

ClickHouse 以列的方式存储和处理数据。到目前为止，官方 .NET 客户端仅支持 HTTP 搭配 RowBinary（一种面向行的格式）。这意味着每个结果都要经过两次转换：服务器将其列块转换为行流，客户端再逐个值解码该流。插入则经过同样的两步反向进行：客户端写入行，服务器再将其解析回列。

原生协议消除了这两次转换。它是 clickhouse-client 使用的协议，也是 ClickHouse 服务器用于分布式查询的协议。数据以 Native 格式、作为列块在双向传输。这样两端的工作量都更少：服务器无需进行格式转换，客户端可以一次批量操作读取整列，而不是一次一个值。

原生协议承载的也不只是数据：在查询运行时，服务器会以数据块之间的独立数据包发送进度、profile 事件、totals 和 extremes，以及（按请求）其自身的日志消息。客户端将它们传回你的回调。而且由于该协议是有状态的，一个会话就是一个 socket：临时表和 SET 语句会保留在同一个连接上（因此也在同一个副本上），即使位于负载均衡器之后也是如此。

两种协议的区别

核心区别在于线上数据的形状。RowBinary 将列交错排列：每一行是其各个值连续排列，然后才是下一行。Native 则将它们分组：一个块包含所有 id，然后所有 name，然后所有 score，并且每一列都以其名称和类型开头。

HTTP 客户端逐个值遍历流。TCP 客户端对每个块的每一列进行一次调用。对于固定宽度类型，该调用是一次批量读入池化缓冲区，你得到的列是一个 ReadOnlySpan<T>。一个块通常包含数千行，因此这节省了大量调用。

复合类型遵循同样的规则。一个 Array(Float64) 列先是它的所有行偏移量，然后所有行的每个元素在一个连续段中：

因此客户端一次性读取整个块的所有元素，一行就是两个偏移量之间的一个切片。这种布局在插入时也有回报：给 InsertAsync 提供扁平值加上偏移量（ClickHouseTcpColumn.CreateArray，或者直接来自 SELECT 的列），每个元素一次拷贝即可发出。交错数组 double[][] 也可以，每行一次拷贝。

优缺点：并非全是玫瑰与彩虹

原生客户端很快，但它不是免费的升级。以下是你得到的和你放弃的。

你得到的

  • 速度。 无需解码的列式读取。 StreamAsync 给你块，每一列的 .Values 是 socket 读入缓冲区上的一个 span。而列式插入基本上就是一次 memcpy。
  • 无需设置的 POCO。 映射在首次使用时编译，每列一个循环，无装箱。
  • 查询元数据。 查询运行期间的回调，用于进度、profile 事件、服务器日志以及 totals 和 extremes。
  • 可到达服务器的取消。 取消会发送一个 Cancel 数据包，因此服务器可以停止查询。
  • 会话。 一个会话就是一个 socket，因此临时表、SET，以及 SET ROLE 在负载均衡器之后也能工作，无需 session_id。
  • W3C 跟踪上下文 传播到 ClickHouse。

你放弃的

  • 它是实验性的。 在标记为稳定之前，API 可能会变化。
  • JSON 仅为文本。 JSON 列以字符串形式到达，你需要自行解析；HTTP 会给你一个 JsonObject 或一个 POCO。服务器上额外的字符串序列化步骤相对较慢，因此如果你是重度 JSON 用户，不要期望有很好的性能。不过，我们计划很快实现对二进制 JSON 格式的支持。
  • 这个 object[] 层级会失去大部分性能优势。 每行一个数组、每个值一次装箱，以及插入时的行到列转置，意味着列式格式的所有性能优势都丧失了。这意味着 ORM（通常使用 object[]（用于读写对象的方法）不会看到任何显著改进。
  • DateTime会以数字形式返回。Columns 和 object[]行会给你原始的 uint/long，从而让读取保持零拷贝和完整精度。使用 ReadAs<DateTimeOffset> 进行转换，或使用具有正确类型的 POCO 属性进行自动转换。
  • 块是借用的。 为避免分配，一个块仅在一次循环迭代内有效，之后其缓冲区会被重用。如果你想把块中的任何数据保留到循环之外，你需要自己将其复制出来。
  • 不支持 ADO.NET（因此不支持 Dapper 或 Entity Framework Core）。
  • 不支持 CSV、Parquet 或 JSONEachRow 等替代格式。
  • 不支持 JWT 身份验证。
  • 并且只支持 {name:Type} 参数（不支持无类型的 @name）。

仅支持 .NET 8 或更高版本。 那么，选哪一个？

  • 对于分析性读取、批量插入和性能敏感的工作负载：试试 TCP。
  • 对于 ORM、不同的文件格式、令牌认证或大量使用 JSON：继续使用 HTTP。

两者都包含在同一个包中，因此你可以在合适的地方使用各自的方式。

性能

我们将两种 TCP 方式（块和 POCO）与 HTTP 客户端进行了基准测试。

  • 设置： 客户端位于 AWS m7i.8xlarge 上，服务器位于 ClickHouse Cloud（26.4）上，通过真实网络连接。
  • 测试组：HTTP 客户端（QueryAsync<T> / InsertBinaryAsync<T>）、使用列（columns）的 TCP（StreamAsync / InsertAsync），以及使用 POCO 的 TCP（QueryAsync<T> / InsertRowsAsync<T>）。
  • 数据： 对 hits 数据集（105 个标量列）进行 100 万行读取和 10 万行插入，以及一个包含 Array、Map 和 Tuple 列的表，以及一个包含单个 JSON 列的表。
  • 数据结果：每个场景在一个进程中运行 5 次。我们报告 4 次预热运行的中位数。

突出之处：

使用列（columns）读取所需时间不到一半（在 hits 上为 0.44 倍，在集合上为 0.45 倍），使用 POCO 则约为三分之二，这是同类比较的数字。

插入在所有场景中都更快。 hits 插入使用列（columns）耗时 0.61 倍，使用 POCO 耗时 0.66 倍。使用 16 个并发插入时，两种方式耗时均为 0.46 倍。

内存

最大的改进在内存方面。读取 100 万行 hits 使用 HTTP 分配 1.6 GB，而使用 TCP 列（columns）仅分配 6 MB。请注意下图中 x 轴为对数刻度。

我们是如何做到的

三条原则驱动了 TCP 客户端中的每一个决策：

  • 零拷贝。 数据仅被复制一次，从套接字复制到列自身的缓冲区。在此复制之上的所有内容都是对它的视图。在写入方向上，你已持有的列从你的数组进入发送缓冲区，只需一次复制。（默认开启的压缩会增加一次解压过程和一次额外复制。下文“零拷贝不可能之处”有详细说明。）
  • 零 GC 分配。 在列式层上，除非绝对必要，否则不会为每一行分配任何内容。列缓冲区来自池并返回池，剩下的只是每个块几个小对象。这就是为什么读取 100 万行 hits 仅分配 6 MB 而不是 1.6 GB。
  • 尽可能少的编码和解码。 对于大多数固定宽度类型，ClickHouse 的线格式和 .NET 的内存布局完全相同。因此 Int64 或 Float64 根本不会被解码。 DateTime 保持为数字，字符串保持为 UTF-8，直到你请求其他内容。

为实现这些原则，我们大量使用了 MemoryMarshal 来原地重新解释而不是解码。固定宽度列是一个池化的 byte[]，由单次读取填充。它的 Values 属性不进行任何转换；它只是将字节重新解释为 T：

1// Reading a fixed-width column (error handling trimmed)2// Borrow the needed space from a pool3int byteCount = checked(rowCount * Unsafe.SizeOf<T>());4byte[] rented = ArrayPool<byte>.Shared.Rent(byteCount);56// A single read copies the entire column from the socket7await reader.ReadBytesAsync(rented.AsMemory(0, byteCount), cancellationToken);89// The column is built around that data10returnnew PrimitiveColumn<T>(columnName, columnType, rented, byteCount, pooled: true);1112// PrimitiveColumn<T>: accessing the values as type T by reinterpreting in place13public ReadOnlySpan<T> Values => MemoryMarshal.Cast<byte, T>(buffer.AsSpan(byteOffset, length));

这涵盖了所有整数和浮点类型、Bool、原始 DateTime 计数、.NET 的 Int128，以及我们自己的 Int256/UInt256，它们被声明为 [StructLayout(LayoutKind.Sequential)]，由四个小端 ulong 组成，因此其内存与线格式匹配。客户端中没有任何 unsafe 代码；项目甚至没有启用它。 Span<T>、MemoryMarshal 和 ArrayPool<T> 完成了所有工作。

批量读取跳过缓冲区。 小读取（如数据包头和长度）通过 16 KiB 缓冲区进行。列数据则不然：ReadBytesAsync 复制出已缓冲的内容，然后直接从套接字将其余列数据读入其池化数组。一个 200 MB 的列需要一个 200 MB 的目标，而不是一个 200 MB 的读取缓冲区。

视图，而非值。 其他类型也保持其线格式。一个 Nullable 列是原始空值映射加上一个零拷贝内部列，因此不会构建 T? 数组，除非显式请求。一个 String 列是一个池化 blob 加上偏移量：GetBytes(row) 无需复制即可提供 UTF-8 字节，而 .NET 字符串仅在请求时创建。 LowCardinality(String) 每个块解码每个字典条目一次，而不是每行一次。

写入时反向使用相同的技巧。 由连续数组支持的列通过 MemoryMarshal.AsBytes 发送，整个切片只需一次复制：

1if (typed is ISpanColumn<T> contiguous)2{3    writer.WriteBytes(MemoryMarshal.AsBytes(contiguous.Span.Slice(start, length)));4return;5}

复合列的工作方式相同。将从 SELECT 读取的列直接传递给 InsertAsync，其空值映射、偏移量或 LowCardinality 字典无需重建即可发送出去。

栈上的短生命周期缓冲区。 在我们确实需要编码的地方，例如将 .NET string 作为 UTF-8 发送时，短值使用 stackalloc，只有较长的值才会触及池：

1int maxBytes = Encoding.UTF8.GetMaxByteCount(value.Length);2if (maxBytes <= 256)3{4    Span<byte> scratch = stackallocbyte[256];5    WriteEncodedString(value, scratch);6}7else8{9// Rent a buffer from ArrayPool<byte>.Shared, encode, return it.10}

借用内存。 Block 背后的缓冲区属于客户端。当你的 await foreach 继续前进时，它们会返回池中，下一个块会重用它们。这就是列式层实现无分配的原因，也是块仅在一次迭代内有效的原因。编译器会提供帮助，因为 ReadOnlySpan<T> 不能跨越 await 存在。如果你仍然保留了一个列对象，在循环继续前进后读取它会抛出异常，而不是悄悄返回另一个块的数据。

列优先，行在其上。借用的规则必须位于最底层，因此我们先构建了无分配的列式 API，然后在其之上添加了 POCO 和 object[] 行。所有权恰好转移两次：从 socket 到块（客户端拥有它），以及从块到你的行或对象。

无需反射或装箱的 POCO

在读取到 POCO 或从 POCO 写入时，我们不会对每一行使用反射。客户端第一次看到具有给定列集的 POCO 类型时，它会为每一列构建表达式树，将其编译为委托，并缓存该计划。

在读取时，每一列获得一个已编译的循环，该循环在整个行范围内填充一个属性。以下是树中为DateTime64 列映射到 DateTimeOffset 属性的内容，以及每个部分的来源：

该值从 span 到属性 setter 始终保持强类型，因此没有任何装箱，并且对于每批行，每列只调用一次委托，而不是每个值调用一次。

转换在循环内部进行。当属性类型与列的类型不同时，列的编解码器会提供转换表达式：一个 DateTime64 列将其原始计数转换为该列时区中的 DateTimeOffset，一个 Enum8 变为你的枚举，而一个 Nullable 列填充一个 T?。

插入是镜像操作。每一列获得一个已编译的循环，该循环从每一行读取一个属性到池化的强类型缓冲区（destination[slot] = rows[start + slot].Id）。对于固定宽度类型，编解码器随后一次拷贝写入该缓冲区。

一个注意事项：在 NativeAOT 下，表达式树是解释执行而非编译执行，而解释执行的树不能包含 ReadOnlySpan<T>。在那里，计划改为通过列的索引器读取，每个值调用一次。

SIMD

大多数客户端不需要 SIMD。当线路布局与 .NET 的内存布局匹配时，我们只是执行一次批量拷贝。我们仅在两种布局不一致时使用向量代码，这为进一步优化创造了机会。

UUID：正确的字节，错误的顺序。

ClickHouse 将 UUID 存储为两个小端序 64 位半部分。.NET 的 Guid 保留一个 int、两个 short，然后是按顺序的八个字节。每个字节都在那里，只是位置不同：

Vector128.Shuffle 使用常量控制向量编译为单条 vpshufb（在 x86 上）（TBL 在 Arm64 上）。在读取时，我们将整个列直接 shuffle 到池化的 Guid[] 中：

1refbyte src = ref MemoryMarshal.GetReference(source);2refbyte dst = ref MemoryMarshal.GetReference(destination);3for (int i = 0; i < count; i++)4{5nuint offset = (nuint)i * UuidSize;6    Vector128.Shuffle(Vector128.LoadUnsafe(ref src, offset), control).StoreUnsafe(ref dst, offset);7}

在我们的微基准测试中，这比逐字节移动快约 9 倍，并且不分配任何内存。不支持向量的机器回退到普通的标量循环。

如果你自己尝试，有一点值得知道：在 .NET 8 和 9 上，Shuffle() 只有在 JIT 能看到控制向量是常量时，才会变成 vpshufb。我们的循环将控制向量作为参数，但它仍然获得 vpshufb，因为 JIT 将其内联到调用者中，在那里 static readonly 字段是可见的。将一个普通参数传递到一个未内联的方法中，你反而会得到对软件回退的调用。.NET 10 加速了两者。你可以用 DOTNET_JitDisasm 检查你自己的代码。

QBit：侧向存储的向量。

ClickHouse 的 QBit(T, N) 类型旨在加速近似向量搜索。它接受 N 个浮点值，并按每个位一个平面（float32 为 32 个平面）存储它们，最高有效位在前，因此像 L2DistanceTransposed(vec, ref, p) 这样的距离函数可以只读取每个元素的前 p 位，以精度换取速度。在插入时，客户端必须进行该转置：

逐位执行，每个元素需要 32 次操作。使用 Vector256，ExtractMostSignificantBits 将 8 个浮点数的最高位收集到一个字节中，这正好是一个平面字节，并且已经处于线路的位顺序中。将每个 lane 左移一位，下一位就在顶部：

1Vector256<uint> lanes = Vector256.LoadUnsafe(ref source, (nuint)(group << 3));2int slot = rowBase + QBitLayout.ByteOfGroup(group, BytesPerRow);3for (int wireIndex = 0; wireIndex < BitWidth; wireIndex++)4{5    scratch[(wireIndex * planeStride) + slot] = (byte)lanes.ExtractMostSignificantBits();6    lanes <<= 1;7}

JIT 将该循环体转换为一条 vmovmskps 和一条 vpslld。它使写入路径在 1,024 维时快了 11.7 倍，在 768 维时快了 16.5 倍。

在无法实现零拷贝的地方

零拷贝是规则，但当线路格式与 .NET 内存布局不一致（或我们必须实例化对象）时，它就无法实现。

字符串是最大的情况。ClickHouse 发送原始字节（通常是 UTF-8，但可以是任何编码），而 .NET 的 string 是 UTF-16，因此你请求的每个字符串都会被解码并分配。如果你可以直接使用 UTF-8，IStringColumn.GetBytes 直接为你获取原始字节数组。字符串也不能在一次拷贝中写入：线路上的每个值都有自己的长度前缀，因此客户端一次写入一个。（FixedString 没有前缀，因此可以。）

一些类型在读取时会改变形状。IP 地址变成 IPAddress 对象，每行一个，Date 变成 DateOnly，小数变成 decimal 或我们自己的 ClickHouseTcpDecimal，所有这些都在块到达时立即发生。而在插入时，Nullable 值和元组字段在你的数据中没有连续的连续段，因此它们会逐值写入，而不是一次拷贝。

从 HTTP 客户端迁移

你不必只选一个。两个客户端都随 ClickHouse.Driver 提供，因此你可以将热路径移至 TCP，并为原生客户端尚未完成的工作保留 HTTP：ORM、文件格式和令牌认证。清单：

连接到原生端口。 即 9000，或使用 UseTls=true 的 9440。服务器设置是字符串；在连接字符串中，为它们加上前缀 set_（set_max_threads=4）。使用依赖注入，services.AddClickHouseTcpDataSource(...) 注册一个池化客户端并分发 IClickHouseTcpClient。

重写参数。 @name 占位符变为 {name:Type}，并且值移入 ClickHouseTcpQueryOptions.Parameters。为时刻指定时区，例如 {t:DateTime64(3, 'UTC')}。

一旦这一步能正常工作，就把重要的循环换成 StreamAsync 和 InsertAsync。

最后，检查是否有破坏性的行为变更：

  • DateTime 列在列式和 object[] 层上会以原始数字返回。POCO 属性会自动转换。
  • 完成或释放每个枚举，以便其连接回到池中。
  • 提前跳出结果或取消，会关闭该连接而不是复用它。
  • MaxPoolSize（默认为 20）限制同时运行的操作数量。
  • ReadTimeout衡量的是读取之间的静默时间，而不是总查询时间。
  • 没有自动重试。对你可能重试的任何插入设置一个 DeduplicationToken。
  • 临时表和 SET 需要 OpenSessionAsync，因为普通调用可能落在任何池化连接上。
  • JSON 以文本形式到达。

文档中的 迁移指南 有完整细节，并且 Tcp_004_MigratingFromHttp.cs 让两个客户端对同一张表运行。
