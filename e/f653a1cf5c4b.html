Snowflake Dynamic Tables更新：更快更灵活

DataHot 速览

本文基于真实账号演示 Snowflake 2026 年 Dynamic Tables 更新。核心新能力是允许对动态表的冻结区（frozen region）执行 DELETE、UPDATE、MERGE，示例中对历史订单的删除和更新均可持久化；对无冻结区或可变窗口内数据的 DML 仍被拒绝。该设计支持 GDPR 删除历史个人数据等场景，并确保非冻结区的手动写入不会被下次刷新覆盖。作者为 Snowflake 首席技术架构师。

为什么值得关注：数据平台从业者可借此理解 Snowflake 动态表在数据一致性和可维护性上的重要演进，尤其是冻结区 DML 对历史数据治理与合规删除的实用价值。

第 5 部分——对动态表执行 DML（是的，真的）

这是最令人惊讶的发现，也是最改变心智模型的一点。

现在可以对动态表运行 DELETE、UPDATE 和 MERGE——前提是你触及的行位于其冻结区域内。

- Order 1 is dated 2024–01–15, inside the frozen region
DELETE FROM dt_orders_enriched WHERE order_id = 1;
 - → number of rows deleted: 1
 - Order 2 is dated 2024–06–20, also frozen
MERGE INTO dt_orders_enriched t
USING (SELECT 2 AS order_id, 999.99 AS amount) src
 ON t.order_id = src.order_id
 WHEN MATCHED THEN UPDATE SET t.amount = src.amount;
 - → number of rows updated: 1

两个更改均持久化。

边界被精确执行。订单 4 的日期位于可变窗口中：

DELETE FROM dt_orders_enriched WHERE order_id = 4;

用户 DML 仅在动态表 'ANALYTICS.DT_ORDERS_ENRICHED' 的冻结区域内受支持。

为什么这种设计是连贯的而不是模型中的漏洞：非冻结区域是派生的，因此手动写入会在下次刷新时被覆盖——Snowflake 阻止它会静默销毁的更改。冻结区域明确排除在重新计算之外，因此手动写入是稳定且允许的。派生的，所以手动写入会在下一次刷新时被覆盖——Snowflake 阻止它会静默销毁的更改。冻结区域明确排除在重新计算之外，因此手动写入是稳定的，允许是安全的。

实际用途非常显著：

  • GDPR 和被遗忘权。删除冻结历史中特定个人的行，而无需重新计算管道。
  • 历史数据修正。直接修复归档数据中的错误值。
  • 对已冻结期间的迟到调整。

以前，这些操作中的任何一个都意味着解冻、重建并支付全部重新计算的费用。

第 6 部分——自适应刷新模式

如果你不能使用主键，并且你的增量管道偶尔遇到完全重算确实更便宜的状态怎么办？这就是自适应模式（公共预览）解决的问题。已验证可行：

CREATE OR REPLACE DYNAMIC TABLE dt_orders_adaptive
 REFRESH_MODE = ADAPTIVE
 TARGET_LAG = '10 minutes'
 WAREHOUSE = dt_refresh_wh
AS
 SELECT order_id, customer_id, amount, order_date
 FROM raw_orders;

SHOW DYNAMIC TABLES 报告 refresh_mode = ADAPTIVE。

可以将其视为“增量，但更智能”。增量，但更智能在每次刷新时，Snowflake 的启发式算法根据当时哪种方式提供更好的性价比，决定使用增量处理还是重新初始化。

它附带两个护栏：

  • 昂贵的函数永远不会意外重新初始化。Cortex AI 函数和 UDF 不会在您的整个历史记录中被静默重新执行——那将是一笔巨额账单。
  • 如果定义根本无法支持增量刷新，创建会主动失败，而不是在运行时悄悄降级。如果定义根本无法支持增量刷新，创建会主动失败，而不是在运行时悄悄降级。

注意这与规则 4 的交互。关于在生产环境中避免 AUTO 的建议是关于不可预测性：一个你从未观察到的静默降级。ADAPTIVE 是一个深思熟虑的、有护栏的选择，让 Snowflake 在每次刷新时进行优化。选择 ADAPTIVE 与保留 AUTO 不是同一个错误。不可预测性：一个你从未观察到的静默降级。ADAPTIVE 是一个深思熟虑的、有护栏的选择，让 Snowflake 在每次刷新时进行优化。选择 ADAPTIVE 与保留 AUTO 不是同一个错误。

第 7 部分——无需重新处理即可迁移：BACKFILL FROM

你有多年的干净历史数据，想要迁移到动态表管道而不重新计算所有数据。BACKFILL FROM 通过零拷贝克隆将现有数据直接放入冻结区域。

CREATE OR REPLACE TABLE hist_orders AS
SELECT order_id, customer_id, amount, order_date
FROM raw_orders
WHERE order_date < '2026-01-01';
CREATE OR REPLACE DYNAMIC TABLE dt_orders_backfilled
 FROZEN WHERE (order_date < '2026-01-01'::DATE)
 BACKFILL FROM hist_orders
 TARGET_LAG = '1 hour'
 WAREHOUSE = dt_refresh_wh
AS
 SELECT order_id, customer_id, amount, order_date
 FROM raw_orders;

生成的表报告 refresh_mode = INCREMENTAL，backfill_from = HIST_ORDERS，insert_only_inputs = true。

BACKFILL FROM 要求有冻结区域——这两个功能是作为一对设计的。指导是明确的：如果你有历史数据，从一开始就使用冻结区域。如果你有历史数据，从一开始就使用冻结区域。事后改造意味着为你试图避免的重新计算付费。

第 8 部分——本次发布的其他内容

刷新边界

默认情况下，管道中的所有动态表共享快照隔离：刷新同步并从同一时间点读取。非常适合一致性，但偶尔过于僵化。

刷新边界（GA）在 DAG 中插入一个软断点，使子管道可以按独立的时效性计划运行。它们还启用了“动态表 → 视图 → 动态表”模式，该模式以前不受支持。动态表 → 视图 → 动态表模式，以前不受支持。

存储生命周期策略

原始事件数据有保质期，但不破坏下游聚合而清除它通常本身就是一个项目。存储生命周期策略（GA）以声明方式附加保留规则——行按自己的计划过期，独立于刷新。无需自定义作业、无需 DELETE 语句、没有重新处理已清除数据的风险。

与冻结区域配对，这是一个强大的架构模式：使原始数据过期，保留聚合。使原始数据过期，保留聚合。冻结区域保护计算历史，而原始层老化。

两端 Apache Iceberg

  • 读取：外部管理的 Iceberg v2 表作为源。PRIMARY KEY RELY 显着提高了此处的更新/删除性能。
  • 写入：动态 Iceberg 表在 Snowflake 管理的外部存储上输出 Iceberg 格式，可直接由 Spark、Trino 和其他引擎读取。

相同的刷新模式、相同的调度、相同的语义——开放格式输出。

dbt 和外部编排

对于不需要持续刷新的团队——数据在早上 5 点准备好，或由 dbt 或 Airflow 驱动的管道——TARGET_LAG 是错误的工具。新的调度器功能允许你为外部编排的管道禁用调度器，并支持与 Snowflake DCM 项目的同步刷新。

dbt 集成几乎是即插即用的替换，因为大多数 dbt 模型已经是 CTAS 语句：无需重写逻辑，保留完整的血缘/测试/文档，外加自动跳过未更改的源。
