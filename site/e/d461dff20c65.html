从分析工程师到上下文工程师

大多数公司如今在企业级 AI 部署中都在走捷径，并陷入数据团队早已深谙的经典陷阱。走“简单路线”——把 AI 直接接上供应商提供的 MCP，再让这些连接直接指向源数据提供商——合计让企业们付出数十亿美元的代价，包括 token 消耗、供应商 API 费用，以及数据所有权和可移植性的缺失。在 dbt Labs，我们最初也不例外。我们一直使用供应商 MCP，直到发现这些隐藏成本竟然如此之高。那时我们才意识到，将 AI 连接到数据的最有效、可扩展的方式，正是我们一直倡导的：把数据集中起来，直接在我们的数据仓库内对上下文进行工程化处理。这让我们获得了拥有自己 AI 上下文层的巨大机会，也让数据团队的职责范围得以扩展。

一切如何开始

随着 Claude 在组织内上线，最大的用户群体之一是销售团队，他们连接 Gong、Salesforce 和其他富含上下文的来源来分析交易。当我们的 GTM（市场拓展）团队请求获取客户洞察，以预防客户流失并识别高价值客户时，我们自然同意了，并允许他们通过原生 MCP 将 AI 代理直接连接起来分析 Gong 数据。

数百名销售人员每天多次使用这些数据，成本迅速累积起来。分析一通电话最多要消耗 50,000 个 token；仅让 AI 读取一份通话记录就相当于 0.25 美元的 token 成本。我们有超过 5 亿 token 的 Gong 通话记录数据可用。加之许多销售人员在一天中运行大量 Claude 会话，我们的 AI 总支出在规模化使用下显著上升。

我们知道必须换一种新方法。于是决定把 Gong 的原始数据导入数据仓库，并用数据建模来总结每通电话。通过主动对通话记录数据进行上下文工程，消除噪声、提取信号，我们将数据量缩小了 20 倍，使 60 分钟通话的 token 消耗从数万降至仅几百。

问题也随之而来：如果我们能把任何数据都转换成更有意义的上下文，那又该如何构建出最小、最有意义，却仍然能回答大多数查询的上下文层？

dbt 如何降低 token 成本

此前，我们的数据团队曾为了 BI 对 Gong 数据建模，但 ROI 并不理想。而现在，Claude 和 ChatGPT 代理解锁了新用例，让我们能够大规模开展定性数据分析，通话记录表也因此成为数据仓库中价值最高的资产之一。

通过数据仓库获取上下文，比直接从 MCP 拉取要高效得多。基于仓库中的摘要对外提供通话记录内容，token 成本下降了约 98%，同时上下文质量保持不变甚至有所提升。

在这个博客系列中，我们将分享：为 AI 高效建模可信上下文的核心模式；我们 Gong 试点的端到端技术详解；一次读取数据即可服务所有代理的基础原则；以及为什么你可以在不改变现有技术栈的情况下，将传统分析工程转变为上下文工程。

规模化的定性数据分析与工程化上下文

在 AI 出现之前，以有意义的规模处理文本数据，要么依赖简单且低效的正则表达式技术（如关键词匹配），要么依赖高级统计与数据科学。对于数据团队来说，为通话录音、支持工单等定性数据源维护复杂的转换流程，实际操作中并不可行。

然而，正如我们在 Gong 项目中的突破所展示的，我们已经跨越了一个门槛：那些过去被忽视的数据和数据源，如今可以构成最有价值、最有用的智能体上下文。团队可以为 AI 构建模型和高效的上下文层，只要将我们通过分析工程开创的通用原则以 AI 为导向加以应用即可。分析团队长期以来一直在为 BI 建模定量数据。上下文工程本质上就是为智能体建模数据，而这些数据远不止指标：

**分析工程 vs 上下文工程**

- **消费者**

- 分析工程：个人用户，查看仪表盘并运行查询

- 上下文工程：整个组织使用的 AI 智能体，如 Claude 和 Codex

- **数据来源 / 格式**

- 分析工程：定量数据：结构化表格和指标

- 上下文工程：定量数据 + 定性数据（电子邮件、通话记录等文本；PDF；通话录音；支持工单；聊天日志）+ 半结构化 / JSON

- **目的**

- 分析工程：将大量数据建模为 KPI，通过图表和仪表盘理解发生了什么

- 上下文工程：为智能体提供业务上下文，使其能够大规模提供准确响应并执行可信操作

仪表盘需要指标，智能体需要上下文。

利用未开发的定性数据释放 AI 价值

未开发的定性数据才是 AI 真正发挥价值的地方。数据团队不再只是向仪表盘提供结构化数据，现在还可以利用 PDF、JIRA 工单等非结构化数据来工程化上下文。LLM 的进步使得这些文件可以在数据仓库内进行移动、存储、建模和处理，并用作智能体 AI 的上下文。这对许多分析师来说是一种新的思维方式，因为从历史上看，数据组织一直对通话记录等非结构化数据持排斥态度，而且理由充分：我们的技术栈并不是为支持这类数据而构建的。

我们之所以被迫改变，是因为我们的 Gong API 调用即将耗尽。每个人都在对非常相似的数据提出非常相似的问题，直接去找 Gong 说：“把我所有的通话记录给我，现在就把每份记录做摘要。”直接的 MCP 调用绕过了我们整个传统的数据建模和数据仓库体系，反复查询原始数据，这造成了冗余的 token 成本，并触发了 API 限制。

那一刻我们意识到：其实我们已经拥有了这样一个流程——把数据建模成可信、受治理、更有用的形式。为什么不把同样的方法应用到面向 AI 的数据上呢？

在与 Fivetran 合并后，我们意识到移动和建模非结构化数据本就在我们的能力范围之内。Salesforce、Zendesk、Gong 等平台现在提供了关键的业务上下文。对这类定性数据建模，并在数据仓库中缓存预构建的 AI 摘要，可以提供可靠、确定性的上下文，同时消除多次高 token 消耗的 MCP 调用、工具泛滥和 API 限制。用户可以通过上下文层中的单一上下文连接器，经 MCP 无缝访问这些建模后的数据。

这大幅降低了 token 成本，将用户体验简化为一次简单的聊天，并在整个组织内打开了可复用、社区驱动的数据模式。

如何实现高性价比的上下文工程

这种方法并没有什么魔力。

从分析工程师到上下文工程师

数据团队将原始数据——无论是定量的、定性的还是半结构化的——转化为智能体上下文。他们采用的方法正是自己已经在实践的流程，而且无需对技术栈进行实质性改造：

压缩：将大规模语料缩减为只包含相关信息的、规模最小的形态。

丰富：将数据与其他相关信息连接起来，从而更容易访问所需的一切，例如机会详情和定性的交易历史。

描述：围绕数据的含义及其适用场景提供说明信息。

治理：精确决定每个智能体为了完成工作可以查看哪些数据。

数据团队只对上下文建模一次，所有工具和智能体都从同一个可信上下文层读取。分析工程师如今成了上下文工程师。这是同一套技能，只不过除了建模指标之外，你还要绘制整个数据资产版图，而且每个数据源现在都参与其中。

所有这些都无需对数据技术栈进行实质性改动。数据团队为整个组织构建一个结构化共享上下文层，在功能上将 AI 叠加在原有数据技术栈之上，方式与 dbt 当前叠加在数据仓库之上相同。整个公司现在都成了消费者，因为每个团队及其使用的智能体都能访问这个上下文层，而不再只有会写 SQL 查询的人。

那么从功能上看，如何将结构化、半结构化和非结构化数据移动、转换并管理到上下文层中？

将数据——无论是传统表还是非结构化文件——送入数据仓库（Snowflake、BigQuery、Databricks）是 Fivetran 的工作。如果表格数据需要进一步加工（过滤、反规范化、连接和聚合），dbt 允许以开放且可移植的方式创建和执行这些转换逻辑。

自动化那些利用目标数据平台中基于 SQL 的 AI 函数的管道，同样是 dbt 的工作。例如，Snowflake Cortex 提供了 AI_EMBED、AI_COMPLETE 和 AI_PARSE_DOCUMENT 等 SQL 函数，它们可以作为 dbt 模型的一部分执行，并由 dbt 模型编排。BigQuery 和 Databricks 也提供类似功能。

原始文本字段、来自电子表格等文件的结构化数据，甚至被复制进来的 PDF 等非结构化文件，都会变成可查询、可检索的上下文，供共享上下文层中的人类数据用户和 AI 智能体使用。它们查找信息所依赖的文档和数据源已经位于同一平台中，由 Fivetran 自动移动和索引，并作为 dbt 模型的一部分进行处理。

上下文层之下的技术栈保持不变：Fivetran 负责移动数据，dbt 负责建模。不过，现在这个技术栈中包含了让 AI 系统变得强大的非结构化上下文。所有一直存在但从未进入管道的 Salesforce 邮件正文、Jira 工单附件、通话转录文本和合同 PDF，现在都可以作为完全可引用、可信的上下文。

最佳实践正在浮现

我们正在继续构建分析工程师进行上下文工程所需的术语、软件包和开源项目。我们已经总结出一些可以分享的最佳实践，未来还会有更多。以下是我们团队正在使用的一些实践预览：

不要聚合上下文，要生成上下文：利用数据仓库原生的 AI 来创建新的上下文，通过解析、分块、嵌入、转换和连接相关信息，将其加工成智能体可以查询的建模数据对象。

上下文质量与聚合

聚合可能会导致上下文丢失，因此在整个管道中保持上下文质量至关重要。

上下文层架构

一个共享、结构化、受治理、开放格式的规范上下文层，每个引擎都可以写入，每个智能体都可以读取。数据行业一直关注的同一单一事实来源，现在指向 AI 作为主要消费者。

读一次，写多次

读取是上下文工程中最昂贵的部分。使用 LLM 在批处理中（更便宜）执行一次昂贵的读取；然后将建模后的形式提供给上下文层中的每个智能体。

增量上下文维护

智能体执行动作，它们需要正确、当前的信息来行动。上下文不能简单地快照，必须随着新事件和新信息的到来而更新。增量模型更新上下文的当前状态（通过构建管道捕获状态变化以便可审计）至关重要。

数据团队的新角色

直到最近，阻力最小的上下文路径是直接获取原始 API 并连接 MCP 服务器。现在，数据分析师可以介入并说：“使用我们现有的数据。我们将用你要求的一些 AI 能力增强它，处理一次，并让每个人都可以无限次使用。” 现在，数据团队拥有 AI，并成为下一个时代企业的关键任务团队。
