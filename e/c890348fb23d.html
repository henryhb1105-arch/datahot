CostBench首测：ClickHouse实时性能每美元高出412-1996倍

DataHot 主播约 1 分钟精华朗读
0:00 / 0:59
DataHot 速览

CostBench首个端到端测试在持续负载下比较云数据仓库的实时分析性能与成本。结果显示，从新数据接入到查询就绪再到聚合/钻取查询的完整链路上，ClickHouse Cloud的性能每美元优于Snowflake、BigQuery和Redshift Serverless达412–1996倍。该基准同时测量摄入、查询就绪维护和查询服务，强调查询引擎之外的数据接入与状态维护同样显著影响整体性价比。

为什么值得关注：该基准把持续负载、端到端链路和每美元成本放进同一评估框架，为实时分析选型提供了可量化的参考，并揭示数据接入阶段对性能的隐藏影响。

译文

AI 逐段翻译

① 聚合查询通过交互式仓库来查询交互式物化视图。虽然视图存在滞后，但查询仍然必须返回当前结果，包括视图上次刷新之后到达的行。

② 在查询编译期间，Snowflake 的规划器决定如何将物化视图与那些较新的行合并。为此，它需要加载自上次刷新以来创建的每个基表微分区的元数据。这一编译过程发生在 Snowflake 共享的云服务层中，在仓库开始执行之前完成。

Snowflake 管理此编译工作的资源；用户无法调整其大小。增加仓库大小只会为后续执行阶段增加资源。

在刷新间隔期间，随着新微分区不断累积，每次查询在编译时需要处理更多的元数据。当刷新追赶上来时，这项工作会减少，等待时间随之下降，然后随着数据持续摄入又开始攀升。

矛盾的是：更快的 Snowpipe Streaming 使当前物化视图查询变得更慢。在异步刷新间隔之间会累积更多的新微分区，因此每次查询都需要承担更多的对账工作。

幕后原理：对账、仓库大小与回退（点击展开）1. 两个查询阶段

每个 Snowflake 聚合查询首先在共享云服务中进行编译（与仓库无关），然后在选定的仓库上执行。

2. Snowflake 如何组装当前的物化视图答案

当交互式物化视图滞后时，Snowflake 不会返回过时的结果。在编译期间，规划器会将视图与自上次刷新以来添加到交互式表中的所有内容进行对账，加载该增量中每个新基表微分区的元数据。

3. 为什么延迟上升然后重置

Snowpipe Streaming 在无服务器物化视图刷新异步运行的同时不断创建微分区。未刷新的增量在两次刷新之间增长，并在某次刷新追赶上来时缩小，从而产生同样的上升-重置模式，这与延迟曲线中所见一致。

4. 我们测量了什么

编译占 Snowflake 聚合查询时间的 85%；仓库执行占 15%。在可接受的五秒回退代理标准下，836 次执行中的 477 次——即 57%——进入了被归因于回退的路径。

5. 为什么更大或回退的仓库无法消除瓶颈

仓库大小只改变执行计算。对账已经在执行到达交互式仓库或 Gen2 Small 回退仓库之前，在共享云服务中完成。

6. 早期诊断证据支持该机制

在一次剖析的查询中，远程微分区元数据 I/O 消耗了编译阶段 5,030 毫秒中的 4,908 毫秒——占 97.6%，大约每分区 25 毫秒。一个并行的 Small 与 X-Large 诊断在约 0.4 至 168 亿原始行上进行，发现即使 X-Large 带 8 倍积分费率，编译时间也没有改善。这些诊断解释了机制；Run14 提供了上述主要测量结果。

7. 成本影响

在等待编译时，仓库可以保持活动并计费，而云服务使用量本身也可能产生费用，当每日云服务消耗超过每日仓库使用量的 10% 时。因此，更快的摄入增加了对账延迟及其潜在成本。

8. 如何解读回退颜色

紫色段是标准化成本的公认耗时代理指标，并非 Snowflake 物理执行回退的查询级证据。超过五秒的作业按其完整端到端运行时间按回退价格计费；等于或低于五秒的作业保持交互式价格。每个作业只能归入一个桶。

由于阈值是分类器，它可能会遗漏发生在五秒或以下的回退；后面的计分框记录了完整的定价边界。

针对事件级数据的钻取查询

在主动摄入期间，基准测试每小时运行两个钻取查询（D1-D2），直接针对事件级表。它们计算小时价格汇总，以及一只股票在其不断增长的历史上的风险与流动性概况。它们的答案必须包含新到的报价，因此事件级表必须保持新行可查询，并采用支持高效过滤的布局。两个查询都按股票代码（表排序或聚簇键的开头列）进行过滤。

该图表跟踪它们随每个事件级表增长时的端到端延迟；Snowflake 以蓝色显示，ClickHouse 以黄色显示。

这些查询绕过了物化视图并直接读取每个事件级表，因此此路径隔离了事件级表布局和服务，而非物化视图对账。两个系统都使用相同的 (sym, t) 排序/聚簇，并有大约 16 个 CPU 的读侧计算；Snowflake 的小型交互式仓库还额外提供了约600 GB 的本地 SSD 缓存。

ClickHouse Cloud： 通过 1000 亿行图表窗口来看，钻取延迟为：

  • 中位数 722.5 毫秒——比 Snowflake 快 1.38 倍
  • P99 1.15 秒——比 Snowflake 快 2.06 倍
  • 最大值 1.18 秒——比 Snowflake 快 2.17 倍

在35 个行数匹配的主动摄入批次中，累计运行时间为50.47 秒。有序 MergeTree 路径的延迟增长更平缓，并在较大数据量下保持较低。

Snowflake： 通过同一图表窗口，钻取延迟为：

  • 中位数 993.5 毫秒——比 ClickHouse Cloud 慢 1.38 倍
  • P99 2.37 秒——比 ClickHouse Cloud 慢 2.06 倍
  • 最大值 2.56 秒——比 ClickHouse Cloud 慢 2.17 倍

在同样 35 个匹配批次中，累计运行时间为74.81 秒。尽管交互式仓库有约 600 GB 的本地 SSD 缓存，但随着数据累积，延迟上升更陡峭；所有 70 次执行都保持在五秒回退阈值以下。

在匹配的钻取工作负载中，ClickHouse Cloud 整体快 1.48 倍，尽管 Snowflake 有约 600 GB 的本地 SSD 缓存。

不断增长的事件级表为查询执行留下了更多工作

下面的阶段分解将 Snowflake 的下钻延迟分为编译和执行两部分。

Snowflake 的阶段遥测显示了与 MV 路径不同的瓶颈。在中位数上，编译耗时 225 毫秒 对于 D1 和 191 毫秒 对于 D2；执行耗时 643 毫秒 和 830 毫秒，分别占提供商报告阶段时间的 74–81%。执行工作随着 Interactive Warehouse 读取和过滤不断扩展的事件级表而增加。与 MV 对账不同，它在仓库内运行，可以通过增加仓库计算资源来减少。

下钻的主要层次是执行：购买更大的仓库可以减少它。 单独的编译层仍在仓库之外。

深入探讨：缓存跟上了。这如何扩展？（点击展开）测量案例

Snowflake 将 Interactive Warehouse 缓存预热 记录为非阻塞的后台进程。在早期对此工作负载的诊断运行中，查询配置文件 报告在活动摄取期间远程读取为零或可忽略，服务字节的中位数为 100% 来自缓存。

在约 75 MB/s 的摄取速率下，查询的工作集适合 Small 仓库大约 600 GB 缓存，预热保持了数据的本地性。这些诊断解释了缓存行为；Run14 提供了上述主要延迟测量结果。

这说明了什么

这是有利的缓存情况：工作集适合且预热跟上。剩余延迟主要来自对增长的事件级表执行扫描和过滤，而不是重复从远程存储获取工作集。

边界 1：工作集容量

即使是最大的 Interactive Warehouse——4X-Large——也有有限的 44 TB 缓存。当查询的工作集超出缓存时，更多读取会远程进行。仓库规模过小，延迟会升至五秒上限，超过该上限的查询会回退；过大，你为不需要的缓存付费。

边界 2：预热吞吐量

Snowflake 记录的缓存预热吞吐量约为 每 X-Small 仓库 300–400 MB/s，并表示更大的仓库预热更快。该记录的 X-Small 速率明显高于此基准测试约 75 MB/s 的摄取速率。

然而，在更高的源速率下，查询相关数据的到达速度可能超过预热使其本地化的速度：总工作集可能仍然适合，但最新的行需要远程读取。

规模调整的含义

Snowflake 客户必须为交互式仓库设置规模，既要考虑查询接触的数据量，也要考虑新数据的到达速度。ClickHouse 查询直接针对有序的 MergeTree 表运行，无需单独填充服务缓存来调整规模或保持预热。

绕过延迟的 Interactive MV 消除了查询时的对账，但将聚合工作留在了 Snowflake 的原始表上。A1 和 A2 过滤 sym——前导聚集键列——但两者都显示出明显的延迟上升趋势，随着 Interactive Table 的增长。在测量的窗口内，即使在这些选择性路径上，更多摄入的数据也增加了查询时的工作。ClickHouse Cloud 的预聚合延迟在同一 1000 亿行窗口内保持基本平坦。

A3 和 A4 是无过滤的全表聚合。在可接受的五秒回退代理下，836 次执行中有 220 次（26%） 超过阈值并归因于回退路径：103 次 A3 执行 和 117 次 A4 执行。在相同的 209 个匹配批次中，Snowflake 的原始表路径累计了 1.10 小时 的运行时间。

绕过延迟的 Interactive MV 通过消除查询时的对账使 Snowflake 更快——但将聚合转移到了原始表上。ClickHouse Cloud 已经当前的预聚合路径在匹配的工作负载上仍然快 347 倍。

在 Snowflake 的两种聚合路径中，未完成的新鲜数据路径工作出现在查询时： • Interactive MV： 在 查询编译 期间对账解释了预聚合缺失的行。 • 原始 Interactive Table： 在 查询执行 期间扫描和聚合直接从事件级行计算答案。 ClickHouse Cloud 在摄取期间执行预聚合，保持当前摘要可供查询。
