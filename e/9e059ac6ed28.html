两位工程师借助AI编码智能体，设计、构建并上线了一个生产级状态页——以下是我们做对了什么、做错了什么，以及下次会如何改进。

在约4个月的时间里，Fivetran的两名工程师——Valentina Mačković和Jelena Kostic——使用AI编码智能体，完成了从需求到生产上线的全流程，设计、构建并交付了一个替代每年6.5万美元SaaS产品的自研方案。该方案如今支撑着Fivetran的公开状态页，服务约26,000名通知订阅者。以下是真实成本、真正有效的做法，以及我们踩过的坑。

背景：我们在替换什么

Fivetran的状态页原本是一个重度定制化的应用，运行在Atlassian Statuspage之上。它完成了设计之初的任务，但我们的使用方式早已远远偏离了Statuspage框架的原生能力。

我们的状态页展示大量独立监控的服务，并且希望为每一项服务提供独立的服务状态与可用性数据——这种形态是托管产品从未真正为支持而设计的。于是我们在其上叠加了定制层：用Google Cloud Functions从BigQuery数据仓库计算可用性，用事件跟踪器同步状态，并用自动化将其接入我们的事件管理流程。

最终形成的系统在成本和收益两侧都带来了真实的运维负担：

- **资金成本**：每年约65,000美元，主要原因是每个通知订阅者都需要按人头付费。我们有约26,000个订阅者。

- **时间成本**：我们花了大量固定工时去管理、排障和修复状态页，每年至少相当于10,000美元的工程师时间。

- **性能问题**：页面加载缓慢，有时首次加载还会失败。对于一个其全部意义就在于“在其他一切系统都不可用时仍然可用”的页面来说，这是严重的失败模式。

- **静默失败**：我们遇到过更新未传播却未被发现的情况。

- **速率限制**：我们自己的自动化曾触达供应商API的速率限制。

公平地说，对Atlassian而言，这并非什么丑闻。这是当你把一个通用产品远远推向其预期形态之外时必然发生的事，同时也是26,000名订阅者按订阅者计价的普通算术题。

在这篇文章中，我们将展示如何利用AI替换一个已经超出其需求边界的系统。

我们为什么决定迁移

状态页处在一个特殊的位置。它是一个小型应用——只有少量读端点、一个管理面板、一个邮件队列——但承载着生产级规模的后果。当Fivetran遇到糟糕的一天时，它是成千上万客户查看的对象，而一次大规模通知事件可能意味着发送超过50,000封邮件。

低复杂度，高 stakes。正是这种组合让它变得有趣。

一年前，自建状态页会是一个干脆的“不”：工程成本远超许可证费用。而如今变化在于，AI移动了某一类软件的这条分界线——这类软件规格清晰、复杂度适中、租赁价格昂贵。我们很快就会发现，这条线是否移动得足够远。

是什么推动了自建 vs 购买的决定

有三点，按权重排序：

对可靠性的控制。

一个依赖第三方提供商的地位页的可靠性，只能达到该第三方的水平，而我们无法修复那些缓慢的部分。拥有它意味着我们可以把它同时从自己的核心平台和外部提供商中解耦。定价模式与产品不一致。我们按订阅者付费，而它在结构上就是一个邮件列表。成本随客户增长而上升，而交付的价值却没有。我们想要的是组织层面的答案，而不仅仅是软件。

2名工程师使用AI智能体，能否刻意地把某个东西从PRD带到生产环境？如果能，那就是一种可复用的能力。状态页是验证这一点的好地方，因为搞砸的爆炸半径是可控的——我们可以让它与旧版并行运行，直到我们信任它。我们也可以在不必投入大量时间、金钱和精力的情况下，把实验称为失败。

我们还想诚实地说明结论的边界。Fivetran自己的产品是一个SaaS产品，我们并不是在论证AI会让SaaS过时。状态页比数据移动平台容易替换得多。但同样的逻辑在边际上也适用于任何供应商：你的使用越是某个通用产品中薄薄的、明确定义的切片，构建这一方的等式就越已经发生了移动。

设置AI

团队做出的最重要的决定，是花很长时间不写代码。在任何功能工作之前，Valentina和Jelena构建了相当于AI智能体入职培训计划的东西。他们编写了一个CLAUDE.md，定义项目规则和一个16步开发流程。他们定义了6个智能体角色，每个角色都有自己的初始化文件：

| 智能体角色 | 负责 |

| --- | --- |

| 项目负责人 | 委派与排序——从不写代码或文档 |

| 产品经理 | 范围、需求、任务分解、审批 |

| 软件架构师 | 技术设计、API契约、代码审查、合并 |

| 软件工程师（后端/前端） | Java后端和React/TypeScript前端实现 |

| QA工程师 | 端到端测试、缺陷分类 |

| SRE工程师 | 部署、监控、GCP运维 |

除了角色之外，他们还构建了一个技能库——针对后端约定、前端模式、整洁代码、JUnit、Bazel、Nx、QA和版本控制的可复用指令集。智能体之间只互相通信；当某个智能体不确定时，它会做出有记录的最大努力决策，而不是等待人类。每个功能都有自己的git分支和工作树，因此多个智能体团队可以并发运行而不会冲突。

他们还给了智能体大多数AI编程尝试会跳过的东西：一份真正的规格说明。PRD和TDD被写成正式文档，转换为markdown，并作为上下文交给智能体，同时还有一个定义每个端点的OpenAPI模式，以及一套用于UI的Figma设计资源。我们决定按原样实现UI设计，这样就可以以现有状态页为参考，自动化大部分Figma和UX设计。

工作量分配是整个项目的关键发现：

| 工作项 | 预估小时数 |

| --- | --- |

| 需求与设计（PRD、TDD） | 52 |

| 为智能体准备的规格（上下文文档、OpenAPI、设计资源） | 88 |

| 智能体工具与编排（角色、技能、CI/CD、流程） | 160 |

| 功能工作前的总投入 | 300 |

| 生成MVP本身 | 162 |

大约每构建1小时，就需要2小时的准备。这个比例不是效率失败，而是机制本身。

与AI协作

智能体之所以如此之快，正是因为上下文已经消除了所有歧义。工作框架就位后，MVP迅速成型。原型仓库的完整提交历史从2026年3月4日持续到4月15日——6周时间，46个拉取请求。前3周几乎全部是上下文与技能文件。随后在3月底至4月初的大约2周内，功能按顺序落地：群组CRUD、服务CRUD、数据库搭建、事件（incidents）、维护窗口、公共页面、CI、单元测试、部署工作流。

由此形成的工作模式是：小任务优于大任务。团队明确测试了这一结论，并将其定为原则。大型功能需求会产生零散冗长、难以评审的拉取请求，这些请求往往只能被丢弃。架构师角色物有所值：一个加载了团队内部约定的专职评审智能体，能在人类看到结构性问题之前就将其捕获——包括一次对后端的彻底重构。

掌控契约的是人，而不是键盘。Valentina和Jelena负责决定“正确”的标准——API的形态、数据模型、上线顺序——并验证输出与标准相符。AI编写代码。工程师构建系统。

陷阱

如果我们假装这一切一帆风顺，那对谁都没有好处。有几处地方，这次尝试的实际复杂度超出了预期：

智能体会重复劳动。群组CRUD用了4个不同的拉取请求才实现完成，服务CRUD则用了5个。原型仓库的46个拉取请求中，有8个从未被合并，都是被放弃的重复工作和死胡同。如果没有人类去追踪实际已完成的工作，并行的智能体就会乐此不疲地反复解决已经解决的问题。

与AI协作是一种新范式。最初的MVP既是项目执行，也是一次学习演练。这是我们的工程师为犯错

与其他一切系统的集成

我们重新接线了现有的数据聚合器和公开事故追踪器 Cloud Functions，使其写入新 API；启用了从事故管理系统中自动创建事故；构建了一个 Java 客户端，让产品仪表板从我们的后端而非供应商处读取数据；并且所有这些都在功能开关（feature flag）后面交付。

订阅者迁移

26,000 名订阅者必须完成迁移，不能有人丢失通知、也不能有人收到重复通知。仅这一项就是 40 小时的脚本工作，外加后续的数据修正。

可审计性

对事故、服务、组或订阅者的每一次更改，都会通过数据库触发器捕获到审计日志中。

规模测试

一场大规模事故可能产生 50,000 多封邮件事件。我们做了压力测试，在 5 分钟内持续发送 9,000 条通知。

一长串正确性 bug

事故标题中的特殊字符渲染不正确。超过 30 天的事故不会影响正常运行时间（uptime）条。维护窗口上出现了双重状态转换，新旧聚合之间还存在 uptime 差异。这些 bug 没有一个是"有趣"的，但所有这些问题都会被客户注意到。

生产加固

生产加固占总工作量的 56%——比需求、agent 框架和整个 MVP 加起来还要多。如果要从这篇文章中记住一个数字，那就是这个。

部署到生产

我们进行了一次刻意平淡的发布。预演（Staging）阶段：我们对公开页面和管理面板做了完整的 QA 检查。生产环境静默运行：新系统部署到生产环境，拥有完整数据和全部自动化——但通知被禁用，也没有客户流量。它在独立域名上与旧页面并行运行了数周，靠自身保持正确。DNS 切换：客户流量迁移到新页面，通知仍然关闭。开启通知：最后一步，也是最不可逆的一步，只有在其余部分都经过充分浸泡后才执行。

随后，系统以一种你无法事先计划的方式得到了验证：一次真实的 P1 事故，需要通知全部订阅者。向大约 26,000 名订阅者的扇出（fanout）由新系统发出。那一刻，它不再是一个实验。

可靠性

状态页有一个不寻常的可靠性要求：它必须在其所报告的对象发生故障时存活下来。因此，其依赖关系是一个设计约束，而不是实现细节。

我们有意识地解耦了以下内容：独立数据库——状态页运行在自己的 Postgres 实例上，不与核心平台系统共享。独立域名和部署管道——状态页的发布不与产品发布耦合，一次糟糕的产品部署不会导致页面宕机。独立的 GCP 项目——它运行在独立的 GCP 项目和可用区（AZ）中，与我们运行 Fivetran 控制平面或数据移动功能的地方分开。管理路径独立——即使产品不健康，我们的支持团队也可以发布事故更新，因为管理面板不依赖产品。

为什么只用一个区域？

今天，状态页运行在单个 GCP 区域中。这是一个刻意的、暂时的权衡。我们实际要防御的故障是 Fivetran 平台事故——对此，单区域隔离完全有效。额外防御区域性云故障是一个不同的、罕见得多的故障，它会使该系统的基础设施和运营成本大约翻倍，而该系统的整个经济论点就是运行成本低廉。

我们选择先交付能解决常见场景的版本，并在生产环境中验证它。我们的要求是：状态页能够在CSP（云服务商）区域故障中存活。只要状态页部署在Fivetran自有区域之外，就满足了最初的故障要求。我们打算让系统达到所需的可靠性水平，这可能意味着在另一个CSP中保留一份缓存副本，但大概也就到此为止了。

下文的成本/投入数字来自跟踪工作项上的估算记录，而非考勤日志。它们涵盖了我们跟踪器中记录的工程工作，不包括未单独跟踪的管理、QA和设计时间。美元金额使用示意性的完全加载费率，即100美元/工程小时，而非实际薪酬。请将其视为一种善意的数量级估算，而非经审计的数字。

我们此前的支出

我们每年为Atlassian Statuspage支付约6.5万美元，主要驱动因素是约2.6万名可计费通知订阅者——此外还有内部工程团队花费在维护叠加于其上的自定义配置、Cloud Functions和自动化上的时间。更不用说还要绕开它的速率限制和静默故障。这些内部成本是真实存在的，但从未被单独列入预算——这本身就是现状的真实成本为何不可见的原因之一。

诚实的账目

我们每年节省约4万至5.3万美元，而一次性构建成本约10.5万美元。这意味着回收期约为2.5年，之后节省会持续累积。

这部分值得仔细品味。这个故事的头条版本是“2名工程师替换了一款6.5万美元的产品”。真实版本是：构建成本高于年度授权费用，节省是真实存在的但并不立竿见影，而做这件事的最有力理由并非纯粹财务性的：

- 页面更快、更可靠，而这才是客户真正体验到的。

- 成本不再随订阅者数量增长，因此随着Fivetran的成长，节省会越来越大。

- 我们拥有了一套可复用的AI开发框架——角色、技能和流程——只一次性投入300小时，并且适用于下一个项目；此外还有2名工程师获得了使用AI构建产品的真实生产环境经验。

我们学到的东西

规格说明才是瓶颈，而不是代码生成。我们每构建1小时，就要花2小时做准备，这个比例是合适的。从AI代理中获益最多的团队，是那些本就善于把需求写下来的团队。

最后一英里仍然是一英里。生产加固占了56%的工作量——比需求、工具链，以及整个MVP加在一起还要大。

AI压缩的是软件开发中本来就已经最快的部分。集成、迁移、认证、可观测性，以及长尾的正确性缺陷，并没有被压缩得那么多。

任何从“我们两周内就做出了可用的演示”外推出来的估算，都会错上两倍或更多。

代理需要一个管理者，而这个管理者不能是另一个代理。重复工作、幻觉式UI、偶尔出现的“掷骰子”式应用，这些都不是边缘情况，而是正常的失败模式。

工程师所增加的价值，是对“什么才是正确的”做出判断，并验证输出是否符合这一判断。

经济账确实发生了变化——对某一特定类别的软件而言。“定义清晰、复杂度适中、按某个对你极为不利的维度定价”，这句话描述的是大多数公司SaaS支出中一个真实且不断增长的条目类别。但它描述的并不是大多数软件。
