为了解释这一结果，我们遵循与数据相同的路径：先准备，再查询服务。

ClickHouse Cloud 如何准备传入数据

该基准测试使用了专用的 ClickHouse Cloud 摄取服务，配置为 两个 2-CPU 节点以实现高可用性，这是在校准期间能够维持目标的最小 HA 配置。共享客户端通过 异步插入发送行数据，该功能内置于每个节点中。

下图展示了这些相同的节点在 总共四个 CPU 核心上处理①列式存储、②对原始数据排序和③有序预聚合，以及后台合并。

① 按列存储并②对数据排序： 当摄取节点刷新其异步插入缓冲区时，它会按 MergeTree 表的 (sym, t) 键（股票代码和事件时间戳）对原始报价进行排序，并写入一个有序的 数据分片。

③ 排序并预聚合数据： 同一节点在内存中对传入的数据块运行 增量物化视图 查询，计算聚合状态，并在写入包含摘要的有序分片之前，按 AggregatingMergeTree 表的 (sym, day) 键对结果进行排序。

后台合并 会整合两个表中的分片。

结果是：原始数据和预聚合 同步推进，来自同一个已刷新的插入数据块，无需单独的刷新周期。

四核摄取服务处理了多少工作？（点击展开） ClickHouse 写入器利用率结果显示摄取与后台维护同时持续进行。CPU 使用率保持在 4 个可用核心中的约 3.1 个，跟踪内存保持在容量范围内，后台合并每秒处理数百万行，每个分区的最大活动分片数保持在约 100。这些诊断信息描述了为本次对比复用的 ClickHouse 源端运行情况。

两个节点均保留以实现高可用性，因此准备成本包含完整的两节点部署。

现在，让我们通过 Redshift Serverless 跟踪相同的准备任务，从 MSK 流到流式视图及其每日摘要。

Redshift Serverless 如何准备传入数据

该基准测试使用了 Redshift 流式摄取，从 Amazon MSK 直接写入物化视图，没有 S3 落地阶段。该视图将每条报价的有效负载存储在 Redshift 的 SUPER 数据类型中，并将股票代码和事件时间戳作为带类型的排序键列公开。图表将此读取路径标记为“SUPER”。

下图展示了①流式视图中的列式存储、②后台排序和③每日聚合物化视图的增量刷新。它显示了用于准备定价的 32-RPU 写入器场景，与查询消费者分开。

① 按列存储： 生产者将报价发送到 MSK。Redshift 的写入器将该主题消费到 quotes_streamed 物化视图中，并设置 AUTO REFRESH YES。实时流式视图保留了标题下钻查询所用的事件级有效负载。

② 对数据排序： 流式视图使用了 SORTKEY (sym, t)，并设置 DISTSTYLE EVEN 以保持符号过滤器的扫描并行性。Redshift 在后台排序，因此新到达的行可能在该布局工作完成之前就可见。

③ 排序并预聚合数据： 一个单独的每日物化视图直接从流式视图按 (sym, day) 分组，并拥有自己的排序键。控制器反复发出增量 REFRESH MATERIALIZED VIEW ... RESTRICT。每日物化视图和带类型的原始投影是兄弟分支；每日摘要不等待带类型分支。

结果是：Redshift 的流式视图、后台排序和每日摘要通过不同阶段推进，因此查询可能会遇到尚未完成的准备工作。

为什么选择这些摄取路径，它们是如何缓冲的？（点击展开） 相同的摄取问题：

源端产生频繁写入，这些写入必须成为高效的分析存储。ClickHouse 通过原生异步插入接受它们。Redshift 推荐的高速率流式路径包括一个 MSK 代理集群和一个消费写入器工作组；两者都属于准备成本。

Redshift 的流式路径：

该 生产者使用了 16 个进程和 lz4 压缩。MSK 在三个可用区提供了三个代理，具有 24 个分区和复制因子三。Redshift 直接消费该流；没有添加中间 S3 加载作业。

ClickHouse 的原生路径：

启用 async_insert 的普通 INSERT 请求在每个接收节点上被缓冲。一个 自适应刷新超时响应传入流量。排序和预聚合在摄取节点上运行；专用的 摄取服务与独立调整大小的读取服务共享存储。

共享节奏：

两个适配器读取相同的 Parquet 数据集，并在相同的目标速率模型下解码相同的模式。并行度和客户端批大小根据每个目的地的 API 进行调整；并未强制它们完全相同。

ClickHouse 批处理：

客户端通过异步插入发送 3,000 行批次。默认缓冲在三个阈值中首先达到的那个时刷新：缓冲 100 MiB、50 毫秒到 1 秒之间的自适应超时，或 450 个排队的插入查询。

Redshift 交付：

生产者确认报告的是 Kafka 交付，而非所有下游视图的完成。流式摄取推进原始流式视图；单独的刷新事务推进带类型投影和每日摘要。

批大小边界：

客户端 INSERT 批次和 Kafka 批次是传输单元。它们不定义最终的 MergeTree 分片、Redshift 存储块或每日物化视图刷新大小。

进度和刷新证据：

监控器在摄取期间采样 SYS_STREAM_SCAN_STATES并记录子刷新日志。这些时间点观察是在工作负载运行时记录的；并非从运行后视图重建。

增量维护：

两个子物化视图直接定义在 quotes_streamed 上，并以 RESTRICT 方式刷新。刷新日志的服务器状态可识别增量更新；仅凭 Manual 或 Auto 这类标签无法断定是增量刷新还是全量刷新。每个子视图独立刷新。

写入端容量边界：

图中的 32 个 RPU 来自 已接受的容量场景：在特性测试中，32 个 RPU 以约 5 秒的流式传输延迟中位数维持了目标，而 16 个 RPU 则落后。长期测量是以 128-RPU 写入端记录的。按 32 个 RPU 定价并不会把这些延迟或新鲜度测量变成 32-RPU 的重新运行。

预聚合延迟

ClickHouse 在插入期间构建汇总；Redshift 则单独刷新它们。下图追踪 Redshift 从 Kafka 事件水位线到其每日聚合物化视图：底层的有效观测显示 中位数延迟为 46 秒。ClickHouse 的零线代表原始数据与汇总同步推进。

Redshift 序列包含流式摄取和每日刷新路径，而 ClickHouse 的基线描述的是原始数据到汇总的同步。针对 Redshift 每日物化视图的查询读取其上次完成的刷新；它们不会自动加入更新的流式行。下面的服务对比保留了这一新鲜度行为。

预聚合新鲜度是如何测量的？（点击展开） Redshift 序列：

该 新鲜度证据使用通过活动端点获取的成功每日刷新记录。它衡量的是每日物化视图中体现的 Kafka 事件水位线，而不仅仅是刷新完成之间的间隔。延迟采样器提供行进度时间线。

统计与显示：

活动每日物化视图序列包含 1,884 次观测，其中 中位数为 46 秒， P95 为 53 秒，以及 最大值为 79 秒 的延迟。图表应用了居中的五观测滚动中位数；其显示的曲线达到约 64 秒。第一个非单调延迟样本和 463 次摄取后每日刷新 被排除。

ClickHouse 基线：

零线是基准语义上的原始数据到汇总基线，而不是单独轮询的源到查询指标。原始表和增量物化视图消费同一个已刷写的插入块。它并不声称零摄取延迟，也不使用与 Redshift 序列相同的源水位线边界。

ClickHouse 将原始数据与汇总保持在一起；Redshift 的每日汇总落后 Kafka 事件水位线 中位数为 46 秒。

新鲜度是准备路径的一个结果。下一张图说明了运行该路径的成本。

保持传入数据可供查询的成本

ClickHouse 在其摄取服务内处理 ① 列式存储、② 原始数据排序和 ③ 有序预聚合。Redshift 在其写入端处理这项工作，并由单独计费的 MSK 集群提供数据。下图对比 ClickHouse 的准备成本与 32-RPU Redshift 写入端场景加 MSK。

ClickHouse 的完整摄取服务成本 $28.69。Redshift 的建模准备路径总计 $522.03： $470.02 用于写入端，包括流式摄取、排序和两条子物化视图刷新路径，加上 $52.01 用于 MSK 代理和存储。共享路径只计费一次。

ClickHouse 以 低 18.2 倍的成本处理完整的准备路径，而 Redshift 写入端加 MSK 场景则不然。

现在跟随原始数据和汇总进入查询服务。

ClickHouse Cloud 如何服务查询

有序原始数据让下钻查询可以跳过不相关的行；预聚合让交互式聚合可以组合已准备好的结果，而不是从单条报价重新计算。下图跟随这两条路径穿过 ClickHouse Cloud 的读取服务： 一个具有 16 个 CPU 和 64 GiB 内存的节点。

下钻： 查询会修剪 事件级 MergeTree 表中的有序原始数据。按 symbol（其 (sym, t) 排序键的首列）过滤，可让读取服务跳过不相关的报价。

交互式聚合： 查询从 AggregatingMergeTree 表读取当前预聚合，从数量少得多的每日汇总行中组合已准备好的计数、求和、最小值和最大值。没有需要等待的独立刷新。

结果是：下钻查询修剪有序原始数据；交互式聚合读取在摄取期间保持最新的汇总。

Redshift 将服务分离到一个消费者工作组中，通过实时数据共享读取流式视图和聚合视图。

Redshift Serverless 如何服务查询

下图显示一个单独的 32-RPU 消费者工作组从写入端读取共享数据。实时数据共享公开流式视图和每日聚合物化视图，而无需将它们复制到第二个服务数据库中。

下钻： 下钻查询会过滤 quotes_streamed 中带类型的 sym 列，然后从 payload 中导航并转换度量字段。其 (sym, t) 排序键支持修剪，但传入行可能在后台排序完成之前被读取。

交互式聚合： 查询读取 每日聚合物化视图截至其上次完成的刷新。它们不会在查询时将更新的流式视图行合并到答案中，因此返回的汇总可能落后于传入数据。

图中的两条路径显示了准备在哪些地方对读者仍然可见：下钻可能遇到未排序的数据，而聚合查询可能读取较早的汇总快照。

Redshift 的刷新和数据共享保证意味着什么？（点击展开） 快照契约：

查询读取每日物化视图的已提交内容。该基准并未在每次查询前强制刷新，也未从更新的流式行重建其答案。因此，测得的聚合延迟保留了 Redshift 的汇总刷新延迟。

刷新契约：

AUTO REFRESH YES 驱动流式摄取。控制器会单独刷新下游物化视图，因为 Redshift 不允许在定义于另一个物化视图之上的物化视图上使用 自动刷新。RESTRICT 仅从已提交的父状态更新指定的子视图。这避免了将带类型投影的刷新延迟叠加到每日汇总新鲜度上。

Live-share 契约：

共享会将写入方已提交的对象暴露给读取方工作组。它将读取计算与准备计算分离；它不会使这些对象更新鲜，也不会在查询访问它们之前对其最新行进行排序。

读取路径边界：

标题级下钻结果来自实时流式视图。同时也维护并测量了一个类型化投影作为替代方案。其刷新和存储布局工作保留在共享准备场景中，尽管其查询执行被排除在本文的评分之外。

规模边界：

在长时间运行期间，读取方固定为 base=max 32 RPU。写入方容量则针对准备成本单独建模。评分将这些声明的成本假设与记录的读取路径结果相结合；它并未将它们呈现为字面意义上的提供商账单。

结果：Redshift 下钻可以在后台排序完成之前读取行；交互式聚合可以从较早的刷新返回摘要。

为什么使用 Redshift 的流式视图，类型化列又如何？（点击展开） 流式视图：

该 流式视图 将有效负载保留为 SUPER，并将 sym 和 t 提升为类型化排序键列。D1 和 D2 过滤类型化的 sym 列，保留修剪意图；它们在计算结果时转换有效负载的度量字段。这与 ClickHouse 的类型化原始表是不同的表示形式。

类型化替代方案：

一个同类的类型化物化视图将有效负载字段投影到列中，具有相同的 (sym, t) 排序键和 EVEN 分布。其查询实现相同的 Redshift 下钻逻辑。在长时间运行期间测量了两种表示形式。

观测结果：

在活跃摄入比较中，类型化替代方案累计下钻运行时间是流式视图的 2.11 倍。D1 大致相等；D2 在类型化数据上 慢 4.42 倍。主要文章遵循测量更快的替代方案，即读取流式视图。

成本边界：

写入方加 MSK 的准备成本包括两个子刷新，并在各读取替代方案之间不变地共享。流式视图的评分仅计入其聚合和下钻查询分配，而不加入类型化查询执行。

解读：

该基准测试测量完整的记录查询结果。它并未分离出差距有多少来自后台排序、有效负载导航、查询表述或其他引擎工作。当完整运行显示相反结果时，不能根据简短表征就假定类型化布局更快。

对有序预聚合数据的交互式聚合

每日预聚合使 A1-A4合并准备好的计数、总和以及价格最小值和最大值。A1-A2 按代码筛选摘要；A3-A4 跨所有代码读取。ClickHouse 读取当前摘要；Redshift 读取其最近完成的每日 MV 刷新。该图表比较了数据持续摄入时的聚合延迟。

ClickHouse Cloud：

  • 中位数 13 毫秒 - 比 Redshift Serverless 快 34.6 倍
  • P99 42 毫秒 - 快 128 倍
  • 最大 111 毫秒 - 快 57.2 倍

累计运行时间为 10.21 秒，涵盖 190 个四查询批次。

Redshift Serverless：

  • 中位数 449.4 毫秒
  • P99 5.32 秒
  • 最大 6.35 秒

累计运行时间为 12.05 分钟，涵盖同样的 190 个批次。这些查询读取已刷新的摘要，无需等待下一次更新。ClickHouse 在插入期间维护摘要的同时更快地提供了这些查询；Redshift 所测得的延迟伴随着依赖刷新的新鲜度边界。

在交互式聚合工作负载中，ClickHouse Cloud 整体快 70.8 倍，且在插入期间维护摘要。

累计查询成本和运行时间

下钻查询占了 Redshift 累计查询运行时间的大部分。下面的图表合并了两个工作负载，并显示了分配给该查询工作的读取器计算资源。

在 每个系统 826 次被接受的执行中，ClickHouse Cloud 累计查询运行时间为 58.12 秒，而 Redshift 为 1.69 小时。归一化查询服务成本分别约为 $0.05 对 $24.97。这些是归属于被接受查询工作的成本，而非完整的提供商账单。

ClickHouse Cloud 整体上以 104.8 倍的速度提供查询工作负载服务，且归一化查询成本低 495 倍。

来自现场：Clay

Clay 的客户感受到了其 Redshift 报告系统的极限。信用使用仪表盘经常超时或加载时间过长，P95 查询延迟约为 60 秒。

将报告工作负载迁移到 ClickHouse 后，Clay 既提升了答案的速度，也提升了其背后数据的新鲜度。在其 Open House 演讲中，软件工程师 Paul Noble 报告称，P95 查询延迟从约 60 秒降至 1 秒，同时仪表盘数据新鲜度从约 75 秒改善至 4 秒。 观看 Clay 的迁移示例。

这些改进解决了面向客户的分析的两项要求：最新数据和足够快以便交互使用答案。Clay 的数据描述了其自身的生产迁移；CostBench 衡量的是上文所述的单独的 Redshift Serverless 工作负载。

在实时分析方面，Redshift Serverless 无法与 ClickHouse Cloud 匹敌

在新数据不断到达的同时，ClickHouse Cloud 在所有三项测量组件中都领先：

  • ① 准备成本：低 18.2 倍 相比 Redshift 写入器加 MSK 场景。
  • ② 归一化查询成本：低 495 倍 涵盖被接受的查询工作。
  • ③ 累计查询运行时间：低 104.8 倍 涵盖两个查询工作负载。

最终图表将这些结果汇总在一起，绘制了新数据到达时合并的准备成本和归一化查询成本与累计查询运行时间的关系。

越靠上表示总建模成本越低；越靠右表示累计查询运行时间越低。

在这一流式对比中，ClickHouse Cloud 每美元端到端性能好 1,996 倍，且在插入期间保持摘要为最新。

差异始于准备路径。ClickHouse 在插入期间对原始报价排序并构建当前摘要。Redshift 的流、后台排序和子 MV 刷新各自独立推进。其下钻查询耗时长得多的，而且即使读取依赖刷新的快照，聚合查询也更慢。

这就是为什么在实时分析方面，Redshift Serverless 无法与 ClickHouse Cloud 匹敌。
