原文

The views expressed here are mine alone and do not necessarily reflect the views of my current, former, or future employers.

We are now in an agentic era with a combination of engines to try to serve queries for real-time needs. To serve the various users, enterprises end up stitching together ETL pipelines, CDC streams, and/or caching layers. Real-time engines, such as ClickHouse, require their own security model and a copy of your data. Iceberg eases the data-movement burden but not the entitlement problem. This is very reminiscent of the 2015 days of Hadoop and Data Warehouses competing for a single copy of data.

I wrote about closing the ingestion half of this gap in 2022 with Snowpipe Streaming — getting data into Snowflake within seconds of an event. This article is the serving half. Snowflake’s Interactive Warehouse is designed to close the gap on the query side: serving that data at sub-second latency with the governance model you already have, not a separate one to manage. The benchmark below tests exactly that.

Streaming on Snowflake

Databricks also claims their Lakehouse RT product with the Reyden engine solves this problem. Unfortunately, their product is still in Preview and based on a video from Aug 2026, their engine is pushing 742 rows at 620ms.

In another post, Ali Ghodsi reposted a claim that the Reyden engine can query 1 billion rows in 258 milliseconds. I don’t have a way to reproduce either the 258ms or 620ms claim.

I was coincidentally working on this benchmark when I saw his post. And it’s why transparency matters when sharing numbers. Data points such as these should be repeatable and/or verifiable.

Let’s see how Snowflake’s Interactive Warehouse performs using repeatable steps and code. Full GitHub code is available here:

The need for Interactive Queries

Real-time dashboards, data-powered APIs, and AI agents share the same requirement: many people (or agents) asking similar questions at the same time and expecting sub-second answers. That’s a different problem than a nightly ETL job or an analyst running an ad-hoc query. It’s not about how much data and compute you can throw at it; it’s about how many of those queries you can serve simultaneously as quickly as possible.

Historically, this required standing up a separate serving layer. That’s real operational overhead for business users and agents. Snowflake’s Interactive Warehouses are built to close that gap without the extra infrastructure, delivering sub-second, predictable latency at high concurrency, on data you already have.

This isn’t about running more queries in parallel; it’s about how fast each query finishes. Interactive Warehouses keep your tables warmed in a local cache and run them through a query engine tuned for short, selective queries, so each query completes faster. This lets concurrency slots free up and refill more often per second, showing up as higher realized QPS at the same connection count.

Let’s Dive into the Reproducible Benchmark

As mentioned above, the code is available in my GitHub repository. My aim was to mimic the high-concurrency nature of a true analytics production workload, pushing the interactive warehouse using various table types and patterns. Here is what was tested.

  • Snowflake Native Table
  • Snowflake Interactive Table
  • External Iceberg Table
  • Snowflake Interactive Table with Masking Policy

For each table I ran two different queries: a point lookup (PL), returning a single row, and an aggregate mimicking a Customer 360 (Agg) query. Note that the masking policy query test was not run with aggregation, only point lookup. Both queries are run at concurrency levels from 10 to 1000 concurrent connections. The script uses a closed-loop model where each parallel connection fires the next query the instant the previous one returns.

-- =====================================================================
-- Real-Time Analytics on Snowflake — Benchmark Query Reference
-- Query patterns tested against TXN_HISTORY_IT (1B rows, 100M customers)
-- =====================================================================

-- ---------------------------------------------------------------------
-- 1. POINT LOOKUP
-- Returns exactly 1 row: No GROUP BY.
-- ---------------------------------------------------------------------
SELECT
    COUNT(*),
    SUM(UNIT_PRICE * QUANTITY)
FROM SNOW_DB.SNOW_SCHEMA.TXN_HISTORY_IT
WHERE CUSTOMER_ID = %s;  -- bind parameter, not a literal value


-- ---------------------------------------------------------------------
-- 2. CUSTOMER 360 (AGGREGATION)
-- Same filter as Point Lookup, but breaks the same customer's
-- transactions with GROUP BY. Returns ~10 rows on average.
-- ---------------------------------------------------------------------
SELECT
    PRODUCT_CATEGORY,
    STORE_ID,
    COUNT(*),
    SUM(UNIT_PRICE * QUANTITY)   AS SPEND,
    MIN(TXN_DATE)                AS FIRST_PURCHASE,
    MAX(TXN_DATE)                AS LAST_PURCHASE
FROM SNOW_DB.SNOW_SCHEMA.TXN_HISTORY_IT
WHERE CUSTOMER_ID = %s
GROUP BY 1, 2
ORDER BY 4 DESC;


-- ---------------------------------------------------------------------
-- 3. POINT LOOKUP (EMAIL) — masking policy test
-- Identical shape to the Point Lookup query, but also selects
-- CUSTOMER_EMAIL (masked column). 
-- ---------------------------------------------------------------------
SELECT
    ANY_VALUE(CUSTOMER_EMAIL), --masked column 
    COUNT(*),
    SUM(UNIT_PRICE * QUANTITY)
FROM SNOW_DB.SNOW_SCHEMA.TXN_HISTORY_IT
WHERE CUSTOMER_ID = %s;


-- Note: every %s above is a bind parameter (randomized CUSTOMER_ID per call)
-- This lets Snowflake reuse cached query plan across every execution 
-- see "Parameterize your queries" in Best Practices.

Note: I tested up to 1,000 concurrent connections because past that point the client became the bottleneck, not Snowflake. Generating 1,000+ truly concurrent queries from a single machine strained Python across multiple processes. 1,000 was enough to show the trend: linear scaling and a second cluster supporting additional demand after 250.

The numbers below were generated using Interactive Warehouse of size XS for Concurrency levels of 10 to 250. Past a concurrency of 250, slowdowns started to show at the higher end (p90), which meant the warehouse was starting to queue queries. Snowflake is able to scale both vertically and horizontally. Moving to a Small warehouse with two clusters was best able to handle the higher throughput and enable linear scaling.

And to demonstrate the true “one-platform” nature of this workload, I benchmarked various combinations of tables: Snowflake Native and External Iceberg. The GA of both those table types is now available — you can read more about interactive warehouses here:

Interactive Warehouse vs Regular Warehouse

Having established the need for Interactive Warehouses, the first comparison puts it to the test to establish a baseline. The same table and queries, run on an Interactive Warehouse versus a regular (non-interactive) warehouse, across 10 to 1,000 concurrent connections.

Note: QPS is defined as queries per 60-second window, measured server-side from ACCOUNT_USAGE (COUNT(status=’SUCCESS’)/60) — not client-observed, and not counting timeouts or errors.

Note 2: Across all 2.36 million queries in this benchmark — every table type, query pattern, and concurrent level — the error rate was 0%. There were no failures, and no queries hit the Interactive Warehouse’s 5-second timeout.

As concurrency hits 250, just like standard warehouses, you can add more compute clusters and continue to see the linear scaling. In this example for point lookup queries, the run peaked at over 2,300 QPS using a Small Warehouse with two clusters. Both queries scaled to Multi-Cluster at the 500 connection mark to continue linear scaling. In both cases, Snowflake was able to handle the concurrent demand.

There is also a high correlation between queries per second and latency. The shorter the duration of the query, the more queries Snowflake can process in a minute. The thing that stands out with Interactive queries is that the p90 (less than 90%) of the queries returned in < 100ms. Even when a regular warehouse is fast (sub-second), it’s unable to keep up when the volume of queries increases. With interactive, the p90 stays relatively flat.

Interactive Tables vs Snowflake Native

The Interactive Warehouse comparison showed the warehouse matters. The next question is whether the table format matters too — does a standard Snowflake table, with no migration or materialization, perform as well as a purpose-built Interactive Table on the same Interactive Warehouse?

At 1,000 concurrent connections, Snowflake Native served 2,277 QPS versus the Interactive Table’s 2,349 QPS, a slight 3% delta on throughput. A standard table, no data movement, matched a purpose-built Interactive Table. This feature just went GA at the time of the blog writing and the results show.

The latency was the interesting trend for the p90 customer 360 aggregation query. Even with the p90 hovering around 300ms for this query at 250 concurrency, the two table types’ QPS stayed within 19% of each other on this query, the widest gap in the test. Again, this shows the warehouse starting to queue around this point with the larger aggregation query. Not shown is the ~200ms of queuing taking place for this query on Native Snowflake tables. There’s also a slight queuing at the 250 level for the other queries, which leads to the increased p90 latency. This is exactly why I scaled up and out at c=500. Fitting your cluster to your demand is key.

Interactive Table vs External Iceberg

The previous tests all used Snowflake-managed tables. The next question is whether Snowflake can serve the same interactive workload directly on data it doesn’t own or manage — an externally written, catalog-linked Iceberg table without copying it to Snowflake.

For this test, I used a catalog-linked Iceberg table to simulate an external engine writing (e.g., Spark) data to an external catalog (e.g., Glue Catalog) where Snowflake is the reader. It’s a harder test because the Iceberg table reads off remote object storage through an external catalog. I demonstrated this to show how Snowflake can be used as a single serving engine without copying data.

At 1,000 concurrent connections, the Iceberg table held 2,102 QPS versus the Interactive Table’s 2,349 — ~11% lower. There is a slight tradeoff with this approach but it reduces your need to move data if your SLAs can support the slightly lower throughput.

Iceberg also shows a similar trend where the latency was spiky with the p90 customer 360 aggregation query. The point lookup query held its own with a ~200ms response time in all concurrency tests. The additional data rows and aggregation spiked to over 700ms for customer 360 query — this tells me a larger cluster may have benefited for this concurrency level with Iceberg.

Interactive Table vs Interactive Table with Masking Policy

The remaining question is whether governance gets in the way of any of this. Does applying a masking policy to a column add meaningful latency to an otherwise sub-second query?

I wanted to highlight using existing governance policies with interactive tables — this may not be a common use case, and honestly, I didn’t know what to expect. Running the point lookup query, I projected another column, email, where the policy displayed ***@email using a regex.

CASE WHEN CURRENT_ROLE() IN (‘SECURITYADMIN’, ‘ACCOUNTADMIN’) THEN val
ELSE REGEXP_REPLACE(val, '^[^@]+', '***') END

Throughout the concurrency tests, there was only a small difference in throughput with the masked query.

The surprising part to me was that the execution time was still sub 250ms, even when having to mask data over 143,000 times in a minute. Not shown in the chart, but I broke out the compilation and execution times to better understand the why behind the higher p90 times. The masked query has an additional 40–110ms of compilation time — this is the reason for the higher latency, not the extra column itself.

Best Practices

Warm your warehouse

Your production, your user demand may be spiky but you will have known peaks (market open, start of shift, a marketing push) and troughs (weekends, evenings). Use Snowflake Tasks to scale your Interactive Warehouse’s cluster count up ahead of a known spike, then back down after.

I didn’t test from cold for this benchmark. A warming pass ran first to get the warehouse into cache, then I measured the results. This simulated a live production workload, not a cold start. In addition, Snowflake supports adding tables to your warehouse so the cache pre-warms when the warehouse starts. This works for standard, Iceberg, dynamic, or interactive tables — get them added at least 10 min before the demand hits.

Wall-clock vs. server-side latency

The numbers in this benchmark use server-side, pulled from ACCOUNT_USAGE. That’s what Snowflake measured, not what your clients or agents will actually register. Wall-clock is as important, if not more important than the server-side. 50ms on Snowflake + 500ms of network latency = ½ second.

This benchmark didn’t take it into account because of the variability of where your client sits (on-prem vs cloud), your driver, connection pooling, and proxy settings. Within the code base, it includes wall-clock metrics so you can view them in addition to the server side metrics. With my setup (on-prem MacBook Pro) I saw an additional ~150–175ms client/network overhead — you can use the tool to see how the numbers break down and where latency is stacking up.

Concurrency

I ran a closed-loop client — 16 Python processes, each having its own connection pool, firing the next query as soon as the last one returned.

On the warehouse side I set MAX_CONCURRENCY_LEVEL (MCL) to 32, up from the default of 8. On its own, MCL=32 didn’t move QPS much. What that bought was headroom — when a flood of queries hits at once, a higher MCL starts more of them immediately instead of queuing them. That headroom matters more once you’re running Multi-Cluster. Set MCL based on how your traffic actually is, whether or not you’re using MCW. You will want to test all these numbers (processes, MCL, MCW) for your workload.

You can push past c=1000 — just make sure your client can actually generate the demand. At high concurrency the load generator can become the bottleneck before the warehouse does, so scale your process/thread count with your core count before trusting the numbers.

Query Patterns

Test your queries before you begin testing Interactive Warehouses. Clustering by CUSTOMER_ID is what made the regular-warehouse point lookups fast, and the same clustering carried over to Interactive too. Getting your clustering key (or search optimization) right for your access pattern matters more than the warehouse size behind it. Check partition pruning before testing and utilize general Snowflake query best practices. If Snowflake isn’t pruning, the warehouse size won’t fix it either.

A counter-intuitive note: Fewer partitions aren’t automatically better — they often create more overlap between partitions’ min/max ranges, which hurts pruning. More micro-partitions or files can reduce that overlap and let Snowflake skip more of them per query. If testing with Iceberg, consider targeting a file size of 16MB (rather than default of 128MB) so the optimizer can prune more files.

Parameterize your queries

Every point lookup and aggregation in this benchmark used bind parameters (e.g., WHERE CUSTOMER_ID=?), not literal values in the SQL text. This lets Snowflake reuse a cached query plan across every call instead of recompiling for each unique value — the same mechanism behind the low compilation times you see throughout this benchmark. If you’re building a data-powered API or agent workload, parameterize your queries; hardcoding literals decreases plan caching and will show up as additional latency.

Conclusion

The repeatable benchmark results are clear. Snowflake’s Interactive Warehouse delivers production-scale sub-second latency and linear concurrency scaling, without a specialized engine, CDC pipeline, or separate security model to manage. Remember that 258ms-on-a-billion-rows claim? That was one query, once, on a product still in Preview. Interactive tables hit sub 125ms latency on a billion-row table and sustained it across 1,000 concurrent connections on a feature that’s already GA.

But the throughput wasn’t even the biggest surprise — a standard Snowflake table, and even an external Iceberg table queried directly with zero copies, held up well against a purpose-built Interactive Table using your existing data.

This blog was written with repeatability in mind. Your data and query patterns are different, so the real test is running it yourself. I ask those interested in real-time analytics to give this a spin whether your tables are standard, Iceberg, or Interactive. And, as with all Snowflake features, they continue to improve over time. Keep an eye on this space as it will only continue to mature from here.
