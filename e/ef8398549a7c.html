引言

在本系列的第 1 部分中，我们分享了 Netflix 如何构建广告事件管道，并将其作为一个系统设计问题来处理：用集中式收集、丰富和标准数据契约取代碎片化的管道。最终结果是 Ads Event Publisher，这个系统从客户端设备收集广告遥测数据，丰富它，加上实际投放的广告的上下文，并向每个下游消费者发布单一的、统一广告事件流：频次上限、指标、计费、测量合作伙伴和报告。任何会员查看或账户详情在端到端流经此管道时都会被加密，并按照 Netflix 严格的隐私和安全实践进行处理，以保护会员 PII。

如果广告投放是“大脑”，广告事件是喂养它的“心跳”，那么丰富就是赋予每个心跳意义的东西，将一条单纯的“[某人]完整观看了一支广告”信号转变为“这个广告活动，这个创意，以这个价格，在这个广告时段。”第 1 部分将丰富步骤描述为架构中的单个方框。本文要讲的是那个方框里面有什么，以及我们为什么重建了它。

第 1 部分以展望未来结束：直播流中的广告、去重和更丰富的数据信号。一个项目通过围绕有状态流处理重建 Ads Event Publisher，同时实现了这三点。我们用 Apache Flink 中的实时流连接替换了数据库查找，这使系统能够为直播扩展，从关键路径上移除了一项依赖，并在不中断的情况下替换了一个高流量管道的引擎。

让我们深入探讨。

简要回顾：丰富和元数据注册表

当广告被投放时，广告服务器知道关于它的一切：广告活动、创意、展示的价格、定向上下文，以及测量合作伙伴期望我们触发的跟踪 URL。相比之下，客户端设备几乎什么都不知道：只有一个不透明令牌和何时发送每个事件。丰富就是让两者重新结合的行为。

在第 1 部分的架构中，这种重新结合通过广告元数据注册表（一个键值存储）发生：

  • 当广告服务器做出决策时，它写入该展示的元数据到注册表。
  • 它只将引用标识符编码到返回给设备的不透明令牌中，保持令牌很小。
  • 之后，当客户端触发携带该令牌的事件时，Ads Event Publisher 解码令牌，查找元数据在注册表中，并将两者拼接成一个丰富的广告事件。

这个设计很好地服务了我们。注册表是全球复制的，这几乎免费给了我们一个有用的属性：到达任何区域的事件都能找到其元数据，无论广告是在哪里决定的。它使令牌面向不断增长的元数据具有未来适应性，并支撑我们度过了 Netflix 广告增长的第一阶段。

但当我們展望未来，尤其是直播流中的广告时，这种设计的局限性变得清晰起来。

为什么我们需要演进

推动因素是直播。Netflix 的直播节目单增长迅速，从NFL 比赛到重磅拳击之夜再到2027 年国际足联女足世界杯，观看人数持续增长。这种流量看起来完全不像订阅视频点播（SVOD）：单个活动可以在几分钟内激增至数千万并发观众，然后在结束时同样迅速地退去。为直播构建广告管道意味着要针对这种轨迹来构建。

为了看清为什么旧设计无法达到那里，我们来看一些数字。当 Netflix 直播杰克·保罗对阵迈克·泰森的比赛给超过 1 亿观众时，这种规模下的一个广告时段会产生数量巨大的广告事件。在旧设计中投放这些广告意味着要为每一个广告写元数据到元数据注册表，并等待确认后才能投放广告：在广告投放关键路径上每秒数百万次必须成功的数据库写入。这种模式在直播规模下造成了三个核心问题：

  1. 这是一个扩展瓶颈。每个广告和每个广告时段都是一次写入。将其乘以数千万并发观众，保持它不丢失（一次丢弃的写入就是一个未投放的广告，以及损失的收入），再加上直播的尖峰式开/关模式，写入负载变得极其巨大。但你不能在活动开始后安全地扩展注册表。添加节点会在集群中重新分配数据以重新平衡，而在直播活动进行中这样做可能会拖慢甚至使你要增加容量来支持的写入失败。这留下了唯一安全的选择：提前为峰值预扩展，并希望预测准确。
  2. 减少关键路径上的依赖。投放广告意味着对注册表进行一次同步的、必须成功的写入，然后等待其确认。关键路径上的每个系统都是另一件可能阻止广告投放的事情，而元数据注册表没有回退方案，因此注册表不健康就意味着投放停止。将该路径上的硬依赖移除是目标，而注册表是我们能移除的最大一个。
  3. 它使事件新鲜度面临风险。如果在负载下写入变慢，或者查找超时，事件就会涌入重试和死信队列，丰富的广告事件就会延迟交付。有些系统可能没问题，但其他系统，例如频次上限，则不行。它需要事件在严格的 SLA 内，以决定下一个选中的广告能否在不违反政策的情况下播放。

所以我们问了一个简单的问题：广告服务器已经知道并记录它所投放广告的一切。它真的需要在热路径上把这些写入数据库吗？我们能否在事后将其与下游始终存在的客户端事件 Kafka 流进行匹配？

写入完全脱离了关键路径；任何共享数据存储的中断都无法阻止服务，而富化变成了我们随 Live 弹性伸缩的东西，而不是一个我们需要照看的集群。

事后匹配两条流就是流式连接，而这正是 Flink 的用武之地。

为什么选择 Flink

我们选择 Apache Flink，是因为近实时、有状态流处理正是它为之而生的，也因为它在 Netflix 拥有经过深度生产验证的平台支持。同样重要的是，我们早已知道如何运行它。正如第 1 部分所述，我们的 Ads Sessionizer 是一个大型有状态 Flink 作业，因此在大规模下运行一个这样的作业、调优状态、检查点以及生产负载下的恢复，对团队来说是熟悉的领域。Flink 上的富化是建立在这段经验之上的，而不是从零开始。

新架构

从核心上讲，新的 Ads Event Publisher 是作为 Apache Flink 流式作业构建的。每个事件都经过几个阶段：

  1. 规范化。客户端事件来自多个来源，包括 SVOD、直播、播放以及嵌入式广告插播，每个来源的形状略有不同。我们先将它们规范化为一种通用形式。
  2. 重新路由。客户端事件和响应事件可能出现在不同的区域；我们检查它们并将它们重新路由到正确的作业处理区域，以成功完成连接。
  3. 连接。作业的核心：我们将每个客户端事件与同一次展示的广告投放响应进行匹配，使用 KeyedCoProcessFunction 用完整的投放上下文对其进行富化
  4. 去重。产生收入的事件会被去重，因此不会有任何内容被重复计数。
  5. 发布。我们为合作伙伴提取测量信标，并将富化后的广告事件路由到其下游消费者。

连接才是有意思的部分。客户端事件和广告投放响应在不同时间到达不同的流，因此作业将最近的响应保存在内存中，并在一个 60 分钟窗口内将事件与它们进行匹配。可能会发生三种情况：

  • 响应已经存在，当事件到达时 → 我们当场对其进行富化。
  • 事件先到达 → 我们将其保留一个配置时长（目前设置为 60 分钟），直到匹配的响应出现，然后对其进行富化。
  • 在窗口内没有响应到达 → 我们将该事件标记为 未匹配，以便稍后恢复。

我们将连接构建为自定义 Flink 算子（KeyedCoProcessFunction），而不是内置的窗口化连接。我们不需要窗口化连接的排序和时间窗口语义，因为下游消费者处理排序；我们只是按键将每个客户端事件与其响应匹配。以其最低 API 形式拥有该算子，让我们能够直接控制匹配状态，包括我们保留它多长时间以及如何处理一个永远不匹配的事件。这使我们能够按流调优保留时间，或稍后将未匹配事件持久化到持久存储，而无需重写连接。我们的目标始终是构建一个强大的基础，以便在扩展时收获收益。

具体来说，想象一位会员正在观看一场直播比赛。当广告服务器决定展示哪个广告时，它会记录其响应，几秒钟后，会员的设备发出一个携带不透明令牌的“第一四分位”事件。两者都以同一次展示为键到达作业，并且由于响应已经在等待，事件会当场用其广告活动、创意、价格和跟踪 URL 进行富化，然后以近实时的方式发布到下游。

为什么是 60 分钟？几乎所有事件，大约 99.999% 的事件，都远在此之前到达作业，因此进一步延长窗口只会增大状态存储并延长检查点，而收益微乎其微。剩余的 0.001% 对于精确计费和报告仍然重要，我们会通过稍后描述的单独路径恢复这些事件。

跨区域：在数据所在之处匹配事件

Metadata Registry 为我们处理了跨区域富化，因为它构建在一个全局复制的键值存储之上：客户端事件可以落在任何区域，仍然能找到其广告的元数据。全局复制是平台提供的一项功能（参见 Netflix 的键值数据抽象层），因此在一个区域投放广告并在另一个区域富化其事件根本不是我们需要考虑的事情。

流式连接并不自带这种便利，而且在这里连接的两侧位于不同的地方。广告投放响应留在广告投放所在的区域。然而，客户端事件是由设备发出的，而设备可以在任何地方：一位会员可能在家用 wifi 上开始观看广告，然后在广告播放中途切换到移动数据，而这一网络变化可能将事件路由到与投放广告的区域不同的区域。因此，客户端事件被路由到一个没有匹配投放响应的区域。

诱人的修复方法是将每个区域的投放响应流式传输到其他每个区域，以便每个区域都能在本地匹配任何客户端事件。我们拒绝了这一方案：那将意味着每个区域都要存储全球范围内的每一个投放响应，而其中绝大多数永远不会在连接中被使用，这在成本和计算上都是浪费的。

相反，我们将这视为一个路由问题，并路由客户端事件而不是复制响应。我们将投放区域编码到广告令牌中，因此当客户端事件到达错误的区域时，我们将其转发到拥有其响应的区域。例如，一个广告在 us-east-2 投放，会员的设备在广告播放中途从 wifi 切换到移动数据，产生的事件到达 us-east-1。该区域读取令牌，看到该广告属于 eu-west-1，然后将事件转发回那里，那里有其投放响应在等待。只有真正跨区域事件的一小部分流量为额外的一跳付出代价。

捕获迟到事件的长尾

六十分钟能覆盖绝大多数事件，但并非全部。设备可能曾离线、广告可能暂停投放，或互动事件延迟数小时才到达。我们没有丢弃这些掉队者，而是将它们暂存，并通过一条配套路径恢复：一个每小时运行的 Spark 批处理作业，由 Maestro 编排——这是 Netflix 的工作流编排器。该作业会将每个掉队事件与来自我们数据仓库（其保留时间远长于我们的流内窗口）的投放响应重新配对，并通过相同的下游接收端发布。这样既能保持流处理作业的内存有界，又能捕获长尾数据。

这也让我们能够支持在 60 分钟窗口之后很久才到达的事件类型，包括某些与跟踪相关的事件，同时为日后将系统扩展到更多事件类型、并按需提升匹配率保留了空间。我们在设计这个离线作业时也考虑到了复用：它可以重放死信队列并回填历史数据，为我们提供了一个同时用于长尾恢复和运维恢复的单一机制。

难点所在

除了架构本身之外，还有三件事需要真正投入精力，而正是它们共同让这条流水线变得稳定、正确且可以安全启用。

保持核心精简。

在实时活动规模下运行有状态的流式连接需要真正的调优，而我们大多数来之不易的经验都归结为一个理念：这个作业唯一的职责就是匹配事件。任何我们想额外附加的东西，比如外部查询或附带的旁路处理，最好都移出热路径，否则它最终会在负载下表现为不稳定。能否做到这一点，决定了一个作业是能从容跟上实时流量，还是会落后。这是不显眼的工作，却也是大部分的工作。

事件去重

在事件处理流水线中，重复是家常便饭。客户端可能会重试事件，而我们的上游投递是至少一次语义，因此同一事件可能不止一次到达。对于产生收入的事件——即那些为计费提供数据的事件——任何内容都不应被重复计数。

这里的解决方案是一个简单且幂等的键。对于每个事件，我们通过哈希几个能唯一标识它的字段来计算一个稳定 ID，例如广告 ID、事件类型，以及对于可重复事件而言的偏移量或时间戳。同一个底层事件始终会哈希得到相同的 ID，因此如果我们之前见过某个 ID，就丢弃重复项。

Flink 带来的变化在于我们记住这些 ID 的位置。之前的设计将它们保存在外部键值存储中，并对每个事件通过网络执行检查并写入；而 Flink 让我们可以把该状态保留在作业本地。我们按事件 ID 对流进行分区，这会将给定事件的每个副本都路由到同一位置，而一个带有较短生存时间的本地状态存储会记住我们最近见过的 ID。按 ID 分区还消除了外部存储必须防范的竞争条件，因为给定 ID 在任一时刻只会在一个地方被处理，热路径上也没有网络跳转。仅这一点就带来了多项改进。

我们对保证级别是审慎的：至少一次投递加尽力而为的去重，而不是精确一次。流内去重会在其窗口内消除绝大多数重复。然而，仍会有少数漏网之鱼，例如通过跨区域重新路由、迟到的恢复或重放近期事件的重启。因此，我们还将事件 ID 一路传递到富化后的广告事件本身，这让需要精确计数的消费者（例如计费系统）可以在自己更长的窗口上运行自己的幂等去重。

生产环境上线

这是项目中最具挑战性的部分。对于一个为计费和频次控制提供数据的系统来说，“相信我，新的是正确的”还不够，所以我们让 Flink 流水线与旧流水线并行运行，让它凭实力赢得流量。

两条流水线持续处理完整的事件流，使我们能够实时比较它们：我们将它们的输出并排发布。我们运行自动化审计，当两者出现偏差时发出告警。这些审计没有白费功夫，它们揭示了我们仅靠仪表盘永远无法发现的细微差异。

我们怎么知道两个系统之间的富化逻辑是相等的，从而让审计有意义？在开发早期，我们将该逻辑提取到一个共享模块中，旧服务与 Flink 作业都依赖该模块，因此任何对事件富化方式的更改都会同时应用于两者。因此，审计失败就指向了流水线机制上的真实差异。

切换与比较是两个不同的问题，而这是需要精确处理的部分。我们不能简单地将随机百分比的事件发送到每条流水线，因为同一事件落入两者会在下游被重复计数。相反，分流是确定性的：每个事件上的一个 稳定键 决定由哪条流水线负责发布它，因此即使两条流水线都看到了所有事件，每个事件也只会被发布一次。提高阈值会将事件从旧流水线一小片一小片地迁移到 Flink，而一旦发现异常，我们可以立即调低。

当我们完全切换完成时，两条流水线在远超过 99.99% 的事件上达成一致，而且我们是逐个区域推出的，而不是一次性全部切换。然后是令人满意的部分：我们关闭了广告服务器对元数据注册表的写入，并退役了旧服务和该注册表本身。广告投放关键路径上的单点故障就这样 消失了。Netflix 最古老的广告投放组件之一被 删除了。

运营 Flink 平台

在生产环境中运行一个大型有状态流处理作业本身就是一项专职工作，而我们并不是独自建立起这种能力的。我们在很大程度上依赖了 Netflix 的 Flink 平台团队。早期，该作业的检查点既慢又重。尤其是第一个检查点耗时很长，而且我们在内存中保存了超出所需的状态。与平台团队合作后，我们精简了状态、缩短了检查点时长，并在负载测试中验证了这些收益。这正是让该作业在直播突发流量期间不会停滞的原因。

同一个团队还为我们提供了无需自行投入的运维脚手架，包括持续交付和金丝雀部署，因此我们可以像对待其他生产系统一样，以相同的护栏和信心来发布和推出这个 Flink 作业。Netflix 运行着超过 25,000 个 Flink 作业（见 在 Netflix 构建可扩展的 Flink 平台），而正是这种成熟度构成了我们的基础。我们在此基础上叠加了自定义金丝雀指标，可在发布前发现问题；搭建了 CI/CD，使我们能够错开滚动发布；还设计了部署流程，在新作业检测到健康检查点之前让旧作业持续运行，因此我们绝不会在新作业给出绿灯之前销毁一个正在工作的作业。

成果

  • 富化不再处于广告投放的关键路径上。 广告服务器不再为了投放广告而执行同步的、必须成功的数据库写入。它记录日志后继续运行，而“查询存储宕机，所以广告投放也宕机”这一整类故障已不复存在。
  • 更少的系统、更少的模式、更少的跳转。 我们同时退役了旧版服务和元数据注册表。
  • 为直播而生，并为此持续测试。 广告插播正是该服务设计要处理的情况，因此在这一过程中，我们还运行了大规模负载测试来模拟真实流量。在最近的负载测试中，单个 AWS 区域处理了一次面向大量并发观众的广告插播，每秒处理数十万条事件，将其中绝大多数事件与其投放响应实时关联，并以相当的速度输出富化后的广告事件，且超时和错误可忽略不计。我们在整个开发过程中都对此进行测试，并随着直播观众规模增长持续测试，而我们尚未触及上限。
  • 我们交付了第 1 部分的路线图。 直播流广告事件、流内去重以及更丰富的实时富化都已在这一基础上发布。

关键要点

  • 尽可能让数据库远离热路径。 我们最大的胜利并非原始性能——而是爆炸半径。用发后即忘的日志加上下游关联，替代同步写入并等待，从而从广告投放中消除了一整类故障模式。
  • 在事件数据所在之处匹配事件。 实时关联优于全局复制，因为它将事件路由到其数据所在之处，而不是将数据复制到所有地方。
  • 赢得切换。 并行运行两套系统并在实时流量上对比其输出，比一刀切式切换更慢——而这正是我们信任结果的唯一原因。

下一步

我们面前有一系列令人兴奋的项目：为下一层级的并发观众扩展直播路径，将剩余的延迟 互动 事件完全引入流式世界，减少我们需要管理的 Flink 状态大小，努力为事件处理管道带来更强的韧性，并继续为下游消费者增加新的事件类型和更丰富的信号。

就地重新架构一条正在运行且对收入至关重要的管道的引擎，确实是一项多团队协作的努力。如果以这种规模构建实时系统正是你的兴趣所在，广告工程团队正在招聘。
