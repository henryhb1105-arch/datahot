原文

Latency distributions, cost per refresh interval, impact on the source database, bulk loads and operations. Measured on the smallest instance that supports mirroring.

Snowflake Postgres, managed PostgreSQL running inside a Snowflake account, has been generally available since 24 February 2026, and data mirroring into Snowflake followed on 15 October 2026. I didn’t just want to see that it works. I wanted real numbers under a simulated load, so that I can tell clients how it actually behaves and compare the cost with what we had expected. The marketing says “seconds” and “sub-minute”, and nobody had published a latency distribution, a cost per interval or the impact on the source database, so I spent two days measuring them.

TL;DR

  • Freshness: new rows show up in TABLE$live after ~26 s (median), ~37 s (p90), no matter whether the refresh interval is 30 seconds or 10 minutes. The table itself lags behind $live by up to one refresh interval.
  • Cost: the serverless apply task cost 0.063 credits/h idle at a 30-second interval and 0.25 credits/h under a steady write load. Switching to 2 minutes cut the loaded cost by 73 %, to 10 minutes by 88 %.
  • Source impact: small OLTP transactions barely notice the mirror. Batch inserts into a mirrored table were 20–30 % slower than into a non-mirrored table on the same instance.
  • Operations: SUSPEND_MIRROR took 2.5–4.7 s under load, RESTART_MIRROR re-copies every table despite saying "soft", adding an 8M-row table to a running mirror took under a minute, and the replication slot survived every suspend/resume of the instance.
  • Gotchas: numeric without precision becomes FLOAT, json/jsonb become TEXT, 2-D arrays become NULL, PostgreSQL refuses ADD COLUMN … DEFAULT <volatile> on mirrored tables, any ADD, DROP or RENAME COLUMN wipes that table's $changes history, and tables without a primary key turn insert-only.

Why this matters

Every team that runs an application on Postgres and analytics in Snowflake owns a pipeline between the two. It is usually one of these:

  • a managed ELT tool (Fivetran, Airbyte, Azure Data Factory, Matillion, etc.), priced by changed rows, data volume or run time depending on the vendor,
  • Snowflake Openflow, a NiFi-based runtime you pay for even when nothing changes,
  • something the team built and runs itself: open-source CDC such as Debezium (it reads the Postgres WAL and publishes every change to Kafka), Kafka Connect or Snowpipe Streaming on the Snowflake side, or a scheduled export script.

All of them work, and each is one more system that someone pays for, upgrades and gets woken up by, and most of them break the first time someone adds a column.

Mirroring replaces that pipeline with one procedure call: selected tables stay continuously replicated into Snowflake, including updates, deletes and schema changes, with no external tool.

How mirroring works under the hood

Mirroring is push-based, and most of the work happens inside Postgres:

  1. Logical decoding. Postgres writes every change to its write-ahead log (WAL) before it touches the table files. Each mirror owns a logical replication slot, and the walsender process decodes the WAL into row-level inserts, updates and deletes.
  2. Capture. The snowflake_cdc extension runs a background worker per mirror. Roughly every 15 seconds it writes the decoded batch into per-table Iceberg change logs (Parquet, via pg_lake) and records it in a meta log.
  3. Apply. On the Snowflake side, a serverless task runs every refresh_interval (30 seconds to 1 day, default 10 minutes) and applies the pending batches. Inserts are appended; updates and deletes become delete + append. Each run is one transaction aligned to the Postgres transaction boundaries, so foreign keys and joins stay consistent.

Every mirrored table gives you three objects:

The picture follows one order from the demo app. At 12:00:00 the customer changes order #500 from 2 to 3 snowboards. About 15 s later the CDC worker pushes the change to the change log, and at the measured median of ~26 s it is visible in ORDERS$live and ORDERS$changes. ORDERS keeps showing 2 until the next apply run, which with a 10-minute interval can be up to 10 minutes later.

Two details are worth knowing before the results. The UPDATE shows up in $changes as a D + I pair (a delete of the old row and an insert of the new one) with _IS_UPDATE = true, and $live is not transactional, so for a moment it can show half of a large transaction.

Setup in six steps

You need a Snowflake Postgres instance of the STANDARD or HIGHMEM family on AWS or Azure. The instance accepts no connections until it has a network policy, and the policy is attached when the instance is created, so it comes first.

Before you start, ACCOUNTADMIN grants three privileges, once, to the role that will own the instance and manage the mirror:

GRANT CREATE POSTGRES INSTANCE ON ACCOUNT TO ROLE PG_ADMIN;
GRANT CREATE NETWORK POLICY ON ACCOUNT TO ROLE PG_ADMIN;
GRANT APPLICATION ROLE SNOWFLAKE.POSTGRES_MIRROR_ADMIN TO ROLE PG_ADMIN;

The application role isn’t granted to anyone by default, not even ACCOUNTADMIN. Run all six steps as that role: every mirror procedure checks that the caller owns the source instance, so the role that creates the instance in step 2 is the one that manages the mirror. (If you create the mirror in Snowsight, under Postgres → Manage → Mirroring, the grants are set up for you.)

1. Create the network policy. Allow Snowflake’s own egress ranges (mirroring and Snowflake apps connect from there, SELECT SYSTEM$GET_SNOWFLAKE_EGRESS_IP_RANGES() lists them) plus the IP of your client. Avoid 0.0.0.0/0.

CREATE NETWORK RULE MY_DB.MY_SCHEMA.PG_INGRESS   -- network rules live in a schema
  TYPE = IPV4 MODE = POSTGRES_INGRESS
  VALUE_LIST = ('192.0.2.0/24', '198.51.100.0/24',   -- sample values: Snowflake egress ranges for your region
                '203.0.113.10/32');                 -- sample value: your client IP

CREATE NETWORK POLICY MY_PG_POLICY
  ALLOWED_NETWORK_RULE_LIST = ('MY_DB.MY_SCHEMA.PG_INGRESS');

The addresses above are documentation placeholders. Take the real ranges for your region from the function, and check them again from time to time, because each one comes with an expiry date.

2. Create the instance (it returns the passwords exactly once, so store them):

CREATE POSTGRES INSTANCE KS_PG_BENCH
  COMPUTE_FAMILY = 'STANDARD_M'
  STORAGE_SIZE_GB = 50
  AUTHENTICATION_AUTHORITY = POSTGRES
  POSTGRES_VERSION = 18
  NETWORK_POLICY = 'MY_PG_POLICY';

3. Let mirroring use the instance, once it is READY:

GRANT USAGE ON POSTGRES INSTANCE KS_PG_BENCH TO APPLICATION SNOWFLAKE;

4. Install the extension in Postgres (it is not there by default):

CREATE EXTENSION IF NOT EXISTS snowflake_cdc CASCADE;

5. Create the mirror:

CALL SNOWFLAKE.POSTGRES.CREATE_MIRROR(
  mirror_name       => 'ks_bench_mirror',
  postgres_instance => 'KS_PG_BENCH',
  postgres_database => 'postgres',
  target_database   => 'KS_BENCH_MIRROR',
  postgres_schemas  => ['bench'],
  refresh_interval  => '30 seconds');

6. Watch the snapshot finish:

CALL SNOWFLAKE.POSTGRES.LIST_MIRRORED_TABLES('ks_bench_mirror');
-- SNAPSHOTTING -> REPLICATING

Most of the gotchas I met while preparing the demo for an internal talk:

Benchmark methodology

The environment was AWS eu-central-1, Enterprise edition, Postgres 18 on STANDARD_M (1 vCPU, 4 GB RAM, 50 GB disk). It is the smallest instance that supports mirroring, so for source impact it is the worst case. One mirror covered schema bench (4 tables at first, 19 by the end, after the seed tables and the type and DDL tests were added), with logical_decoding_work_mem = 64MB and max_slot_wal_keep_size = 5GB.

The test runner is a Python script on my laptop: psycopg 3 for Postgres, the Snowflake connector with key-pair auth, an XS warehouse for polling, results as JSON lines. Write load runs server-side (PL/pgSQL procedures, pg_cron), so network jitter stays out of the TPS numbers. After every test a verification step compares row counts, sums and a content hash between Postgres, the table and $live. All 7 load tables matched after every test, including the runs that crashed halfway (more on those in the operational notes).

For latency, the script commits a batch and then polls $live, the table and $changes every second with separate queries until the batch is complete. Commits come at random gaps of 15–60 s, so they land at random phases of the push and apply cycles. Resolution is about ±1.3 s (query time + poll). I also checked the laptop clock against _COMMIT_TIME; the offset was under 0.1 s.

I report latency as percentiles, because the average hides the slow tail. p50 is the median: half of the commits arrived faster than this, half slower. p90 means 9 out of 10 commits arrived within that time, and max is the single slowest one.

The limitations are real: one region, one instance size and one run per configuration (N = 40–60 samples for latency, 4 repetitions per profile for source impact, up to three runs per operation). Costs come from ACCOUNT_USAGE (up to 3 h delay) in 2-hour windows. The 10-minute latency run also ended early. Polling once a second keeps an XS warehouse busy all day, and near the end of that run the 8-credit resource monitor on it ran out and stopped everything, so that run has 49 samples instead of 60. Use the numbers as an order of magnitude for your own planning; they are not an SLA. The whole benchmark cost about 13 credits (~51 USD), and two thirds of that was my own once-per-second polling warehouse, not the mirroring.

Result 1: latency, and what refresh_interval really changes

The $live median stays in the 21–26 s band at all three settings, which fits the ~15 s push cycle plus the ~30 s $live refresh from the docs. The table is a different story: it lags $live by up to one interval and by half of it on average, so at 10 minutes half the samples needed more than 5.5 minutes to reach the table.

Batch size barely matters. At 30 seconds, a single-row commit reached $live in 30 s (p50), a 100-row batch in 21 s and a 100 000-row batch in 18 s, and $changes tracked $live within a second in every run.

The first single-row run looked broken: the table median came out at 280 s. One apply execution had taken 415 s instead of the usual 3–15 s, and for those 7 minutes the table stood still while $live and $changes stayed fresh. A rerun gave normal numbers, and I have no explanation for the slow run. I kept it in the results, because it is the best argument for pointing any dashboard that has to be fresh at $live.

In practice I decide per consumer which object it reads, and only then pick the interval. Reports and dbt models can read the table at 2–10 minutes. Operational dashboards, Streamlit apps, alerts and AI agents should read $live, which stays at ~30 s whatever the interval. To business users I promise "about half a minute" for $live. If something needs guaranteed seconds, it needs a different tool, and the table can stall for minutes now and then (the 415 s run).

Result 2: cost per refresh interval

I ran six 2-hour windows overnight. “Load” means pg_cron every 5 s inserting 100 rows and updating 10 random rows: about 72 000 inserts and 7 000 updates per hour, spread over 4 tables.

Under load the interval is the main cost lever: going from 30 s to 2 min saved 73 %, going to 10 min saved 88 %.

Idle surprised me. I had expected 10 minutes to be at least 5× cheaper than 30 s when nothing changes, and it came out 3.4×. Two minutes and ten minutes cost the same, about 0.02 credits/h. The docs say the apply task checks for work at least every 2 minutes (that is also how DDL gets through quickly), which would explain the floor. At the other end, 0.063 credits/h at 30 seconds is about 45 credits a month for a mirror that is just waiting. That is the number I’d show a client before they pick 30 seconds just because it is the fastest option.

The load itself was a worst case on purpose. Updating random rows makes delete + append rewrite micro-partitions all over the table, so insert-only workloads should come out cheaper. I haven’t measured that.

You can check your own numbers with a single query:

SELECT DATE_TRUNC('hour', start_time) AS hour,
       ROUND(SUM(credits_used), 4)    AS credits
FROM SNOWFLAKE.ACCOUNT_USAGE.SERVERLESS_TASK_HISTORY
WHERE task_name ILIKE 'APPLY_MIRROR%'
GROUP BY 1 ORDER BY 1 DESC;

Storage is the part that doesn’t show up in that query. Delete + append rewrites micro-partitions, so frequently updated tables accumulate Time Travel of 2–2.5× their active size, and $changes keeps 7 days of history on top. Our most-changed table had 1.6 GB of active data, 4.0 GB in Time Travel and 3.5 GB in $changes. At ~23 USD/TB/month the money is small, but plan for 4–5× the raw table size.

I wanted to shorten Time Travel on the mirror, and you can’t. The target database and all its tables are owned by the SNOWFLAKE application, retention is set to 1 day on the tables and 5 days on the internal change log tables, and both ALTER TABLE … SET DATA_RETENTION_TIME_IN_DAYS and ALTER DATABASE … failed with "Insufficient privileges" for the role that created the mirror. (I did not try it as ACCOUNTADMIN.) So the 4.0 GB above is what a single day of Time Travel looks like on a table that gets updated all the time.

For the instance itself, STANDARD_M runs at about 111 USD/month on Enterprise and 76 USD on Standard edition. An Azure Flexible Server B2s is around 62 USD, but then you still pay for the pipeline.

For a new mirror I’d start at 2 minutes. Under my test load that was ~192 USD/month against ~712 USD at 30 seconds (idle 55 against 180), with $live just as fresh. Thirty seconds pays off only when a consumer has to read the table itself every minute and can't switch to $live. The cost query above belongs in a monthly check, and tables that are updated often need 4–5× their source size in storage.

Result 3: impact on the source database

The docs warn that CDC shares CPU with your application, but give no numbers. So I wrote the same load into Postgres in six write profiles, each one a different kind of work an application does:

Each profile ran for 120 s as fast as it could, and I counted committed transactions per second (TPS). Every profile ran in three situations:

  • no mirror: the day before, on the same instance, before the slot existed;
  • other table: mirror exists, writes go to a non-mirrored table (the walsender still decodes all WAL);
  • mirrored table: writes go to a table in the mirror.

The last two ran 4 times each, alternating in the order other, mirrored, mirrored, other (and again), so that anything drifting during the evening, like a noisy neighbour on the host, hits both sides equally.

The clean comparison is between the “other table” and “mirrored table” columns, which ran the same evening, interleaved. Small transactions show no meaningful difference there. Batch inserts lose 20–30 % when they hit a mirrored table, because decoding and pushing those rows competes with the application for the single vCPU.

I would be careful with the “no mirror” column. It comes from the previous day on a fresh instance, and part of the −7 to −17 % is plain day-to-day variance, so please don’t quote it as “mirroring costs 17 %”.

The CDC worker caught up quickly: the slot drained to under 1 MB within 6–13 s after small-transaction runs and 8–138 s after P4, and Snowflake matched Postgres 10–85 s after the load stopped.

The 138 s came from the run that worried me most. While I was watching the second P4 repetition, the mirror held 4.95 GB of WAL after 120 s of writes, against a max_slot_wal_keep_size of 5 GB. Had the worker fallen a little further behind, Postgres would have invalidated the slot and the mirror would have needed a full re-snapshot. It didn't happen, but on a 1-vCPU instance I'd size this setting with headroom for the largest burst, or split the load.

If your application writes small transactions, like a new order or a status change, you can size the instance as if the mirror weren’t there. Imports and batch jobs into mirrored tables are what to plan for: expect 20–30 % less throughput on them, give max_slot_wal_keep_size headroom above the biggest burst, and move off the smallest instance before a heavy import lands on it.

Result 4: bulk loads, one big transaction vs batches

Everything went through: no RESTART_REQUIRED, wal_status always reserved, verify green after every step.

The split load is the row I looked at twice. Fifty transactions of 100k took 40 % longer to write, but after the last commit the data was in Snowflake twice as fast (28 vs. 54 s) and caused no spill to disk. Measured from the start of the write, both variants landed at about the same time (~105 s). Batching therefore doesn’t speed up the load end to end; what changes is that memory and disk stay flat. A single 5M-row transaction exceeds logical_decoding_work_mem (64 MB), so the decoder spills it to disk and can only push it after the commit, which matches the docs' advice to split bulk loads.

If the import already lands in a staging table, a procedure that commits after every chunk is enough (the benchmark did the same with COMMIT after each 100k-row batch):

CREATE OR REPLACE PROCEDURE load_in_chunks(chunk int DEFAULT 100000)
LANGUAGE plpgsql AS $$
DECLARE lo bigint; hi bigint;
BEGIN
  SELECT min(id), max(id) INTO lo, hi FROM staging.orders_import;
  WHILE lo <= hi LOOP
    INSERT INTO app.orders
    SELECT * FROM staging.orders_import WHERE id >= lo AND id < lo + chunk;
    COMMIT;                      -- each chunk is its own transaction
    lo := lo + chunk;
  END LOOP;
END $$;

CALL load_in_chunks();           -- outside an explicit transaction, or COMMIT failsThe cheapest fix in the whole benchmark is a conversation with whoever owns the imports: commit in chunks of up to 100k rows. Total load time stays the same, the data reaches Snowflake just as soon, and the 1.2 GB spill goes away, which was the closest the 1-vCPU instance came to trouble here.

Result 5: adding a table to a running mirror

CALL SNOWFLAKE.POSTGRES.ALTER_MIRROR(
  mirror_name => 'ks_bench_mirror',
  add_tables  => ['bench_seed.big_l']);

The mirror kept running while the tables were added. A regression over the three points gives about 36 s of fixed overhead plus ~50 MB/s, close to Floredata’s ~40 MB/s on a 70 GB production snapshot. Snowflake stored the data about 4× smaller than Postgres.

Because a new table takes about a minute per gigabyte and needs no downtime, I’d start with the few tables one concrete use case needs and add more with the next one. Every mirrored table adds apply work, Time Travel and $changes storage, and mirroring the whole database "just in case" pays for all of that from day one.

Five things to check before you mirror a real schema

I also pushed every Postgres type group and 14 kinds of schema change through the mirror. Most of it just works (including ALTER COLUMN TYPE and large TOAST values). These are the five findings that change what you do before you start:

  1. Primary keys on every table. Postgres rejects UPDATE and DELETE on a published table without a replica identity, so a table without a PK becomes insert-only. Add the PK before you mirror (Floredata had to delete 7 million duplicates to get there).
  2. No volatile defaults in migrations. ALTER TABLE … ADD COLUMN created_at timestamptz DEFAULT clock_timestamp() fails with "cannot add column … with volatile DEFAULT". Add the column without a default, backfill in batches and set the default afterwards. Constant defaults are fine.
  3. Types that change on the way. numeric without precision (or above 38 digits) arrives as FLOAT and loses precision, json/jsonb arrive as TEXT and need PARSE_JSON downstream, and timetz is normalised to UTC with the offset dropped.
  4. 2-D arrays arrive as NULL. The column exists in Snowflake, the values don’t. This is documented, but easy to miss.
  5. Sentinel dates. infinity and -infinity become 9999-12-31 and 0001-01-01 (−4712-01-01 for date). Plain SQL reads them, but the Snowflake Python connector failed to fetch that table ("ordinal must be >= 1"), and the same values had already crashed my own psycopg script on the Postgres side. If you use them, test your downstream tools.

One more thing turned up only after the benchmark, while I was recording the demo animation. I updated, cancelled and deleted an order and then added a column to the same table. When I went back to $changes for that order's history, it was gone: the change log held only the commit that came after the ADD COLUMN.

So I tested it properly on four fresh tables with the same history (10 inserts, 3 updates, 1 delete, 17 rows in $changes). On three of them I ran one schema change each, ADD COLUMN, DROP COLUMN and RENAME COLUMN, followed by one more update; the fourth got only the update. Within about 30 seconds the three changed tables had lost their whole history, and $changes held just the D + I pair of the update that came after the DDL. The control table kept all 19 rows. The data itself was fine: the table and $live had all 9 rows in every case, and the new, dropped or renamed column showed up correctly.

The docs say that schema changes on mirrored tables rebuild the feed, and this is what that means in practice: $changes keeps 7 days of history or everything since the last schema change on that table, whichever is shorter. Application teams ship migrations all the time, so if $changes is meant to be an audit trail, copy it into a table of your own on a schedule (a task with INSERT … SELECT from $changes since the last copied _COMMIT_LSN is enough).

Operational notes

At first I ran each operation once. Some of the conclusions I drew from that turned out to be too strong, so I repeated the ones that matter for a runbook. The table includes all runs.

Pausing is cheap. The CDC worker keeps decoding WAL and pushing change logs while the mirror is suspended, and only the apply step stops, so the slot held under half a megabyte during 5- and 10-minute pauses under load. On resume, Snowflake applies the queued batches within a minute. I haven’t tested pauses longer than 10 minutes.

The restart is where my first conclusion was wrong. The first time, I checked $changes a few seconds after the tables showed REPLICATING again, found no snapshot rows and wrote down "soft restart, no re-snapshot". When I repeated it and kept watching, the tables went back to SNAPSHOTTING a little later, and every restart (two under load, one idle) ended with a full copy: 505 700 S rows in $changes for events_load alone, and about 9 minutes until all 19 tables were replicating. The docs describe RESTART_MIRROR as a new snapshot, and that is what it does, whatever the return message says.

Restarts also break queries for a while. Snowflake recreates the $live and $changes views, and until it does, every query fails with "does not exist". My verification script crashed on that twice: 35–40 s after the first restart, and around two minutes after one of the three repeated ones. Both times it did what it was built to do and suspended the mirror and the instance, the second time in the middle of the re-snapshot. Resuming was enough to let the snapshot finish.

The error message after an instance resume turned out to be rare. Once, the mirror came back ACTIVE while error_message said "Apply suspended: the source postgres instance is suspended … call RESTART_MIRROR", and the text disappeared after ~5 minutes. I restarted the mirror that time. In the other resumes I logged (at least four more, one of them with 25 pending operations) there was no message, and the mirror caught up on its own within ~3 minutes. Knowing now that a restart means a full re-snapshot, I'd give apply_lag_operations a few minutes before following that advice. This is the one thing I'd like Snowflake to change. A message that recommends RESTART_MIRROR to a mirror that is catching up on its own sends you to the most expensive fix there is, a full re-snapshot that also wipes $changes. And the "soft" in the return value made me believe, the first time, that nothing would be copied again.

The status alone tells you little, because the mirror was ACTIVE during all of this. An alert should look at the lag. DESCRIBE_MIRROR is a procedure, and an alert condition can only hold one statement, so I wrapped the check in a procedure that returns rows only when something is wrong:

CREATE OR REPLACE PROCEDURE MIRROR_LAGGING(MIRROR STRING, MAX_LAG_S NUMBER)
RETURNS TABLE (MIRROR_NAME STRING, STATUS STRING, APPLY_LAG_SECONDS NUMBER,
               APPLY_LAG_OPERATIONS NUMBER, SLOT_LAG_BYTES NUMBER)
LANGUAGE SQL AS
DECLARE res RESULTSET;
BEGIN
  CALL SNOWFLAKE.POSTGRES.DESCRIBE_MIRROR(:MIRROR);
  res := (SELECT MIRROR_NAME, STATUS, APPLY_LAG_SECONDS, APPLY_LAG_OPERATIONS,
                 POSTGRES_STATUS:slot_lag_bytes::NUMBER
          FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()))
          WHERE STATUS <> 'SUSPENDED' AND APPLY_LAG_SECONDS > :MAX_LAG_S);
  RETURN TABLE(res);
END;
CREATE ALERT MIRROR_LAG_ALERT
  WAREHOUSE = MY_WH  SCHEDULE = '5 MINUTE'
  IF (EXISTS (CALL MIRROR_LAGGING('ks_bench_mirror', 90)))  -- 3 × refresh_interval
  THEN CALL SYSTEM$SEND_EMAIL('my_email_int', 'oncall@example.com',
                              'Mirror lag', 'ks_bench_mirror is falling behind');

ALTER ALERT MIRROR_LAG_ALERT RESUME;   -- a new alert starts suspended; needs EXECUTE ALERTThe procedure returned the right rows on my mirror and Snowflake accepted the alert with a CALL in the condition. To run or resume an alert, the owning role also needs the account-level EXECUTE ALERT privilege, which SYSADMIN doesn't have by default. If you also want to catch a slot that is filling up, add a condition on SLOT_LAG_BYTES against your max_slot_wal_keep_size.

Three things from this go straight into a runbook. Pausing is cheap enough to be part of a maintenance plan: suspend the mirror before a big migration and resume it afterwards (I measured up to 10 minutes under load). RESTART_MIRROR is not: it copies every table again, so plan it like the initial load and keep queries on $live and $changes away from it for a few minutes. And whoever is on call should alert on apply lag and slot lag, and give apply_lag_operations a few minutes after an instance resume before restarting anything.

How it compares

Airbyte OSS itself is free. It runs on 2 vCPU / 8 GB in low-resource mode and 4 vCPU is recommended (t3.large–t3.xlarge in eu-central-1 ≈ 70–140 USD/month on demand, + disk), which makes it the cheapest path on paper as long as you don’t count the people who upgrade and watch it.

When I would (and would not) use it

Yes, if:

  • the application can run on Snowflake Postgres (AWS/Azure, same account),
  • you want operational dashboards, apps or AI agents on data that is seconds-to-minutes old,
  • you want to retire a pipeline and a vendor,
  • you need a 7-day change history without building CDC yourself (and copy it away if it has to survive schema changes).

Not yet, if:

  • the source must stay on RDS, Azure Flexible Server or on-prem,
  • you have tables without primary keys you cannot fix,
  • you rely on 2-D arrays, unconstrained numeric or timetz offsets being exact,
  • a 1-vCPU instance has to absorb heavy bulk loads (size up; the docs recommend STANDARD_XL as a starting point).

Settings I’d start with: refresh_interval of 2–10 minutes for the table, $live for anything operational, PKs on everything, bulk loads in ≤ 100k-row transactions, and max_slot_wal_keep_size with headroom above your biggest burst.
